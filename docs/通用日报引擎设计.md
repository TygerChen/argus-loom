## 1. 业界方案盘点

调研结论：这个需求在开源界叫 **Dashboard Subscription / 定时报告**，成熟方案有四类：

| 项目 | 定位 | 定时推送能力 | 与 argus-loom 的关系 |
| --- | --- | --- | --- |
| [DataEase](https://github.com/dataease/dataease) | 开源 BI（Vue3 + Spring Boot，技术栈几乎同款） | 定时报告：仪表板 → 邮件/钉钉/飞书/企微，支持富文本、按角色收件、执行记录 | 完整 BI 平台，独立部署，不建议嵌入 |
| [Metabase](https://www.metabase.com/docs/latest/dashboards/subscriptions) | 开源 BI | Dashboard subscriptions：邮件/Slack + PDF 附件，"无数据跳过发送" | Java 生态但独立系统 |
| [Apache Superset](https://deployopen.com/open-source/apache-superset/features/alerts-and-reports) | 开源 BI | Alerts & Reports：无头浏览器截图 → 邮件/Slack/Webhook | Python 栈，重 |
| [JimuReport 积木报表](https://github.com/jeecgboot/jimureport) | 类 Excel 报表设计器 + ChatBI | Spring Boot 脚手架可集成；AI 一句话生成报表 | 可集成但代码闭源 |

**判断**：完整 BI（拖拽图表、数据建模）不要自建——DataEase/积木报表已经卷死了。
但它们都缺一个 argus-loom 天然有的东西：**LLM**。自建的重心放在"报表订阅管道 +
AI 简报"，这是所有现有方案的短板，也是 argus 从技术 demo 变实用项目的切口。

## 2. 核心抽象：一条报表流水线

```
数据源 → 转换计算 → 渲染 → AI 简报 → 定时调度 → 多渠道推送 → 执行记录
source   transform   render   ai-brief   schedule   deliver       audit
```

资金日报的全部要素（Excel 解析、净额口径、工作日闸门、钉钉推送、合计复核）
都能映射到这条流水线上——它就是 fund-daily-report 的"去业务化"。

## 3. 数据模型（Flyway V10）

```sql
-- 报表定义：一条流水线的完整配置
CREATE TABLE IF NOT EXISTS report_definition (
    id BIGSERIAL PRIMARY KEY,
    owner_user_id BIGINT NOT NULL,
    name VARCHAR(128) NOT NULL,                        -- 「资金日报」「销售日报」
    pipeline_json JSONB NOT NULL,
    -- { source: {type: EXCEL|ONLINE_SHEET|SQL|API, ...},
    --   transform: {rules: [...]},                    -- 规则链，资金日报的口径规则放这里
    --   render: {template_id: ..., variables: ...},
    --   aiBrief: {enabled: true, prompt: ...},
    --   schedule: {cron: "0 18 20 * * *", workdayOnly: true},
    --   deliver: [{channel: DINGTALK_WEBHOOK, target: ...}] }
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP
);

-- 执行记录：每次跑的快照与结果（审计 + 失败可见）
CREATE TABLE IF NOT EXISTS report_execution (
    id BIGSERIAL PRIMARY KEY,
    definition_id BIGINT NOT NULL,
    biz_date DATE NOT NULL,                            -- 报表基准日
    status VARCHAR(16) NOT NULL,                       -- RUNNING/SUCCEEDED/FAILED/SKIPPED
    result_json TEXT,                                  -- 计算产物（看板数据源）
    ai_brief_text TEXT,                                -- AI 解读
    html_content TEXT,
    push_status VARCHAR(16),                           -- PENDING/SENT/SKIPPED/FAILED
    push_detail VARCHAR(512),
    error_message VARCHAR(1024),
    duration_ms BIGINT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (definition_id, biz_date)
);
```

执行量级：个人/小团队每天几条，`@Scheduled` 扫描到期的 definition →
入 `background_job`（复用现有队列：租约/退避/死信），Worker 执行流水线。

## 4. 各环节设计

### 4.1 数据源 SPI（interface + 三个实现）

- `ExcelFileSource`：上传的报表文件（资金日报用，存 MinIO，解析逻辑=移植技能）；
- `SqlSource`：一条只读 SQL 查询（销售额日报用：查订单表聚合）；
- `OnlineSheetSource`（阶段 2）：Univer 协同表的快照数据。

接口统一返回 `List<Map<String,Object>>` 的中间表，后续环节不感知来源差异。

### 4.2 转换：配置驱动的规则链

把资金日报沉淀的业务规则做成可组合的规则（JSONB 描述，Java 解释执行）：
列映射、借贷方向、分组键、剔除关键字（转账/退款）、桶拆分（理财）、汇率折算、
合计复核。每条规则 = `{op, params}`，新报表 = 新规则组合，不写新代码。

### 4.3 渲染

HTML 模板（Thymeleaf，Spring Boot 自带）+ 变量 JSON → 看板 HTML；
PDF 复用现有 PDF 服务模式。模板按报表类型可换，数据结构约定统一：
`{cards:[], tables:[], groups:[]}`。

### 4.4 AI 简报（差异化核心）

复用现有 LLM 网关：把 result_json 喂给模型，按 definition 里的 prompt 生成
一段自然语言解读（"今日资金净流出 1200 万，主因 X 公司支付货款…"），
插在日报开头。**这是 DataEase/Metabase/Superset 都没有开箱即用的能力**
（积木的 ChatBI 是交互式问答，不是主动推送解读），也是 RAG 项目最自然的
业务化延伸。

### 4.5 调度与推送

- 调度：`schedule.cron` + `workdayOnly`（工作日闸门移植为节假日表判断）；
- 推送渠道 SPI：`DingTalkWebhookChannel`（机器人 webhook，个人用）→
  后续可加 `EmailChannel` / `WeComChannel`；
- 凭据环境变量，缺失 → SKIPPED 不阻塞；
- "无数据跳过"学 Metabase：结果为空 → SKIPPED，不制造噪音。

## 5. 资金日报 = 实例 #1

| 流水线环节 | 资金日报的取值 |
| --- | --- |
| source | ExcelFileSource（上传的资金报表） |
| transform | 公司名解析 + 借贷方向 + 转账/理财剔除 + 汇率折算 + 合计复核 |
| render | 资金日报模板（卡片/公司分组/账户明细） |
| aiBrief | "今日资金面解读" prompt |
| schedule | 每日 20:18，仅工作日 |
| deliver | 钉钉 webhook（本人） |

先做实例 #1 把整条管道打通，再抽象通用层——**不要先写抽象再填业务**
（没有真实实例支撑的抽象一定是错的）。

## 6. 实施路线

1. **阶段 1**：V10 建表 + 流水线骨架（Excel 源 + 规则链 + 渲染 + 钉钉推送），
   资金日报作为硬编码实例先跑通；
2. **阶段 2**：把资金日报的规则抽成 pipeline_json 配置 → 引擎真正"通用"；
   加执行记录页面 + AI 简报；
3. **阶段 3**：SqlSource（销售额日报等新报表零代码接入）、OnlineSheetSource、
   邮件渠道。

## 7. argus-loom 的实用化叙事

做完这条线，项目定位从"RAG 知识库 demo"升级为：

> **数据进来（上传/在线表格/数据库）→ 报表自动化跑起来（定时/校验/推送）
→ 有人在看（看板/PDF/钉钉）→ 有问题随时问（RAG + 引用溯源）**

每一环都是真实业务闭环，且各有差异化：队列可靠性、三层权限、Excel 协同、
AI 简报。演示时讲"这个系统每天晚上 8 点 18 分真的在给我发日报"，
比讲任何架构图都有说服力。
