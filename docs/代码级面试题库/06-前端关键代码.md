## 一、Token 刷新与请求封装（http.ts / auth.ts / stores/auth.ts）

**Q1.【问题】你的 accessToken 和 refreshToken 分别存在哪？为什么这么放？**

- **考点**：token 存储位置与 XSS 攻击面。
- **核心概念一句话**：短命的给 JS 用但要防偷，长命的让 JS 根本摸不到。
- **答案要点**：accessToken 只存 Pinia 的内存 state（`stores/auth.ts` 的 `accessToken: string | null`），刷新页面就没了，是故意的——localStorage 里的 token 会被 XSS 脚本偷走，内存态偷不走。refreshToken 在后端下发的 HttpOnly Cookie 里（`api/auth.ts` 注释明确写了），JS 完全读不到，页面加载时 `bootstrap()` 凭 Cookie 静默换回新 accessToken。axios 实例开 `withCredentials: true` 保证跨域也带 Cookie。
- **可能追问**：刷新页面岂不是每次都要换一次 token？——对，`router.beforeEach` 里先 `await authStore.bootstrap()`，走 `/auth/refresh` 换新 token 再放行，代价是一次额外请求，换来的是 token 不落任何持久化存储。

**Q2.【问题】axios 封装里做了什么？为什么不用裸 fetch 发业务请求？**

- **考点**：HTTP 客户端统一封装的能力取舍。
- **核心概念一句话**：封装是把"每个请求都要做的事"收敛到一处，改一处全生效。
- **答案要点**：`api/http.ts` 用 `axios.create` 建全局实例：baseURL 读 `VITE_API_BASE_URL` 环境变量、默认 `/api`，timeout 15 秒，`withCredentials: true`。token 注入不是靠拦截器，而是 `stores/auth.ts` 的 `applyAuthorizationHeader()` 直接写 `http.defaults.headers.common.Authorization`，登录/刷新时 setSession 顺手挂上，登出时 delete 掉，保证登出后不残留旧凭证。另导出 `extractApiError()`：优先取 `response.data.message`（后端业务消息），再退 axios 的 error.message，最后兜底文案，全站 toast 统一用它。
- **可能追问**：全局默认头和请求拦截器有什么区别？——效果类似，但默认头是"状态写入"语义：登录那一刻写一次就永久生效；拦截器是"每次请求时读"。我的实现里 token 变化的时机很少（登录/刷新/登出），写默认头更简单直接。

**Q3.【问题】你说有"并发刷新防抖"，具体代码在哪？多个组件同时触发刷新会怎样？**

- **考点**：single-flight（单飞）模式、共享 Promise 去重。
- **核心概念一句话**：让并发的 N 个调用共享同一个 Promise，第二个来的人直接等第一个人已经起飞的飞机。
- **答案要点**：在 `stores/auth.ts`：模块级变量 `let bootstrapTask: Promise<CurrentUserProfile | null> | null`，`bootstrap()` 先查——已有未完成任务就直接 `return bootstrapTask`（不是再发一次请求，而是 await 同一个 Promise）；任务结束后 `finally { bootstrapTask = null }` 放下一个进来。因为路由守卫每次导航都调 bootstrap，快速连续跳转多个路由也只发一次 `/auth/refresh`。这和后端 Refresh 轮换的互斥是同一场攻防的前端面：前端先去重，后端再用轮换+重放检测兜底。
- **可能追问**：为什么用 Promise 去重而不是一个 isRefreshing 布尔标志？——布尔只能"拒绝"后来的调用，不能让它们"拿到同一个结果"；共享 Promise 能让所有等待者拿到同一份 currentUser，语义最干净。

**Q4.【问题】如果 accessToken 过期了，请求返回 401，你的前端怎么处理？有响应拦截器自动重放吗？**

- **考点**：诚实边界 + 401 处理的通用方案（必被追问的"改进空间"）。
- **核心概念一句话**：我项目当前是"前置刷新"而不是"事后重放"，但标准答案我能口述。
- **答案要点**：诚实说：`http.ts` 里没有 401 响应拦截器。我的设计是把刷新前置——每次路由切换 `bootstrap()` 先恢复会话，accessToken 30 分钟内基本不会在页面停留期间过期，所以事后 401 很少出现；真过期了，`runBootstrap()` 里对 `/auth/me` 失败的兜底就是 `this.refresh()` 换新 token。如果面试官要标准方案，我会补：拦截 401 → 触发 single-flight 刷新 → 把失败的请求存进队列等新 token → 用新头重放 → 之后来的 401 直接入队。这是成熟做法，我项目是简化版（前置刷新 + 单飞），取舍是少一层拦截器复杂度。
- **可能追问**：SSE 的 fetch 请求 401 了怎么办？——`streamAskQuestion` 检查 `response.ok`，不 ok 就读 response.text 抛 Error，走 onError 渲染失败消息；当前不会自动刷新重试，这也是我承认的改进点。

**Q5.【问题】登录后跳到哪个页面是谁决定的？为什么后端都校验了权限前端还要做一遍？**

- **考点**：前端路由守卫的定位——体验而非防线。
- **核心概念一句话**：前端守卫防的是"误入"，后端校验防的是"绕过"，两层永远不能只信一层。
- **答案要点**：`stores/auth.ts` 的 `resolveAuthorizedPath()` 按角色给首页：ADMIN 落 `/app/admin`，FINANCE 落 `/app/excel/finance`，USER 落 `/app/groups`，且 `mustChangePassword` 为 true 时强制先去 `/app/settings`。`resolveRoleRedirect()` 处理"手动改网址"：比如非财务访问 `/app/excel/finance` 会被拉回自己首页。`normalizeRequestedPath()` 还防开放重定向：只接受站内相对路径，`//evil.com` 这种协议相对地址直接拒绝。之所以前端也做，是因为纯后端拦截用户会看到报错页，前端守卫能"静默纠偏"，体验好；但绕过前端直接 curl 接口时，真正的防线是后端每层重做的鉴权。
- **可能追问**：`mustChangePassword` 为什么放在前端判断？——它是 UX 强制（首次登录/管理员重置后引导改密），不是安全控制；就算前端跳过了，后端敏感操作仍按各自权限校验。

**Q6.【问题】`ApiResponse<T>` 包装是谁解开的？为什么有的接口要手动 unwrap 有的不用？**

- **考点**：统一响应结构的不一致面（真实项目常见，能讲清楚反而加分）。
- **核心概念一句话**：包装结构要有一个唯一的"拆包点"，否则错误处理会散得到处都是。
- **答案要点**：`http.ts` 定义 `ApiResponse<T> { success, data, message }` 对应后端包装。拆包在 `api/auth.ts` 的 `unwrapApiResponse()`：`success === false` 就 `throw new Error(message ?? fallback)`，登录/注册/刷新等都走它。但少数接口后端不走包装直接返回对象——`qa/ask` 返回 `AskQuestionResponse`（`api/qa.ts` 注释明确写了），`/assistant/sessions` 列表直接返回数组，这些就绕过 unwrap 直接用。组件层还有个 `unwrapApi()`（SheetEditor.vue 内）做同样的事，因为 excel 接口部分走了包装。
- **可能追问**：这算不算设计缺陷？——算历史不一致，理想状态是 axios 拦截器统一解包。我如实承认并知道正确做法：在响应拦截器里集中判断 success，false 时统一抛业务错误。

**Q7.【问题】WebSocket（STOMP）连接怎么带 token？为什么不能复用 axios 那套？**

- **考点**：WS 鉴权与 HTTP 鉴权的本质差异。
- **核心概念一句话**：WebSocket 不是 HTTP 请求，没有拦截器也没有默认头，只能在握手时自己带。
- **答案要点**：`utils/collabClient.js` 创建 STOMP Client 时把 token 放进 `connectHeaders: { Authorization: 'Bearer ${token}' }`，token 从 `utils/auth.js` 的 `getAccessToken()` 拿（内部读 Pinia store，拿不到返回 null 时直接置 offline 不连）。因为 WS 握手只有一次，之后就是长连接，所以 token 失效后的续期靠断线重连时重新 `connect()` 重建连接头。
- **可能追问**：为什么不用 URL query 传 token？——token 会进 nginx/后端访问日志，泄露面大；连接头只出现在握手请求里，相对安全。

**Q8.【问题】bootstrap 的完整决策树是什么？accessToken 存在但 /auth/me 挂了会怎样？**

- **考点**：失败路径设计、会话恢复的边界情况。
- **核心概念一句话**：会话恢复要考虑"有 token 但 token 坏了"的中间态，每一层失败都有出路。
- **答案要点**：`runBootstrap()` 的顺序：①先 `applyAuthorizationHeader(this.accessToken)` 保证旧头不残留错误状态；②内存里有 accessToken 就先试 `fetchCurrentUser()`（GET /auth/me），成功直接返回；③me 失败（token 过期/无效）就降级走 `this.refresh()` 凭 Cookie 换新；④内存里没 token 也直接走 refresh；⑤refresh 也失败（Cookie 过期）就 `clearSession()` 返回 null，路由守卫据此踢到 /login。全程 `isBootstrapping` 标志控制 loading 态。
- **可能追问**：为什么 me 成功了还要刷新 token？——不刷，me 成功就复用现有 token；只有失败才 refresh，把 refresh 请求压到最低。

**Q9.【问题】错误提示为什么不用 try-catch 里随手写死的文案，而要一个 extractApiError？**

- **考点**：错误信息链路的统一治理。
- **核心概念一句话**：错误信息要从"离用户最近的源头"往回找，找不到才用兜底。
- **答案要点**：`http.ts` 的 `extractApiError(error, fallback)` 有明确优先级：后端响应体里的 `message`（业务语义，比如"知识库不存在"）→ axios 的 error.message（Network Error/timeout）→ 普通 Error 的 message → fallback 兜底文本。`http.test.ts` 专门锁了这三级降级。全站组件统一 `ElMessage.error(extractApiError(err, 'xxx'))`，保证后端给的可读消息能透传到用户，又不会因为后端没给 message 就白屏或显示 [object Object]。
- **可能追问**：单测怎么测 axios 错误而不真发请求？——构造普通对象再 `Object.assign(error, { isAxiosError: true, response: { data: { message: '...' } } })`，`axios.isAxiosError` 按这个标志位判断，不需要真网络。

**Q10.【问题】修改密码后前端做了什么？为什么要重新拉一遍 /auth/me？**

- **考点**：状态一致性——客户端快照与服务器真相的对齐时机。
- **核心概念一句话**：任何"改了自己信息"的操作之后，本地缓存的用户快照就过期了，要么改字段要么重拉。
- **答案要点**：`stores/auth.ts` 的 `changePassword()`：先调 `POST /account/change-password`，成功后立刻把本地 `currentUser.mustChangePassword` 置 false（让"强制改密"引导立刻消失，不等网络），然后 `fetchCurrentUser()` 重拉一次完整档案兜底（万一后端还改了 displayName 等），重拉失败也不打断流程、返回当前值。这是"乐观更新 + 服务端确认"的组合。
- **可能追问**：为什么不能只改本地 mustChangePassword？——本地改只是猜测，服务端可能还有别的派生状态；重拉一次成本低，换来状态和服务器一致。

## 二、Univer 集成与协同编辑（SheetEditor.vue / univerAdapter.js / collabClient.js）

**Q1.【问题】打开一个大 Excel 文档，前端是怎么加载的？为什么要分块？**

- **考点**：大数据量加载的并发池 + 降级设计。
- **核心概念一句话**：大表不能一次拉全量，用"小批次 + 有限并发"拉，失败再降级全量兜底。
- **答案要点**：`SheetEditor.vue` 的 `fetchSheetCelldata()`：每个 sheet 按 chunkCount 切成每批 `CHUNKS_PER_REQUEST = 5` 个 chunk 的区间，用一个手写并发池——`MAX_INFLIGHT = 3` 个 worker 共享一个 `nextBatch` 游标，`Promise.all` 等全部 worker 收工，`results[index]` 按原下标放结果保证顺序；工具栏实时显示 loadedChunks/totalChunks。任何一个批次失败就降级：catch 里改调 `loadAllCelldata()` 一次拉全量并 toast 提示"降级为全量加载"。分块调的是 `api/excel.ts` 的 `loadSheetChunks(docId, sheetId, start, end)`。
- **可能追问**：为什么并发是 3 不是 20？——并发太高会把后端连接池和 DB 打爆，而且进度条体验差别不大；3 是"明显加速又不放大后端压力"的保守值。为什么不直接用后端聚合接口？——聚合接口会把等待时间集中在一个响应里，看不到进度，也失去了对失败批次的隔离。

**Q2.【问题】Luckysheet 格式和 Univer 格式差在哪？你的转换层怎么设计的？**

- **考点**：异构数据格式的适配层（Adapter 模式落地）。
- **核心概念一句话**：两个世界的字段名、枚举值都不一样，中间必须有纯函数翻译层，出错不污染原数据。
- **答案要点**：`utils/univerAdapter.js`（933 行）：后端存的是紧凑的 `{r, c, v}` 稀疏 celldata（LuckySheet 风格），Univer 引擎要的是快照结构（sheetOrder/sheets/cellData/样式表）。文件顶部就是三组映射表：`CELL_TYPE_TO_UNIVER`（s/n/b → 1/2/3）、对齐枚举 `LUCKY_HT_TO_UNIVER`（注意 0 映射 2，两边编号错位）、文本旋转 `LUCKY_TR_TO_UNIVER`。入口 `createUniverWorkbookAdapter({ documentId, metas, celldataList })` 返回 adapter，持有 `originalCells/baselineCells/serverRevisions` 几个 Map，导出 `captureBaseline / collectChangedCells / hasStructuralChange / acceptBaseline / serialize / getLocalSheetId / getServerSheetId`。行列上限贴 Excel 规范 1048576 行 × 16384 列，空表兜底 100×20。
- **可能追问**：为什么函数要"无副作用"？——转换出错时不能污染原数据；纯函数也才能脱离 Vue 单测（format.test/safeMarkdown.test 同思路）。

**Q3.【问题】用户编辑一个单元格后，到别人屏幕上出现新值，前端链路是什么？**

- **考点**：协同编辑的发送-广播闭环、回环去重。
- **核心概念一句话**：本地编辑攒一批、带版本号发出去；服务器广播回来时，自己发的用 requestId 认领跳过，别人的才往画布上画。
- **答案要点**：四步：①Univer 的 `Event.CommandExecuted` 监听（`attachEditListener()`），命令 id 是 `sheet.command.set-range-values` 就进 `handleLocalRangeCommand()`，把范围内每个格子写进 `pendingSyncCells` Map（key 是 `serverSheetId:r:c`）；②`scheduleEditFlush()` 180ms 防抖合并连续输入；③`flushPendingSyncCells()` 给每格生成 `requestId = edit-${Date.now()}-${++collabSeq}` 塞进 `ownRequestIds` Set，经 `collabClient.send()` publish 到 `/app/excel/edit`，并带上 `baseRevision`（乐观锁版本）；④广播回来 `handleCollabMessage()` 先查 requestId——是自己的就从 Set 删除并用广播里的最新 revision 刷新 baseRevision，不是自己的才 `applyRemoteCells()` 往 Univer 写值，写值前把 `applyingRemoteCells` 置 true，防止远程写入又触发了本地监听造成死循环。
- **可能追问**：为什么要 180ms 防抖？——连续打字每敲一个键都是一次 set-range-values 命令，不合并会 flood 服务端；180ms 在"延迟可感知"和"消息量"之间取平衡。baseRevision 什么时候变？——自己的编辑被服务器接受（广播带回 revision）或收到冲突回执时。

**Q4.【问题】两个人同时改同一个单元格怎么办？冲突在前端怎么呈现？**

- **考点**：乐观锁冲突的用户体验（系统不替用户做决定）。
- **核心概念一句话**：前端只负责把"冲突"翻译成人话和选项，覆盖还是放弃由用户选。
- **答案要点**：`handleCollabMessage()` 收到 `type === 'error'` 且 `code === 'REVISION_CONFLICT'` 时弹 `ElMessageBox.confirm`："该单元格已被他人更新。是否用你的内容覆盖服务器上的最新值？"——确认则提示用户重新修改，并拿广播里的 `serverRevision` 更新本地 baseRevision（刷到最新版本重试）；取消则只刷版本放弃本次。baseRevision 本身维护在 `SheetEditor.vue` 的 `baseRevision ref`，注释写明"每次广播/冲突回执都会刷新"。最终冲突仲裁在后端 LWW+版本校验，前端弹窗只是 UX 层。
- **可能追问**：为什么不用 OT/CRDT？——当前场景是低频表格编辑，"单格 LWW+版本冲突弹窗"复杂度低且够用；OT/CRDT 是字符级实时协同的方案，收益撑不起复杂度，这是我面试常准备的"为什么不做"答案。

**Q5.【问题】STOMP 客户端断了怎么感知、怎么恢复？心跳的作用是什么？**

- **考点**：长连接的存活检测与自动重连。
- **核心概念一句话**：心跳是双方定期互发的"我还活着"帧，让断网在秒级被发现而不是傻等 TCP 超时（默认要 15 分钟以上）。
- **答案要点**：`collabClient.js`：`heartbeatIncoming/heartbeatOutgoing` 都是 10000ms，`reconnectDelay: 2000` 断线 2 秒自动重连（STOMP Client 内建重试）；状态回调 `onWebSocketClose/onDisconnect/onStompError` 统一走 `handleStatus('offline')`，`onConnect` 置 online 并重新订阅。连接用 `webSocketFactory: () => new SockJS(url)`——SockJS 是兜底包装，老浏览器没 WebSocket 时自动降级轮询。状态机 online/offline/connecting 驱动右上角连接指示灯；掉线时清空在线用户和远程光标，重连成功后 200ms 再把 pending 的离线编辑 flush 出去（`onStatus('online')` 时 `flushPendingSyncCells()`）。
- **可能追问**：掉线期间的编辑会丢吗？——不会，`pendingSyncCells` 里攒着，重连 online 后 flush；但注意 flush 只在 collabStatus === 'online' 才执行，离线保存走的是 HTTP 保存按钮路径，两条路径独立。

**Q6.【问题】在线用户列表和远程光标是怎么实现的？**

- **考点**：presence 广播与 DOM 层渲染。
- **核心概念一句话**：presence 是"房间成员名单"广播，光标是"坐标 + 颜色"的覆盖层，两者都靠 STOMP 房间隔离。
- **答案要点**：房间隔离：订阅 `/topic/excel/{documentId}`（编辑广播）和 `/topic/excel/{documentId}/users`（USER_LIST → presence 事件），进入时 publish `/app/excel/join/{id}`、离开时 `/app/excel/leave/{id}`——一个文档一个房间，广播只发给同房间的人。在线名单渲染成头像列（`avatarColor()` 按用户名 hash 从 6 色色板取色，同一用户各端颜色一致）。远程光标是 `SheetEditor.vue` 模板里的 `remote-cursor-layer` 绝对定位覆盖层，`pointer-events: none` 不挡编辑操作，badge 用 transform translate 移动。
- **可能追问**：颜色为什么要 hash 而不是随机？——随机会导致同一用户每次刷新换色，多人协作时分不清谁是谁；稳定 hash 让"颜色即身份"。

**Q7.【问题】保存按钮按下后前端怎么判断"发全量还是发增量"？**

- **考点**：快照 diff 与结构变化/内容变化的分流。
- **核心概念一句话**：行列增删这种结构变化没法用单元格 patch 表达，只能整本重建；纯格子改动就只发改过的格子。
- **答案要点**：`saveChanges()`：先 `workbook.save()` 拿当前快照，调 adapter 的 `hasStructuralChange(snapshot, activeSheetId)`——为 true（增删 sheet/行列）就走 `saveWorkbook(docId, sheets)` 全量重建，并用返回的 `sheetIdMap` 调 `updateServerSheetIds()` 对齐本地/服务端 sheet id；否则 `collectChangedCells(snapshot)` 对 baseline 做 diff，`batchUpdateCells(docId, changedCells)` 只发变化的格子。两条路径成功后都 `acceptBaseline()` 重置基线、清 dirtyCells。没有变化时提示"没有需要保存的修改"。导出前会拦一道 `hasUnsavedChanges`，防止导出旧数据。
- **可能追问**：baseline 是什么？——打开文档时 `captureBaseline(workbook.save())` 记录的初始快照，是 diff 的参照物；保存成功 acceptBaseline 把参照物更新成当前状态。

**Q8.【问题】组件卸载时 Univer 和 STOMP 怎么清理？漏了会怎样？**

- **考点**：SPA 路由切换的资源泄漏。
- **核心概念一句话**：长连接和第三方实例不清理，就是路由切换后的"僵尸监听器"继续发消息、继续占内存。
- **答案要点**：`disposeWorkbook()` 在 `onBeforeUnmount` 调用，顺序：断开 collabClient → 清 `ownRequestIds/pendingSyncCells` → dispose Univer 命令监听（`commandDisposable?.dispose()`）→ 清 180ms 防抖定时器 → `univerAPI.disposeUnit(activeWorkbookId)` + `univerApp.dispose()` → 清 DEV 调试挂载的 `window.__argusUniverAPI` → 重置协同状态。漏掉 collabClient 的话，离开页面后 WebSocket 还订阅着房间，别人编辑还会推给一个已死的组件；漏掉定时器的话闭包持有组件引用，内存泄漏。
- **可能追问**：为什么要 try-catch 包 disposeUnit？——销毁顺序上 workbook 可能已不可用，dispose 链路本身就是"尽力而为"，不能让清理过程自己抛错打断后续清理。

**Q9.【问题】Univer 挂载到 DOM 的时机有什么讲究？为什么 bootWorkbook 前要 await nextTick？**

- **考点**：第三方 DOM 库与 Vue 虚拟 DOM 的协作。
- **核心概念一句话**：Univer 需要一个真实存在的 DOM 容器，而 Vue 的 DOM 是渲染后才有，必须等它渲染完。
- **答案要点**：`createUniver` 的 `UniverSheetsCorePreset({ container: 'univer-container' })` 按 id 找容器。`initDocument()` 里先加载数据、`loading.close()` 后 `await nextTick()` 再 `bootWorkbook()`，确保 loading 遮罩卸载、容器可见后再挂载。加载中用 `ElLoading.service({ lock: true })` 全屏锁。Univer 用 0.25 的 presets 体系挂了 11 个 preset（core/条件格式/数据验证/图形/查找替换/筛选/超链接/批注/排序/表格/线程评论），每个 preset 配一份 zh-CN locale 合并进 locales。
- **可能追问**：为什么不用 v-if 控制容器再挂载？——本质一样，nextTick + ref 容器或 v-if 后的 mounted 钩子都行；关键是"容器必须先于 createUniver 存在"这个约束。

**Q10.【问题】财务明细行的乐观锁指纹是什么？为什么不用后端 version 字段？**

- **考点**：前后端协作的行级冲突检测（这是真实代码里少见的亮点）。
- **核心概念一句话**：把"我编辑时的那行长什么样"做成指纹交给服务端比对，等价于给行加了乐观锁，但不需要后端加字段。
- **答案要点**：`utils/fingerprint.js`：`computeRecordFingerprint()` 把 18 个业务字段按固定顺序拼成明文串（金额字段统一数值化文本去尾零），用户打开行编辑器那一刻算好指纹，提交时带回；服务端 `FinanceImportService.recordFingerprint` 用同一套字段和格式重算，不一致说明期间被人改过，拒绝覆盖。注释特别强调"必须与服务端保持一致，否则乐观锁会误判为冲突"。
- **可能追问**：明文拼接 vs SHA-256？——当前服务端就是明文比对，没有哈希；这是性能够用下的简化，风险是超长行数据多传一串，可接受。

## 三、SSE 流式问答（api/qa.ts / api/assistant.ts / QaView.vue / AssistantView.vue）

**Q1.【问题】为什么你的 SSE 用 fetch 手写解析，而不用浏览器自带的 EventSource？**

- **考点**：EventSource 的能力边界（SSE 必考题）。
- **核心概念一句话**：EventSource 只能发 GET、只能带 Cookie 不能带自定义 Authorization 头，而问答是带请求体的 POST + Bearer 鉴权，只能用 fetch 自己读流。
- **答案要点**：`api/qa.ts` 的 `streamAskQuestion()`：`fetch(POST ${baseUrl}/qa/stream-ask)`，headers 手动放 `Authorization: Bearer ${accessToken}` 和 `Content-Type: application/json`，body 是问题 JSON，`signal` 接 AbortSignal 支持中断。`response.body.getReader()` 拿 ReadableStream，`TextDecoder('utf-8')` 开 `stream: true` 循环 decode，往 `buffer` 里追加后按 `\n\n` 切事件。这条手写解析链在 qa.ts 和 assistant.ts 各有一份，是全前端最值得讲的"底层能力"代码。
- **可能追问**：为什么不 GET + EventSource？——问题文本可能超 URL 长度限制，且 EventSource 无法设 Authorization 头，只能靠 Cookie 鉴权，与项目"Bearer 短 token"的鉴权体系不匹配。

**Q2.【问题】SSE 一个事件被 TCP 分包切成两半，你的代码怎么处理？**

- **考点**：流式解析的缓冲区（粘包/半包，后端出身的天然共鸣点）。
- **核心概念一句话**：和后端 TCP 粘包是同一个问题——不完整就留在缓冲区，凑齐分隔符再切。
- **答案要点**：核心循环（`streamAskQuestion` 内）：`buffer += decoder.decode(value, { stream: true })`，然后 `while ((separatorIndex = buffer.indexOf('\n\n')) >= 0)` 循环——切出 `buffer.slice(0, separatorIndex)` 作为完整事件交给 `dispatchQaSseEvent()`，buffer 剩下不完整的尾巴等下一个 chunk 拼上。`stream: true` 参数很关键：UTF-8 多字节字符可能被 chunk 从中间切开，不开 stream 模式 decode 会产出乱码。这是标准的生产级写法，我能逐行讲。
- **可能追问**：为什么按 `\n\n` 切？——SSE 规范里事件之间用空行分隔，事件内部是 `event: xxx\ndata: yyy` 的行，空行是唯一可靠的事件边界。

**Q3.【问题】SSE 定义了哪些事件类型？各自的 payload 是什么格式？**

- **考点**：事件协议设计（前后端契约）。
- **核心概念一句话**：协议设计的原则是"频繁的小事件用裸文本，低频的 结构化数据用 JSON"。
- **答案要点**：问答流（`dispatchQaSseEvent`）五类：`token`（data 是纯文本增量，直接拼不 JSON.parse，省开销）、`citations`（JSON 数组，解析失败降级为空数组，不能因为引用挂了把答案弄丢）、`evidence-overview`（JSON，失败传 null）、`error`（JSON `{message}`，解析失败把原始文本当消息）、`record`（JSON `{recordId}`，畸形直接忽略——此时答案已送达）。助手流（`parseSseEvent`）是 `delta/done/tool_call/error`，data 统一 JSON。解析都按行扫描 `event:`/`data:` 前缀，多行 data 用 `\n` join 还原多行文本。
- **可能追问**：token 事件为什么不也包成 JSON？——token 是最高频事件（每秒几十上百个），裸文本省掉两端 JSON 序列化开销；结构化字段（citations）才值得 JSON。

**Q4.【问题】流式过程中 Vue 怎么渲染"打字机效果"？有什么响应式陷阱？**

- **考点**：Vue 3 响应式系统的一个真实深坑（代码注释里自己写了）。
- **核心概念一句话**：push 进响应式数组的对象会被包一层 Proxy，必须拿 Proxy 后的引用改属性，改原始对象 Vue 感知不到。
- **答案要点**：`AssistantView.vue` 有段注释级的坑位自述：先往 `messages.value.push(assistantMsg)` 放占位消息，然后必须 `const target = messages.value[messages.value.length - 1]` 重新取——push 后 Vue 会把元素包成 Proxy，只有通过这个 Proxy 改 `target.content` 才触发视图更新；留着 push 前的原始对象引用去改，"写到原始内存但 Vue 不知道"，打字机效果直接失效。流式回调里 `target.content += ev.delta` 逐段追加，QaView 是 `streamedContent` 累加后 `updateMessage(sessionId, assistantId, { content: streamedContent })` patch 消息对象。
- **可能追问**：每个 token 都触发一次重渲染，性能受得了吗？——token 粒度追加对长回答每秒几十次 patch，Vue 的 diff 对纯文本插值很轻；真要优化可以做 rAF 节流合并，但当前量级没必要，这也是"先测再优化"的态度。

**Q5.【问题】用户中途点"停止生成"，前端做了什么？**

- **考点**：AbortController 与流的中断语义。
- **核心概念一句话**：abort 让底层 fetch 连接断掉，read() 抛 AbortError，前端把已收到的内容留住而不是整条丢掉。
- **答案要点**：`AssistantView.vue`：发请求前 `streamAbort = new AbortController()`，signal 传进 `streamAssistantMessage`；中断时 `streamAbort.abort()`，catch 里判断 `err.name === 'AbortError'`——这不是失败：置 `streaming = false`，已有内容保留，空则补 `_(已中断)_`，有内容则追加一行中断标记；其他错误才标 `failed = true` + `failureMessage`。finally 里 `streaming = false`、`streamAbort = null`，并静默刷新会话列表（后端可能自动改了标题）。停止按钮由 `streaming.value` 控制 v-if 显隐。
- **可能追问**：前端 abort 后后端知道吗？——TCP 连接断开后，服务端写响应会抛 IOException，SSE emitter 的异常处理会终止生成；具体到本项目后端如何感知没有逐行验证过，我不编造，只确认前端断开是明确语义。

**Q6.【问题】流式回答的"最终内容"为什么以 done 事件为准而不是本地累积？**

- **考点**：流式渲染的权威数据源（一致性）。
- **核心概念一句话**：本地累积的是"过程副本"，服务端最终落库的才是"权威答案"，两者可能不一致。
- **答案要点**：`onStreamEvent` 的 `done` 分支：`if (ev.reply != null && ev.reply.length > 0) target.content = ev.reply`——用服务端权威回复整体覆盖本地累积的 delta 拼接，同时绑定 `messageId`（`localId = srv-${messageId}`，把本地临时 id 换成服务端 id 供后续评价/引用），再设置 citations。为什么不信任累积？——中途重试、内容过滤、后处理（如截断）都可能让最终文本和增量之和不完全一致，以服务器为准消歧义。
- **可能追问**：done 没到连接就断了怎么办？——本地累积内容还在（保留已收部分），streaming 复位，用户看到的是不完整回答；刷新会话时会从服务端重新拉取权威记录。

**Q7.【问题】问答页的历史会话是怎么和流式消息捏合的？hydrate 是什么？**

- **考点**：本地会话模型与持久化记录的两段式设计。
- **核心概念一句话**：列表页只拉摘要，点开某条才按需拉全量——这就是 hydrate（按需注水）。
- **答案要点**：`views/qa/composables/useQaSessions.ts` 管本地会话；历史记录走 `api/qa.ts` 的 `listQaRecords`（分页摘要：question/answerPreview/latencyMs/userRating）和 `getQaRecord(recordId)`（全量：answer/citations/evidenceOverview/tokens）。`QaView.vue` 的 `hydrateHistorySession(sessionId)`：会话有 recordId 且未 hydrated 才调 `getQaRecord` 填充完整引用，`session.hydrated` 标志防重复拉。并发安全用 `requestSeq` 计数：响应回来时 `requestSeq !== historyRequestSeq` 就丢弃，防止快速切换时旧请求覆盖新状态（竞态防护）。
- **可能追问**：为什么不用后端会话列表直接渲染？——问答历史以 qa_records 为准，前端 session 是展示壳；两段式让列表秒开，详情懒加载。

**Q8.【问题】Markdown 回复直接 v-html 会有什么风险？你怎么防的？**

- **考点**：存储型 XSS（PROJECT_TRUTH 硬约束："前端 Markdown 渲染必须净化"）。
- **核心概念一句话**：模型输出和用户上传都是不可信输入，marked 解析出的 HTML 必须经 DOMPurify 洗一遍才能进 v-html。
- **答案要点**：`utils/safeMarkdown.ts` 是全站唯一 Markdown 渲染入口：`marked.setOptions({ gfm: true, breaks: true })`，`renderSafeMarkdown()` 先 `marked.parse`，再 `DOMPurify(window).sanitize(html, { FORBID_TAGS: ['script','style','iframe','object','embed','form','base'], FORBID_ATTR: ['style'] })`。有个细节：测试环境（happy-dom/jsdom）下 DOMPurify 拿不到全局 window 会静默跳过净化，所以显式 `DOMPurify(window)` 绑定保证浏览器和测试行为一致。a/img 的 href/src 走 DOMPurify 默认协议白名单，javascript:/data:/vbscript: 一律移除。
- **可能追问**：为什么 FORBID style 属性？——CSS 也能攻击（ phishing 覆盖、UI 重绘），且样式注入是存储型 XSS 的常见旁路；CSP 只是兜底，净化才是第一道。

**Q9.【问题】nginx 和 Vite 代理对 SSE 做了什么特殊配置？为什么？**

- **考点**：真实踩坑——代理缓冲会杀死流式（本项目最有故事的题）。
- **核心概念一句话**：默认情况下反向代理会把响应攒够一块再转发，SSE 的"逐字推送"就变成了"憋半天一次性到"，打字机效果全毁。
- **答案要点**：两层各有一套。Vite dev 代理（`vite.config.ts`）：`/api` 配 `selfHandleResponse: false` 让 http-proxy 直接透传字节，并在 `configure` 里挂 `proxyRes` 监听，发现 `content-type` 含 `text/event-stream` 就设 `cache-control: no-cache, no-transform`、`x-accel-buffering: no`、删掉 `content-length`（注释原文：禁用代理缓冲，防止 delta 堆到最后才送达浏览器，破坏打字机效果）。生产 nginx（`nginx.conf`）：`/api` location 里 `proxy_buffering off; proxy_cache off; proxy_read_timeout 300s`——300 秒是给长回答留时间，默认 60 秒会掐断长流。`x-accel-buffering: no` 这个响应头正是给 nginx 看的开关。
- **可能追问**：怎么发现是这个问题的？——现象是本地 dev 正常、走 nginx 后回答整段卡住再一次性蹦出来，逐层排查代理配置后关掉 buffering 恢复；这也是我背熟的真实踩坑故事。

## 四、状态管理与路由守卫（Pinia / router / composables）

**Q1.【问题】为什么用 Pinia 而不是 Vuex？你的 store 怎么组织的？**

- **考点**：状态管理选型与 Pinia API。
- **核心概念一句话**：Pinia 是 Vue 3 官方推荐：去 mutations、天然 TS 支持、store 可按需拆。
- **答案要点**：项目 Pinia 3.0，`stores/pinia.ts` 创建实例、`main.ts` 里 `app.use(pinia)`，注意顺序：pinia 必须在 router 之前 use，因为路由守卫里要用 `useAuthStore()`。auth store 用 Options 风格 `defineStore('auth', { state, getters, actions })`：state 存 accessToken/currentUser，getters 派生 isAuthenticated/isAdmin/isFinance/isUser/homePath，actions 是 login/logout/bootstrap/refresh。全项目目前只有 auth 和 app 两个 store——刻意克制，组件局部状态（比如编辑器的脏格 Map）不放全局，因为它们生命周期跟页面走。
- **可能追问**：为什么 accessToken 不放 localStorage 由 store 持久化插件同步？——持久化 = 落盘 = XSS 可偷，宁可刷新页多一次 refresh 换 token，见 Q1-1。

**Q2.【问题】模块级 ref 的 composable 和 Pinia store 有什么区别？你两个都用了，怎么选？**

- **考点**：两种共享状态方案的边界（代码里有真实对照）。
- **核心概念一句话**：模块作用域的 ref 天然就是单例——所有组件 import 到的是同一个变量，这是"穷人版 store"。
- **答案要点**：`useQaSessions.ts` 把 `sessions/activeSessionId` 两个 ref 定义在**函数外**的模块作用域，所有调用 `useQaSessions()` 的组件共享同一份（问答页多组件：侧栏/输入框/消息区）。Pinia 则用于需要 devtools、跨页面持久的登录态。我的选择标准：跨"页面级"共享、需要严格调试的用 Pinia；一个页面族内部共享的用模块 ref 更轻。另一细节：`useQaSessions` 返回的函数都是闭包，操作同一份模块状态。
- **可能追问**：模块 ref 状态会随路由切换保留吗？——会，模块在 SPA 生命周期内不销毁；刷新页面才重置。这也意味着问答页离开再回来会话还在，是产品预期。

**Q3.【问题】路由守卫 beforeEach 里做了哪几件事？顺序为什么是这样？**

- **考点**：守卫的完整决策链（面试手册"前端生存五连"第 2 条）。
- **核心概念一句话**：先恢复会话，再判断登录态，再纠偏角色路径，最后套 meta 声明式门槛——每一步依赖上一步的结果。
- **答案要点**：`router/index.ts` 的 `beforeEach` 五连：①`await authStore.bootstrap()`（内部单飞去重）恢复会话；②已登录访问公开页（/ /login /404）→ 重定向 `authStore.homePath`；③未登录访问受保护页 → /login；④已登录受保护页调 `resolveRedirectForPath(to.path)` 做角色路径纠偏（财务页只许 FINANCE）；⑤meta 声明式拦截：`requireAdmin && !isAdmin` 或 `requireFinance && !isFinance` → 送回 homePath。另有 `afterEach` 统一设 `document.title`。
- **可能追问**：bootstrap 为什么要 await？——守卫是异步函数，未恢复登录态就判断 isAuthenticated 会误踢；代价是每次导航串行一次恢复检查，好在 bootstrap 内部有短路（已有会话直接返回）和单飞。

**Q4.【问题】路由级懒加载怎么做的？为什么不把所有页面打一个包？**

- **考点**：代码分割的基本功。
- **核心概念一句话**：`() => import('...')` 让每个页面成为独立 chunk，首屏只下载用户访问的第一个页面。
- **答案要点**：`router/index.ts` 全部 18 个路由组件都是 `component: () => import('../views/...')` 动态 import——AdminDashboard、SheetEditor、FinanceDashboard 等各成 chunk，用户不进 Excel 页就不会下载 11MB 的 Univer 依赖。配合 `vite.config.ts` 的 manualChunks 把 vendor 分成 vendor-univer/vendor-element/vendor-vue/vendor-office 四块，vendor 稳定不变、浏览器可长缓存，业务代码迭代不影响 vendor 缓存命中。layout（DefaultLayout）也是动态 import。
- **可能追问**：怎么验证懒加载生效？——build 产物里能看到每个 view 的独立 js 文件；Network 面板按路由跳转观察按需加载请求。

**Q5.【问题】Element Plus 你是全量引入还是按需引入？为什么？**

- **考点**：诚实面对技术选型的取舍（手册"待验证"原则）。
- **核心概念一句话**：全量引入省配置和心智，代价是 vendor-element 变大——我如实说，并知道按需方案怎么改。
- **答案要点**：`main.ts` 里 `app.use(ElementPlus)` + 全量 CSS `import 'element-plus/dist/index.css'`，是全量引入，没有上 unplugin-vue-components 按需。理由：项目用 Element 的组件多（表格/弹窗/下拉/消息/加载），按需插件配置成本和构建不确定性换来的体积收益有限，而且 vendor-element 单独成 chunk 只在首次访问缓存一次。要说改进：接入 `unplugin-vue-components` + `ElementPlusResolver`，CSS 也会随组件按需注入。这是我知道正确答案但有意取舍的点，不装。
- **可能追问**：为什么图标单独引？——`@element-plus/icons-vue` 按名字具名导入（SheetEditor 里 import { ArrowLeft, Filter... }），tree-shaking 自然生效，本来就按需。

**Q6.【问题】AdminDashboard 一次要拉 5 个接口，怎么做既快又稳？**

- **考点**：并行请求 + fail-soft（部分失败不拖垮整页）。
- **核心概念一句话**：Promise.all 提速的前提是"每个 promise 自己 catch"，否则一个接口挂全部挂。
- **答案要点**：`AdminDashboard.vue` 的 `loadDashboard()`：`Promise.all([fetchAdminUsers().catch(() => []), fetchGroups().catch(() => 默认结构), fetchDocuments().catch(() => []), fetchMetricsOverview().catch(() => null), fetchPlatformStats('LAST_7_DAYS').catch(() => null)])`——五个请求并行，每个都带独立降级值：列表类给空数组、指标类给 null，页面展示"0 人/0 份"而不是整页报错。外层 loading/error 状态控制骨架屏与错误条。这是 fail-soft：单接口故障被隔离成"那一块没数据"。
- **可能追问**：Promise.all vs allSettled？——allSettled 语义更标准，但我需要"给每个失败一个默认值"，逐项 catch 正好就地完成降级，比 allSettled 之后再映射更直白。

**Q7.【问题】前端怎么防"用户直接改 URL 进入无权页面"？能防住吗？**

- **考点**：前端权限的真实定位（被问概率极高）。
- **核心概念一句话**：前端守卫是引导，后端鉴权才是墙；前端权限被绕过不造成数据泄露才算设计正确。
- **答案要点**：三层：路由守卫的 requireAdmin/requireFinance meta 检查 + `resolveRoleRedirect` 路径纠偏（详见 Q3）；组件级 `canEdit`（SheetEditor 从 `doc.canEdit` 读，false 时 `workbook.setEditable(false)`、隐藏保存/编辑按钮、只读 tag）；请求层面所有数据都来自带 Bearer 的接口，后端对每个接口重新校验文档 ACL（ExcelPermissionService/DocumentRoleGate），就算有人绕过前端用 curl 打接口也拿不到数据。所以"防住"的标准是：数据层防住，交互层尽力。
- **可能追问**：canEdit 是后端返回的，前端能自己改成 true 吗？——能，但改了也只是解除 UI 限制，写操作到后端会被 ACL 拒绝；这就是"前端权限是体验不是防线"的具体含义。

**Q8.【问题】你的前端有测试吗？测什么？为什么不多测点？**

- **考点**：测试策略的诚实陈述。
- **核心概念一句话**：测"纯函数层"性价比最高——它们是格式契约，坏了就是数据损坏。
- **答案要点**：Vitest 5，14 个测试全过。三个文件：`http.test.ts` 锁 extractApiError 的三级降级；`safeMarkdown.test.ts` 锁 XSS 净化（script/iframe 被剥除）；`format.test.ts` 锁格式化。选它们的逻辑：这三个是"纯输入输出"且坏掉的后果最严重（错误文案错→用户体验；净化失效→安全漏洞；格式转换错→数据损坏），而 Vue 组件的交互大多被后端 1634 个测试 + 手工验收覆盖。要说扩展方向：collabHelpers 的纯函数（isEditCommand/remoteLuckyToUniver）也是理想单测对象，注释里就写了"可独立单测"。
- **可能追问**：组件测试为什么不做？——Vue Test Utils 对 Univer/Element Plus 重组件的 mock 成本高、维护脆；把逻辑抽成纯函数再测（项目已有此实践：collabHelpers 就是从 SheetEditor 抽出来的）是更划算的路径。

## 五、打包优化与工程化（vite.config.ts / nginx.conf / 构建）

**Q1.【问题】你的构建产物里最大的 chunk 是什么？知道为什么吗？怎么治理？**

- **考点**：技术债的量化认知（已登记在 PROJECT_TRUTH 风险清单）。
- **核心概念一句话**：11.4MB 的 vendor-univer 是 Univer 引擎 11 个 preset 的代价——先量化承认，再给三步治理方案。
- **答案要点**：`vendor-univer` 约 11.4MB、gzip 约 2.9MB（PROJECT_TRUTH 明确登记）。原因：SheetEditor 静态 import 了 11 个 Univer preset 及各自 CSS（条件格式/数据验证/图形/查找替换/筛选/超链接/批注/排序/表格/线程评论/核心）。它已通过 manualChunks 独立成 chunk 且配合路由懒加载，**不影响非 Excel 页首屏**，影响的是进编辑器的等待时间。治理三步（ROADMAP P1-3 登记）：①确认 Univer 只在 Excel 路由加载（已做到）；②manualChunks 分包（已做到）；③评估按需 preset——比如查找替换/排序走 Univer 内置 command 即可，砍掉对应 preset；再评估滚动加载替代一次挂全量数据。
- **可能追问**：gzip 2.9MB 用户实际要下多少？——首次进编辑器要下完整 2.9MB（gzip 后），之后命中浏览器缓存；所以优化重点是"是否真的需要全部 preset"，比压缩更有效。

**Q2.【问题】manualChunks 具体怎么配的？为什么分这四类？**

- **考点**：分包策略的缓存友好设计。
- **核心概念一句话**：分包的目的是"按变化频率分组"——vendor 几乎不变吃长缓存，业务代码天天变也不影响 vendor 缓存。
- **答案要点**：`vite.config.ts` 的 `build.rolldownOptions.output.manualChunks(id)`（Vite 8 用 rolldown）：id 含 `@univerjs/` → `vendor-univer`；`element-plus`/`@element-plus/icons-vue` → `vendor-element`；`vue-router`/`pinia`/`vue/` → `vendor-vue`；`exceljs`/`file-saver`/`marked` → `vendor-office`。按"变化频率+使用场景"分组：univer 只编辑器用、office 类只导出/渲染用、element 全站用但版本稳定、vue 全家桶最稳定。返回 undefined 的走默认分包。
- **可能追问**：manualChunks 会不会造成循环依赖警告？——按包名整库分组天然避免拆碎依赖环；如果按业务目录拆反而容易引出初始化顺序问题，所以选了最粗粒度。

**Q3.【问题】vite.config 里那个 `define: { global: 'globalThis' }` 是干嘛的？**

- **考点**：浏览器端复用 Node 生态包的兼容手段（细节记忆点，答出来很加分）。
- **核心概念一句话**：sockjs-client 是从 Node 代码改编的，运行时引用 Node 的 global 对象，浏览器里没有，必须编译期替换。
- **答案要点**：`define: { global: 'globalThis' }`——sockjs-client 在浏览器 bundle 里引用 Node 的 `global`，浏览器没有这个标识符会直接 ReferenceError；`define` 在构建时把 `global` 字面量替换成 `globalThis`（标准全局对象，浏览器和 Node 都有）。注释原文写明"sockjs-client 在浏览器 bundle 里引用 Node 的 global，必须替换为浏览器全局对象"。这是 STOMP/SockJS 技术栈在 Vite 下的经典配置。
- **可能追问**：还有别的解法吗？——升级到原生 WebSocket 就可以整个甩掉 SockJS；项目保留 SockJS 是为了老浏览器降级能力。

**Q4.【问题】开发环境代理和生产 nginx 的配置为什么要"两边都配 SSE"？**

- **考点**：环境一致性意识（同一坑两个口）。
- **核心概念一句话**：dev 代理和生产代理是两套实现，SSE 不缓冲的配置必须各配各的，漏一边就"本地正常线上坏"。
- **答案要点**：dev 走 Vite 的 `server.proxy`（http-proxy 实现），生产走 nginx，是两个不同的代理软件，缓冲行为各自独立。Vite 侧：`selfHandleResponse: false` + proxyRes 钩子改头（见三-Q9）。nginx 侧：`proxy_buffering off`。任何一边漏配，症状相同——SSE 变成"憋着一起到"。这就是那次真实踩坑的教训：修好一处后另一环境复现，才意识到要成对配置。
- **可能追问**：怎么快速定位是代理缓冲问题？——绕过代理直连后端（或 curl -N 直打 SSE 端点）看是否逐字到达：直连正常、过代理异常，就锁定代理层。

**Q5.【问题】nginx 里 WebSocket 和 SSE 的配置差在哪？**

- **考点**：两种长连接的代理语义差异。
- **核心概念一句话**：WS 是"升级协议"要显式 Upgrade 头，SSE 还是 HTTP 只是"不结束的长响应"，要关缓冲。
- **答案要点**：`nginx.conf` 的 `/ws` location：`proxy_http_version 1.1`（Upgrade 头必须 HTTP/1.1）+ `proxy_set_header Upgrade $http_upgrade` + `Connection "upgrade"` + `proxy_read_timeout 3600s`（长连接默认 60s 会被掐）。`/api` location：`proxy_buffering off; proxy_cache off; proxy_read_timeout 300s; proxy_send_timeout 300s`，为 SSE 服务。另外整站：`client_max_body_size 110m`（Excel 上传）、`try_files $uri $uri/ /index.html`（history 路由刷新 404 的经典解法）、静态资源 `expires 30d + immutable`。
- **可能追问**：为什么静态资源要加 immutable？——告诉浏览器内容永不变化，连 304 协商都不用发；因为构建产物带 contenthash 文件名，内容变则文件名变。

**Q6.【问题】history 模式路由刷新 404 是怎么回事？你怎么解的？**

- **考点**：SPA 部署的经典题。
- **核心概念一句话**：history 模式的路径是前端虚构的，服务器上没有这个文件，必须兜底回 index.html 交给前端路由。
- **答案要点**：路由用 `createWebHistory(import.meta.env.BASE_URL)`（history 模式，URL 无 #）。直接访问或刷新 `/app/excel/3` 时 nginx 找不到该路径的文件，`location /` 的 `try_files $uri $uri/ /index.html` 依次尝试：真实文件 → 目录 → 兜底 index.html，由前端路由接管渲染。hash 模式没这个问题但 URL 难看、SEO 差，所以选 history + nginx 兜底。
- **可能追问**：兜底后静态资源 404 怎么办？——静态资源有独立的 `location ~* \.(js|css|png...)` 块且 `try_files $uri =404`，资源真丢了就明确 404 而不是错误地返回 HTML。

**Q7.【问题】前端哪些东西不该进包但容易被顺手引进去？你项目怎么控制的？**

- **考点**：包体卫生意识。
- **核心概念一句话**：包体卫生的钥匙是"依赖只进真正用它的 chunk，环境差异编译期解决"。
- **答案要点**：几个实际控制点：①DEV 调试工具不进生产——`window.__argusUniverAPI` 挂载包在 `if (import.meta.env.DEV)` 里，生产构建直接摇树掉；②重库按使用场景分 chunk（exceljs 只在导出时被 import，落在 vendor-office，页面级懒加载之下）；③类型导入用 `import type`（api/*.ts 大量使用），TS 类型编译后不留痕；④CSS 的 Univer preset 样式跟随对应 preset 静态 import，进 vendor-univer 而不是全局。
- **可能追问**：怎么发现"不该进来的依赖"？——rollup/rolldown 的构建产物分析（visualizer 类工具）看每个 chunk 的模块构成；或对可疑 id 在 manualChunks 里加 console 打印来源。

**Q8.【问题】如果让你给这个前端做一次"上线前体检"，你会查什么清单？**

- **考点**：前端工程化的全局观（收束题，展示体系化）。
- **核心概念一句话**：体检 = 加载性能 + 安全 + 可靠性三条线，每条都有本项目的真实对应物。
- **答案要点**：加载线：vendor-univer 11.4MB 治理（P1-3 已登记）、首屏只进 vendor-vue/vendor-element、静态资源 immutable 缓存。安全线：safeMarkdown 净化是唯一 v-html 入口（AGENTS 硬约束）、token 内存态 + HttpOnly Cookie、路由守卫不替代后端鉴权、normalizeRequestedPath 防开放重定向。可靠性线：SSE 双环境 buffering 配对、WS 心跳+自动重连+离线编辑缓存、Promise 逐项 fail-soft、onBeforeUnmount 资源清理、Vitest 锁纯函数契约。三条线我都指着真实代码说，不背概念。
- **可能追问**：哪条线最弱？——打包线：vendor-univer 治理只完成两步，preset 按需化未做；组件测试覆盖率低。这是我主动交代的改进项。

## 六、前端高危追问 Top5（后端出身被问前端，最容易露馅的五个点）

**Top1.【追问】"你一个后端，前端就是 CV 的吧？说说你的 SSE 解析怎么写的？"**

- **对策**：这是身份质疑题，唯一解法是把最"底层"的一段代码讲到逐字级。答：fetch + `response.body.getReader()` + `TextDecoder('utf-8', { stream: true })` + buffer 按 `\n\n` 切事件 + 按行解析 event:/data: 前缀，五种事件类型分发。主动抛"stream: true 防多字节字符被 chunk 切开"和"EventSource 不能 POST 不能带 Authorization 头"两个细节，基本能镇住。这在 `api/qa.ts` 和 `api/assistant.ts` 各有一份真实实现，可白板复现。
- **反例**：只会说"用了 EventSource"——直接暴露没用过自定义鉴权的流。

**Top2.【追问】"前端 token 过期了正好有一个请求在飞，怎么办？"**

- **对策**：先诚实再展示广度："我项目当前是前置刷新——每次路由导航 bootstrap 单飞恢复会话，没有做 401 拦截器重放队列，这是我承认的简化。标准方案我知道：single-flight 刷新（共享同一个 refresh Promise）+ 401 请求排队 + 新 token 重放 + 重试次数上限防死循环。"——诚实边界 + 标准答案，比编"我实现了"被追问代码强十倍（手册铁律 3）。

**Top3.【追问】"Vue 的响应式原理讲讲，你的代码里哪里有体现？"**

- **对策**：用 AssistantView 那段真实注释答：push 进 reactive 数组的对象被包成 Proxy，改属性必须通过"push 之后从数组里重新取出的引用"，改原始对象不触发更新——这是我踩过的真实坑，注释就写在 `AssistantView.vue` 351-353 行。再带一句 `ref` 的 `.value` 是 getter/setter 拦截、computed 是缓存依赖。原理 + 实战坑各占一半，比背原理贴金。

**Top4.【追问】"为什么 vendor-univer 有 11MB？你不知道这很大吗？"**

- **对策**：绝不慌。答：知道，PROJECT_TRUTH 风险清单第 4 条和 ROADMAP P1-3 都登记了，gzip 后 2.9MB，且因路由懒加载 + manualChunks 独立成 chunk，不影响非 Excel 页首屏；真实代价只在进入编辑器时。治理方案三步已列：preset 按需评估、滚动加载、按需 preset 砍配置。"已知、已量化、有方案、有优先级"是技术债的标准姿势，比假装没有强。

**Top5.【追问】"协同编辑怎么保证两个人不打架？你用了 CRDT 吗？"**

- **对策**：先讲清现状再谈演进："没用 CRDT。现状是 STOMP 房间广播 + 单格 CELL_EDIT + baseRevision 乐观锁 + 后端 LWW，冲突时前端弹窗让用户选覆盖或放弃，requestId 去重回环。"然后主动给理由：表格协同是低频单元格编辑，粒度是"格"不是"字符"，LWW+冲突弹窗复杂度低且够用；CRDT/OT 解决的是字符级多人同时打字的合并问题，收益撑不起复杂度。"为什么不做"比"做了"更显判断力。
