## 一、AuthController（认证入口）

**Q1.【问题】登录接口的完整入口做了哪些事？为什么 Controller 里几乎不写逻辑？**

- **考点**：分层职责、注解式横切能力。
- **答案要点**：`POST /api/auth/login`，方法上三个注解各管一件事：`@Valid` 触发 `LoginRequest` record 上的 `@NotBlank` 校验；`@OperationLog` 做审计日志；`@RateLimit(limit = 10, window = 60, scope = "用户登录")` 做 60 秒 10 次的登录限流。方法体只有三步：`authService.login(request.loginId(), request.password())` 拿 `AuthTokens`，`authCookieSupport.writeRefreshTokenCookie(response, tokens.refreshToken())` 把 refresh token 写进 httpOnly Cookie，最后返回 `AuthTokensResponse.from(tokens)`。Controller 只做协议转换，业务判定全在 AuthService，这样 Service 可以脱离 HTTP 被单测直接调用。
- **可能追问**：refresh token 会不会出现在登录响应体里？——不会，`AuthTokensResponse` 只有 `accessToken` 和 `currentUser` 两个字段，refresh 只走 Cookie，Javadoc 明确写了"不在此响应中"。

**Q2.【问题】为什么 refresh token 放 httpOnly Cookie 而不是像 access token 一样放响应体？**

- **考点**：XSS 防御、token 生命周期与暴露面设计。
- **答案要点**：access token 30 分钟短命、随 `Authorization` 头走，前端 JS 必须能拿到它；refresh token 14 天长命，一旦被偷等于账号被长期劫持。放 httpOnly Cookie 后浏览器 JS 完全读不到，XSS 脚本偷不走；后续 `/api/auth/refresh`、`/api/auth/logout` 由浏览器自动带 Cookie，前端代码甚至不需要感知 refresh token 的存在。配合 `SameSite=Lax` 和生产环境 `secure=true`，还能挡跨站携带。
- **可能追问**：Cookie 会不会被 CSRF 利用？——`refresh` 是 POST 接口，SameSite=Lax 下跨站 POST 不会携带该 Cookie；项目同时是无状态 JWT + CSRF disable，这套组合是有意为之。

**Q3.【问题】`extractRefreshToken` 方法为什么自己手写遍历 Cookie，而不用 `@CookieValue` 注解？**

- **考点**：容错路径设计。
- **答案要点**：`@CookieValue` 在 Cookie 缺失时会直接抛 `ServletException`，进入 Spring 的异常链路；手写的 `extractRefreshToken` 把"没有 Cookie"降级成返回 `null`：`cookies == null || length == 0` 返回 null，遍历比对 `authProperties.getRefreshCookieName()`（默认 `ARGUS_RAG_REFRESH_TOKEN`），找不到也返回 null。这样"没登录来登出"、"Cookie 过期来刷新"都能走统一的业务错误处理，登出接口甚至对 null 直接静默成功，天然幂等。
- **可能追问**：Cookie 名从哪来？——`AuthProperties.refreshCookieName`，配置前缀 `argus.rag.auth`，改配置就能换名，不用动代码。

**Q4.【问题】登出接口为什么不需要"必须已登录"？它如何保证幂等？**

- **考点**：失败路径、幂等设计。
- **答案要点**：`/api/auth/logout` 在 `SecurityConfig` 里 permitAll，也在 `JwtAuthenticationFilter.shouldNotFilter` 的四个放行路径里（login/register/refresh/logout 精确 equals 匹配）。因为 access token 过期后用户仍应能登出——此时靠的只有 refresh Cookie。`AuthService.logout` 对 null/blank 的 refresh token 直接 return；对无效 token，`revokeToken` 内部 `findActiveToken` 返回 empty 就返回 false，不抛错，接口照样返回 success 并 `clearRefreshTokenCookie`。重复登出、带着脏 Cookie 登出都不会 500。
- **可能追问**：登出后 access token 还能用吗？——能用，最长剩 30 分钟，因为 access JWT 无状态不落库。这是有意的取舍：access 短命 + 服务端只吊销 refresh。要彻底即时失效就得引入 token 黑名单（代价是每次请求查库/查缓存）。

**Q5.【问题】`/api/auth/refresh` 为什么不在方法上加 `@RateLimit`？这算不算漏洞？**

- **考点**：限流策略的分层思考。
- **答案要点**：确实没有加。我的理解是 refresh 的防滥用主要靠三道机制：token 是 `tokenId.secret` 格式且 secret 是 24 字节 `SecureRandom`，猜不出来；每次刷新都要通过 `findActiveToken` 的 BCrypt 比对和 `revokeByIdIfActive` 原子吊销，重放直接 `AUTH_TOKEN_REPLAYED`；而且刷新一次旧 token 就作废，攻击者没有"反复试"的载体。但要说改进空间：注册和刷新接口都没有限流，匿名共享一个限流桶（见限流切面那节），补一个匿名维度限流是合理的加固点。
- **可能追问**：那登录接口 10 次/60 秒够吗？——够防单账号爆破；但注意限流 key 是"用户维度"，匿名登录请求实际共享 `anonymous:AuthController.login` 这一个桶，细节在 RateLimitAspect 那节展开。

**Q6.【问题】`/api/auth/me` 接口的鉴权链路和 login 有什么本质区别？**

- **考点**：过滤器链 vs 放行路径。
- **答案要点**：`me` 不在 `shouldNotFilter` 的四个放行路径里，所以 `JwtAuthenticationFilter` 会解析 `Authorization: Bearer` 头，验签通过后把 `AuthenticatedUser` 写进 `UserContext` 和 `SecurityContextHolder`。Controller 里调 `currentUserService.getRequiredCurrentUser()`，它不是直接信 JWT，而是拿 `UserContext` 里的 userId 再回库查一次 `userQueryService.findById`：查不到抛 `AUTH_USER_NOT_FOUND`，`status == DISABLED` 抛 `ForbiddenException("账号已被禁用")`。所以即使 JWT 还在有效期内，被禁用的用户调 `me` 也会被拒——这是每请求 fail-closed。
- **可能追问**：为什么明知 JWT 已验签还要再查库？——JWT 里的角色/状态是签发时刻的快照，30 分钟内用户可能被禁用或改角色；对"读当前用户身份"这种安全敏感读取，回库校验换来的是即时生效。

**Q7.【问题】如果让你给 AuthController 挑一个"最容易被面试官追问的并发点"，你挑哪个？**

- **考点**：并发登录与单设备语义。
- **答案要点**：挑登录的"吊销旧 token + 签发新 token"两步。`AuthService.login` 先 `revokeActiveTokens(user.getId())` 再 `issueToken`，两步在同一个 `@Transactional` 里；同时 `loadUserForLogin` 用的是 `selectByLoginIdForUpdate`，SQL 是 `where username = #{loginId} or email = #{loginId} order by id for update`，行锁把同一账号的并发登录串行化，避免两个请求交叉执行"互相吊销对方的 token"或者出现两个并存的有效 refresh token。
- **可能追问**：为什么拒绝密码之前要拿行锁？会不会影响吞吐？——锁在验证密码期间持有，确实拉长了持锁时间，但 BCrypt 校验本来就慢（有意的），同一账号并发登录是低频场景，用正确性换吞吐是值得的。

**Q8.【问题】注册接口为什么没有加行锁或分布式锁？并发注册同名用户会怎样？**

- **考点**：check-then-act 竞态与数据库约束兜底。
- **答案要点**：`AuthService.register` 的 `ensureUniqueIdentity` 是先 `userMapper.exists(username)` 再 `exists(email)`，两次检查两次插入之间存在竞态窗口。兜底是数据库：V1 迁移里 `users` 表有 `CONSTRAINT uq_users_username UNIQUE (username)` 和 `uq_users_email UNIQUE (email)`，并发撞名时 insert 会抛唯一约束冲突，事务回滚，不会出现脏数据。应用层检查只是为了给出"用户名已存在"这种友好错误，真正的正确性由唯一约束保证。
- **可能追问**：唯一约束冲突时用户看到什么错误？——会走 DataIntegrityViolation 的通用处理而不是 `AUTH_IDENTITY_EXISTS` 友好文案，这是可以改进的点（catch 后翻译成业务错误码）。

## 二、AuthService（认证核心服务）

**Q9.【问题】讲一下登录方法的七步流程，为什么整个方法要 `@Transactional`？**

- **考点**：事务边界与失败路径。
- **答案要点**：`AuthService.login`（`@Transactional`）按序做七步：① `validateLoginCommand` 归一化校验；② `loadUserForLogin` 加行锁查用户；③ `ensureUserCanLogin` 校验状态+密码；④ `refreshTokenService.revokeActiveTokens` 吊销旧 refresh（单设备语义）；⑤ `issueToken` 签发新 refresh 落库；⑥ `updateSuccessfulLogin` 用 `LambdaUpdateWrapper` 只更新 `lastLoginAt` 一个字段；⑦ `issueAccessToken` 签 JWT 并组装 `AuthTokens` record（含 `mustChangePassword` 和 `currentUser`，避免调用方重复查库）。包事务的原因：④⑤⑥是三次写库，若⑤失败而④已生效，用户所有旧 token 被吊销却拿不到新的——事务保证"要么整体成功要么整体回滚"。
- **可能追问**：JWT 签发在事务内还是事务外？——`issueAccessToken` 是纯内存计算不落库，但它作为方法内第⑦步逻辑上在事务提交前执行；如果事务最终回滚，JWT 虽已生成但随异常一起被丢弃，不会泄漏给调用方。

**Q10.【问题】"账号或密码错误"这个统一文案是怎么实现防账号枚举的？有没有漏网之鱼？**

- **考点**：信息泄露面分析、fail-closed 思想。
- **答案要点**：类常量 `INVALID_CREDENTIALS_MESSAGE = "账号或密码错误"` 在两处复用：`loadUserForLogin` 查不到用户时抛 `AUTH_CREDENTIALS_INVALID` + 这个文案，`ensureUserCanLogin` 密码不匹配时抛同样的错误码和文案。攻击者无法从报错区分"账号不存在"还是"密码错了"。但要诚实地说出边界：`ensureUserCanLogin` 里状态检查在密码检查**之前**，`DISABLED` 账号无论密码对错都抛 `UnauthorizedException("账号已被禁用")`——这其实泄露了"该账号存在"。更严的做法是先验密码再验状态，或禁用账号也返回统一文案。这是我能主动指出的改进点。
- **可能追问**：注册接口的"用户名已存在"不也泄露账号存在性吗？——是的，注册场景泄露不可避免（注册本来就要查重），业界通行做法是注册也要防滥用（邮箱验证/验证码），本项目当前靠用户名格式限制 + 无限流兜底，可以讨论加验证码。

**Q11.【问题】为什么密码校验前要检查"UTF-8 字节数不超过 72"？这个 72 是哪来的？**

- **考点**：BCrypt 算法细节、静默截断风险。
- **答案要点**：BCrypt 算法只处理输入的前 72 字节，超出部分被静默截断。如果不拦，用户设置一个 100 字节的密码，实际生效的只有前 72 字节——"第 73 字节之后随便写什么都能登录"，用户以为的长密码是假安全。所以 `validateLoginCommand` 里三连检查：非空、`length() > 256` 字符拒绝、`password.getBytes(StandardCharsets.UTF_8).length > BCRYPT_MAX_PASSWORD_BYTES(=72)` 拒绝。注意用的是**字节数**不是字符数，一个中文占 3 字节，24 个中文就超限。`AuthConfiguration` 里的 `PasswordHasher` 实现在 `hash`/`matches` 入口还有一道同样的 72 字节防线，双层防护。
- **可能追问**：为什么不在注册时就允许超长？——注册侧 `PasswordPolicyValidator.validate` 同样检查 `MAX_BYTES = 72`，注册和登录口径一致，否则会出现"注册成功但永远登录不了"的诡异问题。

**Q12.【问题】`selectByLoginIdForUpdate` 支持用户名或邮箱登录，SQL 怎么写的？如果一个标识命中多个用户怎么办？**

- **考点**：MyBatis XML SQL、防御性编程。
- **答案要点**：SQL 在 `mappers/UserMapper.xml`：`select ... from users where username = #{loginId} or email = #{loginId} order by id for update`。返回 `List<User>`，`loadUserForLogin` 先判空（抛统一文案），再过 `ensureUniqueLoginMatch`：把所有 id 收进 `LinkedHashSet`，`size() > 1` 说明用户名和邮箱交叉命中了两个不同用户（比如 A 的邮箱恰好是 B 的用户名），抛"登录标识存在冲突，请联系管理员处理"而不是悄悄取第一个——静默取第一个等于随机登录成别人。最后 `users.getFirst()`（Java 21 的 List API）。
- **可能追问**：为什么这能命中多个？username/email 不是唯一约束吗？——唯一约束只分别保证 username 唯一、email 唯一，不保证"A 的 email != B 的 username"，跨列冲突仍可能，所以要有这个检查。

**Q13.【问题】登录成功后为什么要把旧的 refresh token 全部吊销？这带来了什么产品语义？**

- **考点**：单设备登录设计、安全与体验取舍。
- **答案要点**：`revokeActiveTokens(userId)` 的 SQL 是 `update ... set revoked_at = now where user_id = ? and revoked_at is null and expires_at > now`，把该用户所有未吊销未过期的 refresh token 一次清掉。语义上是**单设备登录**：用户在新设备登录，旧设备的 refresh token 立即失效，旧设备 access token 最多再撑 30 分钟就被迫重新登录，而重新登录又把当前设备踢掉。安全收益是丢了不知道的登录态会自动收敛；代价是多设备用户会互相踢。用户列表里 `lastLoginAt` 字段配合这个语义可观测。
- **可能追问**：要改成多设备共存怎么改？——去掉 `revokeActiveTokens` 调用即可，表结构本身支持多行并存（每行一个 tokenId），再加个每用户最大设备数的清理策略更稳。

**Q14.【问题】refresh 的重放检测是怎么做的？讲清楚"原子吊销失败"这条分支。**

- **考点**：并发安全、原子条件 UPDATE。
- **答案要点**：`AuthService.refresh` 流程：空 token 或 `findActiveToken` 查不到 → `AUTH_TOKEN_INVALID`；用户不存在 → `AUTH_USER_NOT_FOUND`；`ensureRefreshAllowed` 拦 DISABLED；然后 `refreshTokenService.revokeTokenById(activeToken.id())`——底层是 `UserRefreshTokenMapper.revokeByIdIfActive`，SQL 为 `update user_refresh_tokens set revoked_at = #{revokedAt} where id = #{id} and revoked_at is null`，返回受影响行数。如果两个请求拿同一个 token 并发刷新，只有一个能更新成功（`revoked_at is null` 条件只对第一个成立），另一个返回 0 行 → 进入重放分支：`revokeActiveTokens` 兜底吊销该用户全部 token、`log.warn("refresh token 重放攻击")`、抛 `AUTH_TOKEN_REPLAYED("refresh token 已被使用，请重新登录")`。refresh token 是一次性使用的，重放是 token 被窃取的强信号。
- **可能追问**：兜底吊销在抛异常后会不会回滚？——会。`AuthService.refresh` 是 `@Transactional`，`BusinessException extends RuntimeException`，抛出时整个事务回滚，兜底吊销也被回滚。真正生效的保护是：重放的 token 早在上一次成功刷新（已提交的事务）里被吊销了，它永远换不出新 token。要把兜底吊销做实，需要 `REQUIRES_NEW` 单独开事务——这是可以主动提的改进。

**Q15.【问题】为什么 refresh 方法里查到 token 后还要 `userMapper.selectById` 再查一次用户？**

- **考点**：状态校验的时机。
- **答案要点**：`user_refresh_tokens` 表里只有 `userId`，token 本身验证通过只说明"这个 token 没被吊销没过期"，不代表用户仍然处于可登录状态。所以 refresh 里 `userMapper.selectById(activeToken.userId())` 后先判空（`AUTH_USER_NOT_FOUND`），再 `ensureRefreshAllowed` 拦 `DISABLED`（`UnauthorizedException("账号已被禁用")`）。如果跳过这步，被禁用用户能靠手里的 refresh token 无限续期，管理员禁用就形同虚设——配套地，`AdminUserService.updateUserStatus` 禁用时会吊销全部 refresh token，两层防线互为补充。
- **可能追问**：`ensureRefreshAllowed` 为什么不校验密码？——refresh 流程没有明文密码可验，用户状态是唯一能查的服务端状态。

**Q16.【问题】`register` 方法里新用户的初始字段是怎么设的？`userCode` 为什么直接用 username？**

- **考点**：数据模型理解。
- **答案要点**：`validateRegisterCommand` → `ensureUniqueIdentity` 之后：`user.setUserCode(command.username())`、`setUsername`、`setEmail`、`setDisplayName`、`setPasswordHash(passwordHasher.hash(...))`、`setSystemRole(SystemRole.USER)`（最小权限，无财务无管理员）、`setStatus(UserStatus.ACTIVE)`、`setMustChangePassword(false)`，然后 `userMapper.insert`。`userCode` 注释明确是"前端展示用，不可修改"，注册时先用 username 顶上，展示标识和登录标识初始一致，之后 username 语义归登录。注意 `RESERVED_USERNAMES`（admin/root/null/undefined/system）在 `normalizeUsername` 里已拦截，防止注册"admin"冒充系统账号。
- **可能追问**：为什么新用户不是 `mustChangePassword=true`？——那是管理员重置密码（`resetUserPassword`）用的强制改密标记，自注册用户自己设的密码不需要强制改。

**Q17.【问题】`AuthService` 注入了一个 `Clock`，为什么不用 `LocalDateTime.now()`？**

- **考点**：可测试性设计。
- **答案要点**：`AuthConfiguration` 提供 `@Bean Clock authClock()` 返回 `Clock.systemDefaultZone()`，`AuthService`、`JwtAccessTokenService`、`RefreshTokenService` 全部注入使用，`updateSuccessfulLogin` 里是 `LocalDateTime.now(clock)`。好处是测试里注入 `Clock.fixed(...)` 就能精确控制"过期/未过期"的判定——refresh token 14 天有效期、access token 30 分钟，手工造数据几乎不可能测边界，固定时钟让"token 恰好过期一毫秒"这种 case 可复现。这也是 jjwt 签发用 `clock.instant()` 的原因，签发与校验时钟同源。
- **可能追问**：多实例下 Clock 不一致怎么办？——都取系统默认时区，与数据库 `now()` 可能有毫秒级偏差，`isActive` 判断的是秒级过期窗口，可接受。

## 三、JwtAccessTokenService（JWT 签发与解析）

**Q18.【问题】access token 里都装了什么 claims？为什么把角色塞进 JWT 而不是每次查库？**

- **考点**：JWT 内容设计、无状态取舍。
- **答案要点**：`issueToken` 用 jjwt 0.12.6 的 `Jwts.builder()`：`issuer` 取 `authProperties.getIssuer()`（默认 `argus-rag`）、`subject` 是 `userCode`、`issuedAt/expiration` 由注入的 `Clock` 算出（默认 30 分钟），自定义 claim 四个：`uid`（userId）、`displayName`、`systemRole`（枚举 name）、`mustChangePassword`。角色进 JWT 后，`JwtAuthenticationFilter` 每请求解析一次就得到权限，不用每请求查库——这是无状态 JWT 的核心收益。代价是角色变更不即时生效，所以 `updateUserRole` 会吊销 refresh token 强制重新登录拿新角色 token。
- **可能追问**：密码哈希为什么不放进去？——JWT 只是 base64 编码不是加密，payload 任何人可解码，绝不能放敏感数据；这也是为什么连 userId 都只是 id 而不含邮箱。

**Q19.【问题】JWT 密钥是怎么加载和校验的？密钥太短会发生什么？**

- **考点**：fail-fast 配置校验。
- **答案要点**：`AuthProperties.jwtSecret` 上有 `@NotBlank` + `@Validated`，配置缺失启动即失败；`JwtAccessTokenService` 构造器里 `buildSigningKey` 再加一道：`secretBytes.length < MIN_SECRET_LENGTH(32)` 抛 `IllegalStateException("JWT secret 至少需要 32 字节")`，然后 `Keys.hmacShaKeyFor(secretBytes)` 生成 HMAC-SHA `SecretKey`。双重 fail-fast：配置层拦缺失，代码层拦长度。32 字节对应 HMAC-SHA256 的安全强度要求。
- **可能追问**：密钥从哪来？——只能来自环境变量（生产硬约束，`ProductionConfigGuard` 也在做启动守卫）；密钥泄漏等于任何人可伪造任意用户的 token，所以它比数据库密码更敏感。

**Q20.【问题】`parse` 方法怎么防止"伪造但格式正确"的 token？claims 校验为什么还要手动做一遍？**

- **考点**：签名验证与语义校验的层次。
- **答案要点**：`parse` 用 `Jwts.parser().verifyWith(signingKey).build().parseSignedClaims(token)`——`verifyWith` 强制验签，签名不对直接抛 `JwtException`。但验签只能证明"token 是持钥方签的、未被篡改"，不能证明"字段完整"：所以 `validateClaims` 手动校验 issuer 必须等于配置值（防止拿同一密钥签的其他系统 token 混入）、`subject/uid/displayName/systemRole/mustChangePassword/iat/exp` 七项任一为 null 都抛 `AUTH_TOKEN_INVALID`。防御深度：签名层 + 签发者层 + 完整性层。
- **可能追问**：过期校验在哪？——jjwt 的 `parseSignedClaims` 内置 exp 校验，过期抛 `ExpiredJwtException`（`JwtException` 子类），统一被 catch 成 `AUTH_TOKEN_INVALID`"access token 非法或已过期"。

**Q21.【问题】parse 的 catch 块为什么要分三种情况写？**

- **考点**：异常处理精细化。
- **答案要点**：三个 catch 按序：`catch (BusinessException e) throw e`——`validateClaims` 抛的业务异常必须原样透出，不能被下面吞掉重包；`catch (JwtException | IllegalArgumentException e)`——jjwt 验签/过期/格式错误统一转成 `AUTH_TOKEN_INVALID` 并把原始异常作为 cause 传入（保留排查链路）；`catch (RuntimeException e)`——兜底任何运行时异常（比如 claims 类型转换炸了）也转成同一个错误码，保证对外永远是有序的 401 JSON 而不是 500。错误信息统一为"access token 非法或已过期"，不向外泄露内部细节。
- **可能追问**：为什么不 catch `Exception`？——受检异常会掩盖真正的 bug；RuntimeException 兜底已覆盖解析场景的意外。

**Q22.【问题】`AccessTokenClaims` 和 `TokenSubject` 为什么定义成 record 还放在 Service 内部？**

- **考点**：Java 21 record、内聚设计。
- **答案要点**：两个都是嵌套 `public record`：`TokenSubject(userId, userCode, displayName, systemRole, mustChangePassword)` 是签发入参，`AccessTokenClaims(userId, userCode, displayName, systemRole, mustChangePassword, issuedAt, expiresAt)` 是解析出参。record 天然不可变，token 身份数据不该被中途改；嵌套在 Service 里表示这是该服务的"协议类型"，不污染公共 model 包。`AuthService.issueAccessToken` 用 `new JwtAccessTokenService.TokenSubject(...)` 构造，`JwtAuthenticationFilter` 消费 `AccessTokenClaims`。
- **可能追问**：`mustChangePassword` 放 JWT 里的用途？——前端拿到后提示改密；`AccountService.changePassword` 成功后置 false，但要重新登录拿新 token 才刷新（refresh 也会带上最新值）。

**Q23.【问题】access token 为什么设计成 30 分钟这么短？短 token + 长 refresh 的组合解决什么问题？**

- **考点**：双 token 体系的设计动机。
- **答案要点**：access 是自验证的（无状态），服务端无法单个吊销，泄露后只能等它自然过期——所以把它压到 30 分钟，暴露窗口可控。refresh 是服务端落库的（`user_refresh_tokens` 表，只存 BCrypt 哈希），可以精确吊销（登出、改密、禁用、改角色全部调 `revokeActiveTokens`），所以可以放 14 天承担"记住登录"。两者组合：日常请求无查库开销，安全事件发生时吊销 refresh 即切断续期路径，已发出的 access 最多 30 分钟内自然失效。前端配套了并发 401 时的刷新防抖（多个请求同时 401 只触发一次 refresh），避免刷新风暴。
- **可能追问**：30 分钟内被禁用的用户还能访问？——过滤器只信 JWT，确实还有窗口；但走 `CurrentUserService` 的接口（如 `/me`）会回库校验状态直接拒绝，财务等敏感域还有独立角色校验，窗口影响被压缩。

## 四、RefreshTokenService（刷新令牌管理）

**Q24.【问题】refresh token 的格式和存储方案是什么？为什么这样设计？**

- **考点**：不透明 token vs JWT、哈希存储。
- **答案要点**：格式 `tokenId.secret`，分隔符 `.`：`tokenId` 是 `UUID.randomUUID()` 去横线的 32 位 hex，`secret` 是 `SecureRandom` 生成的 24 字节经 `Base64.getUrlEncoder().withoutPadding()` 编码（约 32 字符）。签发时整串 token 做 BCrypt 哈希存 `token_hash` 字段，库里的 `user_refresh_tokens` 表只有 `id/userId/tokenId/tokenHash/expiresAt/revokedAt/createdAt`——**明文 token 永不落库**，数据库拖库也还原不出可用 token。它刻意不用 JWT：不需要携带信息（用户 id 在表里），只需要不可猜测 + 可吊销，不透明随机串 + 哈希存储是最简方案。
- **可能追问**：为什么 secret 用 24 字节？——192 位随机熵远超暴力猜测成本，Base64URL 编码保证能安全放进 Cookie 且 URL 安全。

**Q25.【问题】`findActiveToken` 为什么按 tokenId 先查库再做 BCrypt 比对，而不是全表比对哈希？**

- **考点**：BCrypt 慢哈希的性能设计。
- **答案要点**：BCrypt 是故意设计得很慢的哈希（抵抗离线爆破），不能拿它做全表逐行比对。方案利用了 token 自带 `tokenId` 明文段：先 `selectOne(eq(tokenId))` 按索引（V1 迁移里有 `idx_refresh_token_token_id`）定位**唯一一行**，再对这一行做一次 `passwordHasher.matches(refreshToken, record.tokenHash())`。这样每次刷新请求只付一次 BCrypt 代价（约几十毫秒），且 tokenId 是随机 UUID，无法通过它枚举有效 token——比对失败一律返回 `Optional.empty()`，与"token 不存在"不可区分。
- **可能追问**：查到行但哈希不匹配，要不要顺带吊销？——当前实现直接返回 empty；更激进的防窃取策略可以记录告警，但要注意攻击者拿到 tokenId（前 32 位是明文可见的）可以伪造不匹配请求，不能把它当强信号。

**Q26.【问题】`RefreshTokenRecord.isActive` 的判定逻辑是什么？过期和吊销为什么用同一张表的两个字段？**

- **考点**：状态建模。
- **答案要点**：`isActive(now)` = `revokedAt == null && expiresAt.isAfter(now)`——未吊销且未过期。两个字段语义不同：`expiresAt` 是签发时定死的自然寿命（14 天），不可变；`revokedAt` 是服务端主动作废的时间戳，初始 null。分开存的好处是可以区分"自然过期"（正常轮换）和"被吊销"（登出/安全事件/重放），为安全审计留了信号——重放检测正是依赖"曾经被吊销过"这个事实才能识别。`findActiveToken` 里是在 `matches` 通过**之后**才判 `isActive`，避免给无效 token 多做一次哈希运算的顺序优化。
- **可能追问**：过期行会清理吗？——当前代码没有清理任务，表会随登录次数增长，加一个定时清理 `expires_at < now - 保留期` 的 job 是合理演进（结合项目的 background_job 体系）。

**Q27.【问题】`revokeByIdIfActive` 这条原子 SQL 为什么是整个重放检测的基石？用应用层"先查后更"行不行？**

- **考点**：check-then-act 竞态、数据库级原子性。
- **答案要点**：SQL 是 `update user_refresh_tokens set revoked_at = #{revokedAt} where id = #{id} and revoked_at is null`，把"是否有效"的判断和"吊销"动作合并成一条条件 UPDATE，由数据库行锁保证原子。如果用应用层"先查 revoked_at 是否为 null，再 update"，两个并发请求可能都查到 null、都执行 update、都认为自己拿到了新 token——一次性语义被破坏。现在两个请求竞争，只有一个的 where 条件成立返回 1，另一个返回 0，`revokeTokenById` 用 `> 0` 翻译成布尔。这是典型的"把并发正确性下推到数据库"。
- **可能追问**：需要 SERIALIZABLE 隔离级别吗？——不需要，单行条件 UPDATE 在 READ COMMITTED 下就是原子的，靠的是行锁而非隔离级别。

**Q28.【问题】`revokeToken(String)` 和 `revokeTokenById(Long)` 两个吊销方法分别用在哪，为什么登出走的是前者？**

- **考点**：API 语义区分。
- **答案要点**：`revokeToken` 接收完整 token 字符串：内部先 `findActiveToken`（parse + 按 tokenId 查库 + BCrypt 比对 + isActive）拿到记录，再委托 `revokeTokenById(record.id())`。登出场景手里只有 Cookie 里的 token 字符串，走它；`AuthService.refresh` 已经通过 `findActiveToken` 拿到记录 id，直接走 `revokeTokenById`，避免重复哈希比对。`revokeTokenById` 返回 false 的含义两处不同：登出场景表示"token 本来就无效"，静默即可；refresh 场景表示"被并发抢先吊销"，升级为重放告警。
- **可能追问**：登出的 findActiveToken + revokeTokenById 之间有窗口吗？——理论上存在（查完后被 refresh 抢先吊销），但登出对 false 的处理是幂等静默，窗口无危害。

**Q29.【问题】这个服务里为什么也注入了 `PasswordHasher`？复用的是密码哈希器会不会有安全问题？**

- **考点**：组件复用与慢哈希选型。
- **答案要点**：`RefreshTokenService` 注入 `PasswordHasher`（BCrypt 实现）来 `hash(refreshToken)` 和 `matches(refreshToken, tokenHash)`。复用是合理的：token 和密码一样都是"高熵秘密需要防拖库离线破解"，BCrypt 自带盐、慢速的特性同样适用。token 是 24 字节 `SecureRandom` 高熵值，不存在密码那种弱口令问题，BCrypt 的慢只影响单次验证性能（已通过 tokenId 索引定位单行来控制）。它同时被 `AuthService`（用户密码）、`AccountService`、`AdminUserService` 共用，一处实现统一口径。
- **可能追问**：换成 HMAC-SHA256 存 token 哈希会不会更好？——会更快（微秒级 vs 几十毫秒），因为 token 本身高熵不需要抗暴力枚举的慢哈希；BCrypt 在这里偏保守，是可讨论的优化点。

**Q30.【问题】`revokeActiveTokens` 的 SQL 为什么要带 `expires_at > now` 条件？**

- **考点**：更新范围精确性。
- **答案要点**：完整条件是 `user_id = ? and revoked_at is null and expires_at > now`——只吊销"当前活着的" token。不加过期条件也能达到安全目的，但会把历史过期行的 `revoked_at` 也写上，破坏了"自然过期 vs 主动吊销"的数据区分（审计时无法分辨该 token 是到期还是被吊销）；`revoked_at is null` 条件则避免重复 update 覆盖原始吊销时间。V1 迁移里还有配套索引 `idx_refresh_token_user_active` 支撑这个查询模式。该方法被四个场景复用：登录（单设备）、refresh 重放兜底、改密、管理员禁用/改角色/重置密码。
- **可能追问**：登录时吊销会不会把"刚签发还没写入"的 token 误伤？——不会，`login` 里 revoke 在 issue 之前顺序执行且有行锁串行化，同事务内先删后插。

## 五、JwtAuthenticationFilter + SecurityConfig（过滤器链与安全配置）

**Q31.【问题】讲一下 JWT 过滤器处理一个请求的完整决策树。**

- **考点**：过滤器内部逻辑。
- **答案要点**：`JwtAuthenticationFilter extends OncePerRequestFilter`。先过 `shouldNotFilter`：四个路径（`/api/auth/login|register|refresh|logout`，精确 `equals` 匹配）直接跳过——登录注册刷新登出本身不能要求已登录，否则鸡生蛋。进入 `doFilterInternal`：① 没有 `Authorization` 头 → 直接 `filterChain.doFilter` 放行（可能是匿名可访问接口，交给 Security 规则决定 401）；② 有头，去掉 `Bearer ` 前缀（没有前缀也容错地取整个值 trim）后为空 → 立即 `writeUnauthorized` 返回 401 JSON（"提供了假票"）；③ `jwtAccessTokenService.parse` 成功 → `UserContext.set(new AuthenticatedUser(...))` + `SecurityContextHolder` 里放 `UsernamePasswordAuthenticationToken`（principal 是 userId，credentials null，authorities 是单个 `ROLE_ADMIN/ROLE_FINANCE/ROLE_USER`，switch 映射，default 兜底 `ROLE_USER`）→ 放行；④ `BusinessException` → 401 JSON。`finally` 里 `SecurityContextHolder.clearContext()` + `UserContext.clear()`。
- **可能追问**：token 非法为什么立刻 401 而不是放行给 Security？——匿名放行是为了让公开接口可用；但"带了假票"是明确的认证失败意图，直接 401 JSON 响应，前端据此触发刷新流程。

**Q32.【问题】为什么 `finally` 里必须 clearContext 和 clear？不清理会发生什么？**

- **考点**：ThreadLocal 与线程池复用——高频必考。
- **答案要点**：Tomcat 用线程池复用请求线程，`SecurityContextHolder` 默认是 ThreadLocal 策略、`UserContext` 是自建 ThreadLocal。请求结束不清理，下一个复用该线程的请求会"继承"上一个用户的身份：如果下一个请求恰好是匿名路径（过滤器放行没设置新值），业务代码从 `UserContext` 读到的是**别人**——这是真实的越权事故源头，也是 ThreadLocal 内存泄漏的高发地（线程不死，条目不释放）。所以 `doFilterInternal` 的 finally 里两个 clear 成对出现，`UserContext.clear()` 底层是 `ThreadLocal.remove()`。
- **可能追问**：异步场景（@Async/自建线程池）下 UserContext 还有效吗？——无效，ThreadLocal 不跨线程传递，新线程读不到；本项目耗时任务（ETL 等）不依赖 UserContext 做权限判定，权限在入队前校验，这是设计上规避该坑的方式。

**Q33.【问题】为什么要维护 UserContext 和 SecurityContext 两套"登记簿"？一套不行吗？**

- **考点**：架构取舍。
- **答案要点**：两本登记簿服务不同读者。`SecurityContextHolder` 是 Spring Security 的权威：`@PreAuthorize`、`SecurityConfig` 的 `hasAuthority("ROLE_FINANCE")`、401/403 入口点都查它。`UserContext` 是给业务代码的便民窗口：`DocumentRoleGate`、`CurrentUserService`、限流切面都从这拿人，`UserContext.get()` 一行静态调用，避免业务代码去解析 `SecurityContextHolder` 里的 principal 强转。`JwtAuthenticationFilter` 的教学注释里明确写了这个分工：Spring Security 鉴权体系只认自己的上下文，业务代码直读 UserDetails 很啰嗦。两本都要在 finally 清理。
- **可能追问**：会不会出现两本不一致？——同一过滤器在同一次 try 块里先后写入，数据同源（都来自 `AccessTokenClaims`），唯一风险是忘清理，用 finally 保证。

**Q34.【问题】SecurityConfig 里 `sessionCreationPolicy(STATELESS)` 和 `csrf(disable)` 为什么能一起用？**

- **考点**：无状态安全模型。
- **答案要点**：CSRF 防的是"浏览器自动携带的会话凭证被第三方站点利用"，传统 session-cookie 架构下它是必需的。本项目认证凭证在 `Authorization` 头里，第三方站点无法读你的 localStorage 去设置请求头，天然免疫 CSRF；唯一自动携带的凭证是 refresh Cookie，但它是 httpOnly + `SameSite=Lax`（`AuthCookieSupport` 写死 `SAME_SITE_POLICY = "Lax"`），Lax 下跨站 POST 不携带 Cookie，且用到 Cookie 的 `/api/auth/refresh|logout` 都是 POST。所以 STATELESS + csrf disable + SameSite=Lax 是一套自洽的组合，每一项都有明确理由，不是随手关掉。
- **可能追问**：如果哪天把 refresh 改成 GET 刷新会怎样？——Lax 只放行顶级导航 GET，改 GET 会重新打开 CSRF 面，所以保持 POST 是约束的一部分。

**Q35.【问题】SecurityConfig 的 URL 规则里，财务相关的两条为什么这么设计？**

- **考点**：财务隔离红线、角色独立校验。
- **答案要点**：两条规则：`/api/finance/hr/self/**` 用 `.authenticated()`——员工的考勤/薪酬自助查询，任何登录角色可查本人数据，URL 特意避开 `/api/finance/**` 前缀；`/api/finance/**` 用 `.hasAuthority("ROLE_FINANCE")`——财务数据硬隔离，**系统管理员 ADMIN 也在拦截范围内**（没有隐式财务豁免），这是项目的 P0 硬约束："财务 API 必须经过 ROLE_FINANCE 校验；系统管理员没有隐式财务豁免"。角色变更后 refresh token 被吊销，拿不到带 ROLE_FINANCE 的新 token 就进不来。401/403 分别由 `restAuthenticationEntryPoint`（"未登录或登录已过期"）和 `restAccessDeniedHandler`（"无权访问该资源"）输出统一 JSON。
- **可能追问**：过滤器给了 ROLE_USER 的 JWT 能不能通过 `hasAuthority("ROLE_FINANCE")`？——不能，SimpleGrantedAuthority 逐字匹配；改角色必须重新登录换新 token。

**Q36.【问题】`/api/admin/**` 在 SecurityConfig 里没有按角色限制，只靠什么防护？这够吗？**

- **考点**：防御深度评估（诚实边界题）。
- **答案要点**：`anyRequest().authenticated()` 之下，admin 接口只要求"已登录"，角色控制在 `AdminUserController` 每个方法开头手动调 `currentUserService.requireSystemAdmin()`——非 ADMIN 抛 `ForbiddenException`（403）。功能上是安全的（每个入口都有显式检查），但属于"约定式防护"：新增 controller 方法时漏写一行就裸奔。更稳的做法是在 SecurityConfig 加 `.requestMatchers("/api/admin/**").hasAuthority("ROLE_ADMIN")`，把门槛前移到过滤器链，形成 URL 层 + 方法层双重防线。这是我会主动提出的加固点。
- **可能追问**：为什么现在还每次查库（requireSystemAdmin 内部 getRequiredCurrentUser 回库）？——同样是防"JWT 快照过期"：token 里的 ADMIN 是签发时刻的，回库查的是当下状态。

**Q37.【问题】SecurityConfig 里那个永远抛异常的 `UserDetailsService` Bean 是干什么用的？**

- **考点**：Spring Boot 自动配置的细节。
- **答案要点**：Spring Boot 检测到没有 `UserDetailsService` 时会自动生成一个内存默认用户并打 "Using generated security password" 日志、留一个随机密码后门。本系统是无状态 JWT，认证在 `JwtAuthenticationFilter` 完成，不需要用户源，所以声明一个空实现：任何 username 一律抛 `UsernameNotFoundException("用户不存在：" + username)`。作用纯粹是"占位让自动配置闭嘴"，不引入任何真实认证路径。这体现对框架默认行为的理解：安全组件里不能留自己不掌控的默认值。
- **可能追问**：这个 Bean 会被调用吗？——正常请求链路不会（没有 form login/basic），只在框架内部需要用户源时触发，一触发就异常，fail-closed。

**Q38.【问题】过滤器为什么注册在 `UsernamePasswordAuthenticationFilter` 之前？`permitAll` 和 `shouldNotFilter` 双重放行是否冗余？**

- **考点**：过滤器链拓扑。
- **答案要点**：`addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)` 把自定义过滤器插到 Spring Security 认证过滤器之前——先解析 JWT 建立身份，后面的授权规则才有身份可判。`permitAll`（SecurityConfig 授权规则）与 `shouldNotFilter`（过滤器自身跳过）确实都覆盖四个 auth 路径，但不冗余而是各管一层：`shouldNotFilter` 决定"过滤器要不要尝试解析 token"（这四个路径即使带了过期 access token 也不该被 401 拦截，比如用户带着过期 token 来 refresh）；`permitAll` 决定"授权层要不要拒绝"。两层语义不同，都保留才能保证 refresh/logout 在 access token 失效时依然可用。
- **可能追问**：`shouldNotFilter` 用 equals 精确匹配，`/api/auth/login/` 带斜杠会怎样？——会进入过滤逻辑，但无 Authorization 头时照样放行，不影响功能；有头时验签失败 401，属于可接受的严格行为。

## 六、AuthCookieSupport + 配置类（Cookie、属性、初始化）

**Q39.【问题】refresh Cookie 的完整安全属性是什么？每个属性防什么？**

- **考点**：Cookie 安全属性逐项。
- **答案要点**：`AuthCookieSupport.buildCookie` 用 Spring 的 `ResponseCookie`：`httpOnly(true)`——JS 读不到，防 XSS 偷 token；`secure(authProperties.isRefreshCookieSecure())`——默认 true，只走 HTTPS，防明文传输被嗅探；`sameSite("Lax")`——防跨站 POST 携带（CSRF）；`path("/")`——全站可带，因为刷新接口在 `/api/auth/refresh` 但 path 收紧到 `/api/auth/` 也是可选优化；`maxAge` 等于 `refreshTokenExpireDays`（14 天），与 token 服务端有效期一致——Cookie 和服务端记录同生同死。登出用 `clearRefreshTokenCookie`：同名 Cookie 置空 + `Duration.ZERO` 立即过期。写入方式是 `response.addHeader(SET_COOKIE, ...)`。
- **可能追问**：为什么 secure 不写死 true 而是可配？——本地开发是 HTTP，`refreshCookieSecure=false` 才能联调；生产 profile 必须保持默认 true。

**Q40.【问题】`AuthProperties` 上 `@Validated` 和各字段的校验注解解决什么问题？**

- **考点**：配置 fail-fast。
- **答案要点**：`@ConfigurationProperties(prefix = "argus.rag.auth")` + `@Validated`：`issuer @NotBlank`、`accessTokenExpireMinutes @Min(1)`、`refreshTokenExpireDays @Min(1)`、`jwtSecret @NotBlank`、`refreshCookieName @NotBlank`。绑定阶段就校验，配错（比如过期分钟数配成 0 或负数）应用直接起不来，而不是运行到某个请求才炸出诡异行为。默认值也有讲究：30 分钟 / 14 天 / `argus-rag` / `ARGUS_RAG_REFRESH_TOKEN` / secure 默认 true（保守默认，安全性向）。
- **可能追问**：jwtSecret 的长度校验为什么不也放这里？——注解校验字节数不直观（`@Size` 数的是字符），32 字节的语义校验放在 `JwtAccessTokenService.buildSigningKey` 用 UTF-8 字节判断，那里才拿得到编码后的真实长度。

**Q41.【问题】`DevAdminInitializer` 做了什么？为什么它是 `@Profile("dev")`，生产跑了会怎样？**

- **考点**：环境隔离意识（安全敏感题）。
- **答案要点**：`ApplicationRunner` 实现，`@Profile("dev")` 限定。启动时按 `argus.rag.dev-admin.*` 配置（默认 username=admin，password=Admin@123456）查库：不存在则插入一个 `SystemRole.ADMIN` + `ACTIVE` 的管理员；**存在则更新**——重置邮箱、displayName、`passwordHash`、角色、状态、`mustChangePassword=false`，即"Dev admin refreshed"。生产如果误开了 dev profile，等于把已知口令的管理员账号刷回来，是灾难性配置错误——所以 profile 隔离是这条代码的红线，配合 `ProductionConfigGuard` 的启动守卫降低风险。它 `@Transactional`，创建或刷新原子完成。
- **可能追问**：为什么要每次刷新而不是只创建？——dev 调试时频繁改库/重置库，保证"可预测的管理员"永远可用；代价是 dev 里手工改的 admin 密码每次重启被覆盖，这是有意的。

**Q42.【问题】`PasswordPolicyValidator` 的策略是什么？为什么它同时被注册和改密共用？**

- **考点**：策略复用与一致口径。
- **答案要点**：`validate(password)` 四步：null 或长度 < 8 → 抛"新密码必须至少 8 位，且同时包含字母和数字"；长度 > 256 抛"密码长度非法"；`getBytes(UTF_8).length > 72` 抛 BCrypt 字节上限；循环用 `Character.isLetter/isDigit` 判断必须同时含字母和数字。共用方：`AuthService.validateRegisterCommand`（注册）和 `AccountService.changePassword`（改密）。共用保证两处口径永远一致——不会出现"注册允许、改密拒绝"的分裂体验。注意它检查的是**新**密码；`AdminUserService.resetUserPassword` 当前只做了非空检查没有调它（详见 Q50 的改进讨论）。
- **可能追问**：为什么只要字母+数字不要特殊字符？——NIST 800-63B 的现代观点：长度和熵比符号种类更重要，强制特殊字符反而诱导用户写规律后缀；当前策略是保守折中。

**Q43.【问题】`AuthConfiguration` 里 `PasswordHasher` 为什么做成接口 + 匿名内部类，而不是直接用 `BCryptPasswordEncoder`？**

- **考点**：抽象层价值。
- **答案要点**：`PasswordHasher` 是项目自定义接口（`hash`/`matches` 两方法），`AuthConfiguration.defaultPasswordHasher()` 里用匿名实现包装 `BCryptPasswordEncoder`，包装层加了 `validateInputLength`：null 或 UTF-8 字节 > 72 抛 `BusinessException("密码长度超过安全上限，请控制在 72 字节以内")`。价值三点：① 把"BCrypt 72 字节截断"这个算法细节的防御收口在唯一入口，所有调用方（注册/登录/改密/token 哈希）自动获得保护；② 接口隔离了具体算法，将来换 argon2 只动这个 Bean；③ 业务层永远不直接依赖 Spring Security 的类，依赖方向干净。
- **可能追问**：登录时也会走到这个校验？——会，`matches` 同样校验，与 `AuthService.validateLoginCommand` 的 72 字节检查形成双保险（后者先拦，正常到不了前者）。

## 七、CurrentUserService（当前用户与角色断言）

**Q44.【问题】`getRequiredCurrentUser` 的完整逻辑是什么？它和"直接读 JWT claims"差在哪？**

- **考点**：每请求 fail-closed 的关键实现。
- **答案要点**：先 `UserContext.get()`：null → 抛 `UnauthorizedException("当前请求未登录")`（401）。非 null 拿 `authenticatedUser.userId()` 调 `userQueryService.findById` 回库：查不到 → `BusinessException(AUTH_USER_NOT_FOUND, "当前用户不存在")`；`user.status() == UserStatus.DISABLED` → `ForbiddenException("账号已被禁用")`；通过后才组装 `CurrentUser` record（userId/userCode/displayName/systemRole/mustChangePassword）。差别在于：JWT claims 是签发时刻快照，这里是数据库实时状态——被禁用用户的请求即使带着有效 access token 也会被拒。所有走 `CurrentUserService` 的接口天然获得这个每请求校验。
- **可能追问**：每次请求多一次查库，性能怎么办？——findById 走主键，代价是一次索引点查；换取"禁用即时生效"，值得。要优化可以加短 TTL 缓存，但要权衡失效窗口。

**Q45.【问题】`requireSystemAdmin` / `requireFinance` / `requireBusinessUser` 三个断言分别定义了什么边界？**

- **考点**：三层权限模型的角色语义。
- **答案要点**：系统三种角色 `ROLE_USER / ROLE_FINANCE / ROLE_ADMIN`。`requireSystemAdmin`：非 `SystemRole.ADMIN` 抛 403"当前用户不是系统管理员"——admin 接口的门槛。`requireFinance`：非 `SystemRole.FINANCE` 抛 403"财务数据仅限财务/领导角色访问"——注意是**相等判断**，ADMIN 不满足，这正是"管理员没有隐式财务豁免"红线的代码落点。`requireBusinessUser`：`systemRole == ADMIN` 抛 403"系统管理员不能访问普通业务区"——反向隔离，管理员不能混入普通用户数据区（审计清晰）。另有静态 `isFinanceUser(CurrentUser)` 做 null 安全判断（null 返回 false），供跨模块调用。
- **可能追问**：为什么 ADMIN 反而不能进业务区？——管理员拥有跨用户管理权，若同时能进普通用户数据区，"管理员操作"和"用户本人操作"在审计上无法区分；隔离是数据归属清晰的要求。

**Q46.【问题】`CurrentUser` record 的三参构造器是干嘛的？会不会有默认值陷阱？**

- **考点**：便利构造器的取舍。
- **答案要点**：`CurrentUser` 是五字段 record（userId/userCode/displayName/systemRole/mustChangePassword），另提供了三参便捷构造器 `CurrentUser(userId, userCode, displayName)`，默认 `SystemRole.USER` + `mustChangePassword=false`。它方便测试和内部工具快速造对象，但陷阱是：如果业务代码不小心用三参版构造了一个"真实用户"上下文，等于静默把角色降成 USER 或抹掉强制改密标记。当前生产路径（`toCurrentUser`、`loadUserById`）都走五参全量构造，三参只在测试里用。这是便利性与显式性的经典权衡。
- **可能追问**：为什么 record 还能有额外构造器？——record 允许定义任意与规范构造器兼容的附加构造器，最终都必须委托到规范构造器。

**Q47.【问题】`AuthTokens` 响应里为什么要带 `currentUser`？前端少了一次请求，还有别的用意吗？**

- **考点**：API 设计与前端状态同步。
- **答案要点**：`AuthService.AuthTokens` record 含 `mustChangePassword` 和 `toCurrentUser(user)` 的结果，登录/刷新时用户实体已经查出来了，顺手转换放进响应，前端免掉一次 `/me` 往返。更深的用意：登录和 refresh 都是"身份重新确立"的时刻，响应里的 currentUser 是**签发 token 时刻的身份快照**，与 access token claims 一致，前端 Pinia 状态据此重建，避免"token 是新的、用户信息是旧的"的错位。`AuthTokensResponse` 只暴露 `accessToken` + `currentUser`，refresh token 被刻意排除在响应体外。
- **可能追问**：refresh 响应也带 currentUser？——带，`refresh` 同样组装 `AuthTokens`，因为刷新也可能跨了角色变更（管理员改角色后旧 refresh 已被吊销，能刷新成功的说明角色未变，快照一致）。

## 八、AccountService / AdminUserService（用户域服务）

**Q48.【问题】修改密码的完整校验顺序是什么？每一步失败的错误码是什么？**

- **考点**：业务校验链、错误码体系。
- **答案要点**：`AccountService.changePassword`（`@Transactional`）顺序：① `passwordValidator.validate(request.newPassword())`——先验新密码复杂度（≥8 位、字母+数字、≤72 字节）；② `selectById` 查用户，null 或 `passwordHash == null` → `USER_NOT_FOUND "用户不存在"`（HTTP 404，ErrorCodes 里 USER_NOT_FOUND 映射 404）；③ `passwordHasher.matches(currentPassword, hash)` 不匹配 → `USER_PASSWORD_MISMATCH "当前密码不正确"`；④ `currentPassword.equals(newPassword)` → `USER_PASSWORD_SAME_AS_OLD "新密码不能与当前密码相同"`；⑤ 全过才 `setPasswordHash(hash(new))` + `setMustChangePassword(false)`，`updateById` 返回 0 也当 `USER_NOT_FOUND` 处理；⑥ `refreshTokenService.revokeActiveTokens(userId)` 吊销全部 refresh token。
- **可能追问**：为什么改密后旧 access token 还能用？——无状态 JWT 无法吊销，最多剩 30 分钟；refresh 已全部吊销，攻击者即便偷到 access 也续不了期，窗口可控。这是双 token 设计的核心收益场景。

**Q49.【问题】改密流程第①步先验新密码复杂度、第③步才验旧密码，这个顺序有什么问题或好处？**

- **考点**：校验顺序的信息泄露与体验权衡。
- **答案要点**：好处是"fail-cheap"：格式校验是纯内存操作，先拦掉明显非法输入，避免为垃圾请求付出 BCrypt 比对和查库代价（BCrypt 慢是有意的，能省则省）。问题在新密码复杂度报错会先于"当前密码不正确"返回，攻击者可以通过报错顺序试探策略细节——但密码策略本来就不是秘密（前端同样有提示），泄露价值极低。真正的敏感点第③步已经用 `USER_PASSWORD_MISMATCH` 精确文案处理（改密场景必须告诉用户哪个错了，否则没法用），这与登录场景的防枚举统一文案不同：改密时用户已通过认证，不存在枚举面。
- **可能追问**：为什么登录要防枚举而改密不用？——登录的调用方是未认证的任何人；改密的调用方已持有效 access token 且必须答对当前密码，身份已确立。

**Q50.【问题】管理员重置密码和用户自改密码的处理有什么差异？你发现什么不一致了吗？**

- **考点**：代码一致性审查能力（主动发现问题的题）。
- **答案要点**：`AdminUserService.resetUserPassword` 流程：非空检查 → 查用户（null → `USER_NOT_FOUND`）→ `setPasswordHash(hash(newPassword))` + `setMustChangePassword(true)` → `updateById` → `revokeActiveTokens`。与 `AccountService.changePassword` 的关键差异：**重置路径没有调用 `PasswordPolicyValidator.validate`**，只检查了非空——管理员可以设置一个不满足"8 位+字母数字"策略的密码。`mustChangePassword=true` 保证用户下次登录（`AuthTokens.mustChangePassword` 透传前端）被引导改密，算是缓解，但严格说这是一处策略口径不一致，改进方向是补上 validator 调用。另外重置后同样吊销全部 refresh token，被重置的用户立即失去登录态。
- **可能追问**：mustChangePassword 怎么流转？——管理员置 true → JWT claim 携带 → 前端登录/刷新响应里读到就弹改密页 → 用户改密成功后 `AccountService` 置 false 并吊销 token，重新登录拿干净的 token。

**Q51.【问题】禁用用户、改角色、重置密码三个管理操作为什么都以"吊销 refresh token"收尾？各自防什么？**

- **考点**：吊销语义与安全闭环。
- **答案要点**：三者都在 `@Transactional` 里最后调 `refreshTokenService.revokeActiveTokens(userId)`，但目的不同：禁用（`updateUserStatus`，status 置 `DISABLED`）——防止被禁用户靠 refresh 无限续期（refresh 入口的 `ensureRefreshAllowed` 是第二道）；改角色（`updateUserRole`，同角色抛 `USER_ROLE_ALREADY_SET` 409）——JWT claims 里的角色是快照，必须让用户重新登录拿新角色 token，否则升降权不生效；重置密码——旧密码知情者（或偷到 token 者）立即失效。三者共同的底层逻辑：**refresh token 是持久化的登录态，任何"身份语义变更"都必须切断它**。而 access token 30 分钟自然消亡，无需处理。
- **可能追问**：为什么 updateUserRole 对"角色没变"抛 409 而不是幂等返回？——`USER_ROLE_ALREADY_SET` 映射 409 Conflict，语义是"请求与当前状态冲突"，同时给前端明确反馈避免误操作；这是接口语义设计选择，改成幂等 200 也合理，但要写进接口契约。

**Q52.【问题】`AdminUserController` 五个方法每个都手写 `requireSystemAdmin()`，Service 层为什么不再校验一次？**

- **考点**：权限校验的分层归属。
- **答案要点**：当前实现是"Controller 层集中校验"：`listUsers/getUser/updateUserStatus/updateUserRole/resetUserPassword` 每个方法第一行都是 `currentUserService.requireSystemAdmin()`，非管理员在这里就抛 403，Service 收到的调用一定是已授权的。Service 不重复校验的理由：`AdminUserService` 是内部服务，其调用方不止这个 Controller（测试、未来其他入口），把角色检查放 Controller 与"HTTP 端点是权限边界"的模型一致。风险在 Q36 已说：约定式防护依赖每个方法记得写。`@OperationLog` 标在类上，所有管理操作留审计日志。
- **可能追问**：`requireUserId` 的 `userId <= 0` 检查防什么？——路径变量的负数/零，提前抛"用户ID非法"，避免无意义的 selectById；这是入参卫生。

**Q53.【问题】`UserQueryService` 为什么要独立存在？它和 `AdminUserService` 的职责怎么分？**

- **考点**：读服务与写服务分离、循环依赖规避。
- **答案要点**：`UserQueryService` 是 users 表的只读门面：`listUsers`（`orderByAsc(User::getId)` 全量转 `AdminUserItemResponse`）、`getUser`（null → `USER_NOT_FOUND`）、`existsByUsername/existsByEmail`、`findById`（返回精简 `UserRecord` record，不存在返回 null——供 `CurrentUserService` 跨模块调用）、`findByUserCodeOrUsername`（`or()` 拼接 + `LIMIT 1`）。独立出来的价值：`auth` 包的 `CurrentUserService` 依赖它做每请求回库校验，若挂在 `AdminUserService` 上会让"当前用户校验"依赖管理员写服务，依赖方向混乱；读写分离后 auth 只依赖最小的查询面。注意 `findByUserCodeOrUsername` 的 `LIMIT 1` 语义是"存在即取第一个"，与登录路径 `selectByLoginIdForUpdate` 的"多命中即报冲突"不同——前者用于展示类查询容忍歧义，后者是认证必须严谨。
- **可能追问**：listUsers 没有分页，数据量大了怎么办？——当前用户量级可接受，改进是加 MyBatis-Plus 的 `Page` 分页参数，属于已知演进项。

## 九、RateLimitAspect（登录限流切面）

**Q54.【问题】登录限流是怎么实现的？key 怎么设计的？匿名用户算谁？**

- **考点**：AOP 限流实现与 key 设计缺陷。
- **答案要点**：`@RateLimit(limit = 10, window = 60, scope = "用户登录")` 由 `RateLimitAspect` 的 `@Around("@annotation(rateLimit)")` 拦截。key 拼法：先尝试 `currentUserService.getRequiredCurrentUser()`，成功则 `"user:" + userId`，异常（未登录）则保持 `"anonymous"`，再拼 `":" + joinPoint.getSignature().toShortString()`。关键事实：`/api/auth/login` 在 `shouldNotFilter` 放行名单里，`UserContext` 永远是空，所以**所有匿名登录请求共享同一个桶** `anonymous:AuthController.login`——全局每分钟只放 10 次登录尝试。防爆破效果成立，但有 DoS 面（恶意打满桶可干扰他人登录）和限流粒度问题（无法按 IP 区分）。
- **可能追问**：改进方案？——key 加入 IP（从 `RequestContextHolder` 取），匿名改为"IP+方法"维度；多实例部署时换成 Redis 滑动窗口（当前 `ConcurrentHashMap` 是 JVM 内的，PROJECT_TRUTH 已把"限流是本地内存"列为多实例风险第 1 条）。

**Q55.【问题】这个限流是"滑动窗口"吗？`compute` 之后为什么又检查了一次过期？**

- **考点**：限流算法辨析、并发细节。
- **答案要点**：诚实地说：实现是**固定窗口**计数器，不是真滑动窗口。`counters.compute(key, ...)` 里窗口过期（`now - windowStartMs > windowMs`）就 `new WindowCounter(now, new AtomicLong(1))`，否则 `incrementAndGet`；compute 之后又做了一次过期复查，过期就 `put` 重置——这是对 compute 与后续判断之间时间差的补刀，但在并发下两次检查之间仍有微小竞态（理论上可能多放行极少量请求，固定窗口本身容忍）。类注释写"滑动窗口计数器"与实现有出入，面试时我会指出：真滑动窗口需要记录时间戳队列或分桶，当前实现是更轻的固定窗口，存在固定窗口固有的边界突刺（窗口交界处最多 2 倍流量）。计数器 record 是 `WindowCounter(windowStartMs, AtomicLong count)`，`ConcurrentHashMap.compute` 保证同 key 原子。
- **可能追问**：超限后返回什么？——抛 `RateLimitExceededException`，全局异常处理器按 HTTP 429 返回，`scope` 字段用于日志定位。

**Q56.【问题】为什么用 AOP 注解而不是写个 Filter 对所有接口限流？**

- **考点**：限流粒度与声明式设计。
- **答案要点**：`@RateLimit` 是方法级声明：只有标注的方法被限流（当前主要是登录），每个方法可自定义 `limit/window/unit/scope`。Filter 方案是全局限流，无法表达"登录 10 次/分钟、问答 20 次/分钟"这类差异化策略，而且 Filter 在认证之前拿不到用户身份。AOP 方案在方法前后执行，能拿到 `CurrentUserService`（此时 JWT 过滤器已设置 UserContext）。代价是 AOP 只对 Spring Bean 的公开方法生效、自调用不触发——所以 `@RateLimit` 必须标在 Controller 方法上（AuthController.login 正是如此），这也解释了为什么它是注解驱动的声明式而非编程式。
- **可能追问**：scope 参数有什么用？——纯日志用途（`scope = "用户登录"` 打进限流触发日志），让运维能定位是哪个业务被限流。

## 本包高危追问 Top5

**1. "ThreadLocal 不清理会发生什么？你们怎么保证的？"**
答：Tomcat 线程池复用请求线程，`SecurityContextHolder`（ThreadLocal 策略）和自建 `UserContext`（ThreadLocal）若不清理，下一个复用线程的请求可能继承上一个用户的身份——直接越权，匿名路径尤其危险（过滤器对无 Authorization 头的请求直接放行，没有覆盖写入）。保证手段：`JwtAuthenticationFilter.doFilterInternal` 的 `finally` 里成对执行 `SecurityContextHolder.clearContext()` + `UserContext.clear()`，`UserContext.clear()` 底层是 `ThreadLocal.remove()`。要能继续往下聊：异步线程（@Async、自建线程池）不继承 ThreadLocal，所以耗时任务不能依赖 UserContext 做权限判定，权限校验必须在入队前的请求线程完成——本项目的 background_job 体系正是这样设计的。

**2. "重放检测里兜底吊销会随事务回滚，你的 token 防窃取还成立吗？"**
答：成立，但要讲清楚层次。`AuthService.refresh` 是 `@Transactional`，`BusinessException extends RuntimeException`，所以重放分支里 `revokeActiveTokens` 的兜底吊销会被回滚。真正生效的保护是：refresh token 一次性使用，`revokeByIdIfActive` 的条件 UPDATE（`where revoked_at is null`）在上一次成功刷新时已提交，重放的 token 永远查不到 active 记录，换不出新 token；`AUTH_TOKEN_REPLAYED` 报错 + `log.warn("refresh token 重放攻击")` 提供了检测信号。要让"重放即吊销全家"真正落库，兜底吊销需要 `REQUIRES_NEW` 独立事务——这是我知道的改进点，也能顺势聊"事务传播与异常回滚"。

**3. "access token 无状态没法吊销，改密/禁用后 30 分钟窗口你们怎么收敛的？"**
答：四层收敛：① access 只有 30 分钟寿命，窗口天然有界；② 所有身份变更（改密、禁用、改角色、重置密码、登出、新登录）都调 `revokeActiveTokens` 吊销全部 refresh token，攻击者无法续期；③ 走 `CurrentUserService` 的接口每请求回库校验状态（`loadUserById` 拦 DISABLED、`AUTH_USER_NOT_FOUND`），不信任 JWT 快照；④ `/api/finance/**` 在 SecurityConfig 用 `hasAuthority("ROLE_FINANCE")` 硬校验，角色进不了新 JWT 就进不了财务域。残余风险：纯靠 JWT claims 的接口在窗口内仍用旧身份，这是无状态架构的已知代价，可再收敛的方案是短 TTL 的服务端 token 黑名单，代价是每请求多一次查询。

**4. "为什么财务角色校验不允许 ADMIN 豁免？在代码里落在哪里？"**
答：硬约束"财务 API 必须经过 ROLE_FINANCE 校验；系统管理员没有隐式财务豁免"。落点三处：`SecurityConfig` 的 `.requestMatchers("/api/finance/**").hasAuthority("ROLE_FINANCE")`（ADMIN 的 JWT 只有 ROLE_ADMIN，直接 403）；`CurrentUserService.requireFinance` 是 `systemRole != SystemRole.FINANCE` 即 403 的相等判断；`ExcelPermissionService.userCanAccessDocument` 财务文件门禁同样只认 FINANCE。安全逻辑：财务数据是最高敏数据，管理员权限越大越应该被显式审计，"换上 FINANCE 角色再访问"这一步动作本身留下记录（角色变更走 `updateUserRole` 且有 `@OperationLog`），比静默豁免可追溯。

**5. "如果让你review这套认证代码，你最先提的三个改进是什么？"**
答（按严重度排序）：① 限流的匿名桶问题——`RateLimitAspect` 对未登录请求全共享 `anonymous:方法名` 一个 key，登录接口全局 10 次/分钟既是 DoS 面又无 IP 维度，改 key 加 IP + 多实例换 Redis；② `AdminUserService.resetUserPassword` 没调 `PasswordPolicyValidator`，管理员可绕过密码策略，补一行 validate 调用即可；③ `ensureUserCanLogin` 状态检查在密码校验之前，DISABLED 账号返回"账号已被禁用"会泄露账号存在性，与登录的防枚举统一文案（`INVALID_CREDENTIALS_MESSAGE`）目标冲突，建议先验密码再报状态或统一文案。还能提：`/api/admin/**` 加 URL 层角色规则、`user_refresh_tokens` 过期行清理任务、唯一约束冲突翻译成友好错误码。每条都能落到具体类和方法名，不是空谈。
