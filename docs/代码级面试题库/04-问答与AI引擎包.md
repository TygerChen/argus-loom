## 1. 全链路编排：QaChatService（拒答、LLM 调用、硬/软失败）

**Q1.1 完整描述一次同步问答的调用链，每层干什么？**
【考点】分层职责 / PROJECT_TRUTH 真实分层。
【答案要点】`QaController.askQuestion`（HTTP + @RateLimit 20/60s）→ `QaService.ask`（群组成员校验 requireGroupReadable、落库 qa_records、LLM 计量）→ `QaChatService.askWithUsage`（编排）→ `ReadyChunkDocumentRetriever.retrieveEvidence` → `HybridChunkRetrievalService.retrieve`（规划/双路/融合/重排/邻居/证据评估）→ `CitationAssembler` 组引用 → 落 qa_record_citations。一句话：Controller 不懂业务规则，QaService 不懂检索细节，QaChatService 不懂权限和记账。
【可能追问】为什么成员校验放 service 不放 Controller？→ 规则只有一份，以后加定时任务/RPC 入口不会漏；且挡在检索和 LLM 之前，省的是真金白银的 token。

**Q1.2 什么条件下直接拒答且不调 LLM？返回给前端什么？**
【考点】拒答分支 / 同步与流式差异。
【答案要点】`askWithUsage` 中 `documents.isEmpty() || evidenceLevel == EvidenceLevel.INSUFFICIENT` 时，直接返回 `AskQuestionResponse.unanswered(INSUFFICIENT_CODE, INSUFFICIENT_MESSAGE, List.of())`，不发起 LLM 调用，usage 全 0。INSUFFICIENT_CODE 是 `ErrorCodes.RETRIEVAL_NOT_GROUNDED`，消息是常量"检索到的有效证据不足，暂不回答。"同步路径 HTTP 200 返回该响应体。
【可能追问】流式路径同样情况怎么表现？→ `askStream` 返回 `Flux.error(new BusinessException(INSUFFICIENT_CODE, ...))`，Controller 发 SSE `error` 事件（仅 message），错误码不进事件，落 `qa_records.reason_code`。

**Q1.3 LLM 调用失败和 JSON 解析失败，你的处理为什么完全不同？**
【考点】硬失败 vs 软失败的区分（`getStructuredAnswer`）。
【答案要点】两种失败的处理在 `getStructuredAnswer` 里刻意分开：① 模型调用本身抛 RuntimeException（超时/网络/服务不可用）→ 没有响应可回退，是**硬失败**，归一为 `BusinessException(ErrorCodes.MODEL_UNAVAILABLE, ...)` 上抛，经全局异常处理器透出，绝不误标成格式错误；② 已拿到模型文本、只是 JSON 结构解析失败 → **软失败**，走 `fallbackParse` 复用原始文本解析。注释原话："已拿到模型文本；JSON 结构解析失败属「格式问题」，可回退原文解析，不算模型不可用。"
【可能追问】为什么不统一抛 500？→ 硬失败用户重试可能恢复且要显式提示；软失败还能救回来，报错是把可恢复问题放大。

**Q1.4 fallbackParse 的输入是什么？会不会二次调用 LLM？**
【考点】兜底解析的成本设计。
【答案要点】`fallbackParse(chatResponse, evidenceBundle)` 只复用**首次调用已返回的原始文本**：`answerParser.parse(rawAnswer)` 再解析一次，注释明确"复用首次 LLM 调用的原始文本做回退解析，不再重新调用 LLM"。usage 从同一 chatResponse 提取。若 chatResponse 结构不完整或解析仍失败，返回 `LlmCallResult(null, ...)`，上层据此返回 FORMAT_ERROR_CODE 拒答（并附 evidenceOverview）。
【可能追问】为什么不让模型重试一次？→ 重试=双倍延迟+双倍成本，且格式失败是概率性的，回退路径已覆盖大多数 case；这是成本与质量的取舍。

**Q1.5 answered=false 的模型自拒答怎么处理？**
【考点】三层拒答来源的区分。
【答案要点】第三层拒答：模型在结构化输出里返回 `answered=false`（代码判断 `!result.output().answered() || !StringUtils.hasText(result.output().answer())`），此时透传模型给的 `reasonCode/reasonMessage`，同样附 evidenceOverview。所以系统共三层拒答：检索层无证据（RETRIEVAL_NOT_GROUNDED，不调 LLM）、格式层解析失败（ANSWER_FORMAT_ERROR）、模型层自拒答（透传模型原因码）。
【可能追问】监控上怎么区分？→ QaService 落库时业务拒答 success=true（系统按设计正确工作），只有系统异常 success=false——拒答率和故障率是两条独立监控线。

**Q1.6 流式路径的 Prompt 和同步路径有什么本质区别？**
【考点】双 Prompt 设计。
【答案要点】同步路径用 `qaChatClient.prompt(userPrompt)` 走默认 JSON 系统提示词（prompts/qa/system.st，"请严格输出 JSON"）；流式路径在 `askStream` 里显式覆盖 system："……请直接输出纯文本回答正文……不要输出 JSON、Markdown 等任何格式标记。"因为 token 流是直接推给前端打字机渲染的，JSON 包裹会让前端解析痛苦且首字延迟高。
【可能追问】流式怎么拿 usage？→ `.stream().chatResponse()` 逐响应读 `getMetadata().getUsage()`，非空且 >0 就写入 usageRef；流结束后若仍为空，用 `charCount/4` 估算 completion tokens 并标 `estimated=true`。

**Q1.7 流式超时怎么做的？埋点为什么有个"上移"？**
【考点】Reactor timeout 与计量空洞（`askStream` 关键注释）。
【答案要点】`tokenFlux.timeout(Duration.ofSeconds(max(1, llmTimeoutSeconds)))`（默认 45s）。关键设计：`doOnComplete/doOnError` **上移到 timeout 之外**挂在 streamFlux 上——如果挂在 timeout 内层，超时产生的错误不会流过内层回调，造成"计时黑洞"。代码注释原话："超时/中断也经由 doOnError 结束计时，避免计时空洞"。另外用 `boolean[] recorded` 标志位 + 预构建 successTimer/errorTimer，保证一条流只 finish 一次。
【可能追问】为什么 successTimer/errorTimer 要提前构建？→ doOnComplete/doOnError 回调在 Reactor 线程执行，不能在回调里才依赖请求线程的上下文，预构建是线程安全的传递方式。

**Q1.8 createUserPrompt 的三个槽位各是什么？**
【考点】提示词模板变量分工。
【答案要点】`createUserPrompt` 往 `qaUserPromptTemplate` 填三变量：`question`（用户问题原文）、`evidenceLevel`（枚举名，如 SUFFICIENT）、`evidenceGuidance`（来自 `EvidenceAssessor.guidanceFor` 的策略指导语，如 WEAK 对应"必须明确说明依据有限"）。evidenceLevel 为 null 时兜底 NONE——等级本身也是提示词约束的一部分，模型必须遵守该等级的作答策略。
【可能追问】guidance 在哪生成？→ `HybridChunkRetrievalService.retrieve` 末尾 `EvidenceAssessor.guidanceFor(evidenceLevel)`，随 `RetrievedEvidenceBundle` 一起返回。

**Q1.9 对话级埋点怎么组织的？**
【考点】Micrometer Timer.Sample 用法。
【答案要点】同步路径 `dialogueMetrics.start()` 拿 Timer.Sample，finally 里 `finish(dialogue, "qa", "sync", !failed)`，failed 由 catch RuntimeException 置位——异常也计入且按失败统计；流式路径则是预构建 success/error 两个 Timer + recorded 数组防重复 finish，计时结束在流的 terminal 信号上。指标 tag 是 module=qa、mode=sync/stream、success=true/false。
【可能追问】为什么 finally 里 finish 而不是 return 前？→ 抛异常路径也要结束计时，否则活跃计时器泄漏、失败率统计缺失。

**Q1.10 AskResult 里为什么要带 evidenceLevel 和 documents 出去？**
【考点】编排层返回值设计。
【答案要点】`AskResult(response, usage, evidenceLevel, documents)`：QaService 需要 documents 做落库（引用快照、证据概览）和计量，需要 evidenceLevel 落 qa_records；流式路径同理用 `StreamContext(tokenStream, documents, evidenceLevel, recordIdRef)`，recordIdRef 是 AtomicReference，由 QaService 在流完成回调里回填持久化 ID，Controller 在收尾 `record` 事件里读 `streamContext.recordId()` 推给前端。
【可能追问】为什么用 AtomicReference 而不是返回值？→ 流式回调在 Reactor 线程执行，方法主线程拿不到回调内的局部变量，AtomicReference 是"跨线程信箱"。

## 2. SSE 流式链路：QaController.streamAsk + QaService.askStream

**Q2.1 为什么用 StreamingResponseBody 而不是 WebFlux？**
【考点】Servlet 栈下的 SSE 实现选型。
【答案要点】项目是 Spring MVC（Servlet 栈），`/stream-ask` 返回 `ResponseEntity<StreamingResponseBody>`，produces = TEXT_EVENT_STREAM。StreamingResponseBody 的 lambda 在**另一个线程**执行，所以必须手动传递线程上下文：进入 lambda 先 `UserContext.set(authenticatedUser)`（在 Controller 线程先取出），finally 里 `UserContext.clear()`。Reactor 的 Flux 只用作 token 流容器，写出侧靠 `blockLast()` 同步阻塞消费。
【可能追问】SecurityContext 为什么不自动带过去？→ SecurityContextHolder 默认 THREAD_LOCAL 策略，线程换了就丢；要么手动 set，要么配 MODE_INHERITABLETHREADLOCAL（有线程池复用风险，不选）。

**Q2.2 SSE 事件有哪几种？收尾顺序是什么？**
【考点】事件协议设计（`writeStream`）。
【答案要点】事件类型：`token`（每个文本片段）、`citations`（流完成后 `citationAssembler.assembleDocuments(documents)`，非空才发）、`evidence-overview`（非 null 才发）、`record`（recordId 非空才发，Map.of("recordId", recordId)）、`error`（初始化失败时 `GlobalExceptionHandler.userFacingMessage(exception, "请求处理失败")`）。写出格式由 `SseEventWriter.write`：`event:<name>\n` + `data:<payload>\n\n` 并立即 flush。
【可能追问】为什么 citations/record 放 doOnComplete 而不是单独接口？→ 一次连接交付完整答案，前端不用二次请求；recordId 也依赖流结束后的落库回填。

**Q2.3 中途出错为什么不直接断流？**
【考点】SSE 错误语义。
【答案要点】`askStream` 初始化阶段（含检索）异常时，catch 里 `writeJsonEvent(outputStream, "error", Map.of("message", userFacingMessage))` 后 flush 再 close——让前端收到结构化错误事件优雅提示，而不是浏览器侧 "net::ERR" 式裸断；客户端已断开时 IOException 静默忽略。token 流中途错误则 `doOnError` 只记日志（此时 error 语义已由业务层落库处理），流终止由 Reactor 完成。
【可能追问】error 事件里为什么不带错误码？→ 当前实现只放 message（PROJECT_TRUTH 明确记录），错误码存 qa_records.reason_code——前端按"回答失败"统一呈现，不暴露内部码。

**Q2.4 流式路径的落库发生在哪？失败也落库吗？**
【考点】doOnComplete/doOnError 双落库。
【答案要点】`QaService.askStream` 包装 token 流：`doOnNext(answerBuilder::append)` 边推边攒完整答案；`doOnComplete` 组装 `AskQuestionResponse.answered(answerBuilder.toString(), List.of())` 落库成功记录并回填 recordIdRef；`doOnError` 也落库——用 `error instanceof BusinessException` 取 code，等于 RETRIEVAL_NOT_GROUNDED 判为业务拒答（success=true，evidenceLevel=NONE），否则记 SYSTEM_ERROR（success=false）。注释强调"通过结构化 code 识别，而非依赖 message 文本前缀"。
【可能追问】为什么拒答 success=true？→ 系统按设计正确工作了；把拒答记成故障会让故障率虚高，拒答率无法独立观测。

**Q2.5 cache() 在流式链路里防什么？**
【考点】冷 Flux 重订阅的副作用重复。
【答案要点】Flux 是冷流：上层若断线重连重试订阅，`doOnNext/doOnComplete/doOnError` 整套副作用会重跑——重复调 LLM、重复插 QA 记录、重复计量（重复扣费）。`persistedTokenStream.cache()` 把首次订阅的产出固化，后续订阅只重放缓存，副作用只发生一次，实现"token 级重试幂等"。这是 `QaService.askStream` 最后一行包装，注释写明是该目的。
【可能追问】cache() 有什么代价？→ 全量 token 缓存在内存里直到 GC/失效窗口过；对本场景（单答案几百~几千 token）可接受，海量并发要设过期或改 replay 策略。

**Q2.6 用量信息怎么从 Reactor 线程传回主流程？**
【考点】跨线程结果传递双信箱。
【答案要点】两个 AtomicReference：QaChatService.askStream 内部 usageRef 攒 provider usage，doOnComplete 里组装 UsageInfo（可能是 charCount/4 估算）回调 `onUsageReady`；QaService.askStream 传入的回调把它 `usageRef.set(usage)` 并立即 `recordUsage(...)` 计量。计量函数整体 try-catch 只 warn 不抛——"没记上账"不能让用户已拿到的回答作废；但落库失败是要抛的（业务数据完整性）。
【可能追问】为什么计量可容忍失败而落库不行？→ 计量是旁路观测数据，丢了只影响报表；QA 记录是用户可见的业务数据（历史列表引用它）。

**Q2.7 代理层关 buffering 的踩坑是什么？**
【考点】SSE 实战坑（PROJECT_TRUTH/AGENTS 记录）。
【答案要点】SSE 靠"服务端逐事件 flush → 中间层不攒不缓存 → 浏览器逐事件渲染"成链。反向代理（Nginx、Vite dev proxy）默认会缓冲响应体，导致打字机效果变成一次性吐全部。前端新增 SSE 时必须保持 Vite 代理关闭缓冲；服务端侧对应措施：响应头 CacheControl.noStore()、SseEventWriter 每个事件后立即 flush。第三方"经验"会说 SSE 需要额外心跳保活，本项目实测当前链路无此需求（待验证项仅剩长连接空闲超时场景）。
【可能追问】还有哪些常见 SSE 坑？→ gzip 压缩缓冲、response 被 @ResponseBody 拦截、事件里混入未转义换行破坏 data 帧边界。

**Q2.8 流式接口为什么也加 @RateLimit？**
【考点】成本闸门一致性。
【答案要点】`streamAsk` 与 `ask` 一样是 `@RateLimit(limit = 20, window = 60, scope = "知识库流式问答")`——两个 scope 分开统计。大模型调用又贵又慢，流式并不因为"体验好"就豁免限流；且流式建立长连接后持有更久，更需要防滥用。
【可能追问】限流在检索之前还是之后？→ 在 Controller 入口、成员校验之前，被限流请求不产生任何检索/LLM 成本。

**Q2.9 recordId 事件在什么时机发出？如果落库慢会阻塞答案吗？**
【考点】收尾事件的依赖链。
【答案要点】doOnComplete 里落库是同步执行的：recordIdRef 回填完成后，Controller 的 doOnComplete（挂在外层）才会写 citations → evidence-overview → record 事件。所以落库慢会推迟收尾事件，但不会影响已推完的 token 内容；用户感知是"正文出完后收尾事件晚一点"。这是一种刻意排序：引用和 recordId 必须在正文完成后才有意义。
【可能追问】落库失败会怎样？→ doOnComplete 抛异常会转为流错误路径，前端收不到 record 事件但正文已收到；失败记录进日志。

**Q2.10 后端还有什么保证 SSE 事件边界的机制？**
【考点】SSE 协议帧格式。
【答案要点】`SseEventWriter.write` 严格按规范写 `event:` + `data:` + 空行，token 数据若含换行会破坏帧——写入侧由 Jackson `writeValueAsString` 把 JSON 序列化成单行（换行被转义为 \n）保证帧完整；纯文本 token 事件按单片段写，每个事件独立 write + flush。
【可能追问】为什么不直接用 SseEmitter？→ StreamingResponseBody 给了 OutputStream 的完全控制权（手动 flush、错误时手写 error 事件），与 UserContext 手动传递方案配合更直接；SseEmitter 属等价选型。

## 3. 查询规划：QueryPlanningService（四策略）

**Q3.1 四种查询策略分别什么时候触发？**
【考点】QueryPlanStrategy 语义。
【答案要点】DIRECT：问题清晰，原句直接检索（最优路径零额外开销）；REWRITE：口语/指代问题改写成书面语；DECOMPOSE：复合问题拆多个子问题分别检索再融合；GLOBAL："总结整个知识库"类全景问题，转 `retrieveGlobal` 全局遍历。由规划 LLM 通过 `queryPlanningChatClient.prompt(planPrompt).call().entity(QueryPlanResult.class)` 结构化返回。
【可能追问】REWRITE 的最终语句列表长什么样？→ `buildRewriteQueries`：**原句 + 改写句**（LinkedHashSet 去重），原句保留是因为改写可能丢专有名词，两路都查更稳；再 `limitQueries` 截到 MAX_QUERY_COUNT=3。

**Q3.2 MAX_QUERY_COUNT 为什么是 3？模型返回 5 条怎么办？**
【考点】检索放大系数 / 不信任模型输出。
【答案要点】每条检索语句要跑向量+ES 两路，3 条=6 次检索，检索收益边际递减而延迟成本线性上涨，3 是平衡点；`limitQueries` 用 `.limit(MAX_QUERY_COUNT)` 硬截断——类注释原话："永远不要信任大模型的输出会自觉遵守约定，代码侧必须有硬性护栏"。
【可能追问】为什么不按子问题重要性选 3 条而是截前 3？→ 模型没有可靠的重要性排序信号，顺序即其认为的优先级；更优方案是加重要性字段，当前没做（演进项）。

**Q3.3 规划失败为什么回退 DIRECT 而不是报错？**
【考点】可选增强环节的降级原则。
【答案要点】`plan()` 整个 try-catch，任何 RuntimeException 都 `return QueryPlanResult.fallback(originalQuestion)`。规划是"锦上添花"不是"没有它不能检索"：LLM 超时/格式错只该意味着退化为拿原句直接检索，用户最多损失一点召回质量，不该看到报错。类注释点题："降级路径是检索类系统的标配"——与 rerank 出错回退 RRF 原序同构。
【可能追问】validatePlan 还防什么？→ 模型返回 null/空 strategy → fallback；GLOBAL 但语句列表被编造 → 强制只保留原句；语句空白/重复 → normalizeQueries 规范化去重（\s+ 压成单空格）。

**Q3.4 GLOBAL 策略的检索语句为什么被强制换成原句？**
【考点】validatePlan 对 GLOBAL 的特判。
【答案要点】`validatePlan` 中 GLOBAL 直接 `return new QueryPlanResult(GLOBAL, List.of(originalQuestion))`——全局遍历不走语义检索，规划出的检索词没有意义，且防止模型编造的查询污染 GLOBAL 分支。随后 `HybridChunkRetrievalService.retrieve` 里 `if (queryPlan.strategy() == GLOBAL) return retrieveGlobal(...)`。
【可能追问】retrieveGlobal 怎么取证据？→ selectList 同 group + status=READY + deleted=false，orderByAsc(id)，`last("LIMIT " + maxGlobalDocuments)`（默认 50），每文档取 chunkIndex==0 的首切片（没有就取第一个），metadata 标 retrievalSource=GLOBAL、coverageMode=GLOBAL_TRAVERSAL、score=1.0，evidenceLevel 强制 SUFFICIENT 配专用指导语。

**Q3.5 查询规划用的 ChatClient 和问答用的有什么不同？**
【考点】多 ChatClient 隔离。
【答案要点】构造器 `@Qualifier("queryPlanningChatClient")` + `@Qualifier("queryPlanningUserPromptTemplate")`——规划是独立的小模型调用（模型名独立配置），只返回策略+语句的结构化 JSON；问答走 `qaChatClient`（带 qaRetrievalAdvisor 和 JSON 问答系统提示词）。一个请求内部实际可能发生多次 LLM 调用：规划 1 次 + （可选改写复用同次）+ 生成 1 次。
【可能追问】规划的 LLM 挂了会拖慢整体吗？→ 会增加一次失败调用的延迟（超时时间独立配置），但功能不降级到不可用；这是"每加一个 LLM 环节就多一份延迟预算"的直接体现。

**Q3.6 QueryPlanResult.fallback 返回什么？**
【考点】降级行为精确性。
【答案要点】fallback(originalQuestion) = DIRECT 策略 + 仅原句一条查询。注意 fallback 不等于"跳过规划"——它仍产出合法 QueryPlanResult，下游 `retrieve` 无需感知"规划是否成功"，只按 strategy 分支执行。这是把降级收敛在类型层面的设计。
【可能追问】DIRECT 的 queries 是什么？→ `List.of(originalQuestion)`，即只有一句，双路只跑一轮。

**Q3.7 规划环节和 QuestionQueryRewriteService 什么关系？**
【考点】新旧两条改写路径的辨析（防张冠李戴）。
【答案要点】`QuestionQueryRewriteService` 是**基于规则**的改写（正则 SPLIT_PATTERN `[？?。；;]` 拆子句、去客套词），独立 @Service；生产主链路用的是 **LLM 查询规划** QueryPlanningService。两者并存：规则版零成本零延迟可作离线/兜底用途，LLM 版覆盖口语化与指代。回答时务必分清，别把规则拆句说成"我的查询规划"。
【可能追问】为什么保留规则版？→ 测试友好（纯函数级确定性）、可作为 LLM 规划不可用时的降级候选，删除成本大于收益。

## 4. 双路召回与 RRF：HybridChunkRetrievalService / RrfFusion / RetrievalCandidate

**Q4.1 双路召回的执行顺序是并行还是串行？为什么？**
【考点】真实并发拓扑（PROJECT_TRUTH 强调）。
【答案要点】**向量 + ES 双路是顺序执行**：`for (String plannedQuery : queryPlan.queries()) { mergeVectorHits(...); mergeKeywordHits(...); }`。真正并行的是 You.com 网页搜索子查询——`retrievalExecutor`（AppThreadPoolConfig 注入的有界队列 + CallerRuns 线程池）只用于 `searchWebQueries` 的 CompletableFuture 并行提交。PROJECT_TRUTH 明确记录这一点，别说成"三路并行"。
【可能追问】为什么检索路不并行？→ 两路都是本机内网毫秒级（pgvector + 本机 ES），并行的工程收益小、还要处理线程池与超时；You.com 是外网调用（秒级），并行收益大——按延迟特征决定并行化对象。

**Q4.2 RRF 融合发生在代码里的哪个位置？是独立步骤吗？**
【考点】融合的实现形态（高频陷阱题）。
【答案要点】**不是独立融合步骤**。RRF 分数在候选合并时逐命中累加：`RetrievalCandidate.mergeVectorHit(hit, rank)` / `mergeKeywordHit(hit, rank)` 里 `this.rankingScore += RrfFusion.rankScore(rank)`。`HybridChunkRetrievalService` 的 mergeVectorHits/mergeKeywordHits 传 `index + 1` 作为通道内排名。candidates 是 `Map<Long, RetrievalCandidate>`（LinkedHashMap），同 chunkId 自动聚合。排序发生在全部合并完成后：按 rankingScore 降序、chunkId 升序兜底。
【可能追问】这样设计和"召回完再统一融合"等价吗？→ 分数上等价（加法交换律），工程上少一次遍历和中间结构；但要求候选对象是有状态的，这也是 RetrievalCandidate 从嵌套类提为顶层 package-private 类的原因。

**Q4.3 RrfFusion 的公式和默认 k？k=0 意味着什么？**
【考点】RRF 细节。
【答案要点】`rankScore(rank, k) = 1D / (Math.max(k, 0) + Math.max(rank, 1))`，`DEFAULT_K = 0`，即精确 1/rank。k 是平滑项，防止头部排名权重过大；k=0 时头部更陡，实测对本项目 topK=5 截断更友好。rank 0/负数按 1 处理（Math.max(rank,1)），k 负数按 0 处理——防御性写法保证输出恒在 (0,1]。
【可能追问】k=0 是拍脑袋吗？→ 评测定参：改参数必须过评测集，k 的取值是评测对比的输出（必考题集 L3 同口径）。通用文献常用 k=60，那是为长列表平滑设计的，对 topK=5 的场景头部陡峭反而有利。

**Q4.4 为什么用 RRF 而不是分数加权融合？**
【考点】融合选型论证。
【答案要点】BM25 分和余弦相似度量纲不同、分布不同，加权要先归一化且对参数敏感。RRF 只用排名不用分值：天然同量纲、免归一化、免调参、稳健。且本项目 ES 侧分数已做 `min(1, log1p(raw)/log1p(100))` 压缩（EsKeywordScoring），向量侧是 cosine——即便都归一到 [0,1]，分布形态仍不同，加权融合的权重没法跨语料复用。
【可能追问】RRF 丢掉了原始分数信息，损失了什么？→ 损失"遥遥领先 vs 勉强上榜"的差距信息；补偿手段是后续 cross-encoder 精排——两阶段设计里初排只负责"别漏"，精排负责"排准"。

**Q4.5 RetrievalCandidate 里存了几种分数？各自语义？**
【考点】候选数据结构。
【答案要点】五种：`vectorScore`（多次向量命中的**最大值**）、`keywordScore`（多次 ES 命中的最大值，注意 merge 的是 `hit.normalizedScore()`）、`rankingScore`（RRF **累加值**）、`rerankScore`（Cross-Encoder 打分，非 final，包内可写）、以及派生 `source()` 返回 BOTH/VECTOR/KEYWORD（vectorMatched && keywordMatched → BOTH）。另有 chunkText、documentId/chunkId/chunkIndex。
【可能追问】vectorScore 取 max 而不是累加，为什么不对称？→ 原始分用来回答"这条内容本身有多相关"，多次命中同一查询组不该重复抬分；RRF 累加值才负责跨查询/跨通道的"多路印证"信号。两者职责不同。

**Q4.6 角色过滤发生在哪些点？为什么在 rerank 之前？**
【考点】fail-closed 权限设计（PROJECT_TRUTH 表格事实）。
【答案要点】`DocumentRoleGate` 在检索层被调用两次：① 检索前 `effectiveAllowedDocumentIds(groupId)` 解析当前角色可读 docId 集合，**空集直接返回 RetrievedEvidenceBundle.empty()**——与"查无此文"同呈现，绝不返回"无权访问"，杜绝存在性泄露；② 双路召回合并后 `candidates.values().removeIf(c -> !allowedDocIds.contains(c.documentId()))` 剔除受限切片。两次都在 rerank 之前——受限切片不能进入重排打分（打分本身也是信息泄露，且浪费算力）。roleGate 为 null 仅存在于历史/单元测试构造路径。
【可能追问】UserContext 拿不到时 currentRole 返回什么？→ USER（最低权限，fail-closed），不会因上下文缺失而放大权限。

**Q4.7 每文档 chunk 配额和文档覆盖模式怎么选？**
【考点】RetrievalCandidateSelector 两种模式。
【答案要点】`shouldPreferDocumentCoverage(question)` 关键词匹配（"每个文档/各个文档/所有文档/all documents"等 13 个短语，toLowerCase 后 contains）触发覆盖模式；普通模式按相关性取前 topK（可叠加 maxChunksPerDocument 配额，0=不限制）。覆盖模式两遍挑选：第一遍每文档只取最高分一条（多样性优先），第二遍按全局相关度补足剩余席位，补足同样受每文档配额约束防绕过。
【可能追问】覆盖模式为什么还要第二遍？→ 第一遍解决"单文档霸榜"，但凑不满 topK（文档数 < topK）；第二遍在不违反配额下用剩余高分切片填满，兼顾覆盖与精度。

**Q4.8 类簇（RetrievalCluster）是怎么构建的？**
【考点】RetrievalClusterBuilder。
【答案要点】按 documentId 分组后组内按 chunkIndex 排序，`isContinuousWith`（chunkIndex 连续）则并入当前簇，否则开新簇；簇列表按 rankingScore 降序、primaryChunkId 升序排。作用：同一文档连续命中的多个切片聚成一簇，作为邻居窗口扩展的单元，避免 topK=5 全是同文档相邻碎片的重复上下文。
【可能追问】为什么不直接用滑动窗口合并？→ 簇保留了 primary（入口切片）身份和独立评分，窗口扩展是组装时的行为；混为一谈会丢失"哪条是命中本身"的信息。

**Q4.9 邻居窗口怎么实现？代价是什么？**
【考点】EvidenceDocumentAssembler 窗口扩展。
【答案要点】`DEFAULT_NEIGHBOR_WINDOW = 1`：`cluster.expandedStartChunkIndex(neighborWindow)` / `expandedEndChunkIndex` 各向外扩 1。`buildEvidenceWindow` 用 `chunkWindowCache.computeIfAbsent(documentId, -> selectReadyActiveChunksByDocumentId(groupId, documentId))` 拉全文档 active 切片（每文档只查一次库），按 chunkIndex 落在 [start,end] 的拼文本，首行"文件名：xxx"。注意：**邻居扩展发生在最终 topK 选出之后**，是每个入选证据的上下文补全，不占 topK 名额，也不参与评分。
【可能追问】窗口会不会把 topK=5 撑成 15 个 chunk 的超长上下文？→ 会扩 token，但 chunk 目标 240 tokens，最多 5×3=15 片 ≈ 数千 token，在上下文预算内；窗口大小是常量而非配置，改动需重评证据长度分布。

**Q4.10 EvidenceAssessor 的 score 是什么分？0.85 是余弦阈值吗？**
【考点】最高危的概念题（见文末 Top5）。
【答案要点】**不是余弦相似度**。Document metadata 的 `score` 是 `RetrievalRowGuard.normalizeScore(cluster.rankingScore())` = **1.0 - exp(-rawRrfScore)**——对 RRF 累加分做指数压缩映射到 (0,1)。EvidenceAssessor 里的 0.85/0.30/0.40 阈值全部作用在这个压缩分上。例如单路 rank=1 命中 raw=1.0，normalizeScore≈0.632。所以"topScore≥0.85"实际要求多路/多查询叠加后的 RRF 分 ≥ -ln(0.15)≈1.9。
【可能追问】为什么不用余弦分做阈值？→ 融合后只有 RRF 分是跨通道可比的全局分；用余弦分得先解决"ES 命中但向量低分"的通道缺失问题，RRF 压缩分天然覆盖两路信息。

**Q4.11 You.com 结果怎么进入证据列表？**
【考点】第三通道的定位。
【答案要点】`searchWebQueries(queryPlan.queries())` 并行收集各子查询结果，主流程**单线程编号追加**：继续 E{n} 递增编号，复制原 metadata 再覆盖 evidenceId。单子查询失败只记日志跳过（网页搜索是可选增强通道）；`retrievalExecutor` 未注入或 queries.size()==1 时顺序执行；CompletableFuture 提交被拒（RejectedExecutionException）也退化顺序执行。默认 You.com 关闭（可选配置）。
【可能追问】网页结果参与 RRF/精排吗？→ 不参与，它们在精排和选择之后追加，只作为补充证据进入上下文和 EvidenceAssessor 统计——增强通道不改主排序，避免外部结果扰动内部可复现性。

## 5. 精排三级降级链：RerankingConfiguration / RemoteHttpRerankingService / NoOp

**Q5.1 精排的装配有哪几档？怎么切换？**
【考点】RerankingConfiguration 双档装配。
【答案要点】`argus.rag.reranking.provider`：显式 =remote 时装配 `RemoteHttpRerankingService`（@ConditionalOnProperty）；否则 @ConditionalOnMissingBean 落到 `RerankingService.NoOp` 原序放行。remote bean 声明在 NoOp **之前**，@ConditionalOnMissingBean 据此让位。2026-10-24 已在 local profile 启用 remote；默认 NoOp。参数：base-url 默认 http://127.0.0.1:11435、model 默认 BAAI/bge-reranker-base、timeout-ms 8000。
【可能追问】为什么默认 NoOp 而不是 remote？→ 上线前必须先完成离线对比评测（HitRate/MRR/延迟，对照 scripts/rag_eval/report.md 基线）——"先评测后启用"是配置类功能的安全开关设计。

**Q5.2 "三级降级"具体是哪三级？各在哪层实现？**
【考点】降级链的层次（必背）。
【答案要点】① **remote 服务内保序回退**：RemoteHttpRerankingService 自身永不抛异常——非 200、响应长度不符、索引非法/重复、任何 Exception 都 `return fallback(candidates)`（保序分 1.0 - i*0.001，与 NoOp 同口径）；② **管线级 try-catch**：`HybridChunkRetrievalService.applyReranking` 整段 try-catch，任何漏网异常 `log.warn("Reranking failed, falling back to RRF order")` 返回原 candidates；③ **装配级 NoOp**：provider 未配或 bean 缺失时干脆没有远程调用。三道保险确保模型异常不变成问答失败。
【可能追问】为什么不把 ② 去掉、信任 ① 永不抛？→ 纵深防御：① 是人类写的承诺，② 保证 ① 的承诺被破坏（如将来重构引入受检包装）时链路仍不中断；代价只有一层 try-catch。

**Q5.3 RemoteHttpRerankingService 校验了哪些响应合法性条件？**
【考点】远程结果信任边界。
【答案要点】四个硬校验，任一不满足立即 fallback：① statusCode == 200；② `results` 是数组且 `size == candidates.size()`（长度不符直接回退，不做部分采纳）；③ 每个 `index` 在 [0, size) 且未被见过（`boolean[] seen` 防重复索引）；④ 全部通过后按 score 降序排序返回 `RerankResult(index, score)`。HTTP 客户端 connectTimeout 3s、请求 timeout 8s。
【可能追问】长度不符为什么不做"能用的部分"？→ 重排结果索引与候选一一对应，缺失意味着打分管道异常，部分采纳会引入不可解释的排序偏差；保序回退的确定性更值钱。

**Q5.4 applyReranking 怎么把重排结果映射回候选？超出的候选去哪了？**
【考点】rerank 与召回列表的拼接。
【答案要点】`recallSize = min(candidates.size(), retrievalOptions.recallK())`（默认 50），取头部 subList 做重排；`results.size() != recall.size()` 时**直接返回原 candidates**（又一道防线）；否则按返回的 index 把 rerankScore 写回 `recall.get(r.index())` 组成 reranked 列表；`recallSize < candidates.size()` 时把尾部剩余候选**保持原序**直接接在后面——重排只影响头部 recallK，尾部按 RRF 序兜底。
【可能追问】尾部候选还有机会进上下文吗？→ 有：RetrievalCandidateSelector 从 reranked 列表按序选 topK，头部不够时尾部补位，顺序语义仍是"重排后的头部 > 原 RRF 序尾部"。

**Q5.5 NoOp 的分数为什么是 1.0 - i*0.001 而不是全 1.0？**
【考点】保序分的设计。
【答案要点】全 1.0 会让下游排序不稳定（等值时依赖输入顺序或排序算法稳定性）；1.0、0.999、0.998… 幅度极小不足以改变相对顺序，但让下游"有分可排序"，稳定保留原始 RRF 序。NoOp 与 remote 的 fallback 共用同一公式——**口径一致**保证"降级前后排序行为完全相同"，降级损失可控可测。
【可能追问】为什么不用 0 分？→ 0 分与 rerankScore 判空/判零逻辑混淆，且下游如果有分数过滤会被误伤。

**Q5.6 精排 50 对 3.47 秒，慢怎么办？你量化过降级损失吗？**
【考点】评测数字支撑决策。
【答案要点】50 对 BGE cross-encoder 实测 3.47s，问答总预算内可接受；优化路径：批量推理、先截断再精排（50→20）、结果缓存。关键是**降级敢不敢**有数：NoOp 基线 170 例评测 HitRate@5 = 97.6%、综合 94.1%——NoOp 与精排开关对比直接量化了降级损失，所以任何一级降级都是"已知损失地降"，不是盲目兜底。40 例在线栈基线准确率 95%（精选集上 rerank 与 NoOp 持平，基线饱和），压测集对比进行中。
【可能追问】既然持平为什么还要开 remote？→ 40 例精选集已饱和（HitRate 双双 100%），区分度不足；真实收益要在更难的压测集上看，且 remote 开启后 NoOp 仍是自动安全网，风险为零。

**Q5.7 rerank 失败会被用户感知成什么？**
【考点】降级的用户语义。
【答案要点】什么都不感知：applyReranking 回退后链路继续走选择/聚类/组装，证据顺序退化为 RRF 序，答案质量可能略降（有评测数字背书），但不会有报错、不会变慢（远程调用失败本身要等超时——最坏 8s timeout + 3s connect，这是降级的主要成本）。
【可能追问】8 秒超时会不会拖垮整条问答？→ 会侵蚀延迟预算，这是真实权衡：超时设置在"等 rerank 结果"与"快速退化"之间，当前 8000ms 偏保守；可观测手段是 rerank 环节日志与耗时指标。

**Q5.8 为什么 rerank 只重排文本不重排元数据？chunkText 空怎么办？**
【考点】rerank 输入契约。
【答案要点】cross-encoder 只需要 (query, text) 对：`texts = recall.stream().map(c -> c.chunkText != null ? c.chunkText : "")`——空文本送空串占位，保证 index 对齐（候选与打分结果按 index 一一对应）。重排改变的是顺序，元数据留在 RetrievalCandidate 对象上随 index 移动，无需复制。
【可能追问】空串打分会怎样？→ cross-encoder 给低分，自然沉底，等价于剔除；用占位保 index 是最小侵入做法。

**Q5.9 RerankingService 接口怎么定义的？为什么返回 index 而不是文本？**
【考点】接口契约设计。
【答案要点】`List<RerankResult> rerank(String query, List<String> candidates)`，`record RerankResult(int index, double score)`。返回 index+score：① 避免大文本在结果里复制传输；② index 是与输入列表的唯一对齐键，调用方按 index 回写 rerankScore；③ 降级 fallback 构造的就是 identity 映射（index=i）。已排好序返回（按分降序），调用方无需再排。
【可能追问】为什么接口不感知 chunkId？→ 保持 rerank 纯打分职责，与存储 ID 解耦——换 embedding 模型/候选来源不影响接口。

**Q5.10 cross-encoder 和 bi-encoder 的区别，你为什么选 cross-encoder 做精排？**
【考点】模型原理（结合 ADR-004 离线原则）。
【答案要点】bi-encoder（embedding 检索）query 和 doc 各自编码成向量再算相似度，可离线建索引但精度有限；cross-encoder 把 (query, doc) 拼接后 jointly 编码，token 级交互捕捉细粒度相关性，精度高但每对都要一次前向，无法预计算——所以只能对 topK 小集合精排。本项目遵循 ADR-004：本地/零 API 费用原则，用本地网关 fastembed 的 BAAI/bge-reranker-base。
【可能追问】embedding 和 reranker 是同一个模型吗？→ 不是：embedding 是本地 bge-small-zh（512 维，langchain4j ONNX，JVM 内），reranker 是独立进程网关的 bge-reranker-base——两阶段两模型是标准形态。

## 6. 证据分级与拒答：EvidenceAssessor / EvidenceLevel / retrieveGlobal

**Q6.1 五个证据等级的判定规则精确是什么？**
【考点】EvidenceAssessor.evaluate 全分支（必背）。
【答案要点】documents 为空 → NONE。然后：`size>=2 && (hasBothSource || (hasVectorEvidence && topScore>=0.85))` → SUFFICIENT；`topScore<0.30 || (size<=1 && avgScore<0.40)` → INSUFFICIENT；`hasBothSource || size>=2` → PARTIAL；否则 WEAK。hasBothSource 指 metadata.retrievalSource == "BOTH"（双通道都命中同条=交叉印证）；topScore/avgScore 是压缩分（1-exp(-RRF)）的最大/均值。注意分支顺序：SUFFICIENT 先判，INSUFFICIENT 其次——高分但单条也会先看是否 SUFFICIENT 不满足再落入 INSUFFICIENT。
【可能追问】PARTIAL 和 WEAK 的本质区别？→ PARTIAL = 有多源命中或 ≥2 条（覆盖了几个方面），可以"部分、有依据地答"；WEAK = 只剩单源且分数不高的弱命中，只能"说明依据有限地谨慎答"。

**Q6.2 哪些等级会触发拒答？谁消费这个判断？**
【考点】分级与拒答的解耦。
【答案要点】EvidenceAssessor 本身**不拒答**，只产出等级和指导语；拒答决策在 QaChatService：`documents.isEmpty() || evidenceLevel == INSUFFICIENT` 时不调 LLM 直接拒。NONE 不会出现在正常路径（documents 为空时 retrieve 返回 empty bundle），但 createUserPrompt 会兜底 null→NONE。WEAK/PARTIAL 不拒答，而是通过 evidenceGuidance 约束模型措辞（"必须明确说明依据有限"）。
【可能追问】为什么不把 WEAK 也拒了？→ 拒答过激会伤正常用户；评测集里专门放了"知识库没有"的问题要求拒答 100% 命中，同时要求正常问题不误拒——阈值卡在两边都有指标的边界上。

**Q6.3 guidanceFor 每级给模型什么指令？**
【考点】等级→提示词的翻译层。
【答案要点】NONE→"当前没有可用证据，必须直接拒答。"；INSUFFICIENT→"检索到的证据相关性太低，不应强行回答。请告知用户当前知识库中暂无足够相关信息。"；WEAK→"……只能谨慎回答，必须明确说明依据有限，不能给出确定性结论。"；PARTIAL→"只能回答证据明确支持的部分，未覆盖部分必须明确说明不足。"；SUFFICIENT→"可以正常回答，但仍然不得超出证据进行臆测。"。这条指导语填进 user.st 的 evidenceGuidance 槽位，配合系统提示词的等级规则生效。
【可能追问】为什么既要等级又要文字？→ 枚举给程序分支用（如拒答判断），文字给模型执行用——同一个事实的两种消费形态。

**Q6.4 EvidenceAssessor 为什么是纯函数集合而不是 Spring Bean？**
【考点】可测试性设计。
【答案要点】类注释明确："仅对传入的 documents 与 EvidenceLevel 做纯计算，不触碰检索编排、候选排序、DAO 或任何内部状态。抽离后独立可测，且不改变任何对外行为。"private 构造器 + 全静态方法。同构设计的还有 RrfFusion、RetrievalCandidateSelector、RetrievalClusterBuilder——检索包里"编排有状态、计算无状态"两分。
【可能追问】这种拆分带来什么实际收益？→ 证据阈值调参时可以拿评测集离线批量回放 evaluate()，不用起 Spring 上下文；也避免阈值逻辑藏在服务私有方法里无法单测。

**Q6.5 GLOBAL 模式为什么强制 SUFFICIENT？**
【考点】retrieveGlobal 的评估豁免。
【答案要点】全局遍历没有"相关性分数"概念（score 硬编码 1.0、retrievalSource=GLOBAL），EvidenceAssessor 的阈值体系对它无意义；所以直接 `EvidenceLevel.SUFFICIENT` + 专用指导语"当前为全局遍历模式，已列出所有可用文档的概览……仍然不得超出提供的信息进行臆测"。豁免的是**相关性评估**，不是**内容约束**——防幻觉约束始终在。
【可能追问】GLOBAL 模式也会被拒答吗？→ 文档列表为空时 RetrievedEvidenceBundle.empty() → 上层 documents.isEmpty() 拒答；只要取到文档就必走 LLM。

**Q6.6 拒答的评测怎么验证 100%？**
【考点】评测驱动（PROJECT_TRUTH + 必考题集口径）。
【答案要点】评测集专门包含"知识库中不存在答案"的问题，要求全部拒答（拒答准确率 100%）；正常问题同时验证不误拒。2026-10-24 首轮在线栈基线：精选 40 例 HitRate@5=100%、拒答准确率 100%、综合 95.0%（docs/operations/live-stack-verification-20261024.md）。阈值调整属于"改参数必过评测集"的管制范围。
【可能追问】用户抱怨误拒怎么办？→ 先归因：看该 case 双路召回是否命中——命中被挤掉是排序问题，没命中是切片/向量化问题；归因到层再改，不全局放宽阈值。

**Q6.7 EvidenceLevel 在 qa_records 里怎么用？**
【考点】等级的持久化与审计价值。
【答案要点】`RetrievedEvidenceBundle(documents, evidenceLevel, guidance, typedEvidences)` 一路带回 QaService，落库 saveQaRecord 时写进 qa_records 的证据等级字段；流式失败落库时，RETRIEVAL_NOT_GROUNDED 场景强制记 NONE（此时 evidenceLevel 语义已不可信）。等级落库让"拒答率按等级分布"可事后分析——比如 INSUFFICIENT 集中在某类问题时指向语料缺口。
【可能追问】typedEvidences（RetrievalEvidence）是干什么的？→ Document 的强类型投影（fromDocument），供需要结构化访问证据的调用方（如 assistant/概览组装）使用，避免反复从 metadata Map 取值。

## 7. 上下文组装与引用防错位：CitationAssembler / EvidenceDocumentAssembler

**Q7.1 引用编号为什么不会错位？机制本质是什么？**
【考点】引用防错位（本包核心题）。
【答案要点】本质：**引用列表完全由服务端从证据集组装，不信任模型输出的任何编号**。证据在组装期就定死编号 E1..En（HybridChunkRetrievalService 的 evidenceIndex 递增，写进 metadata.evidenceId 和 Document.id）；CitationAssembler.assembleDocuments 直接遍历这份 documents 生成引用，编号天然与证据一一对应。系统提示词明确"不要输出 citationRefs 或其他未声明字段"，KnowledgeAnswerOutput 上 @JsonIgnoreProperties(ignoreUnknown=true) 兜底丢弃模型擅自输出的字段。模型编造不存在的引用编号在结构上无法进入引用列表。
【可能追问】如果产品要求答案内嵌角标跳转怎么办？→ 必须改为：提示词要求输出证据编号 + 装配时校验编号 ∈ 证据集、越界丢弃（必考题集 L2 同口径），这是当前留好的演进口而不是已实现事实。

**Q7.2 CitationAssembler 为什么按文件名去重？丢了什么？**
【考点】去重取舍（类注释原文）。
【答案要点】`Map<String, Citation> citationsByFileName = new LinkedHashMap<>()` + `putIfAbsent`——每个文件只保留第一条命中（= RRF/重排序里最相关的块），LinkedHashMap 保持插入顺序。代价是丢掉同文档其他块信息；类注释点明：当前粒度面向"来源可信"不是"段落定位"，若产品要"引用跳转到具体段落"，要去掉去重或改成一文件多引用嵌套——两种产品诉求的组装策略不同。
【可能追问】去重会让引用数少于证据数，前端怎么对齐？→ 引用与证据概览是两个独立展示区，不要求角标一一对应；这正是当前"来源可信"粒度的边界。

**Q7.3 缺文件名的证据为什么直接丢弃引用？**
【考点】fail-safe 语义。
【答案要点】`toCitation` 读不到 fileName（先读 "fileName" 回退 "documentName"，都空）返回 null，该证据不进引用列表——"宁可少一条引用也不展示『来源未知』的引用"，一条没有出处的引用会拉低整份答案可信度。元数据读取全部走安全读取（MetadataReaders，类型不符返回 null 而非抛异常），因为元数据来自向量库/ES 两条链路，类型实现可能有差异，组装层必须防御。
【可能追问】pgvector 侧元数据类型差异的例子？→ PgVectorRetrievalAdapter.requireLong 同时兼容 Number 和 String 两种存储形态；CitationAssembler 的 readLong 只认 Number（此处数据已经过 Assembler 规整），两处防御层级不同是刻意的。

**Q7.4 一条 Citation 里有哪些字段？snippet 为什么是 null？**
【考点】Citation record 结构。
【答案要点】`Citation(documentId, chunkId, chunkIndex, fileName, score, snippet=null, groupId)`——documentId/chunkId/chunkIndex 支撑前端跳原文定位，score 是压缩分，groupId 用于权限二次校验。snippet 传 null：当前接口不回传片段文本，用户点开引用按 documentId+chunkIndex 到文档预览定位，避免响应体膨胀和内容二次泄露面。
【可能追问】落库的引用实体一致吗？→ QaRecordPersistenceService.toCitationEntity 从同一 documents 读同名字段（MetadataReaders 兼容驼峰/小写），qa_record_citations 与响应口径一致。

**Q7.5 证据文本的格式契约是什么？模型看到什么？**
【考点】上下文格式（rag-context.st）。
【答案要点】每条证据文本 = "文件名：{fileName}\n" + 窗口内切片文本（\n 连接、trim）；rag-context.st 模板声明"以下是可用证据。每条证据都有 evidenceId。你只能基于这些证据回答"。Document.id = evidenceId（E1..En），metadata 携带完整溯源链（groupId/documentId/chunkId/chunkIndex/primaryChunkId/startChunkIndex/endChunkIndex/score/retrievalSource/coverageMode/vectorScore/keywordScore/hybridScore）。
【可能追问】为什么把文件名拼进文本而不是只放 metadata？→ 模型只看 text；文件名在正文里让模型回答时能自然说出"根据《xxx》"，引用可信度感知更好。

**Q7.6 toDocument 里"检索结果与文档切片不一致"的异常防什么？**
【考点】数据一致性断言。
【答案要点】`if (!documentId.equals(cluster.documentId()) || !chunkIndex.equals(cluster.primaryChunkIndex()))` 抛 BusinessException——row 来自 `selectQaReadyChunksByIds`（按 chunkIds 批量查），与簇的 primary 身份必须一致；不一致说明数据竞态（如查询间隙切片被删/重建）。这是防御式断言，宁可抛错也不组装张冠李戴的证据。
【可能追问】这里抛异常会怎样传导？→ retrieve 整体失败向上抛，QaChatService 未捕获 → 全局异常处理返回系统错误；概率极低（毫秒级窗口），fail-fast 比组装错证据更安全。

**Q7.7 cluster 窗口查询为什么按 documentId 做缓存？**
【考点】chunkWindowCache 的 N+1 治理。
【答案要点】`Map<Long, List<DocumentChunkEntity>> chunkWindowCache = new LinkedHashMap<>()`，`computeIfAbsent(documentId, -> selectReadyActiveChunksByDocumentId(groupId, documentId))`——同文档多个簇/多次窗口计算只查一次库。topK=5 时最多 5 次文档级查询，若无缓存最坏每簇每窗口一次。窗口过滤在内存完成（chunkIndex ∈ [start,end]）。
【可能追问】为什么不一次 SQL 把所有文档的切片都查出来？→ 文档切片数不可控（大文档数千片），按需按文档拉取 + 内存过滤是查询量与传输量的平衡；且 selectReadyActiveChunksByDocumentId 顺带过滤了 READY/active 状态。

**Q7.8 EvidenceOverviewAssembler 和 CitationAssembler 的分工？**
【考点】两个收尾组装器的职责边界。
【答案要点】CitationAssembler：引用来源列表（按文件名去重，"答案出自哪份文档"）；EvidenceOverviewAssembler：证据概览（"这次检索到了什么质量的证据"），在拒答和格式错误场景也会组装（`.withEvidenceOverview(...)`），让用户看到"为什么答不了"。同步响应、SSE citations/evidence-overview 事件、落库链路三处消费口径一致。
【可能追问】为什么拒答也要给概览？→ 拒答体验的关键是"说清楚为什么"——概览展示已命中的证据及等级，把拒答从黑盒变成可解释行为。

## 8. JSON 结构化输出与兜底：QaAnswerParser / KnowledgeAnswerOutput

**Q8.1 sanitizeJson 具体做了什么？**
【考点】剥壳函数逐行（高频手写题）。
【答案要点】两步：① `rawAnswer.replaceAll("(?m)^```[A-Za-z]*\\s*", "").replaceAll("```", "").trim()` 去掉 Markdown 代码围栏（含 ```json 语言标注行）；② 取 `indexOf('{')` 到 `lastIndexOf('}')` 的子串，兼容模型在 JSON 前后加的附言。找不到花括号时原样返回（让 Jackson 报错走 fallback）。
【可能追问】这个截取有什么已知局限？→ 只适配**单个顶层 JSON 对象**；若模型输出两个对象或字符串值内含未转义 `}`，lastIndexOf 可能截出损坏 JSON——所以它只是提高成功率的预处理，兜底仍是 fallbackParse。这是"宽进严出"：剥壳尽力，解析严格。

**Q8.2 主链路的解析调用顺序是什么？parse 和 sanitizeJson 谁是主线？**
【考点】别误读 QaAnswerParser（类注释专门警告）。
【答案要点】主线（QaChatService.getStructuredAnswer）直接用**静态方法** `QaAnswerParser.sanitizeJson(text)` + 自己的 objectMapper.readValue(text, KnowledgeAnswerOutput.class)；`parse(rawAnswer)` 是**另一条链路**（非 RAG 主路径）的兜底入口，内部封装 sanitize+readValue、失败返回 null。QaChatService.fallbackParse 调的才是 parse。类注释原话："parse 并不是『主 RAG 一旦失败才来回退』的回退引擎"——回退引擎是 QaChatService 自己的 fallbackParse。
【可能追问】这个设计有什么历史原因？→ parser 先于 fallback 重构存在；重构时把剥壳逻辑提为静态工具供主线直连，保留 parse 兼容旧调用方，注释就是为了防后人把两条链路接反。

**Q8.3 KnowledgeAnswerOutput 的字段和容错注解？**
【考点】结构化输出契约。
【答案要点】`record KnowledgeAnswerOutput(boolean answered, String answer, String reasonCode, String reasonMessage)` + `@JsonIgnoreProperties(ignoreUnknown = true)`。ignoreUnknown 兜住模型多输出的字段（如被提示词禁止的 citationRefs），不至于整个解析失败；answered 是 primitive boolean——缺失时反序列化为 false，天然走拒答分支（fail-closed：模型不声明 answered 就当拒答处理）。
【可能追问】answered 缺失当 false 有没有副作用？→ 会把"忘了输出 answered 但正文写好"的 case 变成模型层拒答；权衡后接受，因为提示词已强制字段要求，且拒答比不可信回答安全。

**Q8.4 如果让你给结构化输出再加一层校验，加什么？**
【考点】演进设计题（开放但要有据）。
【答案要点】按当前代码缺口答：① answered=true 但 answer 空白已被 `StringUtils.hasText` 兜住（归入拒答分支）；可再加 reasonCode 白名单校验（当前透传模型任意码，存在语义漂移风险）；② answer 长度上限防御超长输出；③ answer 与证据集的 n-gram 重叠率检测作为幻觉粗筛（评测集抽样核对的自动化替代）——引用当前"prompt 约束 + 评测抽样"的组合，说明工程上做不到 100%，所以引用可回溯把人工抽查成本压到近零。
【可能追问】为什么现在不实现 n-gram 检测？→ 有误杀（同义改写），需要评测集标定阈值；按"改参数必过评测"流程，它是下一轮评测驱动迭代的候选。

**Q8.5 模型不听话输出了 JSON 数组或截断 JSON，各层怎么表现？**
【考点】故障传导链完整推演。
【答案要点】sanitizeJson：lastIndexOf('}') 对数组返回 -1 → 原样返回 → Jackson readValue 抛 JsonProcessingException → catch（RuntimeException | JsonProcessingException）→ fallbackParse → answerParser.parse 再失败返回 null → fallbackParse 返回 LlmCallResult(null) → askWithUsage 判 output==null → 返回 unanswered(ANSWER_FORMAT_ERROR, "模型返回格式错误，无法解析回答。") 且带证据概览，usage 仍记录（模型确实消耗了 token）。截断（如 max_tokens 打断）同理。
【可能追问】为什么 FORMAT_ERROR 也算拒答而不是 500？→ 它是模型的"产物质量问题"，属于业务结果而非系统故障；用户拿到可解释提示比 500 更好，且监控上与真实系统故障分开。

**Q8.6 结构化输出为什么不用 Spring AI 的 .entity() 一把梭？规划那里不是用了 entity 吗？**
【考点】两种结构化调用方式的对比。
【答案要点】QueryPlanningService 用 `.call().entity(QueryPlanResult.class)`（Spring AI 自动转换，BeanOutputConverter 内部也是提示词注入+解析）；问答主链路**手动** chatResponse + sanitizeJson + readValue，因为：① 需要拿到 ChatResponse 的 Usage 计量（entity() 不直接暴露）；② 需要自定义剥壳与 fallback 时机（entity() 失败直接抛，没有回退钩子）；③ 模板里已手写 JSON schema 约束（system.st 的字段说明），不需要再注入 BeanOutputConverter 生成的 schema。
【可能追问】entity() 失败和手动失败的表现差异？→ entity() 抛异常会走进"模型调用失败"分支被误判 MODEL_UNAVAILABLE——这正是手动解析把"格式失败"从"调用失败"里拆出来的动机之一。

## 9. engine 基础设施：PgVectorRetrievalAdapter / ElasticsearchChunkIndexService / RetrievalOptions

**Q9.1 向量检索怎么保证不跨群组泄露？**
【考点】双保险设计（PgVectorRetrievalAdapter 类注释）。
【答案要点】两层：① `SearchRequest.builder().query(question).topK(topK).filterExpression(new FilterExpressionBuilder().eq("groupId", groupId).build())`——查询级过滤，pgvector 只在当前 group 的向量里搜；② 结果返回后 `toVectorHit` 二次校验每条 metadata 的 groupId，不一致**抛 BusinessException("向量检索返回了跨群组数据")**——防御向量库本身 bug 导致的数据泄露。fail-closed：宁可检索失败也不泄露。
【可能追问】filter 失效的常见原因？→ metadata 写入缺失/类型不匹配导致 filter 静默不命中或被忽略；二次校验正是防这种"过滤器悄悄失效"的情况。

**Q9.2 ES 检索失败为什么返回空列表而不是抛异常？**
【考点】通道级降级语义。
【答案要点】ElasticsearchChunkIndexService.search 检索失败捕获后**降级返回空列表**（类注释："检索失败不抛异常，降级返回空列表，保证服务不中断"）——关键词通道挂了，向量通道仍能撑起单路召回，RRF 退化为单路排名和，问答继续。对比：pgvector 适配器的跨群组校验是抛异常的——**可用性降级**（ES）与**安全性失败**（跨组数据）策略相反，是刻意区分。
【可能追问】ES 挂了检索质量掉多少？→ 只剩向量路，精确关键词（型号、编号）召回会掉；这正是双路设计的原因——任一通道故障都只是质量降级不是服务中断。

**Q9.3 ES 打分怎么归一化的？为什么用 log1p？**
【考点】EsKeywordScoring.normalizeRaw。
【答案要点】`min(1.0, log1p(rawScore) / log1p(KEYWORD_SCORE_REFERENCE))`，KEYWORD_SCORE_REFERENCE=100。BM25 分无上界且对词频超线性，log1p 压缩长尾：raw=100 → 归一 1.0，raw=10 → log(11)/log(101)≈0.516。检索打分是"bool 初排 + rescore 二次精排"，多字段（fileName/chunkText）各配 match_phrase/match 加权。IK 中文分词。
【可能追问】归一化到 [0,1] 后能和余弦直接比大小吗？→ 形态上可比但分布仍不同（这正是选 RRF 的原因）；归一化是为了 EvidenceAssessor 阈值体系有稳定输入和 metadata 可读性。

**Q9.4 ES 客户端为什么用 JDK HttpClient 裸调 REST？**
【考点】依赖取舍。
【答案要点】项目刻意不加官方 elasticsearch-java 客户端依赖——只用"索引管理 + 关键词检索"两个能力，REST API 面很小；JDK 原生 HttpClient（connectTimeout 5s、REQUEST_TIMEOUT 5s）零额外依赖、连接池复用、mock HttpClient 可注入测试（包私有构造器）。索引名默认 argus_rag_document_chunks，volatile indexInitialized 做启动时惰性建索引。
【可能追问】裸调的代价？→ 失去客户端的重试/发现/序列化生态，版本升级要手改 JSON；在"单机 ES、能力面小"的当前规模是净收益，规模化后可回换官方客户端（接口收敛在 Service 内，调用方无感）。

**Q9.5 RetrievalOptions 四个参数是什么？怎么防非法配置？**
【考点】参数表与下限收敛。
【答案要点】`RetrievalOptions(channelTopK, recallK, maxGlobalDocuments, maxChunksPerDocument)`，defaults() = (50, 50, 50, 0)（与历史硬编码一致，零回归）。record 紧凑构造器里 clamp：前三个下限 1，per-document 下限 0（0=不限额，仅收敛负数）——"非法配置自动落到安全值，不会拖垮检索链路"。配置键 argus.rag.retrieval.*，管理员诊断端点 /api/admin/retrieval 只读输出参数值（不暴露向量/提示词/文档内容，且控制器内 requireAdmin 二次校验防 URL 规则被绕过）。
【可能追问】recallK 和 channelTopK 都是 50，区别是什么？→ channelTopK 是单通道单查询的召回条数（喂给 RRF），recallK 是融合排序后进入重排的截断条数；当前相等意味着"全部进入重排"，分开配是为了将来"50→20 只排头部"的优化不留死代码。

**Q9.6 queryEmbedding 在哪做的？检索时还要调 embedding 模型吗？**
【考点】embedding 链路（结合 ETL 侧）。
【答案要点】Spring AI VectorStore 抽象层内完成 query 向量化（local bge-small-zh，512 维，langchain4j ONNX，JVM 内推理，零 API 费用）——PgVectorRetrievalAdapter 只传 question 文本，向量化对检索层透明。文档侧 embedding 在 ETL 入库时离线完成（pgvector HNSW + cosine）。
【可能追问】每次问答 query embedding 的开销？→ 小模型 ONNX 毫秒级；DECOMPOSE 3 条子查询就是 3 次 query embedding + 6 次检索，这是 MAX_QUERY_COUNT=3 延迟账的一部分。

**Q9.7 selectQaReadyChunksByIds 为什么要再查一次库？**
【考点】召回与组装的分离。
【答案要点】向量/ES 召回只拿到 ID 和分数；组装证据需要权威行数据（chunkText、fileName、groupId、chunkIndex）——从 PostgreSQL 按 chunkIds 批量查（selectQaReadyChunksByIds 过滤 READY/active）。这保证：① 上下文里的文本以 DB 为准（ES 索引可能滞后/分词变形）；② 查不到的 chunk（已被删）自然落 row==null 被跳过，证据集自动收敛到真实存活切片。
【可能追问】ES/向量库里的脏数据会漏到答案吗？→ 不会：文本以 DB 查询结果为准，召回层的 text 仅用于 rerank 打分；最坏情况是给已删切片打了一次无意义的分。

**Q9.8 QaRetrievalService 这个门面给谁用？**
【考点】Facade 模式实际应用。
【答案要点】QA 模块对外检索门面，供 assistant 等模块复用检索能力：收拢 ReadyChunkDocumentRetriever（按文档直查）+ HybridChunkRetrievalService（混合检索）+ CitationAssembler 成"给问题，还你带引用的证据包"。两个配额参数：`kb-routing.per-group-top-k`（默认 4，每知识库最多出几条，防单库淹没）与 `kb-routing.overall-top-k`（默认 12，全局上限，控上下文长度）——多库检索的配额思想。
【可能追问】assistant 走的门面 topK 和问答的 top-k(5) 为什么不同？→ assistant 跨多知识库路由，需要给每个库留名额并压总量；问答单库场景 5 条刚好。同一引擎不同配额策略，正是门面存在的意义。

## 10. 提示词约束与评测驱动

**Q10.1 system.st 的核心约束有哪几条？**
【考点】提示词内容（背骨架）。
【答案要点】① 角色："你是群组知识问答助手，只能依据给定证据回答，不得补充外部知识或猜测"；② 输出格式："请严格输出 JSON，不要输出 Markdown 或任何额外说明"，字段 answered/answer/reasonCode/reasonMessage；③ 规则：能答时 answered=true 简体中文；不能答时 answered=false、answer 置空并给 reasonCode/reasonMessage；④ "不要输出 citationRefs 或其他未声明字段"；⑤ 证据有限时必须说明"依据有限"，不能伪装确定结论；⑥ 必须遵守 evidenceLevel 和回答策略。
【可能追问】这些约束哪些有代码兜底？→ citationRefs 由 @JsonIgnoreProperties 兜；answered 缺失由 primitive false 兜；JSON 围栏由 sanitizeJson 兜——提示词约束从来不单独承重。

**Q10.2 user.st 的执行要求如何把 EvidenceLevel 翻译成模型行为？**
【考点】等级约束的提示词落地。
【答案要点】user.st 把 evidenceLevel、evidenceGuidance 两个变量展开成"执行要求"清单，逐级硬规定：NONE 必须拒答不得给事实性回答；WEAK 可以谨慎答但必须声明"依据有限"，不能下确定结论；PARTIAL 只能答证据明确支持的部分，未覆盖部分必须说明无法确认；SUFFICIENT 可正常答但不得超出证据。另有"多子问题只答覆盖到的部分""优先保证准确，不为完整而编造"。
【可能追问】模型违反等级约束输出确定结论怎么办？→ 无运行时强校验（当前事实）；依赖提示词 + 评测集抽样核对。可以讨论的演进：对 WEAK 级输出的确定性措辞做正则审计。

**Q10.3 "评测驱动迭代"在你代码里怎么体现？说三个具体例子。**
【考点】方法论落地（核心加分题）。
【答案要点】① RRF k=0：通用文献建议 k=60，但在评测集对比下 k=0（精确 1/rank）对 topK=5 截断更优，写进 RrfFusion.DEFAULT_K 注释"与原实现一致"；② 精排启用：remote 档默认关闭，"上线前必须先完成离线对比评测"，40 例精选集与 NoOp 持平（基线饱和）所以保持 NoOp 默认、local profile 试点，170 例离线基线 HitRate@5 97.6%/综合 94.1% 作为对照组；③ 拒答阈值：0.85/0.30/0.40 的每次调整都要同时满足"无据问题拒答 100%"与"正常问题不误拒"两个指标。原则一句话：**参数是评测的输出，不是输入**。
【可能追问】评测集怎么构建的？→ 170 例离线集（含知识库没有的问题）+ 精选 40 例在线栈基线（live-stack-verification-20261024）；改参数必过评测集，评测脚本在 scripts/rag_eval/（report.md 存基线）。

**Q10.4 检索质量排查的归因链条？**
【考点】排查分流（与必考题集 Q5 L3 呼应但落到代码观测点）。
【答案要点】日志埋点齐全可定位：`混合检索开始 → 查询规划完成(strategy, queries) → 双路检索完成(candidateCount, vectorHits, keywordHits) → 检索层角色过滤剔除 → RRF融合排序完成(rankedCandidates, clusters) → 混合检索完成(evidenceCount, evidenceLevel, elapsedMs)`。用户反馈"该答没答"：先看 evidenceLevel 和 vectorHits/keywordHits——双路都没命中=切片/embedding 问题；命中但 evidenceLevel=INSUFFICIENT=阈值问题；进上下文但答错=生成问题（引用对=检索的锅/引用错=生成的锅的分流依据是 CitationAssembler 的引用快照）。
【可能追问】埋点为什么用 log.info 打点而不是全靠 metrics？→ 排查需要"单次请求全链路上下文"（groupId/questionLength/各阶段条数），metrics 只有聚合值；两者互补，Timer 只管延迟分布。

**Q10.5 同一个请求里发生了几次 LLM 调用？各自的模型可以不同吗？**
【考点】LLM 调用拓扑与成本账。
【答案要点】最多 2 次：查询规划 1 次（queryPlanningChatClient，独立模型配置）+ 生成 1 次（qaChatClient，argus.rag.qa.model-name 默认 qwen-plus）。GLOBAL 策略下跳过生成前的规划语义（规划仍发生，用于判定 GLOBAL）。拒答/证据不足时只有 0~1 次。计量按 endpoint 区分：QA_ASK / QA_STREAM_ASK 记问答那一次的 usage；规划调用的 token 不计入问答记录（独立模型独立计量口径）。
【可能追问】规划调用的成本可控吗？→ prompt 短（一个问题+输出 schema），输出是几十 token 的 JSON；相比生成调用可忽略，且失败即回退不重试——成本上限是明确的。

**Q10.6 如果要把拒答率降下来，你动的第一个旋钮是什么？**
【考点】参数理解深度（防"无脑调阈值"）。
【答案要点】先分桶：看 qa_records 里 INSUFFICIENT 拒答 case 的检索日志——① candidateCount=0：召回问题，先查切片参数（240/320/32/2 是否适配该语料）与 embedding 质量，改后重跑评测；② candidateCount>0 但压缩分 < 0.30：若双路都命中说明排名融合信号弱，可调 EvidenceAssessor 阈值但必须过"拒答 100%"评测线；③ 单条 avg<0.40：可考虑放宽到"PARTIAL 指导语回答"而非拒答。第一个旋钮通常是**数据侧**（切片/语料覆盖）而非阈值——阈值是最后才动的全局变量。
【可能追问】为什么最后才动阈值？→ 阈值是全局的，动它影响所有请求的精确率/召回率平衡，且有拒答 100% 硬指标压制；数据问题数据解决。

## 本包高危追问 Top5

1. **"你说 topScore≥0.85 很高——这是余弦相似度吗？"**（Q4.10）
   埋雷点：面试官把 0.85 当余弦阈值质疑合理性。正确答法：不是。score = `RetrievalRowGuard.normalizeScore(rrfRaw)` = **1 - exp(-RRF 累加分)**，映射到 (0,1)；0.85 意味着 RRF 原始分 ≥ -ln(0.15) ≈ 1.9，通常需要多路/多查询叠加命中。cosine 从未直接参与阈值判断。答错成"余弦 0.85"会连环暴露没读懂融合链。

2. **"RRF 融合在哪一步做的？k=60 才是常见值，你为什么 k=0？"**（Q4.2/Q4.3）
   埋雷点：答"检索完单独融合一次"就错了——RRF 是 `RetrievalCandidate.mergeVectorHit/mergeKeywordHit` 里 `rankingScore += RrfFusion.rankScore(index+1)` **逐命中累加**，没有独立融合步骤；k=0 是评测集对比后的选择（对 topK=5 截断友好），且必须能说出"参数是评测的输出"。

3. **"rerank 服务挂了，用户看到的证据顺序到底是什么？"**（Q5.2/Q5.4/Q5.6）
   埋雷点：答"回退到向量序"或"回到原始分数序"都不准确。精确链：RemoteHttpRerankingService 内部 fallback 与 NoOp 同口径的**保序分 1.0 - i*0.001**（i 是进入重排时的位置，即 RRF 融合序）→ 即使这层失效，applyReranking 的 try-catch 返回 candidates（RRF 序）→ 装配层还有 NoOp 兜底。顺序 = RRF 序，且有 170 例 NoOp 基线（HitRate@5 97.6%/综合 94.1%）量化了损失。

4. **"流式接口里用户没证据时，HTTP 状态码是多少？前端收到什么事件？"**（Q1.2/Q2.3）
   埋雷点：答 4xx/5xx 就错。同步路径 HTTP 200 + unanswered(RETRIEVAL_NOT_GROUNDED)；SSE 路径 200 建立 EventStream 后发 `error` 事件（data 只有 message），错误码不进事件、落 qa_records.reason_code。两路不一致是刻意设计（SSE 一旦开始没有"改状态码"的机会），能主动讲出这个不对称为加分项。

5. **"流式被断线重连重试，会不会重复调 LLM、重复扣费？"**（Q2.5/Q1.7）
   埋雷点：不知道冷流副作用问题就接不住。答案要点：Flux 冷流，重订阅会重跑 doOnNext(攒答案)/doOnComplete(落库)/计量整套副作用；`QaService.askStream` 用 `persistedTokenStream.cache()` 固化首次执行实现 token 级重试幂等。追问延伸：timeout 的 doOnComplete/doOnError 挂在 timeout 之外防"计时空洞"、recorded[] 防双次 finish、usage 缺失时 charCount/4 估算标 estimated=true——三个细节都能报出来说明真读过流式代码。
