## 一、BackgroundJobService.java —— 队列核心（入队 / 认领 / 完成 / 失败）

**Q1. 你的"消息队列"是怎么实现的？为什么不用 RabbitMQ/Kafka？**
- 【考点】技术选型与量级匹配、数据库队列的独有红利。
- 【答案要点】我用 PostgreSQL 的 `background_job` 表（V8 迁移）实现了队列：状态机 `QUEUED → RUNNING → SUCCEEDED | DEAD_LETTER`，没有 PENDING/RETRY 中间态。三个不换 MQ 的理由：① 任务量级是百级/天，远够不着 MQ 的适用区间；② 任务和业务数据同库，`UploadedDocumentFinalizer.finalizeUploaded` 在**同一个事务**里写文档行和任务行，要么都提交要么都回滚——MQ 要靠 Outbox 模式迂回才能拿到这个强一致；③ 表字段和 MQ 消息语义几乎一一对应（`status`↔消息状态、`next_run_at`↔延迟投递、`payload_json`↔消息体），量级上来后迁移是平滑的。
- 【可能追问】什么时候必须换？——日任务到百万级或需要扇出广播时；届时 SKIP LOCKED 语义可翻译成消费者组+手动 ack+死信交换机，分发逻辑不用改。

**Q2. 任务会不会重复创建？入队怎么幂等？**
- 【考点】幂等入队、唯一索引兜底。
- 【答案要点】`enqueue(NewBackgroundJobCommand)` 先 `selectByIdempotencyKey` 查同键任务：存在就复用返回，不存在才 insert。兜底是 `uk_background_job_idempotency` 唯一索引（V8 DDL，`idempotency_key VARCHAR(191)`）。幂等键是业务语义不是随机数：上传链路是 `INGEST:{documentId}:0`（`retryGeneration` 代数），手动重试入口 `DocumentDeleteService.retryFailedDocumentIngestion` 用 `System.currentTimeMillis()` 做新代数，避免撞上历史已成功/死信的键。
- 【可能追问】先查后插并发下安全吗？——两个请求同时查都可能没查到，但唯一索引会挡住第二个 insert，数据库是最后防线；待验证点：当前代码没有捕获重复键异常做二次查询，并发窗口极小但存在。

**Q3. 幂等命中时，如果老任务是死信怎么办？**
- 【考点】死信复活、条件 UPDATE 防并发双复活。
- 【答案要点】`enqueue` 命中已有任务分三种：QUEUED/RUNNING 复用；SUCCEEDED 也复用（文档没变不该重跑 ETL）；DEAD_LETTER 走 `reviveDeadLetter`——不能返回死信（永远不会再执行），也不能插新行（唯一索引挡住），只能复活。复活用 MyBatis-Plus `UpdateWrapper` 显式 `set` 全部字段，把 `lease_owner/lease_until/last_error_code/last_error_message/finished_at` 清 null，`attempt_count` 归 0，`next_run_at` 置 now，条件带 `eq("status", "DEAD_LETTER")`——并发双复活时只有一个 UPDATE 影响 1 行，另一个影响 0 行直接放弃。
- 【可能追问】为什么要用 UpdateWrapper 而不是 `updateById`？——MyBatis-Plus 的 `updateById` 默认忽略 null 字段，清不掉错误信息；这是真实的坑。

**Q4. 两个 Worker 同时抢一个任务怎么办？讲讲你的领取 SQL。**
- 【考点】FOR UPDATE SKIP LOCKED、原子认领。
- 【答案要点】`claimDueJobs` 是 @Transactional 短事务：先 `selectDueJobs`（`BackgroundJobMapper.xml`）选候选，SQL 末尾是 `FOR UPDATE SKIP LOCKED`——被别的 Worker 锁住的行直接跳过，不等待不阻塞；然后逐条 `claim(id, QUEUED→RUNNING, leaseUntil)` 条件更新，`WHERE id=#{id} AND (status=#{fromStatus} OR (status='RUNNING' AND lease_until<=now()))`，影响行数=1 才算抢到，抢到后再 `updateLease` 回写 `lease_owner/lease_until`。整个事务内行锁持有到提交，同任务只可能被一个实例认领。
- 【可能追问】为什么 claim 里还要带状态守卫，SELECT 不是已经锁行了吗？——防御纵深：认领条件更新是第二道闸，`attempt_count = attempt_count + 1` 也在这条 UPDATE 里原子推进。

**Q5. `selectDueJobs` 的 WHERE 条件为什么有两支？**
- 【考点】到期语义、租约过期接管。
- 【答案要点】两支：`status='QUEUED' AND (next_run_at IS NULL OR next_run_at<=#{now})` 是正常到期；`status='RUNNING' AND lease_until IS NOT NULL AND lease_until<=#{now})` 是**租约过期的 RUNNING 任务**——Worker 拿到任务后崩溃了，5 分钟租约一过，任务重新变成"可领取"，其他实例自动接管，这是实例崩溃自愈的关键。排序 `ORDER BY id LIMIT #{limit}`，近似 FIFO；配合 `idx_background_job_claim(status, next_run_at)` 索引。
- 【可能追问】表里有 `priority` 列吗？——有，V8 预留了 `priority INT DEFAULT 0`，但当前排序没用它；真要优先级先做"按类型分线程池"的粗隔离，再考虑 `priority DESC, id` 细粒度排序。

**Q6. 租约机制具体怎么工作？字段有哪些？**
- 【考点】lease_owner / lease_until、持有者校验。
- 【答案要点】认领时 Worker 传入 `LocalDateTime.now().plusMinutes(5)` 作为租约到期时间（`BackgroundJobWorker.pollAndDispatch` 第 67 行），`updateLease` 写入 `lease_owner`（`worker-` + UUID 前 8 位）和 `lease_until`。任务完成必须凭持有者身份：`complete` 的 SQL 是 `UPDATE ... SET status='SUCCEEDED' ... WHERE id=#{id} AND lease_owner=#{workerId}`——租约已被别人接管时，老 Worker 的 complete 影响 0 行，静默失败，这正是 at-least-once 语义的来源之一。服务层还声明了 `LEASE_MINUTES = 5` 常量（与 Worker 硬编码值一致）。
- 【可能追问】租约为什么是 5 分钟？——取正常任务耗时 P99 再放宽；太短会误接管造成双执行，太长真崩溃要等很久。租约解决"接管"，幂等解决"接管后重跑不出错"，两者必须成对出现。

**Q7. 失败任务怎么重试？退避参数是什么？**
- 【考点】failOrRetry、RETRY_BACKOFF_MINUTES、maxAttempts。
- 【答案要点】`failOrRetry(jobId, workerId, JobFailure)`：读任务，`newAttemptCount = attemptCount + 1`，超过 `maxAttempts`（入队传 3）置 `DEAD_LETTER` 且 `next_run_at=null`；否则 `backoffIndex = Math.min(attemptCount, RETRY_BACKOFF_MINUTES.length - 1)`，按常量数组 `{1, 5, 15}`（分钟）设置 `next_run_at` 重排为 QUEUED。错误信息落库并截断：`last_error_code` 64 字符、`last_error_message` 512 字符（`truncate` 方法）。
- 【可能追问】首次失败到底等几分钟？（见本节 Q8，高危细节）

**Q8.（诚实边界题）按代码第一次失败实际退避多久？**
- 【考点】读码精度：常量口径 vs 实际执行路径。
- 【答案要点】我如实说：注释和教程口径是"1/5/15 分钟"，但 `claim` 在认领时就把 `attempt_count` 加到 1（实体注释明确"已尝试次数含当前执行"），所以 `failOrRetry` 里读到的 `attemptCount=1`，`backoffIndex=min(1,2)=1`，**首次失败实际落 5 分钟档，第二次 15 分钟，第三次耗尽死信**；1 分钟档只有 attemptCount=0 时才取得到。单测 `failOrRetrySchedulesBackoff` 断言的是 `nextRunAt` 晚于 now+4 分钟，与 5 分钟实现一致但没有钉死下标。如果让我修，改成 `attempts - 1` 即对齐文档口径。
- 【可能追问】为什么测试没抓到？——断言只验证"至少 4 分钟"，边界没钉死；这本身是"测试断言强度"的好例子。

**Q9. 死信之后任务就永远死了吗？**
- 【考点】死信的定位：待办事项而非垃圾桶。
- 【答案要点】DEAD_LETTER 不再自动重试，但保留完整现场（错误码/错误信息/尝试次数），等人工。两条出路：① 同键再次入队时 `reviveDeadLetter` 条件复活（重置为 QUEUED、清错误、尝试次数归零）；② 手动重试端点 `POST /api/documents/{documentId}/retry-ingestion` 走**全新幂等键**（时间戳代数的新任务行），不触发复活。注意手动重试只接受 FAILED 状态的文档，先重置为 PROCESSING 再入队。
- 【可能追问】死信怎么被发现？——`argus.job.dead_letter` Micrometer Gauge + `QueueHealthIndicator`：死信数 > 0 直接 DOWN（见第七节）。

**Q10. 任务和业务数据的一致性靠什么保证？**
- 【考点】同库同事务 vs Outbox。
- 【答案要点】任务表和文档表同库，入队调用发生在 `finalizeUploaded` 的事务内：入队失败（数据库异常）向上抛出让上传整体回滚——"没有 ETL 任务的文档永远不会变 READY，宁可上传失败也不留假文档"。消费端 `claimDueJobs` 也是短事务。跨边界的（如 Excel 协同广播）才用真正的 Outbox（`excel_collab_outbox`，事务内 PENDING、提交后广播置 SENT）。
- 【可能追问】Outbox 重放有什么已知缺口？——诚实答：`selectPending` 无认领语义，多 API 实例下存在消息丢失/重复窗口（PROJECT_TRUTH 多实例审计已记录），当前仅 Worker 可安全水平扩展。

## 二、BackgroundJobWorker.java + BackgroundJobMapper.xml —— 消费端

**Q1. Worker 的轮询是怎么写的？有什么讲究？**
- 【考点】@Scheduled、fixedDelay vs fixedRate。
- 【答案要点】`pollAndDispatch` 用 `@Scheduled(fixedDelayString = "${argus.job.poll-interval-ms:15000}", initialDelayString = "${argus.job.poll-initial-delay-ms:20000}")`。必须用 fixedDelay：上一轮跑完后隔 15 秒再跑，天然串行；fixedRate 是每 15 秒触发不管上一轮完没完，执行慢了下一轮会叠进来，多批任务并发。每轮最多领 10 条，提交 `taskExecutor` 执行。
- 【可能追问】poll 间隔可配吗？——可，`argus.job.poll-interval-ms` 覆盖默认 15000；`argus.job.poll-initial-delay-ms` 默认 20000，给启动留缓冲。

**Q2. 为什么每次轮询都新建 workerId？**
- 【考点】租约持有者凭证。
- 【答案要点】`"worker-" + UUID 前 8 位`，每轮一个。它写入 `lease_owner` 字段，是"这个任务归我管"的凭证——`complete` 校验持有者，防止别的实例误改我认领的任务。每次轮询新建而非进程级固定：同一进程重启后旧 workerId 不会复活，语义上"一次认领一个身份"。
- 【可能追问】跨实例会撞 workerId 吗？——UUID 截断 8 位在单机每 15 秒一次的频率下冲突概率可忽略；真要严格可以用完整 UUID + 实例 IP。

**Q3. 轮询本身抛异常怎么办？**
- 【考点】定时任务的兜底原则。
- 【答案要点】`pollAndDispatch` 整体 try-catch，失败只 `log.warn("后台任务轮询失败...")` 不抛。数据库抖一下导致这轮空转，15 秒后下一轮自然恢复。原则：**这一轮空转不可怕，可怕的是把调度线程搞死**——@Scheduled 里抛未捕获异常会影响后续调度的信任边界（默认调度器会记录但任务代理可能终止该次触发链）。
- 【可能追问】`JobQueueMetrics.refresh` 也是这个写法吗？——是，同样 catch 全部异常只 warn，指标刷新失败不能拖垮调度线程。

**Q4. Worker 怎么分发任务？支持哪些类型？**
- 【考点】硬编码 switch、未知类型处置。
- 【答案要点】`executeSafely` 里是硬编码 switch，只认 `INGEST_DOCUMENT`：从 `resourceId` 取 documentId、从 `payload_json` 用 Jackson `readTree` 取 groupId，调 `DocumentIngestionAsyncService.ingestDocument` 后 `complete`。没有 processor 注册机制；`BackgroundJob` 类注释里的 `EXCEL_EXPORT / FINANCE_IMPORT` 是预留描述，不是当前 Worker 能力——Excel 导出走专用 `excelExportExecutor`，不进这张表。
- 【可能追问】未知类型会立刻死信吗？——不会，走 `failOrRetry(new JobFailure("UNKNOWN_JOB_TYPE", ...))`，和普通失败一样过退避档位，attempt 耗尽才进 DEAD_LETTER；"看不懂的任务"本质是需要人看的异常，不静默忽略。

**Q5. payload 解析失败会发生什么？（诚实边界题）**
- 【考点】失败路径追踪。
- 【答案要点】`readGroupId` 解析失败返回 null，Worker 里 `if (documentId != null && groupId != null)` 不满足就**跳过执行直接 complete**——任务 SUCCEEDED 但什么都没干。我如实承认这是当前边界：上传侧同事务写 payload，正常必有 groupId，所以实际触发概率极低；防御性更好的做法是这种情况走 failOrRetry 或直接死信。面试里主动指出比被问到强。
- 【可能追问】怎么改？——把"资源参数缺失"归为不可重试错误，直接置 DEAD_LETTER（错误码如 `BAD_PAYLOAD`），避免无意义重试。

**Q6. 领取后任务提交到哪个线程池？**
- 【考点】线程池隔离。
- 【答案要点】构造器注入 `@Qualifier("taskExecutor")`，即 `AppThreadPoolConfig` 里 4/8/200 的 `argus-async-` 池——和 @Async 共用。ETL 本身重（解析、向量化、ES 索引），所以 Worker 轮询线程只做"领取+派发"，执行在异步池。
- 【可能追问】队列满触发 CallerRuns 会怎样？——轮询线程自己执行任务，相当于自然背压：这一轮变慢，fixedDelay 自动把下一轮往后推，不会雪崩。

**Q7. 认领和执行的边界在哪？事务覆盖到哪里？**
- 【考点】事务边界设计。
- 【答案要点】`claimDueJobs` 是 @Transactional 短事务：SELECT FOR UPDATE + 条件 UPDATE + 回写租约，提交后锁释放；任务执行（可能几十秒到分钟级）**绝不在事务内**——长事务会长时间持行锁、拖垮连接池。执行结果再通过独立的 `complete` / `failOrRetry` 短语句落库。
- 【可能追问】为什么不"事务内执行完再提交状态"？——执行分钟级，事务分钟级等于把行锁变成全局瓶颈，这是队列设计的经典反面教材。

**Q8. `claim` SQL 里 `started_at = COALESCE(started_at, now())` 是什么意图？**
- 【考点】SQL 细节。
- 【答案要点】保留首次执行时间：任务被接管重跑时 `started_at` 不被覆盖，观测上能区分"首次开始"和"最近一次重试"。类似的还有 `complete` 里 `finished_at` 直接覆盖（完成时间取最后一次）。
- 【可能追问】attempt_count 从几开始？——认领即 +1，首次执行后就是 1；enqueue 时是 0，复活时归 0。

**Q9. 这套队列的投递语义是什么？**
- 【考点】at-least-once。
- 【答案要点】at-least-once：租约过期接管、Worker 重试都可能让同一任务跑多遍，队列不保证 exactly-once。所以三处幂等互相独立：入队幂等（idempotency_key 唯一索引）、认领原子（条件更新）、执行幂等（ETL 先清理后重建）。**at-least-once 投递 + 幂等消费 = 效果上的 exactly-once**。
- 【可能追问】能不能让队列直接保证 exactly-once？——通用任务队列做不到，工程上从不朝这个方向努力；Flink 这类流引擎在特定拓扑里可以。

## 三、DocumentIngestionAsyncService.java —— 业务层重试与幂等 ETL

**Q1. ETL 的完整流程是什么？**
- 【考点】ingestDocument 四步。
- 【答案要点】`ingestDocument(documentId, groupId)`：① `requireDocument` 校验文档存在（不存在抛 `DOCUMENT_NOT_FOUND`）；② `markJobRunningQuietly` 推进 `ingestion_jobs` 观测记录；③ `cleanupProcessingArtifacts` 先删旧 chunk/向量/ES 索引；④ `documentIngestionProcessor.process` 解析分块 → `syncSearchIndex` 同步 ES → `markDocumentStatus(READY)` → `markJobSucceededQuietly`。文档状态机 `PENDING→PROCESSING→READY/FAILED` 的每次迁移都在这一类里。
- 【可能追问】为什么第一步先删？——可重跑的幂等流程：重试意味着同一次 ETL 可能完整执行多遍，"先清后建"保证第 N 遍结果和第 1 遍一致。

**Q2. 业务层的重试参数是什么？和队列层什么关系？（必考）**
- 【考点】两层重试互斥（2026-10-24 演练修正结论）。
- 【答案要点】方法上 `@Retryable(retryFor = RuntimeException.class, maxAttempts = 3, backoff = @Backoff(delay = 2000, multiplier = 2.0))`，即 2s/4s/8s。关键结论：**两层重试不是叠加而是互斥**——`@Recover` 的 `recover:149` 在 Spring Retry 耗尽后"正常返回"，异常不会传给 Worker，所以 Worker 会调用 `complete` 把队列任务置 SUCCEEDED。业务性失败（如坏 PDF）走"文档 FAILED + 队列 SUCCEEDED"，**不进死信**；队列级 1/5/15 退避只对未被 Spring Retry 包裹捕获的系统级异常生效。实测坏 PDF 演练 `argus.job.dead_letter` 全程为 0。
- 【可能追问】这场演练怎么做的？——故意投喂腐坏文件 + 模拟 worker 挂死，现象是坏文件没进死信，定位到 @Recover 吞异常，结论沉淀为"中间件叠加≠可靠，失败路径必须演练"。

**Q3. @Recover 吞异常是 bug 吗？怎么定位失败？**
- 【考点】失败可见性分层。
- 【答案要点】是有意语义：`recover` 清理中间产物、`markDocumentStatus(FAILED, truncateFailureReason(...))`、`markJobFailedQuietly`——把失败变成"用户可见、可重试"的确定状态，而不是永远转圈。失败原因写进 `documents.failure_reason`（截 512 字符），用户在界面能看到"为什么失败"并点重试。队列死信只是失败的**其中一种**载体，不是唯一载体。
- 【可能追问】那什么样的失败才进死信？——@Recover 自身再抛出的、或绕过 Spring Retry 代理的系统级异常（如连接池耗尽抛 Error 级），由 Worker 的 catch 转 `failOrRetry("EXECUTION_FAILED", ...)`。

**Q4. 重试为什么是 2s/4s/8s，队列退避却是分钟级？两套不乱吗？**
- 【考点】重试间隔匹配故障画像。
- 【答案要点】不乱——**重试间隔要匹配故障的预期时长**。ETL 的失败多是秒级抖动（连接闪断、ES 短暂超时），指数退避 2/4/8 秒大概率恢复；队列任务的失败常是分钟级故障（磁盘满、外部服务宕机），1/5/15 分钟还带"人工介入前别疯狂空转"的意味。两处都配了上限（maxAttempts=3）：**重试策略永远和放弃策略成对出现，只写重试不写放弃是定时炸弹**。
- 【可能追问】指数退避为什么优于固定间隔？——固定间隔会以相同节奏撞上同一个故障窗口；指数拉开间隔命中恢复点的概率更高，还给下游喘息。

**Q5. markJobSucceededQuietly 这些 try-catch 是"防御性编程"还是"吞异常"？**
- 【考点】容忍划线标准。
- 【答案要点】有边界的容忍，划线标准是**"它是不是用户可见的事实"**。`ingestion_jobs` 是观察窗口（"Quietly 三兄弟"：markJobRunning/Succeeded/FailedQuietly），更新失败顶多监控盲区，只 warn 不抛；`documents.status` 是用户看到的事实，`markDocumentStatus` 更新影响 0 行会抛 `DOCUMENT_PROCESSING_FAILED`。同一个原则在 QaService：LLM 记账失败可容忍，问答落库失败必须抛。
- 【可能追问】观察窗口坏了你怎么发现？——warn 日志有告警；ingestion_jobs 与 documents.status 可做定期对账。容忍 ≠ 不管，是降低爆炸半径后再监控它。

**Q6. ETL 的幂等具体靠什么保证？（三层）**
- 【考点】幂等实现细节。
- 【答案要点】三层：① 任务开头 `cleanupProcessingArtifacts` 依次删 chunk（`documentChunkMapper.deleteByDocumentId`）、向量（`vectorIngestionService.deleteDocumentVectors`）、ES 索引（`elasticsearchChunkIndexService.deleteDocumentChunks`），每项清理失败仅 warn 不中断后续清理；② chunk 落库先删后插；③ 向量 ID 用 documentId+chunkIndex 生成的**确定性 UUID**，重跑写入同 ID 覆盖而不是新增。另外 ES 索引不在 ETL processor 内，而在 `syncSearchIndex`（调 `indexReadyChunks`）。
- 【可能追问】清理失败继续走会不会留脏数据？——可能留旧 chunk，但后面"先删后插"覆盖同名数据；这是容忍层级：清理失败可容忍，落库重复不可容忍。

**Q7. ingestDocument 上的 @Transactional 覆盖了什么？多轮重试呢？**
- 【考点】Spring Retry 与事务的交互。
- 【答案要点】@Retryable 生成的代理在外层，每次重试都是一次完整的方法调用，每次调用有自己的事务边界——第 N 次重试从干净状态开始，前一次失败的事务已回滚。这和"先清理后重建"配合：任何一次执行都是自包含的。注意 `markJobSucceededQuietly` 在同一事务内，它自己失败被吞不会回滚主流程（记录表失败可容忍）。
- 【可能追问】@EnableRetry 在哪开的？——`ArgusBackendApplication` 上，同文件还有 @EnableAsync、@EnableScheduling、@MapperScan。

**Q8. recover 里的失败原因为什么要截断？**
- 【考点】字段边界防御。
- 【答案要点】`FAILURE_REASON_MAX_LENGTH = 512`，`truncateFailureReason` 超长截断、空值回退"文档处理失败"。数据库列长度有限，异常消息（尤其 SQL 异常）可能极长，直接写入会 `value too long` ——兜底方法自己再抛异常就把 FAILED 标记也搞失败了。队列侧 `last_error_code/message` 的 64/512 截断同理。
- 【可能追问】还有哪里做了同样的事？——`QueueHealthIndicator` 干脆不回传异常消息，只报 "queue probe failed"（安全考虑，见第七节 Q4）。

**Q9. workerId() 方法生成的是什么？和队列的 workerId 什么关系？**
- 【考点】两个 worker 标识的区分。
- 【答案要点】`DocumentIngestionAsyncService.workerId()` = 线程名 + `@` + identityHashCode 十六进制，写给 `ingestion_jobs` 观测表，便于排查"哪个线程执行了这次摄入"。它和 `background_job.lease_owner`（worker-xxxxxxxx）**不是同一个东西**：前者是业务观测层，后者是队列租约层。
- 【可能追问】为什么不统一？——分层职责不同：队列层只需要"谁持有租约"，观测层要能定位到具体线程实例。

**Q10. 一分钟讲完你们的异步链路（收尾题）**
- 【考点】全局表达。
- 【答案要点】逐字稿："上传接口只做三件事：存文件、建文档记录、同事务入队，秒回。后台 Worker 用 SKIP LOCKED 从任务表原子认领，执行 ETL——先清理旧产物再解析分块再向量化再同步 ES，保证可重跑的幂等。业务性失败由 Spring Retry 2/4/8 秒退避后兜底置 FAILED，用户可见可重试；系统级失败由队列 1/5/15 分钟退避接管，三次耗尽进死信等人工。Worker 崩溃由 5 分钟租约兜底，其他实例自动接管。监控看三条线：READY 率、死信数量、最久等待时间。"
- 【可能追问】任何一个词深挖都接得住：入队=`finalizeUploaded`，认领=`claimDueJobs`，幂等=`cleanupProcessingArtifacts`，退避死信=`failOrRetry`，租约=`lease_until`。

## 四、StaleProcessingDocumentRecoveryRunner.java —— 启动恢复

**Q1. 这个 Runner 解决什么问题？**
- 【考点】中断恢复、ApplicationRunner。
- 【答案要点】服务异常中断时，正在处理的文档会永远卡在 PROCESSING，前端一直"处理中"。它实现 `ApplicationRunner`，启动完成后批量把遗留 PROCESSING 文档置 FAILED：`markStaleProcessingDocumentsFailed(PROCESSING, FAILED, "文档处理任务因服务中断未完成，请重试。", null, now)`。这是"自动恢复代替人肉重启"的设计。
- 【可能追问】为什么用 ApplicationRunner 而不是 @PostConstruct？——Runner 在应用完全启动后跑，此时数据源等基础设施就绪；@PostConstruct 在 Bean 初始化期执行，依赖可能未装配完。

**Q2. 它会把任务重新入队吗？（诚实边界题）**
- 【考点】与教材口径冲突时的以代码为准。
- 【答案要点】**不会重新入队**——只批量置 FAILED，靠用户手动重试（`retry-ingestion` 端点）。部分旧材料（零基础教材 7.3）写"自动重入队"，与当前代码不符，以 PROJECT_TRUTH 和代码为准：不区分中断时间、不重新入队。Runner 自己的 Javadoc 补了一个兜底：遗留任务若仍在队列中，Worker 租约到期接管执行完成后会把文档改回 READY。
- 【可能追问】为什么不直接重入队？——中断原因未知（代码 bug 还是资源不足），盲目重入队可能风暴；置 FAILED 把决策权交给用户，语义可控。

**Q3. 有没有时间窗？staleBefore 参数是干什么的？**
- 【考点】XML 条件与"从未生效的配置"。
- 【答案要点】`markStaleProcessingDocumentsFailed` 的 XML 带 `<if test="staleBefore != null"> and updated_at < #{staleBefore}</if>` 条件，但 Runner **传 null**——即不设时间窗，全量回收。此前注释声称的 `document.ingestion.processing-timeout-minutes` 时间窗从未生效，PROJECT_TRUTH 明确说不要引用。当前取舍：重启窗口内正在执行的任务极少，全量回收+用户可重试比复杂的时间窗判断更简单可靠。
- 【可能追问】会不会误伤"重启瞬间还在正常跑的任务"？——重启意味着本进程任务全断了；另一个实例的 Worker 若持有租约仍会跑完并把状态改回 READY，存在短暂的 FAILED→READY 抖动，可接受。

**Q4. 事务和幂等怎么考虑？**
- 【考点】单条 UPDATE 的原子性。
- 【答案要点】`run` 方法标了 @Transactional，一条批量 UPDATE 天然原子：影响行数就是回收数，>0 打 warn 日志"启动回收遗留处理中文档: recoveredCount=N"，=0 打 info"无需回收"。重复启动幂等：第一次跑完后没有 PROCESSING 文档，第二次影响 0 行。
- 【可能追问】多实例同时启动会怎样？——同一批量 UPDATE 语义幂等，双方各自影响部分或全部行，最终一致；行级锁保证不产生脏写。

**Q5. 这和队列的租约接管是不是重复了？**
- 【考点】两层恢复的分工。
- 【答案要点】不重复，分工不同：租约接管救**任务**（RUNNING 且租约过期的 background_job 被其他 Worker 领走重跑）；这个 Runner 救**文档状态**（任务表没记录或任务已终态但文档卡 PROCESSING 的不一致窗口）。两者叠加覆盖"进程死亡"的各种时序。
- 【可能追问】为什么文档会卡 PROCESSING 而任务表没有对应运行中任务？——手动重试入口先重置文档为 PROCESSING 再入队，中间崩溃就会出现这种窗口。

**Q6. 为什么失败原因写死一句通用文案？**
- 【考点】用户体验与可操作性。
- 【答案要点】`DEFAULT_FAILURE_REASON = "文档处理任务因服务中断未完成，请重试。"`——服务中断时拿不到单文档的真实异常，通用文案+明确的行动指引（请重试）比空白或技术堆栈对用户更友好；技术细节留给日志。同类设计：死信任务的 `last_error_message` 才存真实错误，给人工看。
- 【可能追问】用户点重试后走什么链路？——`retryFailedDocumentIngestion`：校验仅 FAILED 可重试 → 重置 PROCESSING → 以时间戳代数的新幂等键入队，队列机制完整接管。

**Q7. 如果重启发生在 Worker 正在执行 ETL 的中间呢？**
- 【考点】组合故障时序推演。
- 【答案要点】三步推演：① 进程死亡，ETL 中断，chunk/向量可能写了一半；② 任务还在 RUNNING 且租约未过期——5 分钟后其他实例（或重启后的本实例）的 `selectDueJobs` 第二支认领，attempt_count+1 重跑；③ ETL 开头 `cleanupProcessingArtifacts` 清掉半成品，重跑到 READY。若任务已耗尽尝试，进死信；文档侧由本 Runner 置 FAILED。**每一层都有对应的恢复动作，这就是纵深**。
- 【可能追问】重启后的本实例什么时候开始接管？——`poll-initial-delay-ms` 默认 20 秒后开始轮询。

## 五、ProductionConfigGuard.java —— 生产配置守卫

**Q1. 这个类解决什么问题？**
- 【考点】fail-fast 配置校验。
- 【答案要点】生产 profile 启动前对关键凭据做 fail-fast 校验。没有它，缺失的环境变量要等到对应 Bean（数据源、MinIO 客户端）创建时才以 "Could not resolve placeholder" 失败，报错晚且难定位；空串、示例值（changeme/minioadmin）则根本不会失败，直接以弱凭据上线。守卫把所有问题**一次列全**并给可操作提示，抛 `IllegalStateException` 阻止启动。
- 【可能追问】为什么是"一次列全"？——`resolveQuietly` 把占位符解析异常转成"缺失"问题统一收集，避免被 Spring 默认占位符异常打断、一次只暴露一个错误。

**Q2. EnvironmentPostProcessor 的执行时机是什么？为什么选它？**
- 【考点】Spring Boot 启动生命周期。
- 【答案要点】它在 `SpringApplication.prepareEnvironment` 阶段执行——**早于上下文刷新、早于任何 Bean 创建**。本类标 `@Order(Ordered.LOWEST_PRECEDENCE)`，时序上晚于 ConfigData 环境后处理，所以 profile 解析、.env 导入都已完成，读到的是**最终生效值**。校验必须在这个时机：进到 Bean 层就太晚，报错散落在各处堆栈里。
- 【可能追问】它比 @PostConstruct、ApplicationRunner 早多少？——PostConstruct 在 Bean 初始化期，Runner 在启动完成后，都在"上下文刷新之后"；EnvironmentPostProcessor 是唯一能在这之前拦截的常规扩展点。

**Q3. 怎么注册的？能用 @Component 吗？**
- 【考点】SPI 注册机制。
- 【答案要点】注册在 `META-INF/spring.factories`：`org.springframework.boot.env.EnvironmentPostProcessor=com.argus.rag.config.ProductionConfigGuard`。不能用 @Component——它执行时 Spring 上下文还没创建，容器扫不到也不会调用它；必须走 spring.factories SPI 让 SpringApplication 在启动最早期实例化。也因此**类里不能注入任何 Bean**，只能操作 `ConfigurableEnvironment`。
- 【可能追问】Spring Boot 2.7+ 有没有新注册方式？——有 `META-INF/spring/org.springframework.boot.env.EnvironmentPostProcessor.imports`，本项目用的是经典 spring.factories（待验证是否两者皆可，当前代码只有前者）。

**Q4. 校验哪些键？防哪些值？**
- 【考点】REQUIRED_KEYS / REJECTED_VALUES 常量。
- 【答案要点】`REQUIRED_KEYS` 共 9 个：`spring.datasource.url/username/password`、`spring.ai.openai.api-key`、`storage.minio.endpoint/access-key/secret-key`、`argus.rag.auth.jwt-secret`、`elasticsearch.host`——与 application-prod.yml 的环境变量占位符一一对应。`REJECTED_VALUES` 拒绝 9 个示例/默认值：changeme、changeit、password、admin123、minioadmin、local-dev、your-access-key、your-secret-key、your-password（trim + 转小写比较）。命中即进问题清单。
- 【可能追问】为什么 reject 列表要枚举？——弱口令不会报错，只有显式黑名单能拦住"照着 README 原样上线"的事故。

**Q5. JWT 密钥为什么单独校验长度 32？**
- 【考点】HS256 密钥强度。
- 【答案要点】`MIN_JWT_SECRET_LENGTH = 32`：HS256 要求密钥 ≥256 位（32 字节）。jjwt 对过短密钥要到**签发时**才抛 `WeakKeyException`，那时已是运行期，更难排查——提前到启动期拦截。这项校验独立于 REJECTED_VALUES，只要非空且 <32 字符就报"长度不足 32 字符（HS256 需要 ≥256 位密钥）"。
- 【可能追问】为什么不在校验里强拒空值之外再查熵？——当前边界：只查长度和黑名单，熵检测（如重复字符）是可讨论的增强项。

**Q6. 只在什么条件下生效？**
- 【考点】profile 守卫。
- 【答案要点】`postProcessEnvironment` 第一行检查 `environment.getActiveProfiles()` 不含 "prod" 直接 return——开发/本地/测试完全不受影响。这是"守卫不添乱"的设计：严格性跟着环境走，prod 必填必强，dev 允许默认值。
- 【可能追问】如果生产误用 dev profile 启动呢？——守卫不生效，这是它的边界；缓解手段是部署脚本固化 `--spring.profiles.active=prod`（部署文档约定）。

**Q7. resolveQuietly 为什么要 try-catch？**
- 【考点】占位符解析异常处理。
- 【答案要点】`environment.getProperty(key)` 在占位符无法解析（prod yml 引用了不存在的环境变量）时抛 `IllegalArgumentException`，不处理的话 Spring 默认行为会在这里直接打断——一次只能看到一个错误。捕获后返回 null，当作"缺失"进清单，最终一次性列出全部问题。
- 【可能追问】吞异常会不会掩盖别的错误？——只捕获 `IllegalArgumentException` 这一种明确对应占位符失败的类型，不是宽泛 catch (Exception)。

**Q8. 这道守卫和凭据卫生审计是什么关系？**
- 【考点】安全工程语境。
- 【答案要点】它来自 P0-1 凭据卫生专项（`docs/operations/credential-hygiene-audit.md`）：审计发现 dev 默认口令曾入库，落地三件事——prod fail-fast 守卫、`.gitignore` 补 `backend/upload/`、确认 `application-local.yml` 从未入库。守卫是"制度变成代码"：**生产密钥只能来自环境变量**是硬约束，守卫负责在门口执行。
- 【可能追问】密钥轮换做了吗？——诚实答：轮换步骤已写入审计文档，等用户手工执行（PROJECT_TRUTH 记录），我不能声称已完成。

**Q9. 为什么不在 yml 里写默认值让它"能启动"？**
- 【考点】安全默认 vs 可用性取舍。
- 【答案要点】生产配置的哲学是 fail-closed：缺配置宁可拒绝启动，也不能带弱凭据或连错环境悄悄运行。这个类的存在本身就是把"配置错误"从运行期事故前移到部署期拦截——启动失败是最便宜的失败。和权限侧的 fail-closed（`DocumentRoleGate` 拒绝时返回空集）是同一条原则在两个维度的应用。
- 【可能追问】测试环境怎么绕过？——profile 判断天然绕过；单测直接 new ProductionConfigGuard 传入 mock Environment 验证 9 键与黑名单逻辑（`ProductionConfigGuard` 相关测试存在于 1634 全量中）。

## 六、AppThreadPoolConfig.java —— 线程池收口

**Q1. 为什么要自定义线程池？默认的不好吗？**
- 【考点】线程池治理动机。
- 【答案要点】此前 @Async、@Scheduled、`CompletableFuture.runAsync`、parallelStream 都落在 Spring 默认执行器或 JVM 公共 ForkJoinPool 上：队列无界、无拒绝策略、与业务争抢公共线程。`AppThreadPoolConfig` 收口后做到三点：线程名可辨识（`argus-*` 前缀，日志/线程转储可直接归因）；队列有界 + CallerRuns 拒绝策略（不丢任务，背压交回调用线程）；按用途隔离四类池，互不饿死。
- 【可能追问】为什么不用 `Executors.newFixedThreadPool`？——队列无界，任务堆积 OOM；《阿里 Java 开发手册》强制手动 new ThreadPoolExecutor。

**Q2. 项目里有哪些池？参数分别是什么？**
- 【考点】四个池的画像。
- 【答案要点】① `taskExecutor`：`ThreadPoolTaskExecutor` 4/8/200，前缀 `argus-async-`，通用异步（文档 ETL 执行、长期记忆抽取、LLM 用量采集），命名沿用 Spring 约定让 @Async 默认解析到它；② `excelExportExecutor`：原生 `ThreadPoolExecutor(2, 4, 60s, ArrayBlockingQueue(100), CallerRunsPolicy)`，前缀 `argus-export-`，`destroyMethod = "shutdown"`；③ `retrievalExecutor`：4/8/64，`argus-retrieval-`，仅并行 You.com 网页搜索子查询（向量+ES 双路召回是顺序执行）；④ `taskScheduler`：poolSize 2，`argus-sched-`，定时任务调度。
- 【可能追问】导出为什么是独立原生池而不是 ThreadPoolTaskExecutor？——导出服务按 taskId 持有 `Future`，取消时 `cancel(true)` 能真正中断写盘线程；ExecutorService 形态更直接。

**Q3. 七个核心参数在你代码里怎么落的？（对应八股 Q14）**
- 【考点】参数与执行流程的落地。
- 【答案要点】`buildExecutor(coreSize, maxSize, queueCapacity, prefix)` 统一构造：核心 4、最大 8、队列 200/64（ArrayBlockingQueue 语义）、默认空闲存活、线程工厂（`namedThreadFactory`：AtomicInteger 序号 + 非 daemon）、拒绝策略 CallerRuns。执行流程：核心没满开核心→满了进队列→队列满开到最大→再满触发 CallerRuns（调用者自己跑）。所有池 `setWaitForTasksToCompleteOnShutdown(true)` + `awaitTerminationSeconds(20)` 优雅停机。
- 【可能追问】CallerRuns 在这里意味着什么？——不丢用户任务：导出请求太多时宁可提交线程自己慢慢算；对 ETL Worker 派发则意味着轮询线程被拖慢，形成天然背压。

**Q4. 导出池为什么用有界队列 + CallerRuns 而不是 Abort？**
- 【考点】拒绝策略取舍。
- 【答案要点】Abort 会抛 `RejectedExecutionException` 让用户请求失败；Discard 静默丢任务更不可接受。CallerRuns 保证**任务不会被队列满静默丢弃**，代价是提交线程被占用——对导出这种可延迟操作是正确取舍。队列 100 是防内存失控的上界：导出涉及 POI 大对象，无界队列等于 OOM 隐患。
- 【可能追问】线程数为什么是 2/4？——导出重 IO+内存，2 常驻够用，4 上限防并发导出挤爆堆；500 人规模不会同时来几十个导出。

**Q5. taskScheduler 为什么 poolSize 只有 2？**
- 【考点】调度器容量规划。
- 【答案要点】定时任务就几个：JobQueueMetrics 30 秒刷新、队列轮询 15 秒、快照/导出清扫，都是轻任务；2 线程足够且**避免并发快照互相覆盖**。`setRemoveOnCancelPolicy(true)` 及时清理取消的任务防队列积压。
- 【可能追问】调度任务堆积了怎么办？——fixedDelay 串行化天然限流；真堆积说明任务本身过重，应该挪去队列而不是加调度线程。

**Q6. 为什么检索池（retrievalExecutor）的队列只有 64？**
- 【考点】参数与任务画像匹配。
- 【答案要点】检索并行通道的任务短小（毫秒级网页搜索子查询），64 的有界队列足以吸收突发；CallerRuns 兜底把超量任务退回请求线程同步执行，用户只是慢一点而不是失败。它存在的意义是**替代 ForkJoinPool.commonPool**——公共池被占满会拖累 parallelStream 等无关功能。
- 【可能追问】向量+ES 双路召回为什么不用它并行？——当前代码是顺序执行，retrievalExecutor 只服务网页搜索子查询；这是 PROJECT_TRUTH 核实过的事实，别说成"双路并行"。

**Q7. 优雅停机怎么做的？**
- 【考点】停机参数。
- 【答案要点】三个池统一 `setWaitForTasksToCompleteOnShutdown(true)` + `setAwaitTerminationSeconds(20)`：关闭时不再接新任务，最多等 20 秒让在跑任务完成。excelExportExecutor 是原生池，靠 `@Bean(destroyMethod = "shutdown")` 由 Spring 容器回调关闭。停机后未完成任务不丢：ETL 任务靠租约到期被其他实例接管，配合幂等重跑。
- 【可能追问】20 秒还没跑完呢？——强关；队列里任务状态还是 RUNNING，租约过期后被接管重跑，不会丢。

**Q8. 线程工厂为什么要自定义？**
- 【考点】namedThreadFactory 细节。
- 【答案要点】`prefix + AtomicInteger 自增序号`（如 `argus-export-1`），非 daemon 线程。价值：日志和线程转储（jstack）能直接定位具体池与实例，排查问题不用猜"这个线程属于谁"。非 daemon 保证优雅停机时任务有机会跑完。
- 【可能追问】ThreadPoolTaskExecutor 的前缀参数不就够了吗？——对它够；自定义工厂是为原生 `ThreadPoolExecutor`（excelExportExecutor）补上同样的可辨识性。

**Q9. 按负载画像分池的思想是什么？（对应 09 篇）**
- 【考点】隔离设计。
- 【答案要点】导出重（IO+内存，分钟级）、检索轻（毫秒级）、ETL 中（秒到分钟级）。混在一个"大池子"里，一次 10 个导出能把检索饿死，全站问答跟着卡。**按负载画像分池是线程池设计的核心思想**，和部署层"Worker 与 API 分开部署"（资源画像不同的负载分开部署）同源。
- 【可能追问】池之间会互相影响吗？——会通过下游（数据库连接池、ES）间接影响；池隔离只解决 CPU/内存与排队层面的互相饥饿，不解决下游容量问题。

## 七、JobQueueMetrics.java + QueueHealthIndicator.java —— 可观测与健康

**Q1. 队列暴露了哪些指标？怎么实现的？**
- 【考点】Micrometer Gauge。
- 【答案要点】`JobQueueMetrics` 注册 4 个 Gauge：`argus.job.queued`、`argus.job.running`、`argus.job.dead_letter`、`argus.job.oldest_wait_seconds`。实现是 `double[4] snapshot` 数组 + 定时刷新：`@Scheduled(fixedDelayString = "${argus.job.metrics-refresh-ms:30000}")` 每 30 秒查一次各状态计数，Gauge 的 valueFunction 读数组。Prometheus 抓取后可直接配告警。
- 【可能追问】为什么定时快照而不是 Gauge 里实时查询？——Gauge 回调在抓取时执行，放 SQL 会让 scrape 延迟不可控；30 秒快照对告警足够，写少读多。

**Q2. oldest_wait_seconds 怎么算的？有什么细节？**
- 【考点】"最久等待"的语义。
- 【答案要点】`selectOne(status=QUEUED, orderByAsc("next_run_at"), last("LIMIT 1"))` 取最老的排队任务，`Math.max(0, Duration.between(nextRunAt, now).getSeconds())`。细节：分母用的是 `next_run_at` 不是 `created_at`——衡量的是"**已逾期多久**"而非"总年龄"，处于退避期（next_run_at 在未来）的任务会被 clamp 成 0，不会因为正常退避误报积压。告警口径：最久等待 > 15 分钟。
- 【可能追问】为什么说它比积压总数更能代表用户痛苦？——排队 1000 个但都在秒级消费完是健康的；只有 1 个任务等了 20 分钟才是真事故。

**Q3. 健康检查里有什么？自定义探针查什么？**
- 【考点】QueueHealthIndicator 设计。
- 【答案要点】`@Component("queue")` 实现 Spring Boot Actuator 的 `HealthIndicator`，暴露在 `/actuator/health` 的 queue 分组。逻辑：`deadLetterJobs > 0` 或 `pendingOutboxEvents > outboxBacklogThreshold`（`argus.health.outbox-backlog-threshold` 默认 1000）即 `Health.down()`；详情只带三个计数和阈值。含义：**业务探针**——数据库连着不代表系统正常，死信堆积或协同 Outbox 积压时数据库健在但业务已经不健康。
- 【可能追问】"五组件健康检查"的口径？——诚实答：代码里自定义探针只有 queue 这一个；数据库、Elasticsearch 等由 Spring Boot Actuator 自动配置探活，另有 prod 的 k8s liveness/readiness probes（application-prod.yml）。"五组件"是简历汇总口径，面试时按"自动探针 + 业务探针"分层讲，不编造具体五个自定义类。

**Q4. 健康检查失败时为什么只报 "queue probe failed"？**
- 【考点】信息脱敏。
- 【答案要点】健康接口匿名可访问，异常消息可能携带 SQL 片段、连接串、表名。所以 catch 后 `Health.down().withDetail("error", "queue probe failed")`，**不带异常消息和堆栈**——只报告降级事实，细节进服务端日志。这是 `security-baseline.md` 的硬约束："异常消息进健康检查前先脱敏"。
- 【可能追问】运维怎么排障？——先看 DOWN 事实，再上服务器查日志拿真实异常；健康端点面向"快速分诊"，不面向"根因分析"。

**Q5. 指标刷新失败会怎样？**
- 【考点】可观测组件自身的容错。
- 【答案要点】`refresh()` 整体 try-catch，失败 `log.warn("任务队列指标刷新失败...")`，snapshot 保持上一次的值。Gauge 读数组无需额外同步（单线程 @Scheduled 写）。指标系统的原则：**观测自身不能成为新的故障源**，宁可短暂展示旧值。
- 【可能追问】旧值会不会误导告警？——30 秒窗口内可接受；更严谨可以给 snapshot 加时间戳健康度，当前未做（诚实边界）。

**Q6. Prometheus 还暴露什么？端点怎么配的？**
- 【考点】Actuator 暴露面。
- 【答案要点】`management.endpoints.web.exposure.include: health,info,prometheus`——只开三个端点，shutdown 等危险端点默认关闭。`/actuator/prometheus` 供 Prometheus 抓取，配合 `AdminMetricsController`（业务侧 LLM 用量）形成"系统指标 + 业务指标"两层。
- 【可能追问】健康端点要鉴权吗？——当前匿名可访问（内网部署前提），所以才有 Q4 的信息脱敏设计；公网部署需要收紧（待验证：SecurityConfig 对 actuator 的具体放行规则）。

**Q7. 死信告警的完整链路是什么？**
- 【考点】从症状到行动。
- 【答案要点】三层信号互相印证：① `argus.job.dead_letter` Gauge 突增（Prometheus 告警）；② `/actuator/health` 的 queue 分组 DOWN（`deadLetterJobs > 0` 即降级）；③ 排查入口是表本身——`SELECT * FROM background_job WHERE status='DEAD_LETTER'` 看 `last_error_code/message/attempt_count`。死信代表"自动恢复失败了"，是**该人工介入的症状**，所以阈值设 0。
- 【可能追问】为什么死信阈值是 0 而 Outbox 是 1000？——死信意味着某任务彻底失败需要人看，一个就该报；Outbox 积压有协同广播重发机制自愈，1000 以内算正常波动。

**Q8. Outbox 积压和队列积压为什么要放进同一个探针？**
- 【考点】业务探针的聚合口径。
- 【答案要点】两者都是"异步链路不健康"的症状，运维视角希望一个健康端点回答"系统正常吗"。`QueueHealthIndicator` 同时注入 `BackgroundJobMapper` 和 `ExcelCollabOutboxMapper`，任一超阈即整体 DOWN，避免运维漏看另一半。分开的话 DOWN 语义会被稀释。
- 【可能追问】会不会互相掩盖？——详情里两个计数都带，DOWN 时能立刻区分是哪一半出的问题；聚合的是"判定"，不是"信息"。

## 八、metrics 包 —— LLM 成本观测落库

**Q1. LLM 用量观测的链路是什么？**
- 【考点】采集-计算-存储-展示四段。
- 【答案要点】问答、助手等所有 LLM 调用方（`QaService`、`AssistantService`）在调用完成后组装 `LlmUsageRecordDTO` 调 `LlmUsageCollector.record`；`LlmCostCalculatorImpl` 按"每千 token 单价"算 `costAmount`；`LlmUsageCollectorImpl` 异步写入 `llm_usage_records` 表；`LlmUsageStatisticsService` 聚合，`AdminMetricsController`（`/api/admin/metrics/**`）暴露概览/平台/用户/群组四级统计。
- 【可能追问】为什么落库而不是只进 Prometheus？——成本要按用户/群组/模型多维出账单和排行，还要留 `isEstimated`、错误信息等明细维度，表比时序库合适。

**Q2. record 为什么标 @Async 还要套 try-catch？**
- 【考点】双层防御。
- 【答案要点】@Async 让调用方立刻返回、写库在别的线程（走 `taskExecutor` 池）；内层再 try-catch 全部异常只 `log.error`。原则：**统计、审计这类"锦上添花"的操作，决不能让业务主流程为它买单**——用户的答案已经到手，记账失败不能作答回答，也不能炸掉异步线程的调用方。@Async 的异常默认进 AsyncUncaughtExceptionHandler 不会传回调用方，但显式 catch 能保证日志确定落地。
- 【可能追问】@Async 的开关在哪？——`ArgusBackendApplication` 的 @EnableAsync；默认解析到 `taskExecutor` Bean。

**Q3. 成本怎么算的？单价哪来的？**
- 【考点】LlmCostCalculatorImpl。
- 【答案要点】`modelPricing` 是 `ConcurrentHashMap<String, BigDecimal[]>`，存每千 token 的 [输入价, 输出价]（元）：qwen-plus 0.0008/0.002、qwen-turbo 0.0003/0.0006、qwen-max 0.002/0.006；未登记模型回退默认 0.0008/0.002。计算用 BigDecimal：`价格 × token数 ÷ 1000`，`divide(THOUSAND, 6, RoundingMode.HALF_UP)`，输入输出相加。
- 【可能追问】为什么用 BigDecimal 不用 double？——金额必须精确，double 的二进制浮点误差在累加后不可接受；这也是财务模块的同款选择。

**Q4. llm_usage_records 存了哪些字段？**
- 【考点】表结构即观测维度。
- 【答案要点】`LlmUsageRecordEntity`（@TableName("llm_usage_records")）：userId、groupId、module、endpoint、sessionId、promptTokens、completionTokens、totalTokens、isEstimated、costAmount、costCurrency（实现里写死 "CNY"）、latencyMs、success、errorMessage、modelName、createdAt。一次调用一条明细，支持按人/群组/模块/时间聚合。
- 【可能追问】isEstimated 是什么场景？——部分模型的 token 数是估算而非 API 返回时标记，出账时区分精确值与估算值（诚实边界：估算的具体来源逻辑在 llm 模块，我没逐行核实）。

**Q5. 统计接口怎么分权？**
- 【考点】财务级数据的访问控制。
- 【答案要点】`AdminMetricsController` 每个端点（overview/platform/user/{userId}/group/{groupId}）都先 `currentUserService.requireSystemAdmin()`——用量即成本数据，等同财务敏感数据，只给系统管理员；类上还有 `@OperationLog` 记录操作日志。`StatsPeriod` 枚举（TODAY、LAST_30_DAYS 等）统一时间窗口径。
- 【可能追问】普通用户能看自己的用量吗？——当前这些端点全部要求系统管理员；用户级自查是产品上可加的能力，但不在当前代码事实里。

**Q6. 统计是怎么聚合的？**
- 【考点】LlmUsageStatisticsService。
- 【答案要点】用户/群组/平台三级统计都是同一个 Mapper 方法 `selectUsageStats(userId, groupId, period.getStartTime())`，传 null 表示不限该维度；`getOverview` 组合"今日统计（请求数/token/成本/成功率）+ 30 天每日趋势（selectDailyTrend）"。聚合在 SQL 层做（GROUP BY），不在 Java 内存里算。
- 【可能追问】数据量大了怎么办？——当前量级（500 人规模）单表聚合够用；演进方向是预聚合表或按月分表，明细表保留原始记录。

**Q7. 采集失败对用户可见吗？**
- 【考点】失败爆炸半径。
- 【答案要点】不可见：record 内部吞掉，用户拿到的回答不受影响。代价是统计可能少记——**这和"Quietly 三兄弟"是同一条划线**：观察窗口失败是监控盲区，业务事实（问答记录 qa_records）失败才必须抛。QaService 里记账和落库是两条独立链路。
- 【可能追问】怎么发现少记了？——异步线程的 log.error 有日志告警；更主动的做法是对账（qa_records 数 vs llm_usage_records 数），当前未自动化（诚实边界）。

**Q8. 这套观测对面试有什么"值夜班"叙事？**
- 【考点】可观测意识的表达。
- 【答案要点】逐字稿："成本、成功率、延迟是我最关心的三条业务线，所以我把它做成了每次调用强制记账：token 和成本按用户/群组/模型落库可出账单，成功率异常说明上游模型故障，延迟异常说明要切模型或降级。加上队列的四个 Gauge 和健康探针，值班要看的东西都内建在系统里，而不是等用户投诉才发现。"
- 【可能追问】token 数怎么拿到的？——来自 LLM 响应的 usage 字段，流式场景部分是估算（isEstimated 标记）；具体提取代码在 llm 模块（待验证细节）。

## 九、RerankingConfiguration + RemoteHttpRerankingService —— 条件装配与降级

**Q1. Reranker 是怎么装配的？**
- 【考点】@ConditionalOnProperty / @ConditionalOnMissingBean。
- 【答案要点】`RerankingConfiguration` 两档：`argus.rag.reranking.provider=remote` 时创建 `RemoteHttpRerankingService`（base-url 默认 `http://127.0.0.1:11435`、model 默认 `BAAI/bge-reranker-base`、timeout-ms 默认 8000）；未配置或缺 bean 时 `@ConditionalOnMissingBean(RerankingService.class)` 兜底 `RerankingService.NoOp` 原序放行。remote bean 声明在 NoOp 之前，@ConditionalOnMissingBean 据此让位。**链路永不因缺模型中断**是第一约束。
- 【可能追问】为什么默认 NoOp？——上线前必须先完成离线对比评测（HitRate/MRR/延迟）；默认关是对"未验证的增益"保持保守。

**Q2. 远程重排的降级策略具体是什么？**
- 【考点】降级是第一设计约束。
- 【答案要点】`RemoteHttpRerankingService.rerank` 自身**永不抛出**：HTTP 非 200、响应长度不符、索引非法（越界/重复，用 `boolean[] seen` 查重）、超时、任何异常，一律走 `fallback(candidates)`——保序分数 `1.0 - i * 0.001`，与 NoOp 同口径，链路继续用 RRF 原序，只是不享受重排增益。管线侧 `HybridChunkRetrievalService.applyReranking` 还有第二道 try-catch，双重保险。
- 【可能追问】为什么 fallback 要给递减分数而不是原样返回？——统一返回类型（RerankResult 带 score），下游排序逻辑不用区分"真重排"和"降级"两种形态。

**Q3. 响应校验为什么这么严？**
- 【考点】防御外部依赖的脏响应。
- 【答案要点】三重校验：results 必须是数组且 `size == candidates.size()`；每个 `index` 必须在 [0, size) 且未出现过（seen 数组防重复索引）；分数用 `asDouble` 容错。任何一项不过直接整体降级而不是部分采纳——**部分采纳的排序是错的还更难排查**，不如整体回退到已知正确的 RRF 原序。
- 【可能追问】超时设多少？连接超时呢？——请求超时默认 8000ms（可配），HttpClient connectTimeout 3 秒；`Math.max(timeoutMs, 1)` 防止配 0 或负数。

**Q4. 这个设计和你其他组件的降级是同一个思想吗？**
- 【考点】跨模块归纳。
- 【答案要点】是：依赖不可用时"降级到已知安全路径，绝不把故障向上传播"。重排降级到 RRF 原序；查询规划失败回退 DIRECT；权限过滤 fail-closed 返回空集；LLM 记账失败只记日志。区别在方向：重排和规划是**功能降级**（答案质量降但可用），权限是**安全收口**（宁拒勿放）。方向由"这个依赖失败时的正确行为是什么"决定。
- 【可能追问】怎么验证降级真的生效？——2026-10-24 的故障演练验证了坏文件链路；重排降级可通过停掉网关进程观察日志里的"回退原始顺序" warn（待验证：未做专项演练记录）。

**Q5. remote 模式的成本模型是什么？**
- 【考点】与 ADR-004 的离线/零 API 费用原则一致。
- 【答案要点】重排网关是本地 Python 服务（chat-only-gateway.py，fastembed 的 BGE cross-encoder），JVM 外但同机部署，零 API 费用，和 JVM 内本地 embedding（bge-small-zh, 512 维 ONNX）同一成本哲学。实测 50 对约 3.47 秒，所以超时 8 秒是宽松上限，rerank 只对最终 topK 候选做（recallK=50 进重排）。
- 【可能追问】3.47 秒不是会成为瓶颈吗？——会，这是它默认关闭、先过离线评测的原因；优化方向是批量小模型或换更快的 cross-encoder（当前边界：未做压测调优）。

**Q6. 为什么重排配置用 Configuration 类而不是 @Value 注到 Service？**
- 【考点】装配模式选择。
- 【答案要点】因为存在"有/无 bean"两个分支：@ConditionalOnProperty 决定 remote bean 是否创建，@ConditionalOnMissingBean 决定默认实现——这是**类型层面的多态选择**，@Value 只能选参数不能选实现。把构造参数（base-url/model/timeout）通过 @Value 注入 @Bean 方法，配置和装配收敛在一个文件里可读性最好。
- 【可能追问】@ConditionalOnProperty 的 matchIfMissing 默认什么？——默认 false，即不配置就不创建 remote bean，正好落到 NoOp 兜底；语义上"默认保守"。

## 本包高危追问 Top5

**1. "你的队列保证 exactly-once 吗？任务被两个 Worker 同时执行了怎么办？"**
必考组合拳。答：不保证，是 at-least-once——租约过期接管、Worker 重试都可能双执行；防线是三处独立幂等：入队幂等（idempotency_key 唯一索引）、认领原子（条件更新 + SKIP LOCKED）、执行幂等（ETL 先清理后重建 + 确定性 UUID）。加一句"at-least-once 投递 + 幂等消费 = 效果上的 exactly-once"。若追问"complete 会不会被老 Worker 误写"：complete 带 `lease_owner` 守卫，接管后老 Worker 的 complete 影响 0 行；再追问到 `failOrRetry` 当前**没有**持有者守卫（updateById 按 id），极端接管时序下理论上可能覆盖新状态——如实承认并给改进方案（WHERE 加 lease_owner），这是本包最锋利的代码级细节。

**2. "坏文件重试耗尽会进死信吗？两层重试到底谁在生效？"**
2026-10-24 演练的核心结论：**两层重试互斥而非叠加**。`@Recover`（recover:149）吞异常正常返回 → Worker 调 complete → 队列任务 SUCCEEDED、文档 FAILED，实测坏 PDF 演练 `argus.job.dead_letter` 全程为 0。队列级 1/5/15 退避只对绕过 Spring Retry 的系统级异常生效。别背旧材料里"去掉业务层重试"的说法——当前代码 @Retryable 还在，以 PROJECT_TRUTH 和代码为准。

**3. "首次失败到底退避几分钟？1/5/15 是真的吗？"**
读码精度陷阱题。常量 `{1, 5, 15}`，公式 `backoffIndex = min(attemptCount, 2)`，但 claim 认领时已把 attempt_count 加到 1，所以**实际首次失败是 5 分钟档、第二次 15 分钟、第三次耗尽死信**，1 分钟档正常流程取不到；测试只断言 >4 分钟没钉死下标。如实说出这个错位 + 给出 `attempts - 1` 的修法，比背"1/5/15"高级得多。

**4. "EnvironmentPostProcessor 为什么不能用 @Component？它比 Bean 早在哪里？"**
机制题。它运行在 prepareEnvironment 阶段，早于上下文刷新和一切 Bean 创建——容器此时不存在，扫描不到它，必须 spring.factories SPI 注册（`org.springframework.boot.env.EnvironmentPostProcessor=com.argus.rag.config.ProductionConfigGuard`），类内也不能注入任何 Bean。@Order(LOWEST_PRECEDENCE) 保证晚于 ConfigData 处理，读到 profile 解析和 .env 导入后的最终值。9 个必填键 + 9 个拒绝值 + JWT ≥32 字符，问题一次列全，只在 prod profile 生效。

**5. "为什么用数据库表不用 MQ？什么时候必须换？"**
选型态度题。三理由：任务量级百级/天够不着 MQ 区间；任务与业务数据同库同事务（finalizeUploaded 里文档行和任务行一起提交/回滚），MQ 要靠 Outbox 迂回；表字段与 MQ 消息语义一一对应，迁移平滑。换的触发条件：日任务百万级或需要扇出广播；届时 SKIP LOCKED 语义翻译成消费者组+手动 ack+死信交换机。补充已知缺口显得更可信：Outbox selectPending 无认领语义，多 API 实例有消息丢失窗口，当前仅 Worker 可安全水平扩展。
