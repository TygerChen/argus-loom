CH 00导读：这份教程怎么用

这是一份为 argus-loom 项目本身 定制的源码学习教程。它做四件事：

  1. 先用一个通俗故事把整条链路讲成大白话（0.3 节"小王的一次提问"），不碰任何代码也能听懂整个系统在干什么；
  2. 给你一套学习方法（第 1 章，来自《AI 时代学习开源项目的正确姿势》），避免"逐行翻译源码"的假性掌握；
  3. 给你足够的 RAG 领域知识（第 2 章），让你能听懂代码里每个抽象"为什么存在"；
  4. 带你沿真实代码走完两条核心链路（第 4、5 章）：文档摄入 ETL 与混合检索问答——这是本项目 20% 的核心代码。
⚠️ 先泼一盆冷水
AI 把代码解释得越流畅，你越容易产生"我懂了"的错觉。检验标准只有一个：合上所有资料，你能不能白板画出问答链路并说清每个设计取舍。第 8 章的自测就是为此准备的。
😵 觉得难？你多半是读反了顺序
这份教程是两层写的：人话层（好懂，讲清"是什么、为什么"）和源码层（密集，讲清"在哪个类、怎么实现"）。第一遍你只需要走人话线：① 读 0.3 的故事（20 分钟）→ ② 第 2~7 章每章只读开头 💬 蓝框——那段本身就是完整的人话版，读完直接进下一章 → ③ 卡住的词去 0.4 黑话表查。走完这条线，"介绍你的项目"这个面试题你已经能答了。正文里的类名、行号、What-If，是第二遍对照 IDE 深挖、以及面试前复习才需要的。谁规定教程必须从第一页读到最后一页？

0.3 先听个故事：小王的一次提问 大白话版全程

代码先放一边。把整个系统想象成一家 AI 图书馆：你往里放书（上传文档），向一位"只照着书讲、绝不瞎编"的 AI 馆员提问。下面是小王完整走一遍的全过程——读懂这个故事，你就理解了这个项目 80% 在干什么；后面的章节只是把故事里每一步对应到真实代码。

第一幕：把一本书搬进图书馆（对应第 4 章 · ETL）

① 交书。小王把《员工手册 v3.docx》拖进网页。文件比较大，浏览器自动把它切成小块一批批寄给服务器（分片上传）；寄出前先算了个"文件指纹"（SHA-256），服务器一查：这本书已经有人交过了？直接挂"已收藏"的牌子（秒传），不用再传一遍。

② 登记入库。书本体锁进 MinIO 仓库，登记卡写进数据库，状态标成"加工中"。小王的网页立刻显示"上传成功"——他不用干等，因为加工是后厨悄悄做的（异步）。

③ 后厨加工（一条流水线干四件事）：

  • 拆字：把 Word/PDF 里的文字全部抽出来，丢掉乱码和多余空行（解析 + 清洗）；
  • 切卡片：把整本书切成一张张两三百字的"知识卡片"。切的时候很讲究——尽量在标题、段落处下刀，别把一句话切成两半；每张卡片还会和下一张重叠 64 个字，防止关键句刚好骑在缝上、谁都没捞着完整版（结构感知切片）；
  • 打语义指纹：给每张卡片算一串数字（向量 / Embedding），意思越近的卡片指纹越接近——这是"机器懂意思"的全部窍门；
  • 上两套书架：指纹放进 pgvector 指纹柜（按"意思"找），关键词放进 ES 索引柜（按"字面词"找）。齐活，状态改成"可借阅"（READY）。
📌 停一下，只需要记住三样东西
整条加工流水线的产出就三样：一张张知识卡片（切片）、每张卡片的语义指纹（向量）、每张卡片的关键词标签（ES 索引）。后面所有"高大上"的检索技术，本质上都是在更快更准地找到这些卡片。

第二幕：小王提问（对应第 5 章 · 问答九步）

第二天，小王在群里问了一句特别口语的话："年假没休完会作废吗？"

① 过安检。请求进店先查两件事：小王是这个知识库群组的成员吗？他一分钟内是不是问太多次了？——每次提问都要花真金白银的 token，得有限流。

② 查门票。馆里有些书架是财务专属，小王刷不开。系统直接把他看不到的书从候选里剔掉；如果连"能看到哪些书"的名单都拿不到，就当空手处理——宁可不给，不能给错（fail-closed 权限门槛）。

③ 馆员先想清楚怎么找。"年假没休完会作废吗"太口语，直接拿去搜容易扑空。AI 馆员先把它改写成文档里的书面语："未休年假 处理 顺延 作废"（查询规划）。如果一句话里塞了两个疑问（"能顺延吗？能折现吗？"），还会拆成两个小问题分别去找。

④ 两队人马同时出动。指纹队翻指纹柜，找"意思相近"的卡片；关键词队翻索引柜，找"字面匹配"的卡片。各带回 50 张候选（双通道混合检索）。为什么非要两队？——指纹队认得出"把钱拿回来"就是"退换"，却在 QYT-2000X 这种陌生型号前发懵；关键词队正相反。完整例子见 0.5 节。

⑤ 合并榜单。两队打的分数单位不同，没法直接比大小，那就只比名次：把两份榜单按名次合并，两边都点名的卡片最靠谱，打上"双料"标记（RRF 融合）。

⑥ 馆长终审。按设计，这里应该由一个更懂上下文的"重排模型"把最相关的卡片排到最前——但这个岗位现在坐着的还是个实习生（空实现 NoOp），只维持原顺序。插座留好了，灯泡随时能插（第 7 章实验一）。

⑦ 把卡片缝回原文。命中的卡片，前后再各带一张相邻卡片一起送审——免得答案的下半句恰好写在下一张卡里（邻居窗口扩展）。

⑧ 查货验货。这些卡片真的够回答吗？如果不够——比如馆里压根没有年假制度这本书——就直接回复"资料不足，无法回答"，一个字的 AI 都不请：不花钱，也绝不会瞎编（证据评估与拒答）。

⑨ 请 AI 老师作答。够回答，就把卡片摊在 AI 面前，规矩讲死："只能照卡片讲，不知道就说不知道。"老师逐字给出答案，网页上一个字一个字蹦出来（SSE 流式）；答案后面附上出处——哪份文件、哪几张卡片，点开能看到原文（引用溯源）。最后记台账：问了什么、答了什么、花了多少 token（落库）。

✅ 顺手自测一下
不看上文，你能说出"为什么第⑧步的拒答判断要放在请 AI 之前"吗？——因为 AI 一旦上场就要花钱，而且面对空资料它会硬编。能在代码层拦住的事，绝不交给模型自觉。

第三幕：升级版——会自己拿主意的 AI 助理（对应第 6 章 · Agent）

固定流水线很稳，但应付不了这种问题："帮我看看我这个月工资条对不对，顺便查下公司差旅报销标准。"它需要 AI 自己决定先干什么后干什么：先查工资数据（结构化查询工具）？先搜知识库（RAG）？还是上网搜（搜索工具）？这就是 Agent——给模型一个工具箱和决策权，让它像助理一样自己安排步骤。它还带两种笔记本：便签本（本次对话的上下文，聊完可丢）和员工档案（你明确让它记住的事，比如"我对花生过敏"，以后每次都会想起）。

0.5 三个最常问的"为什么"（先给答案，后文章节再展开）

为什么不直接把问题丢给大模型？——大模型没读过你公司的员工手册；就算读过，它训练截止之后的更新也不知道；而且它"不知道"的时候经常一本正经地编（幻觉）。RAG 的本质就四个字：开卷考试——先找到资料，让它照着答。

为什么不把整本文档直接塞给 AI，非要切卡片？——AI 一次能读的字数有限，而且按字数收费。整本塞进去又贵又慢，重点还被稀释。先粗筛卡片、再把少数几张交给 AI 细读，又快又省又准。

为什么两路一起找，一路不够吗？——系统里有两支搜索小队：指纹队按"意思"找（就是 0.3 节说的语义指纹），关键词队按"字面"找（一个字都不差才命中）。单派任何一队都会翻车，而且翻车方式正好相反：

  • 只派关键词队，输在"换了说法"。卡片上写的是"七天无理由退换"；小王问"东西买错了，想把钱拿回来"。意思一模一样，却没有一个相同的字——字面搜索当场扑空，什么也搜不出来。
  • 只派指纹队，输在"专有名词"。小王问"QYT-2000X 怎么退"。对一个只认"意思"的机器来说，陌生型号 QYT-2000X 和它的兄弟型号 QYT-1800S、QYT-3000 没什么两样——都是没有含义的代号，指纹几乎分不开，很可能把别的型号的退货说明排到前面，偏偏漏掉那一条。

反过来看，对方的强项正好补上：关键词队搜"QYT-2000X"一击即中；指纹队能认出"钱拿回来"和"退换"是同一件事。所以两队各查 50 张、合成一张大榜：你漏掉的盲区由对方补上，"一字不差"和"意思相近"一个都不丢。这也是企业级 RAG 公认的第一优先升级项（第 2 章展开）。

CH 01方法论：Architecture First, Code Second

⏭️ 第一遍可以跳过
本章讲"怎么学"，不是"项目是什么"——它治的是"假性掌握"，不解决"看不懂"。走人话线的读者请直接进第 2 章；等你开始第二遍对照源码读了再回来，那时它才有用。✅ 现在跳过是对的。

传统学法是"逐行读源码"。AI 时代这套失效了——AI 能帮你翻译任何一行代码，于是逐行阅读变成思维惰性的遮羞布。正确姿势是：先建立系统级理解，代码只是验证架构猜想的证据。

四个核心动作

🗺️
先系统，后代码

先搞清：解决什么问题 → 输入输出是什么 → 分几个模块 → 数据怎么流。然后只精读 20% 的核心代码。

🛤️
先主干，后边缘

沿 Happy Path（一切正常的理想路径）单向追踪，重试/降级/异常分支先跳过，主干通了再回头。

❓
追问"为什么存在"

对每个抽象做三问：它解决什么问题？不设计它会怎样？如果是我会怎么做？——问"写了什么"是低阶学习。

✍️
脱稿推演验证

终极检验：脱离源码，自己画出架构图和数据流，再与真实代码对比。差距就是没学会的部分。

SOP：核心链路追踪法 套用到本项目

步骤在本项目中的具体操作
1. Repository Survey
让 AI 做全景侦察		 问 AI："总结 argus-loom 的模块划分、技术栈、两条核心链路的入口和出口"。产出 = 第 3 章的模块地图。（本文档已完成这一步，你直接看结论即可）

5. 胶水代码交给 AI DTO、Mapper、配置类、日志——让 AI 一句话总结即可，不要消耗自己的注意力。

把 AI 变成"架构导师"

《AI 时代学习开源项目》给出了一个杀手级用法：让 AI 扮演面试官拷问你，或反过来——你先盲设计，再对比真实源码。针对本项目可以直接用这个 Prompt：

你现在是资深 RAG 系统架构师兼面试官。我正在学习 argus-loom
（一个 Spring AI Alibaba + pgvector + ES 的企业级知识库问答项目）。

规则：
1. 每次只问我一个问题，从检索链路的入口开始，逐层深入；
2. 我答完后：先指出答案里的错误或缺失，再给出你的参考答案（含设计权衡）；
3. 如果我连续两题答得好，升级问题难度到"设计决策"层面
   （例如：为什么 RRF 的 k 取 0？为什么拒答发生在调 LLM 之前？）；
4. 不要一次给我全部答案，逼我自己推理。

开始第一问：用户发来一次提问，从 HTTP 请求进来到返回答案，
这个系统内部大概分几个阶段？每个阶段的职责是什么？

提问层级模型 自检你处在哪层

层级问法本项目示例
L1 What这是什么？RRF 是什么？
L2 How它怎么工作的？RRF 怎么把两路检索结果合成一路？
L3 Why为什么需要它？为什么不能只靠向量检索，非要加 ES 关键词通道？
L4 Design为什么这样设计而非那样？RRF 公式里 k=0，业界常用 k=60，取舍是什么？

达到 L4 才算真正掌握。第 5 章的每个步骤卡都按 L1→L4 组织。

RAG 到底是个啥？一句话：让大模型开卷考试。直接问它你公司的事，它没读过你们的文档，要么说不知道、要么一本正经地编；RAG 的做法是——回答之前，先去文档库里把相关段落找出来，摊在它面前，让它照着答。
找资料这件事，技术上演进了三代：第一代（Naive）最笨，切块搜一下就拼给模型，口语化的问题和精确名词经常搜不准；第二代（Advanced）聪明了，查询先改写、两路检索互补、结果再重排、资料不够就拒答——本项目主要就是这一代；第三代（Modular）把检索变成 AI 可以自主调用的模块（第 6 章的 Agent 雏形）。
企业级系统还要加五个关键件：混合检索+RRF、重排、查询改写、拒答、效果评估——本章后面就是把这五样各讲一段，每张卡片都标了"本项目做了没有"。✅ 记住"开卷考试 + 五个关键件"，本章就可以翻篇了。

RAG 解决什么问题

大模型有三个致命伤：幻觉（一本正经编造）、知识截止（训练之后的事不知道）、私有知识盲区（你公司的文档它没见过）。微调贵且慢；RAG（Retrieval-Augmented Generation，检索增强生成）的思路是：回答之前，先从你的知识库里检索出相关片段，塞进 Prompt 让模型照着证据回答。知识更新=更新文档，不用动模型。

企业级 RAG 的五个关键件 对照记忆

① 混合检索 + RRF

稠密向量管语义泛化（"想把钱拿回来" ≈ "退换政策"，字不重合、意思相近），BM25/关键词管精确词面（QYT-2000X 这类型号、专有名词一搜一个准）。RRF 免调参地把两路排名融合。业内公认的第一优先升级项。

② Cross-Encoder 重排

召回可以"宽"，排序必须"准"。用交叉编码器对 query×chunk 逐对精算相关性，是"性价比最高的精度提升"。代价是逐对推理慢。

本项目：架构在，当前 NoOp 空实现 → 实验一
③ 查询改写

用户问法≠文档写法。"上次说的那个东西"必须改写成可检索的查询；复合问题要拆成多个子查询。

检索侧看 precision/recall@k，生成侧看 faithfulness（忠实度）/answer similarity，RAGAS 是事实标准。没有评估就没有优化方向。

技术选型的 Why（L4 层提问的答案）

决策为什么这样，而不是那样
pgvector 而非 Milvus / Pinecone 业务数据（用户/群组/文档/切片）本来就在 PostgreSQL——向量放同一个库，事务一致、一次 SQL 带 Filter 检索、零新增运维。数据规模到十亿级向量才值得引入专用向量库。
Spring Event 而非 MQ ETL 是单体内部解耦：发布方只管"文档已落库"，监听方异步处理。@TransactionalEventListener(AFTER_COMMIT) 保证了"先提交后触发"的时序正确性。单体阶段引入 MQ 是过度设计——等拆微服务再换 Kafka，接口不变。
本地 bge-small-zh 而非远程 Embedding API JVM 进程内 ONNX 推理：离线可用、零 API 费、无网络延迟；中文优化、512 维够用。代价：占本机 CPU、换模型需重启。
OpenAI 兼容协议 统一接模型 Chat 走 spring-ai-starter-model-openai，指向任何兼容服务（本地 11435 / 云端 agnes-ai）。换模型 = 改 base-url + model 两个配置项，代码零改动。
ES + IK 分词 做关键词通道 向量检索对型号、代码标识符、罕见专有名词天然弱势（它们在语义空间里不突出）；BM25 式词法匹配精确命中。中文场景 IK 分词是标配。
🚨 一个"名不副实"的陷阱
类 RedisChunkCacheService（excel 模块）名字里有 Redis，但项目里没有任何 Redis 依赖——它是进程内有界 LRU+TTL 缓存。别被名字骗了，也别在面试里说错。
🚨 安全红线
DocumentRoleGate.allowedDocumentIds 是检索层授权的唯一入口，fail-closed（拿不到白名单就返回空，宁可误杀不可放行）。项目规定不得改动该判定实现。

CH 04数据链路：文档如何变成可检索的知识 V2 · ETL

💬 人话导读 · 本章完整版
这一章讲图书馆的"后厨"：一本书怎么从"一个文件"变成"能被搜到的知识"。流程像食品加工——验收入库（传到 MinIO 仓库）→ 拆包装（从 Word/PDF 抽出纯文字）→ 切卡片（两三百字一张的知识卡）→ 贴两张标签（语义指纹进 pgvector、关键词进 ES）→ 上架。这章最容易卡住的是三个"为什么"，答案现在直接给你：
① 卡片为什么要重叠？关键句可能刚好骑在两张卡片的分界线上，各占一半，谁都搜不全——重叠让相邻卡片都保有完整关键句，至少命中一张；
② 加工为什么在后台悄悄做？上传的人不该干等几分钟加工时间——网页立刻显示"上传成功"，加工完自动把状态改成"可借阅"；
③ 加工失败重试，为什么不会产生重复数据？每张卡片都有写死的"身份证号"（文档号+序号派生），重试再写也只占同一个坑，不会多出一张卡。✅ 这三个"为什么"能答出来，第 4 章就可以翻篇了。

一条知识文档从上传到能被检索到，要经过"两段旅程"：同步的上传落库 + 异步的 ETL 加工。这一章走第一段和第二段的前台。

4.2 异步触发：事件驱动的正确姿势

// DocumentIngestionAsyncListener.java:46
@Async("taskExecutor")
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onIngestionRequested(DocumentIngestionRequestedEvent event) {
    documentIngestionAsyncService.ingest(event.documentId());

  • @Async：HTTP 请求线程立刻返回，ETL 在线程池里跑，用户不用等 30 秒的 PDF 解析。

What-If：换成普通 @EventListener 会怎样？——事件在事务提交前发布，监听器异步执行时可能读不到文档行（另一个连接看不到未提交数据），ETL 空跑报"文档不存在"，还是偶发的、测试环境永远复现不了的那种。

❓ 480 和 64 这两个数字是怎么来的？
出处都在 application-local.yml 的 ingestion.chunking：target-tokens: 240（卡片目标）、max-tokens: 320（单卡上限）、overlap-tokens: 32（重叠）、chars-per-token: 2（换算系数）。480 = 240×2，是把"一张卡的 token 预算"换算成中文字数的口径；64 = 32×2，这个是代码实打实执行的——StructureAwareChunkTransformer.java:249 把每张卡的开头向前拉回 64 个字符，包住前一张卡的结尾。
为什么目标定 240 token？往两边推都会变差：太大，一张卡挤进多个主题，语义指纹成"平均脸"，哪个主题都搜不准，塞进 Prompt 还贵；太小，一句话一张卡，上下文断裂、卡片数量爆炸。240/320 落在中文 RAG 的甜点区；而且 bge-small-zh 单次最多吃 512 token，240 加上余量，保证每张卡都能完整算出指纹、不被截断。
为什么重叠定 32 token？它是"关键句骑缝"的保险——32 token 约一两句话，刚好把骑在边界上的句子完整包进相邻卡片；约占卡片预算的 13%，再大就是纯浪费（业界常见重叠 10%~20%）。
⚠️ 防露馅的实现细节：estimateTokens 的实现是 text.length()（StructureAwareChunkTransformer.java:321）——预算检查把字符数直接当 token 数用。所以主体路径实际切出的卡是约 240~320 字，而不是 480 字；只有完全没标点的超长文本才走硬截断，步长 320×2=640 字。有意思的是这个简化反而歪打正着：bge 对中文大致"一字一 token"，240 字 ≈ 240 token，恰好贴近真实分词。面试被追问"切块大小怎么定的"，能说出这段的人不多。
What-If：切片从 240 token 加大到 2000 会怎样？——单块信息更全，但：检索粒度变粗（命中的块一半是噪音）、Prompt 塞不下几块、embedding 对长文本的语义表征稀释。切块大小是召回精度 vs 上下文信息量的杠杆，没有标准答案，只有用评估集调出来的平衡点。

Reciprocal Rank Fusion：rankScore = Σ 1/(k + rank)，本项目 k=0。每路只贡献"排名"，不看原始分数——天然规避了"向量余弦分和 ES 相关分单位不同没法直接加"的问题。同一 chunk 被两路都命中时分数累加，并标记 retrievalSource=BOTH——这个标记是后面证据评估判 SUFFICIENT 的关键输入。

What-If ①：直接把两路分数归一化后加权相加？——要调权重、要处理两种分数分布的差异，一个超参错了全盘皆输；RRF 零参数。本期 k=0（纯排名倒数）而论文常用 k=60（削弱第一名通吃、给尾部更多机会）：本项目单通道 topK=50 已很大、后续还有重排和聚类，头部强相关不应被"平均主义"稀释，k=0 是有意识的取舍。What-If ②：删掉 RRF？——BOTH 交叉印证信号消失，证据评估失去最可靠的"充分"判据，拒答误判率上升。

CH 08分级自测：从 What 到 Design

先自己作答（口头或写下来），再点开参考答案。答不上来的回到对应章节重读。

Level 1 · What（是什么）

本项目一个 chunk 的默认大小、重叠、向量维度分别是多少？

目标 240 token（上限 320）、重叠 32 token（=64 汉字）、embedding 维度 512（bge-small-zh）。配置在 application-local.yml 的 ingestion.chunking.*。加分点：estimateTokens 按字符直算 token（text.length()），主体路径实际切出 240~320 字/块，而非 240×2=480 字；这个简化对中文反而更贴近 bge"一字一 token"的真实分词。

项目里两个检索通道分别是什么？各自负责什么？

pgvector 向量通道（HNSW+cosine，语义泛化）+ Elasticsearch 关键词通道（IK 分词，精确词面/型号/专名）。各召回 50 条后 RRF 融合。

证据等级有哪四级？拒答发生在哪个环节之前？

NONE / WEAK / PARTIAL / SUFFICIENT（EvidenceAssessor）。拒答发生在调用 LLM 之前——证据不足直接返回 INSUFFICIENT_EVIDENCE，零 token 消耗。

Level 2 · How（怎么工作）

RRF 是怎么把向量分和 ES 分合成一个排序的？为什么说它"免调参"？

每路结果按名次贡献 1/(k+rank)，同名次同贡献，不看原始分值——所以无需把两种量纲不同的分数归一化或调权重。同 chunk 双路命中则累加并标 BOTH。

结构感知切片的四级降级顺序是什么？每级解决什么问题？

Markdown 标题（跳过代码块内的 #）→ 空行段落 → 中英句子（。！？；!?;）→ 硬截断保底。从"语义天然完整"的边界逐级降级到"只保证不超限"，尽量让每块语义完整。

SSE 流式路径上，token 流为什么要 .cache()？事件顺序是什么？

.cache() 让 Flux 可被重复订阅而不重新执行——否则框架的第二次订阅会再调一次 LLM（重复扣费）。事件序：token* → citations → evidence-overview → record。

短期记忆的 BEFORE_MODEL Hook 每次调用前注入了什么？超限后怎么办？

紧凑摘要 → 会话记忆 → 最近 10 条消息 → 当前问题；token 超 50000 触发运行时压缩（三级压缩 summary → session_memory → compact_summary）。

Level 3 · Why（为什么存在）

为什么拒答要放在调 LLM 之前，而不是让模型自己说"我不知道"？

三个理由：① 成本——不调用就零 token 消耗；② 可靠性——模型"自知无知"不可靠，给空证据它照样可能编；代码级硬闸门是确定性约束；③ 可观测——拒答结构化为 reasonCode，前端可定制话术、后端可统计拒答率。即使放行到模型，system prompt 也只是软约束。

为什么 ETL 用 Spring Event + AFTER_COMMIT 而不是上传线程里直接跑、也不是发 MQ？

同步跑：用户等 30s 的 PDF 解析，HTTP 超时风险。普通异步（事务内触发）：监听器可能读不到未提交的文档行。AFTER_COMMIT 恰好卡在"数据已可见 + 用户已得到响应"的交点。不用 MQ：单体内部解耦 Event 足够，MQ 是跨服务才需要的复杂度（换 MQ 时发布/监听接口可保持不变）。

为什么引用由 CitationAssembler 从 metadata 组装，而不让 LLM 在答案里写 [E1]？

LLM 写引用号会错编、漏标、串号（幻觉高发区），且无法保证可追溯。引用本质是检索结果的确定性投影（哪个 chunk 进了上下文就引哪个），代码组装 100% 准确、可审计，还能携带分数、区间等模型不知道的信息。

为什么向量主键用 UUID(documentId:chunkIndex) 而不是随机 UUID？

幂等。ETL 重试时同一 (documentId, chunkIndex) 生成同一主键，写入天然去重（配合"先删后写"双保险）。随机 UUID 下每次重试都产生新向量，重复条目会污染检索结果（同内容占两个 topK、RRF 分数虚增）。

为什么 pgvector 结果在 FilterExpression 之外还要做一次 Java 层 groupId 校验？

纵深防御。Filter 是"应然"，Java 校验是"实然"——万一 metadata 写坏、表达式构造 bug、或换底层实现导致过滤失效，第二道校验保证跨群组数据绝不流出到响应里。安全控制永远不依赖单点。

Level 4 · Design（为什么这样而不是那样）

RRF 的 k 本项目取 0，论文常用 60。如果让你拍板，你选哪个？依据是什么？

参考思路：k 的作用是削弱头部通吃、给尾部机会。本项目单通道 topK=50、后续有重排（目前 NoOp）和证据评估，头部强相关不该被稀释，k=0 合理；但一旦接上真 Cross-Encoder 重排被移除/降级，或发现某类查询头部被单一通道霸占，k=60 值得实验。结论不重要，"用评估集说话"的决策过程才重要——这正是实验三的目的。

如果知识库涨到 5000 万切片，架构里最先崩溃的是哪一环？怎么改？

参考思路：① pgvector HNSW 在单机内存/写入吞吐上先到瓶颈 → 向量库外置（Milvus/分布式 PG）；② 双通道串行/并行的 50+50 召回和 rerank 延迟放大 → 收紧 CHANNEL_TOP_K、上真重排提高 precision@5 以降低 context 需求；③ ES 单索引分片重排开销；④ ETL 单机线程池吞吐 → 引入 MQ 削峰。先量化（评估集+监控）再动刀。

要求给 qa 模块加"多轮追问"（"那第二种情况呢？"），你会怎么设计？最小改动是什么？

参考思路：最小改动 = 复用 assistant 的短期记忆机制：请求带 sessionId，把上一轮 Q+A（或其摘要）作为查询规划的输入，让 QueryPlanningService 做指代消解（"第二种情况"→展开成完整问题），再走原有单轮链路。核心原则：改写发生在检索之前，历史不直接进生成 Prompt（避免污染证据约束）。

让你把拒答率从 30% 降到 15% 而不引入幻觉，你的排查路径是什么？

参考思路：先量化——从 qa_records 统计拒答样本的 evidence_level 分布与 reasonCode；再分层：① 拒答发生在检索后 → 看是不是切块/检索问题（该命中的没命中：查切片质量、通道覆盖）；② 检索有结果但判级不足 → 调 BOTH/0.85 判据是否过严、接真重排提升 topScore；③ 问题本身超纲 → 不是 bug 是 feature（拒答正确）。顺序不能反：先分清"检索失败"和"知识缺失"，前者是工程问题，后者要补数据。

B4 · 红线与易错点

  • 红线：DocumentRoleGate fail-closed 判定不得改动；响应一律 ApiResponse 包装；异步复用统一线程池；SSE 代理保持去缓冲。
  • 没有真实 Redis：名字带 Redis 的类是进程内 LRU+TTL 缓存，pom.xml 无 redis 依赖。
  • 重排是"空转"的：接口/调用点在，唯一实现 NoOp——接真模型只需注册 Bean（第 7 章实验一）。
  • 拒答在 LLM 之前：证据不足直接返回 INSUFFICIENT_EVIDENCE，零 token 消耗。
  • 引用是代码组装的：答案正文无引用角标，CitationAssembler 从证据 metadata 确定性生成，100% 可溯源。
  • qa 无会话态：每次提问独立；多轮对话与记忆在 assistant 模块。
  • ETL 等事务提交：AFTER_COMMIT 防止监听器读不到未提交的文档行。
  • 向量主键幂等：UUID(documentId:chunkIndex) 派生，重试不产生重复向量。
