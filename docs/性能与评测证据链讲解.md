## 1. 评测体系走读：run_eval.py 到底做了什么

### 1.1 端到端流程（照代码背）

`run_eval.py` 是一个**端到端黑盒评测**：它不 mock 任何内部模块，而是像真实用户一样走 HTTP 接口。
流程五步，每步都有代码依据：

1. **登录**：`POST /api/auth/login` 拿 accessToken。评估必须用普通用户（脚本默认 `evaluser`，
   可 `--register` 自动注册）——因为管理员账号被系统禁止进入业务区，这本身就是项目的权限设计，
   评测脚本被迫遵守它，反而是个可以主动讲的细节。
2. **（`--prepare`）建库**：创建（或按名字复用）"RAG评估专用组"，把 `eval_docs/` 下的 3 篇测试
   文档逐一 `POST /api/documents/upload` 上传，然后**轮询** `GET /api/documents?groupId=`，
   每 3 秒一次，直到所有文档状态变 READY（或 FAILED），超时 180 秒。这一步等的是完整的
   ETL 链路：解析→清洗→切片→向量化→索引。
3. **逐题提问**：循环调 `POST /api/qa/ask`，body 只有 `{groupId, question}`，每题间隔 3.5 秒
   ——因为后端问答接口限流 **20 次/60 秒**，3.5s 间隔是贴着限流设计的，40 题约 3~5 分钟，
   170 题约 10 分钟。
4. **逐题判定**：拿响应里的 `answered`（是否拒答）、`citations`（引用列表）、`answer`（答案文本）
   三个字段，对着测试集里的 `expected_files` / `expected_keywords` / `should_answer` 算分（详见第 3 节）。
5. **落盘两份产物**：`eval_result.json`（逐题明细+指标汇总，可二次分析）和 `report.md`
   （人类可读报告，含逐题判定表）。`--dry-run` 可以不连后端，用确定性伪随机数据演示报告结构。

### 1.2 测试集格式（两个测试集同构）

测试集是自描述 JSON，**判定参数跟着测试集走而不是写死在脚本里**：

```json
{
  "hit_rate_k": 5,                      // HitRate 看前几条引用
  "answer_coverage_threshold": 0.6,     // 关键词覆盖率 >= 60% 判"答对"
  "cases": [
    {"id": 1, "question": "去北京出差住酒店一晚最多能报销多少钱？",
     "expected_files": ["公司差旅报销制度"],   // 引用文件名包含任一子串 => 检索命中
     "expected_keywords": ["500", "一线"]},    // 答案需覆盖的关键词
    {"id": 37, "question": "公司年会定在哪个酒店举办？",
     "expected_files": [], "expected_keywords": [], "should_answer": false}  // 负例
  ]
}
```

`--testset` 参数切换测试集（默认 `testset.json` 40 例；`--testset stress_testset.json --group-id 14`
跑 170 例压力集）。这就是同一套判定代码跑两套数据、口径完全可比的原因。

### 1.3 调用链路的工程细节（面试加分点）

- **401 自动重登**：access token 30 分钟过期，170 题跑不完一个 token 周期。脚本对每题做最多两次
  尝试，第一次收到 401 就重新登录再发一次。2026-10-24 的压力集日志里真实触发过：
  `[i] token 过期，自动重新登录`。
- **单题失败不中断整体**：任何一题请求异常（超时、5xx）不会让整场评估崩掉，而是记一条
  `reasonCode=REQUEST_ERROR` 的占位行继续往下跑——这个设计既是韧性也是隐患，见 1.5。
- **所有结果带 120 字符答案摘录**（`answer_excerpt`），方便事后人工抽检，这是"自动指标+人工复核"
  双保险的证据。

### 1.4 断点续跑怎么实现（真实机制）

代码就三十行，但每一行都有讲究（`run_eval.py` 主循环）：

1. **checkpoint 文件名按测试集区分**：`eval_checkpoint_{测试集文件名去后缀}.json`，
   所以 40 例和 170 例各有各的断点文件，互不污染。
2. **签名校验**：checkpoint 里存 `signature = "{测试集文件名}|{group_id}"`。重跑时签名不一致
   （换了测试集或换了群组）就整体丢弃 checkpoint 从头来——防止拿旧群组的旧答案凑数。
3. **每题落盘**：每答完一题，把"到目前为止的全部结果"整体写回 checkpoint。进程被杀，
   最多损失正在请求的那一题。
4. **续跑只补缺**：重启后先读 checkpoint，`已完成的 id 直接复用结果`，只对缺失的题发请求。
   日志会打印"断点续跑：已有 N 题结果，只补剩余 M 题"。
5. **`--fresh` 全量重测**：忽略断点强制重跑，用于换版本对照（比如 NoOp 精排 vs BGE 精排）。

### 1.5 坏条目污染与清洗：2026-10-24 Agnes 故障实录（真实事件，最有讲头）

这是压测评测体系里**唯一一次真实故障**，证据链完整，建议整段背下来：

- **背景**：2026-10-24 16:44 我在跑"压力集 + BGE 精排开启"的对照实验
  （日志 `eval-stress-rerank-on-20261024.log`）。
- **故障**：LLM 网关（Agnes，本地 chat-only-gateway）中途挂掉，前 153 题全部正常，
  从第 154 题起连续 `Read timed out. (read timeout=120)`——每题都等满 120 秒超时。
- **污染机制**：run_eval 的"单题失败不中断"设计会把失败题写成 `REQUEST_ERROR` 占位行，
  **而且照常写进 checkpoint**。如果直接重跑，断点续跑会把这些占位行当成"已完成"跳过——
  17 道被网关故障冤杀的题会以"拒答+覆盖 0%"计入成绩，把 94% 的真实水位硬拽下来几个点。
  这就是"故障污染 checkpoint"。
- **清洗动作**：把 checkpoint 里所有 `reasonCode=REQUEST_ERROR` 的条目删掉，只保留有效前缀
  （153 条）。证据就在文件系统里：`eval_checkpoint_stress_testset.json` 现在恰好是 **153 条**、
  0 条 REQUEST_ERROR——而日志明明打到第 161 题；第 154~161 题的坏条目就是被清掉的。
- **续跑**：清理后重跑同一命令，签名匹配、153 题复用，从第 154 题接着问。
- **讲法**："我的断点续跑是每题落盘+签名校验，但失败占位行也会被落盘，LLM 网关一次故障
  就能污染断点。我在真实故障里发现并清洗了它，改进方向是占位行不写 checkpoint 或续跑时
  自动剔除 REQUEST_ERROR 条目——这是我评测基础设施的一个已知边界。"
  主动讲出设计缺陷比假装完美强，这个段子和《口径勘误表》的思路一脉相承。

### 1.6 "数字可复现"的完整论证链

面试官问"你这 95% 我凭什么信"，我按这条链答，每环都有实物：

1. **闭世界设计**：3 篇测试文档是我自己写的（`prepare_testset.py` 里的 `DOCS` 字典，内容全部
   硬编码在脚本里），所有"事实"只存在于这 3 篇文档中——所以"标准答案已知且唯一"，命中与否
   可以精确判定，不需要人工标注。
2. **测试集和文档同源生成**：`prepare_testset.py` 一次生成 `eval_docs/*.md` + `testset.json`，
   40 条用例的 `expected_keywords` 都能在文档正文里找到依据。压力集更进一步：
   `build_corpus.py` 内置**关键词自检**——生成时对每条关键词做 `norm(kw) in norm(body)`
   （去空白后的子串匹配）校验，任何关键词在正文里找不到就打警告，跑出"关键词自检：全部通过 ✓"。
3. **判定是确定性代码不是人拍脑袋**：HitRate/MRR/覆盖率/拒答全部是 `run_eval.py` 里
   几十行可审计的 Python（第 3 节逐行讲），同一份响应给任何人跑都是同一个数。
4. **产物可复查**：`eval_result.json` 存 170/40 条逐题明细（含每题首命中排名、覆盖率、答案摘录），
   `report.md` 是人能直接读的判定表。面试官随机抽一题，我能从明细里翻出当时模型回了什么。
5. **原始日志在场**：`eval-run-20261024.log` 等 3 份日志是脚本 stdout 的原样重定向，
   40 例那场从第 1 题打到第 40 题一行不少，最后一屏就是指标汇总。
6. **多次重跑稳定**：40 例集在 2026-09-27 与 2026-10-24（NoOp 与 BGE 精排两种配置，共 3 场）
   综合准确率全部是 95.0%，逐题失分都是同样两题（16、22）——LLM 有随机性但结果稳定，
   说明水位不是运气。
7. **任何人可重跑**：`git clone` 后 `pip install requests`、起后端、`python run_eval.py --register
   --prepare`，约 5 分钟得到自己的 `report.md`。第 6 节有完整命令。

## 2. 评测集设计：两层数据各测什么

### 2.1 40 例基线的真实构成（先勘误再背）

**勘误**：如果旧材料里说过"40 例按正常/改写/多跳/越权分层"——**代码里没有这个分法**。
`testset.json`/`prepare_testset.py` 的真实构成是：

| 维度 | 数量 | 说明 |
| --- | --- | --- |
| 差旅报销制度正例 | 12 | 住宿/交通/餐补/流程/违规，id 1~12 |
| 考勤请假制度正例 | 14 | 工时/迟到/年假/病假/事假/婚假/加班，id 13~26 |
| 平台操作手册正例 | 10 | 上传/拒答/协同/权限/导出，id 27~36 |
| 超纲负例（应拒答） | 4 | 年会酒店/股票代码/体检月份/食堂价格，id 37~40 |
| 合计 | **36 正 + 4 负 = 40** | 三文档 × 三类问题密度 |

不过设计意图上确实覆盖了那些"题型"，只是没有打标签：

- **改写（口语化同义问法）**：题目全部用用户口吻而不是文档标题词，比如文档写"住宿标准"，
  题问"住酒店一晚最多能报销多少钱"；"市内交通报销有上限吗"对应"单日上限 100 元"。
  这就是隐性的 paraphrase 鲁棒性测试。
- **轻量多跳/聚合**：`年假有几天？` 的关键词是 `["5","10","15"]`——正确答案要把三档工龄的
  年假天数**聚合**着说全；`id 28` 一题两问（"最大不能超过多少？更大的文件怎么办？"）。
  是单文档内的事实聚合，不是跨文档多跳——被追问时这样精确表述。
- **越权/权限类：评测集里没有**。权限隔离（DocumentRoleGate、财务角色、群组隔离）由后端
  1614+ 个测试里的权限用例覆盖，RAG 评测只测检索与问答质量。如果面试官问"评测怎么保证
  不越权"，正确回答是："不是在评测集里测，是评测账号本身就被权限体系管着——admin 连业务区
  都进不去，脚本只能注册普通用户跑，这恰好证明权限体系在工作。"

### 2.2 170 例压力集的构成：108 篇语料是怎么拼出来的

`build_corpus.py` + `corpus/manifest.json` 的真实结构（108 篇 = 44 + 10 + 54）：

1. **44 篇基础制度**：考勤/休假/绩效培训/招聘离职/差旅报销/采购预算/信息安全/行政后勤/
   员工福利/研发管理/客户销售/法务合规 12 大类，内容基于公开企业制度范本条款改编
   （考勤罚则、比价采购、保密条款），总 39122 字符，按 240 字符/片估算约 163 个切片，
   实际灌入 ES 后群组 14 共 191 个切片。
2. **10 篇分公司变体**：这是**刻意制造的检索干扰项**。三个模板族按大区展开，同一主题、
   结构雷同、**数字各不相同**：
   - 差旅 5 篇：华南 480/西南 420/华北 460/华中 400/东北 380（一线城市住宿线，餐补 95/85/90/80/80）；
   - 制造基地考勤 3 篇：华东 7:30~19:30、华北 8:30~20:30、西南 9:00~21:00（还有各自的倒班津贴与罚则）；
   - 团建 2 篇：华东/华南不同人均标准。
   测的是"同城不同标准"的组织歧义：问题不带分公司名时，检索层根本无法替用户选版本。
3. **54 篇历史存档版**：**每篇正式文档自动生成一个"上一版"孪生件**——文件名加"-2025存档"
   后缀、文内编号和日期整体回退一年、顶部加一行"⚠ 历史存档版本……执行以最新版为准"声明，
   正文与现行版一致。模拟企业知识库最真实的场景：新旧版本长期并存，测排序是否会
   把过时版本顶到前面。因为两版内容一致，测试集的 `expected_files` 是"版本族"
   （如 `["差旅费管理办法-华南分公司", "差旅费管理办法-华南分公司-2025存档"]`），
   **任一版本命中都算检索正确**——166 条正例的 expected_files 全部是双元素版本族。

测试题 170 条 = 166 正例（由每篇文档的 facts 表自动派生，一文档多题）+ 4 条固定负例
（年会奖品/停车补贴/食堂晚餐/带宠物上班）。按问题文本统计：133 题未指明组织（默认问总部）、
20 题点名分公司、9 题点名制造基地、4 题明说总部——也就是说**约 1/6 的正例（29 条）必须在
同主题多版本干扰下精确命中带组织名的版本**，其余 133 条则要在"总部版+5 个分公司版+存档版"
共 12 篇近似文档共存的压力下命中正确版本族。

### 2.3 为什么分两层（设计动机，可直接口述）

- 40 例是**能力验收**：小而金、闭世界、每题可解释——回答"系统做没做对"。
- 170 例是**压力与干扰实验**：回答"语料规模上去、同主题多版本并存时还做不做得对"。
  分公司变体专测组织歧义，存档版专测新旧版排序，这两个是企业知识库真实的翻车高发区，
  比通用 benchmark 更贴近目标场景。
- 两套测试集同一套判定代码、同一个 `--testset` 开关，口径可比：95.0% → 94.1% 的落差
  本身就是"语料复杂度上升 4 个点"的量化结论，比单报一个数字有说服力得多。

## 3. 判定标准：在脚本里找真实实现

### 3.1 检索命中（HitRate@5 与 MRR）

判定单元是**引用文件名子串匹配**，`citation_hit()` 原文逻辑：取响应 `citations` 的**前 5 条**
（K=5 来自测试集 `hit_rate_k`），从第 1 名往后找，`expected_files` 里任何一个字符串是某条引用
`fileName` 的**子串**，就返回该条排名（1 起）；前 5 都不中返回 0。注意两点：
(1) 压力集里存档版和现行版是"或"关系，中哪个都算；(2) 引用没带期望文件但答案正确
（170 例里的 id 52：覆盖 100%、首命中"-"）会被记为检索 miss 但答案 pass——两个指标独立计分，
这正是 HitRate 和准确率不联动的原因。

汇总公式（`summarize()` 原文）：

- **HitRate@5 = Σ(rank>0 ? 1 : 0) / 正例数**。40 例：40/40=100%；170 例：162/166=**97.6%**
  （未首命中 4 题：id 6、51、52、140）。
- **MRR = Σ(1/首命中排名) / 正例数**，未命中记 0。40 例全排第 1 → 1.0；170 例 → 0.9513。
  MRR 补充 HitRate 的盲区：命中但排第 4 名，HitRate 给满分，MRR 只给 0.25
  （170 例里 id 7 两班倒就排到第 4）。
- 负例不参与检索指标（`retrieval_hit=None`），因为负例根本没有期望文件。

### 3.2 答案准确率（正例判"答对"）

不是人工打分，也不是 LLM 裁判，是**确定性关键词覆盖率**：`keyword_coverage(answer, keywords)
= 命中关键词个数 / 关键词总数`（空关键词集返回 1.0）。正例"答对"必须同时满足：
(1) `answered=true`（系统认为有依据）；(2) 覆盖率 ≥ 0.6（阈值来自测试集
`answer_coverage_threshold`）。比如"年假有几天？"关键词 `["5","10","15"]`，答案必须覆盖
至少两档才算对——逼模型答完整而不是只碰对一个词。

- 40 例：正例答对 34/36=94.4%（失分 id 16、22，均为覆盖 50%——同义词误伤，见 3.4），
  综合 = (34+4)/40 = 38/40 = **95.0%**。
- 170 例：正例答对 156/166=94.0%（失分 10 题：6、51、68、69、71、101、103、104、138、140），
  综合 = (156+4)/170 = 160/170 = **94.1%**。

### 3.3 拒答判定（负例判"答对"）

最简单也最严格的一条：负例的 `answer_ok = (answered == false)`。系统只要对"知识库里不存在
的问题"硬答了（哪怕答案看着合理），就算失败——直接度量"不编造"。两个测试集的 4 条负例
全部正确拒答，`reasonCode` 会记录拒答原因进明细。40 例和 170 例的拒答准确率都是 4/4=100%。

### 3.4 判分的已知盲区（主动讲，防守用）

- **同义词/格式误伤**：文档写"三级甲等医院"，模型回答"三甲医院"，关键词 `三甲` 反而能中、
  `诊断` 却可能不中——id 16/22 扣分就是这类；170 例里"2 万元（20000 元）"对关键词"2万"、
  模型答案带空格导致 id 101/103/104/138 误伤。人工复核（看 answer_excerpt）确认这些答案
  **事实正确**，所以 95.0% 是保守口径，人工复核后事实正确率 100%（40 例那两题）。
- **数字归一化缺失**是已列的改进项：判分侧做数字归一化或换语义相似度/LLM 裁判。
- 这正好回答"为什么不用 LLM 当裁判"的半个问题：关键词判分的误差方向是**低估**，
  从不虚高——报出来的数是下界，这在面试里是可以站着说话的位置。

## 4. k6 压测走读：三个脚本各测什么

三个脚本都在 `scripts/load/`，对应一条流量假设：**知识库读 70% / RAG 问答 20% / Excel 协同 10%**
（写在各脚本首行注释里）。全部支持 `BASE_URL`/`TOKEN` 环境变量注入，默认打 `localhost:8080`。

| 脚本 | 场景 | VUs | 时长 | 阈值 | 请求模型 |
| --- | --- | --- | --- | --- | --- |
| `k6-knowledge-read.js` | 文档列表+详情读路径（70% 流量） | 100 | 30m | `http_req_failed<1%`、`http_req_duration p(95)<500ms` | GET 列表(pageNum=1,pageSize=20) + GET 详情，sleep 1s |
| `k6-rag-stream.js` | RAG 问答（20% 流量） | 20 | 30m | `http_req_failed<1%`、`http_req_duration{type:retrieval} p(95)<2s` | POST `/api/qa/ask` 固定问题，sleep 3s |
| `k6-excel-collab.js` | Excel 协同（10% 流量） | 10 | 30m | `http_req_failed<1%`（注释另声明协同事件 P95<500ms） | GET 工作簿列表 + WS 连接发一条 edit 事件，5s 后断开 |

**各脚本讲什么：**

- **knowledge-read**：最重的一个，100 VU 持续打列表和详情，P95<500ms 对应"读路径必须快"——
  详情接口 check 放行 200/403/404 三种状态码（403/404 对压测账号是合法结果，不算失败），
  这是权限体系的 fail-closed 在压测脚本里的体现。
- **rag-stream**：20 VU 模拟并发提问，每 VU 间隔 3 秒（LLM 生成贵，吞吐按供给能力定）。
  阈值子键 `{type:retrieval}` 意图是把"检索段延迟"单独卡 2 秒线，与 LLM 生成段解耦。
- **excel-collab**：HTTP 拉工作簿列表 + WebSocket 连 `/ws?token=`，向 `/app/excel/edit` 发一条
  单元格编辑事件（documentId=1, r=1, c=1），保持 5 秒后断开——覆盖"拉列表+建连+发事件"
  的协同最小闭环。

**结果怎么读**：k6 结束时输出汇总——`http_req_failed`（错误率，超 1% 即 fail）、
`http_req_duration` 的 p(50)/p(95)/p(99)、checks 通过率；**任一阈值被突破 k6 以非零码退出**，
所以可以直接挂 CI 当性能门禁。看报告先答三个问题：错误率有没有贴 1%？p95 有没有贴阈值？
p99 和 p95 差距大不大（大 = 长尾问题，通常是慢查询或连接池饥饿）？

**诚实边界（照《口径勘误表》风格主动讲，别等人抓）：**

1. `k6-rag-stream.js` 的 `{type:retrieval}` 标签阈值**声明了但请求没有打 tag**——当前这档
   阈值实际约束不到任何请求；要生效需给 http.post 加 `tags: {type: 'retrieval'}`。
   注释里"首 Token P95<5s"也未落成阈值——脚本打的是同步 `/api/qa/ask`，测不了 SSE 首 token
   延迟（需要按 SSE 分帧解析响应流）。名字叫 rag-stream，实测的是同步问答。
2. `k6-excel-collab.js` 注释里的"协同事件 P95<500ms"同样只有声明没有对应阈值实现
   （k6 对 WS 消息延迟要用 `trackEvent` 手动打点）。
3. RAG 接口限流 20 次/60 秒/用户，脚本 20 个 VU 共用一个 TOKEN、人均约 0.33 req/s——
   真跑满会触发限流 429 并把 `http_req_failed` 顶破 1%。所以这套脚本是**目标态容量设计**，
   实跑要么按 VU 配 token 池，要么临时调限流——面试里讲清"我知道限流和压测的冲突"即可。

## 5. "你们的准确率 95% 怎么来的？"——90 秒标准答案（背这段）

> "这个数是 40 条用例的端到端自动化评测跑出来的，整套证据链是闭世界设计：我自己写了 3 篇
> 测试文档——差旅报销、考勤请假、平台操作手册，所有事实只存在这 3 篇文档里，所以标准答案

> 评测脚本像真实用户一样登录、建群、传文档、等 ETL 到 READY，然后逐题调问答接口，

> 答案看关键词覆盖率是否超过 60%，36 条正例里 34 条达标；拒答看 4 条负例是否全部
> answered=false，4 条全对。综合 (34+4)/40 就是 95.0%。没达标的 2 条我逐条人工复核过，

> 分公司差旅变体和 54 篇历史存档版，测组织歧义和新旧版本并存，HitRate@5 是 97.6%、
> 综合是 94.1%。所有逐题明细、原始日志和评测脚本都在仓库里，clone 下来一条命令 5 分钟
> 就能复现。"

（90 秒版本压缩取舍：先给结论和分子分母 → 闭世界设计 → 三个判定口径 → 失分题人工归因 →
压力集对照 → 可复现。面试官任何一个环节追问，都能落到第 1~3 节的细节上。）

## 6. "如果我要复现你的评测"——实操指引（面试官可能真让你跑）

前提：后端（默认 `http://localhost:10001`）已启动，LLM 网关（Agnes，端口 11435）配了
**有效的** key——注意环境变量里的旧失效 key 会覆盖并导致 401，这是 2026-09-27 踩过的真实坑；
key 失效的表象是每题耗时数分钟（Spring AI 内部指数退避重试 8+ 次），看到单题异常慢先查 key。

```bash
# 0. 依赖（只要一个包）
pip install requests

# 1. 生成测试文档与 40 例测试集（幂等，已存在则跳过；改内容后加 --force）
cd scripts/rag_eval
python prepare_testset.py

# 2. 首次运行：注册 evaluser → 建"RAG评估专用组" → 传 3 篇文档 → 轮询等 READY → 逐题评测
#    （admin 被禁止进业务区，必须普通用户，脚本已处理；限流 20/60s，脚本每题隔 3.5s）
python run_eval.py --register --prepare

# 3. 复跑（复用群组，走断点；想全量重测加 --fresh）
python run_eval.py

# 4. 压力集：生成 108 篇语料 → 灌库 → 抽样验证 → 170 例评测
python build_corpus.py                 # 生成语料 + 170 题，内置关键词自检
python bulk_upload.py                  # 上传到"压力测试专用组"，幂等可重跑
python bulk_upload.py --verify 12      # 抽 12 题验证可检索性（正式跑分前的小样本）
python run_eval.py --testset stress_testset.json --group-id 14

# 5. 不连后端看报告结构（演示用）
python run_eval.py --dry-run
```

产物：`eval_result.json`（逐题明细）与 `report.md`（判定表）。预期数字：40 例综合 95.0%、
HitRate@5/MRR 100%、拒答 100%；170 例综合 94.1%、HitRate@5 97.6%。LLM 有随机性，
建议跑 2~3 次取中位数；断点文件 `eval_checkpoint_*.json` 可安全删除重跑。
k6 侧：`k6 run -e BASE_URL=http://<host>:8080 -e TOKEN=<jwt> scripts/load/k6-knowledge-read.js`，
注意 RAG 脚本与接口限流的冲突（第 4 节边界 3）。

## 7. 高危追问 Top5（附应答要点）

**Q1："自己写的文档自己出题，评测集会不会过拟合？"**
应答：承认风险 + 给出三层防线。① 我没有针对评测集调过 prompt 或检索参数——40 例集上
NoOp 精排和 BGE 精排两场对照结果完全持平（95.0%/95.0%），如果是过拟合驱动的调参，
不会容忍"改了模块数字不动"；② 分层验证：同一套判定在 170 例、108 篇陌生语料（含刻意
歧义干扰）上只掉 4 个点，说明学到的是能力不是题目；③ 承认闭世界语料分布单一，
换真实企业文档属于待验证——这正是我保留 `--testset` 参数和测试集生成器的原因，
换语料只要重新生成，判定代码零改动。可以再补一句：评测集和代码一起进版本库，
任何人可以审计题目是否泄露到系统逻辑里。

**Q2："为什么不用 RAGAS / TruLens 这类标准评测框架？"**
应答：框架不是没考虑，是取舍。RAGAS 核心依赖 LLM-as-judge（faithfulness/answer_relevancy
都要 LLM 打分），引入三个问题：裁判 LLM 本身的方差和偏置、每题多倍 token 成本（170 题
× 多指标）、判分不可复现（同一答案两次打分可能不同）。我的场景是**闭世界 + 标准答案已知**，
确定性关键词判分的成本低、可复现、可审计，误差方向还是单边低估——够用且更硬。
框架的价值在**没有标准答案**的开放语料，我列的演进路径是：数字归一化 → 语义相似度（embedding
判覆盖）→ 必要时上 LLM 裁判并做裁判一致性校验，而不是一步跳到 RAGAS。

**Q3："关键词匹配判分靠谱吗？你自己都有同义词误伤。"**
应答：这是刻意保留的保守口径。误伤案例（三甲/三级甲等、2 万元/2万）我都留在了报告和 README 里，
因为它们证明了两件事：判分误差方向是低估不是虚高——公布的水位是下界；人工抽检环节
（answer_excerpt + 逐题复核）能兜住误杀。改进优先级：判分侧数字归一化和去空格预处理（一行代码
消掉一半误伤），再考虑语义判分。反过来问一句：一个只能被低估的指标，是不是比一个
方差未知的 LLM 裁判更适合写进简历？

**Q4："拒答准确率 100% 是不是没有意义？才 4 条负例。"**
应答：样本量确实小，我不会拿 4/4 去宣称"拒答能力满分"，它是"零编造"的 smoke 级证据。
真实的分量在两处：一是两个测试集共 8 条负例全部正确拒答且带 reasonCode，零硬答；
二是负例设计在持续扩充——压力集的负例（年会奖品/停车补贴/食堂晚餐/带宠物）和正语料
高度同域（都是行政后勤话题），"近域干扰下不编造"比远域负例难。要给拒答下统计结论，
需要 50+ 负例的专项集，这是我明确的待办，不回避。

**Q5："k6 脚本这么简单，压测结论可信吗？/为什么没有 SSE 首 token 数据？"**
应答：先讲设计再认边界。设计：三脚本对应 70/20/10 的流量画像，VU 比 100/20/10，
30 分钟稳态持续，阈值卡 P95 和错误率且可直接进 CI 当门禁；详情接口把 403/404 视为合法，
fail-closed 的权限语义在压测里也成立。边界（主动交代）：rag-stream 打的是同步 `/api/qa/ask`
不是 SSE 流，首 token P95 目前只有注释里的目标值没有测量实现；retrieval tag 阈值声明了
但请求没打 tag；WS 事件延迟同理没打点；RAG 限流 20/60s 与 20 VU 单 TOKEN 存在冲突，
实跑要配 token 池。改进版是：SSE 分帧解析测首 token/帧间延迟、WS trackEvent 打点、
tag 补齐、多账号池——这些我都能现场写出改造方案。
