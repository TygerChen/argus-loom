public ListNode reverse(ListNode head) {
    ListNode prev = null, cur = head;
    while (cur != null) {
        cur.next = prev;           // 反转指向
        prev = cur;                // prev 前进
        cur = cur.next;            // cur 前进
    }
    return prev;
}
```

public ListNode reverse(ListNode head) {
    ListNode prev = null, cur = head;
    while (cur != null) {
        ListNode next = cur.next;  // 先存后继
        cur.next = prev;           // 反转指向
        prev = cur;                // prev 前进
        cur = next;                // cur 前进

    return prev;
}
```

**我**：现场推一下，我不太想直接背。递归函数的契约先定义清楚：`reverse(head)` 返回"以 head 为头的链表反转后的新头"。那么对于 1→2→3，我先递归反转 2→3，拿到的 newHead 应该是 3，此时子链已经是 3→2。关键是怎么把 1 接上去——接的位置不是尾部，是 2 后面：`head.next` 是 2，让 2 的 next 指回 head，也就是 `head.next.next = head`；然后 head 自己的 next 必须置 null，否则 1 和 2 之间就成环了。终止条件：head 为 null 或者 head.next 为 null，直接返回 head——最后这个结点就是新头，一路透传回去。

```java
public ListNode reverseRecursive(ListNode head) {
    if (head == null || head.next == null) return head;
    ListNode newHead = reverseRecursive(head.next);
    head.next.next = head;   // 让原来的下一个指回自己
    head.next = null;        // 断开旧方向，防成环
    return newHead;
}
```

**我**：拿 1→2 验证：递归到 2 返回 2；回溯时 head=1，执行 2.next=1、1.next=null，返回 2，得到 2→1。✓ 复杂度 O(n) 时间、O(n) 栈空间，链表特别长会有栈溢出风险——所以工程上优先迭代版，这也是刚才先写迭代的理由。

首先是**dummy 结点**：虚拟头结点 next 指向 head。为什么必须有？因为第一组翻转之后真正的头会变，有 dummy 就统一成"每组的前驱都存在"，不用对第一组做特判。
然后是核心循环的不变量，我用一句话说：**prev 永远指向"已处理完成部分的最后一个结点"，下一组永远从 prev.next 开始数**。每一轮做三步：
1. 从 prev 出发走 K 步，途中若提前碰到 null，说明剩余不足 K 个，按题意保持原样，直接结束；
2. 把这一段单独反转——注意反转的是"子链内部"，段的前驱 prev 和段的后继 end.next 都不能丢，先把 endNext = end.next 存下来，再断开，再复用我刚才那个 reverse 函数反转这一段；
3. 接回去：prev.next = 反转后的新头（原来的 end），原来的段头（反转后变成段尾）.next = endNext；然后 prev 移动到这个新段尾，进入下一轮。

```java
// 骨架：复用迭代版 reverse(ListNode)
public ListNode reverseKGroup(ListNode head, int k) {
    ListNode dummy = new ListNode(0, head);
    ListNode prev = dummy;
    while (true) {
        // 1. 从 prev 向后数 k 个，不足则 break（尾巴保持原样）
        ListNode end = prev;
        for (int i = 0; i < k && end != null; i++) end = end.next;
        if (end == null) break;
        // 2. 摘下 [prev.next, end]，反转，再接回
        ListNode start = prev.next, endNext = end.next;
        end.next = null;                    // 断开，孤立子段
        prev.next = reverse(start);         // 复用迭代版，新头=原 end
        start.next = endNext;               // start 反转后是段尾
        // 3. prev 前进到新段尾，不变量恢复
        prev = start;
    }
    return dummy.next;
}
```

**我**：我自测一下不变量是否守恒：每轮结束 prev=start 是刚处理完那段的最后一个结点 ✓，prev.next 是下一段的头 ✓。用 1→2→3→4、k=2 走：第一组翻成 2→1，prev=1；第二组翻成 4→3，prev=3；结果 2→1→4→3。k=3 的话，第二组只剩 3→4 不足三个，break 保持原样，结果 3→2→1→4。✓
老实说：这里面下标换算和边界我是在白板上靠不变量推的，如果现在要求我把完整可编译版本一次写对，我没有把握——特别是不足 K 的判断和 endNext 的衔接，写完我肯定要用 k=1、k=链表长度、空表这几个用例再走一遍。与其硬写装稳，不如把不变量交代清楚。

**面试官**：（笑了一下）行，你这个"没把握"说得挺痛快。快问快答：k=1，你这段代码行为是什么？

# 第二场 · LRU 完整实现（30 分钟体量）

## 【面试官画像】

陈工，某做文档/内容平台的基础架构组高级工程师，头发不多，问话短。
风格：话少，但每句都是验收标准。开场先把捷径堵死，喜欢看你被逼到手写数据结构之后的样子。
他的信条：取巧版考不出真功底，双向链表指针操作是"写没写过 C/真调过 bug"的试金石。

## 【这场的真实意图】

1. LinkedHashMap 的 accessOrder 版本人人会背——他要堵掉它，逼你暴露指针操作的真实水平；
2. get 和 put 的语义（访问即提头、容量满淘汰尾、覆盖更新也算"访问"）有没有漏；
3. 30 分钟体量里最可能翻车的就是 prev/next 接反——他等着看你**翻车之后怎么处理**：
   是嘴硬、是慌，还是有测试用例走查的自检习惯。最后一项权重最高。
4. 最后留两分钟看你能不能把题和真实系统挂钩——纯刷题党和工程师的分水岭。

---

**面试官**：设计并实现一个 LRU 缓存，get/put 都要 O(1)，容量参数构造时给定。先说一句——`LinkedHashMap` 带 accessOrder 那个版本我看过一百遍了，不算数，手写双向链表。

**我**：好，那就手写。写之前我按习惯先确认边界和语义：get 一个不存在的 key 返回 -1；put 已存在的 key 是"覆盖值且提到最新"；容量满了 put 新 key 要先淘汰"最久未使用"再插入；容量本身我假设调用方传正整数，如果是 0 或者负数我会直接抛 IllegalArgumentException——这个我在构造器里写。对吗？

**面试官**：对，容量非法就抛。结构说一下再动手。

**我**：结构是两层：**HashMap 负责"定位"，双向链表负责"顺序"**。
HashMap 的 value 存链表结点引用，所以 get 是 O(1) 的定位；链表维护新旧顺序，我约定**头部是最新、尾部是最旧**，任何"被访问"的结点 O(1) 摘下来插到头上，淘汰就是摘掉 tail 前面那个。
关键设计是两个 **dummy 结点 head 和 tail**，只当哨兵不存数据，`head ↔ tail` 初始互指。这样"空链表""只有一个元素""删头""删尾"全部统一成同一套指针操作，不用写任何判空——这和昨天反转链表 K 个一组的 dummy 是同一个思想。
画一下：

```
   map: {key -> Node}            head ⇄ [A] ⇄ [B] ⇄ [C] ⇄ tail
   定位 O(1)                      ←最新        最旧→（淘汰 C）
```

**面试官**：行，写。

**我**：先写结点定义和骨架。Node 里必须存 key，不只是 value——这点容易漏：淘汰尾部结点时，我只有链表结点，要靠它手里的 key 反查删除 HashMap 里的条目，不然两边就不同步了。

```java
class LRUCache {
    private static class Node {
        int key, value;
        Node prev, next;
        Node(int key, int value) { this.key = key; this.value = value; }
    }

    private final int cap;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);   // 哑头：最新侧哨兵
    private final Node tail = new Node(0, 0);   // 哑尾：最旧侧哨兵

    public LRUCache(int cap) {
        if (cap <= 0) throw new IllegalArgumentException("cap must be positive");
        this.cap = cap;
        head.next = tail;
        tail.prev = head;
    }
```

**我**：然后是两个最底层的指针原语，全部正确性都压在它们身上：unlink 负责把结点从链里 O(1) 摘除，addToFront 负责头插。

```java
    // O(1) 摘除：把 node 的前后两个邻居直接接起来
    private void unlink(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    // 头插：node 插到 head 和原第一个元素之间
    private void addToFront(Node node) {
        node.prev = head.next;        // ← 这里我写着，待会儿统一走查
        node.next = head;
        head.next.prev = node;
        head.next = node;
    }
```

**我**：接着 get 和 put。get 的语义是"命中 → 返回值，且提到头部"；put 分三种情况：已存在（更新值+提头）、满了（先淘汰尾）、正常插入。

```java
    public int get(int key) {
        Node node = map.get(key);
        if (node == null) return -1;
        unlink(node);
        addToFront(node);             // 访问即最新
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {           // 命中：更新 + 提头
            node.value = value;
            unlink(node);
            addToFront(node);
            return;
        }
        if (map.size() == cap) {      // 满了：淘汰尾部最久未用
            Node eldest = tail.prev;
            unlink(eldest);
            map.remove(eldest.key);   // 靠 Node 里的 key 同步删 map
        }
        Node fresh = new Node(key, value);
        map.put(key, fresh);
        addToFront(fresh);
    }
}
```

**我**：写完了。按流程我走查一遍，就用最小的两个 key：cap=2，put(1,1) → put(2,2) → get(1) → put(3,3)，此时 2 应该被淘汰，get(2) 应返回 -1、get(1) 返回 1。
put(1,1)：map={1→A}，addToFront(A)。我盯一眼刚才 addToFront 的指针：A.prev = head.next，此时 head.next 是 tail，A.prev = tail；A.next = head……不对，**写反了**。我发现问题了——前两行我把 prev 和 next 的赋值对调了：应该是 `node.next = head.next`（接旧头元素）、`node.prev = head`（接哑头），我写成了 `node.prev = head.next`、`node.next = head`。这样 A.next 指向 head 而不是 tail，整个链是反着接的：head.next=A、A.next=head，成了 head 和 A 互指的环，tail 被踢出局。继续走 put(2,2) 会发现 tail.prev 还是 A，put(3,3) 淘汰时 unlink 掉的结点根本不对——这个 bug 每一步都错得很安静，不抛异常，只有走查能暴露。修复：

```java
    private void addToFront(Node node) {
        node.next = head.next;        // node 的后继 = 原第一个元素
        node.prev = head;             // node 的前驱 = 哑头
        head.next.prev = node;        // 原第一元素的前驱改指 node
        head.next = node;             // 哑头的后继改指 node
    }
```

**我**：注意后两行顺序也有讲究：必须先改 `head.next.prev` 再改 `head.next`，反过来 head.next 先变成 node，`head.next.prev` 就成了 node.prev = node 的自环。修完重新走一遍完整用例，我把每步之后的链表状态画出来：

```
put(1,1)  →  head ⇄ [1:A] ⇄ tail                 map={1}
put(2,2)  →  head ⇄ [2:B] ⇄ [1:A] ⇄ tail         map={1,2}
get(1)    →  head ⇄ [1:A] ⇄ [2:B] ⇄ tail   返回 1 ✓（A 命中提头）
put(3,3)  →  满，淘汰 tail.prev=B，map 删 key 2，再插 C：
             head ⇄ [3:C] ⇄ [1:A] ⇄ tail         map={1,3}
get(2)    →  map 无 → 返回 -1 ✓
get(1)    →  命中 A 提头，返回 1 ✓
```

再走一个容量 1 的极端用例：cap=1，put(1,1)、put(2,2)——插入时 size==cap，淘汰 A，map 变成 {2}，get(1)=-1、get(2)=2 ✓。链表从头到尾都只有哨兵加一个元素，dummy 的好处在这儿体现：不需要任何针对"唯一元素"的特判。

**面试官**：追问两个。第一，为什么淘汰的结点不 return 出去或者打个日志，你们生产上缓存淘汰不心疼吗？第二，你这个结构和生产级实现差什么？

**我**：第一个：LeetCode 签名是 void，我按题意来；生产上确实应该有钩子——被淘汰的 value 如果占大对象，最好支持 removalListener 让上层决定是落库还是降级。第二个，和生产级的差距我列得出三条：**线程安全**（HashMap+链表这样裸写在并发下会环、会丢数据，生产要么 ConcurrentHashMap+分段锁要么直接 Caffeine）；**没有 TTL**，纯 LRU 只看访问顺序，冷数据只要一直没人碰也会被误当热点驻留；**没有容量统计的内存口径**，我这是按条数，生产往往按字节数，得加权重。
然后我想主动挂一下：我项目里有个 RedisChunkCacheService，就是有界缓存，淘汰策略是 LRU 加 TTL 双维度——当时选型的逻辑和今天这题完全同源：LRU 解决"最近用的一定要留住"，TTL 解决"再热的数据过期也得失效"，两个正交条件一起裁剪缓存。那套是站在 Guava/Caffeine 肩膀上配的，但参数为什么这么配，就是从手写这版理清楚的。

**面试官**：你提了 Caffeine，那我问一个：它为什么不用纯 LRU？听说过 W-TinyLFU 吗？

**我**：（停顿两秒）说实话——W-TinyLFU 我知道定位：Caffeine 的准入+淘汰用的是"频率 sketches 加新近窗口"的混合策略，动机是防偶发扫描把真正的热点挤出去，纯 LRU 只反映"最近"，不反映"经常"。但它的具体结构——Count-Min Sketch 怎么老化、窗口和主段怎么加权，我没读过源码，细节我说不准，就不装了。

**面试官**：（点头）不知道就说不知道，挺好。那回到你的走查：删头、删尾你验证过吗？

**我**：验证过，而且这正是我用 dummy 哨兵的原因：本实现里"头"永远是被 dummy 包着的普通结点，"删头"= unlink(head.next)，和删中间结点走的是同一行代码；删尾 = unlink(tail.prev)，也就是淘汰路径本身。没有 dummy 的版本里这两个都得单独写 if，我的版本里它们根本不作为特例存在——容量 1 的用例其实已经同时覆盖了"删头即删尾即删唯一元素"。

**面试官**：OK，今天到这。

## 【本场评分】

- 流程分 ✅：开场主动对齐语义（未命中返回 -1、覆盖即访问、非法容量抛异常），画图讲清两层结构再动笔；写完不等追问，主动给 [1,2] 双 key 用例加容量 1 的极端用例，两轮完整走查。
- 代码分 ⚠️：addToFront 的 prev/next 对调是双向链表的经典手误，被自己走查抓出来而不是被面试官抓出来，挽回大半；修复时顺带说清了赋值顺序的自环坑，说明不是蒙对的。扣在"第一遍就不该反"。
- 沟通分 ✅：全程边写边讲指针语义，白板可跟随；结尾不等提问主动对比生产级差距并挂钩 RedisChunkCacheService 的 LRU+TTL 选型，把算法题拉回了工程语境——本场最大加分项。

## 【如果重来一遍要改什么】

1. addToFront 写反这一下暴露了手写双向链表的熟练度不足：四个指针赋值应该按"先接 node 两条、再改邻居两条、邻居先 prev 后 next"的固定口诀写，回写到肌肉记忆。
2. 走查用例可以更早开始——写完 unlink/addToFront 就先走一遍再往上写 get/put，把 bug 拦在最小单元，而不是整个类写完才走。
3. 容量按字节数加权这个生产点是被追问才说的，本可以放在最初的语义确认里主动提，显得考虑更完整。

# 第三场 · SQL 手写 + 即兴设计（20 分钟体量）

## 【面试官画像】

陈姐，数据平台方向的 Tech Lead，语气温和但问题刁钻，习惯性追问"然后呢"。
风格：不看你 SQL 写得多花哨，看你**是否知道自己的 SQL 在数据脏了之后会发生什么**。
她的口头禅是"数据不会像题目这么干净"。设计题环节她会故意给模糊需求，看你问不问。

## 【这场的真实意图】

1. 连续登录 N 天的"日期减行号分组"是套路题，她真正考的是：知不知道内层去重这道工序、以及窗口函数在 1 亿行上的代价；
2. "数据量 1 亿怎么办"不是要标准答案，是要看你有没有量级感——分区、离线、活跃口径，说出任意两条并知道代价就算过；
3. 即兴点赞设计完全不留缓冲，考的是四步框架（澄清→模型→方案→权衡）是不是刻进了肌肉记忆，以及唯一索引兜底这种"防御性设计"的直觉。

---

**面试官**：表结构给你：`login_log(id, user_id, login_date)`。查连续登录大于等于 3 天的用户。手写。

**我**：先对齐两个口径：第一，"连续"按自然日算，昨天和今天算连续两天；第二，同一天登录多次我理解只算一天——如果按"次"算这题就不是日期连续问题了。另外 3 天是指"任意连续 3 天"还是"从今天往回数 3 天"？我按更一般的"任意连续 3 天"做，如果是后者反而更简单。可以吗？

**面试官**：按任意连续 3 天，同日多次只算一天。

**我**：好，思路：这题的钥匙是**日期减行号的分组技巧**。按 user_id 分区、按 login_date 升序编行号，那么"日期连续"的行的 `login_date - 行号` 会得到同一个值——因为日期每加 1，行号也加 1，相减抵消；一旦日期断了一天，日期跳 2 而行号只跳 1，差值就变了。所以差值相同的连续段天然被归到同一组，每组 COUNT 达到 3 就是答案。

```sql
SELECT DISTINCT user_id
FROM (
    SELECT user_id, login_date,
           login_date - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS grp
    FROM login_log
    GROUP BY user_id, login_date          -- 先去重（同日多次登录）
) t
GROUP BY user_id, grp
HAVING COUNT(*) >= 3;
```

**我**：……写完我走查一下。用户 A 在 1 号、2 号、3 号各登录一次：行号 1、2、3，差值 0、0、0，一组三行，HAVING 命中 ✓。用户 B 在 1 号、3 号、5 号：行号 1、2、3，差值 0、1、2，三组各一行，不命中 ✓。

**面试官**：（不置可否）数据不会这么干净。同一天登录两次呢？

**我**：（停两秒，扫了一眼自己的 SQL）……被你问到了，我确认一下我写的顺序——GROUP BY 是写在子查询里的，在内层就已经按 user_id、login_date 去重了，所以同日多次登录不会进入行号编号。但我想借这个多说一句：**这行 GROUP BY 是这题最容易丢的工序**，如果漏掉它，同一个日期出现两次，后面的行号会整体偏移 1，差值就断了——比如 1 号两次、2 号、3 号各一次，四行的行号是 1、2、3、4，差值 0、-1、-1、-1，真正连续的三天被拆成两组，**该命中的用户被漏掉**，而且是安静的漏，不报错。所以你这一问我答：已处理，在 `GROUP BY user_id, login_date` 这一行。

**面试官**：行。顺手考一个：你这用了 ROW_NUMBER，它和 RANK、DENSE_RANK 什么区别？

**我**：三个都是窗口排序函数，区别在"并列怎么处理"。ROW_NUMBER 无脑 1、2、3、4，并列也硬分先后；RANK 并列同名次、下一名跳号，1、1、3；DENSE_RANK 并列同名次、不跳号，1、1、2。这题必须用 ROW_NUMBER，因为我不是在排名，是在"编行号做差值"，行号必须严格连续，RANK 跳号会把差值算破。什么时候用哪个：比赛榜单要跳号用 RANK，比如第二名并列两个那下一个是第四；要"前 3 名包含所有并列的人"用 DENSE_RANK，我平时取部门 Top3 就用它。

**面试官**：窗口函数一行一行算，数据量 1 亿呢？

**我**：这是量级题，我按代价拆。1 亿行的窗口函数全表排序，单机实时跑不动，我给三个方向，按我自己的优先级：
第一，**缩小统计口径**——真正关心连续登录的往往只是活跃用户，先把窗口限定在"最近 N 天有登录行为的 user_id 集合"上，1 亿注册用户可能活跃的只有几百万，索引按 login_date 走范围扫描，这一步往往是数量级的缩减；
第二，**分区**——login_log 按 login_date 做 RANGE 分区，月表或日表，查询剪枝掉不相关的分区，配合分区裁剪，老数据还能直接归档；
第三，**离线批算**——连续登录本质是用户画像类指标，不需要毫秒级新鲜度，扔给离线任务（每天跑一次，按天增量处理当日登录、维护每用户"当前连续天数"状态位）比在线窗口函数便宜得多，在线接口只查结果表。
三者的共同逻辑是：**OLAP 指标别用 OLTP 的姿势现场算**。老实说 1 亿这个量级我没有实际运维过，以上是标准解法加我自己做分页深翻优化的类比经验。

**面试官**：可以，知道自己量级的边界是好习惯。换个方向，即兴设计题：给内容平台做"点赞"功能，你怎么设计？

**我**：我按四步走，先澄清：几个问题——①量级假设：日活百万、单条内容点赞峰值几千还是几万？②要不要支持"取消点赞"和"点赞列表"（我点过赞的内容）？③点赞数要不要实时精确，还是允许短暂延迟？我先按"要取消、要个人列表、计数允许秒级延迟"这个通用假设做，假设不对您打断我。

**面试官**：按这个假设做。

**我**：第二步，数据模型。核心一张表：

```sql
CREATE TABLE user_like (
    user_id   BIGINT     NOT NULL,
    target_id BIGINT     NOT NULL,     -- 内容 ID
    created_at DATETIME  NOT NULL,
    PRIMARY KEY (user_id, target_id)   -- 天然"一人一条内容一赞"
    -- 或 UNIQUE KEY uk_user_target (user_id, target_id)，主键另用自增
);
```

我特意把"防重复点赞"压进**唯一索引兜底**：不管上层用什么缓存、什么消息队列，只要重复点赞的并发漏到这里，数据库唯一索引冲突会把最后一道门关死——这和我项目里幂等键的思路一样，**上层的所有去重都是优化，唯一索引才是约束**。取消点赞就是删这一行，重复取消幂等无副作用。
计数不单独依赖 count 这张表，另存计数字段。

第三步，核心方案，按写入压力分两档：
- 中低并发：直接写 user_like，点赞数用 `UPDATE counter SET cnt = cnt + 1`，简单正确，量不够再演进；
- 高并发：写路径先落 Redis——Set 存 `like:{target_id}` 的成员、INCR 维护计数，**异步批量落库**刷回 user_like 和计数字段；读路径上"内容点赞数"读 Redis 计数，"个人点赞列表"读库或读个人维度的 Set。

第四步，权衡和边界，三个：
① 两种读的取舍：用户点赞列表（个人维度）和内容点赞数（内容维度）不可能都做成主读强一致，我选**计数走缓存容忍秒级延迟、列表走库保准确**，因为产品上计数抖动无感、列表错一条就是事故；
② Redis 丢数据风险：异步落库前 Redis 挂了会丢赞——可接受就加落库频率，不可接受就先写库再刷缓存，看业务对点赞的态度；
③ 刷赞对抗：单用户频控限流，异常增速告警，这超出本题主干，但做内容平台绕不开。

**面试官**：那我也追问一个：你 Redis Set 存点赞集合，一条爆款内容几百万人点赞，Set 会不会把 Redis 撑爆？

**我**：会，这是这个方案的硬上限——大 Set 是 Redis 的经典反模式，成员上千万之后 SADD 和持久化都会退化。所以我会加一层尺寸策略：`like:{target_id}` 只保留"最近 N 条"或者只做频控去重，完整点赞关系以数据库 user_like 为主存，Redis 只承担热点内容的计数和高频去重的前置过滤。极端量级（微博级别）就要换成"计数全走 INCR、去重靠唯一索引、列表分页查库"，把 Set 从主链路上摘掉。设计到这一步其实是同一个权衡的变体：内存结构放"热且小"的东西，放不下就回库。

**面试官**：最后考你一个：高并发下同一个用户对同一条内容狂点，你的链路里哪一步防住重复？

**我**：三道防线，层层递退：Redis Set 的 SADD 本身幂等（已存在返回 0，可以挡掉绝大多数）；异步落库如果重复入队，靠 upsert（`INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE`）吸收；最后就算前两道全穿，user_like 上的唯一索引冲突兜底，数据库拒绝，不会出现一人两赞的脏行。回答完毕。

**面试官**：好，今天就到这。你有什么想问我的吗？

**我**：两个问题：一是咱们组这类 SQL 和设计题考察的能力，入职后主要落在什么场景——报表、风控还是业务后台？二是团队里新人前三个月一般背什么指标？我想对照着补课。

**面试官**：（笑）问得挺实在。回去等通知吧。

## 【本场评分】

- 流程分 ✅：SQL 动笔前澄清了"自然日/同日去重/任意段还是回看段"三个口径；设计题严格走完澄清→模型→方案→权衡四步，且澄清是主动的、带假设兜底的（"假设不对您打断我"）。
- 代码分 ⚠️：SQL 一次成型且与标准答案一致，含内层去重；但走查用例只给了正例和反例各一个，没覆盖"同日多次登录"这个脏数据用例——防线是被面试官的追问问出来的，不是自己铺出来的，差半档。1 亿追问的三个方向（活跃口径、分区、离线批算）都有且带了代价意识，并诚实声明了量级边界。
- 沟通分 ✅：被"数据不干净"将军时的应对是本场亮点——停两秒、扫自己的 SQL、指出防线所在行号，还反向讲清了漏掉那行的后果；点赞设计的唯一索引兜底讲出了"上层去重是优化、约束才是底线"的工程观。

## 【如果重来一遍要改什么】

1. SQL 走查应该主动把"脏数据用例"编进测试集——同日重复、跨月边界日期（日期减法在 DATE 类型上的行为）这些正该是自检清单项，不该等面试官喂。
2. "1 亿"回答里"只统计活跃用户"应该放在第一位先说，先砍量级再谈技术，顺序上我讲反了半拍。
3. 点赞设计的时间分配：模型阶段讲得略久，权衡阶段的 Redis 丢数据可以更早抛出"看业务对点赞的态度"这句话，把选择题交还面试官，更像真实协作。
