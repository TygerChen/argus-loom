# 从 0 到上线的完整生命周期——以 Argus-Loom 为活教材（2026-10-25）

> 回答一个问题：面试官问"讲讲你从需求到上线的完整流程"时，考察的不是你做了什么功能，而是**你知不知道每个阶段该发生什么、会踩什么坑、出事怎么处理**。这份教材按真实公司的 8 个阶段展开：每阶段 = 标准做法 → 你的项目里对应的事实 → 预判追问 → 诚实答法。
> 最后附一条 3 分钟连贯叙事逐字稿（"讲一个你从 0 到 1 负责的项目"的标准答案）。

## 全景：一个项目从 0 到上线的 8 个阶段

```
立项/需求来源 → ①需求分析 → ②方案设计与技术评审 → ③排期与里程碑
→ ④开发（分支/CR/联调） → ⑤测试（金字塔/验收） → ⑥上线（发布/回滚）
→ ⑦运维（监控/告警/on-call） → ⑧迭代与技术债
                    ↑__________________________|
                          （复盘驱动下一轮）
```

你的项目在每一段都有**真实发生过的对应物**——这就是你的底气。缺的只是"公司里多人协作的仪式感"，下文每一节都会告诉你怎么诚实桥接。

## 阶段 0：立项——需求从哪来

**标准做法**：公司里需求来源通常是三类——业务方提（客户反馈/战略）、数据发现（留存/投诉）、技术驱动（重构/稳定性）。立项要回答：给谁解决什么问题、成功指标是什么、为什么是现在做。

**你的项目对应事实**：
- 需求起源可以诚实讲述："企业内部资料散落在各个文档和表格里，找一个数字要翻半小时；财务数据的保密又要求权限隔离。我给自己写的立项问题就一句话：**怎么让员工用一句自然语言拿到带出处的答案，同时保证财务数据不被越权看到**。"
- 成功指标你真的定过：**问答准确率（评测 95%）、拒答质量（100%）、测试全绿（1646）**——这就是"可度量的立项目标"。

**预判问答**：
| 问 | 答 |
| --- | --- |
| 需求是谁提的？ | "独立项目，需求是我自己基于企业场景定义的——这反而让我完整经历了把一个模糊想法拆成可验收需求的过程。" |
| 怎么确定范围不跑偏？ | MVP 切割：一期只做文档问答，二期才加 Excel 协同，三期财务导入。每个阶段有明确验收线（评测指标） |

## 阶段 1：需求分析——从想法到可验收的 PRD

**标准做法**：产出 PRD/用户故事（作为…我希望…以便…），验收标准（Acceptance Criteria）可测试；需求评审会上产品/研发/测试三方对齐；变更走变更管理（评估影响→排期决策）。

**你的项目对应事实**（面试时可以举例，全是真的）：
- "支持回收站和版本快照"就是一条典型需求演化：一开始文档删了就没了 → 意识到企业场景误删是事故 → 加回收站（batchDelete/batchRestore/batchPurge）→ 再加版本快照与回滚。**这就是一次真实的需求变更管理**：先识别数据丢失风险，评估影响（存储翻倍+删除链路改异步），再排进迭代。
- 财务需求的验收标准写得非常硬："财务角色的接口必须独立校验，权限失败 fail-closed，越权查询返回空证据而非 403"——可以直接讲：**验收标准=测试用例**，这条后来真的被测试覆盖。
- 12 篇用户教程的存在说明：需求包含"可被新人理解"这条非功能指标。

**预判问答**：
| 问 | 答 |
| --- | --- |
| 举一个需求变更的例子？ | 回收站/版本快照那条（上面完整版本） |
| 需求评审怎么做的？ | "我自己的项目没有正式评审会，但有替代动作：每个需求写清验收标准再动手，并且把'为什么做/不做什么'记进决策文档（ai-handoff/DECISIONS_AND_CONSTRAINTS.md）。公司里我知道标准是三方评审+影响评估，这套我按同样严谨度自己执行。"（诚实+展示方法论） |
| 怎么平衡功能与技术债？ | 每个 MVP 阶段留 20% 时间给债；具体例子：前端 Univer vendor chunk 11.4MB 警告，记录为优化项而不是视而不见 |

## 阶段 2：方案设计与技术评审——你最硬的部分

**标准做法**：产出技术方案文档（背景/目标/架构/选型对比/风险/里程碑），过架构评审（会被资深工程师怼选型和容量），定接口契约再开发。

**你的项目对应事实（这是你的王牌区）**：
- 架构决策有书面记录：`ai-handoff/ARCHITECTURE.md` + `DECISIONS_AND_CONSTRAINTS.md`——这就是个人版的"技术方案+评审纪要"。
- 三次标志性选型，每个都有量级依据：
  1. **PG 队列 vs RabbitMQ**：日均几百单，MQ 运维成本>收益；同库事务消除"业务成功消息丢"窗口；留了迁移路径（队列深度指标）。
  2. **模块化单体 vs 微服务**：单人交付+内部规模，单体把复杂度降到最低；分包边界保证日后可拆。
  3. **SSE vs WebSocket**：问答单向流用 SSE（轻、自动重连），真正双向的表格协同才用 WS。
- 每个选型都有"为什么不选别的"——**评审会上被怼的就是这个**，你已经准备了全部答案（追问集）。

**预判问答**：
| 问 | 答 |
| --- | --- |
| 你们的架构评审什么样？ | 诚实版："独立项目没有评审会，我把评审内化成两个动作：每个选型写'对比+否决理由'，以及把方案先讲给 AI 要求它扮演质疑者攻击设计——大量否决意见真的改过设计。"（这是 AI 协作开发者的真实工作方式，且极有说服力） |
| 为什么单体不怕将来拆不开？ | controller/service 分包+权限门禁在模块边界上；无跨模块裸 SQL；共享仅走接口 |
| 容量怎么估的？ | 目标 500 内部用户、日均几百 ETL 任务；压力集 170 例验证检索链路；k6 压测脚本在 scripts/load/ |
| 数据库设计怎么评审的？ | 举实例：excel_sheet_chunk/delta 两表设计（为什么拆）；document_chunk 冗余 fileName 供检索展示的取舍 |

## 阶段 3：排期与里程碑——延期是常态，管理预期是能力

**标准做法**：WBS 拆任务、估算（人日）、留 buffer（20%）、里程碑（MVP→内测→公测）；延期第一动作是**砍范围不是加时间**。

**你的项目对应事实**：
- 你的里程碑天然清晰：一期问答跑通（40 例评测 95%）→ 二期 Excel 协同 → 三期财务+运维完善。可以讲成"我按验收指标倒排"。
- AI 协作带来的排期特点可以大方讲："写代码的时间占比从 70% 降到 30%，省下的时间花在验收标准和测试上——**交付速度上来了，但排期风险从'写不完'变成'验收不严'**，所以我把测试先行当成硬规则。"

**预判问答**：
| 问 | 答 |
| --- | --- |
| 估算不准怎么办？ | "先承认估算必不准：我的做法是任务拆到半天粒度+留 20% buffer+每周重估剩余量；延期第一动作砍范围保核心验收指标。" |
| 砍过范围吗？ | 例子：NL2SQL 自由查询、HyDE 改写——评测显示现有方案已达标，砍掉不为技术清单堆功能 |

## 阶段 4：开发——分支、CR、联调

**标准做法**：分支策略（feature branch→MR→CR→合并主干）、接口契约先行（Swagger/OpenAPI）前后端并行、每日站会对齐阻塞。

**你的项目对应事实**：
- 接口契约真实存在：后端有 Swagger/Knife4j，前端 Vite 代理联调——"契约先行，前后端在同一个 spec 上并行"是真的（哪怕是同一个人分饰两角）。
- Code Review 你做了更狠的版本：**AI 产出必须先说明调用链/事务边界/失败路径，人工审查安全红线后才合并**——这就是你的 CR 流程，而且你真的通过它抓出 2 个 IDOR。
- 联调难题你真踩过：前端 SSE 在 Vite dev 代理下被缓冲——"代理层必须关 buffering"这种坑，就是联调阶段最典型的东西。

**预判问答**：
| 问 | 答 |
| --- | --- |
| 代码怎么 review 的？ | "我的 CR 分三层：①AI 产出先自我陈述调用链/事务/失败路径；②人对着安全与一致性红线逐条审（抓出过两个越权洞）；③测试先行作为 CR 的硬门槛——没有失败测试的 PR 不存在。团队协作场景我理解标准是 MR+至少一人 approve+CI 绿。" |
| 前后端联调踩过什么坑？ | SSE 被代理缓冲导致流式失效（nginx `proxy_buffering off` / Vite 同理）；Excel 大文件上传要调 `client_max_body_size`——都是真实踩的 |
| 分支策略？ | "独立项目主干开发+小步提交；团队场景我理解 feature branch + MR 的价值在于 CR 和隔离" |

## 阶段 5：测试——你有全场最硬的证据

**标准做法**：测试金字塔（单测多→集成中→E2E 少）、回归全量、验收测试（UAT）、质量门禁（CR+CI 绿才能合）。

**你的项目对应事实（直接报数字）**：
- 1646 后端测试 0 失败 + 14 前端测试：单测为主（服务层语义与失败路径）、控制器层测权限与参数、关键链路集成测试。
- **126 项端到端 smoke 测试**（scripts/full_smoke_test.py）：注册→登录→上传→问答→Excel→导出→回收站全链路——这就是 UAT 的自动化形态。
- 评测集（40 基线+170 压力）是"效果层面的回归测试"——大多数候选人完全没有这个概念。
- 失败注入：腐坏 PDF 演练暴露了两层重试互斥——**故障演练也是测试**。

**预判问答**：
| 问 | 答 |
| --- | --- |
| 测试怎么分层的？怎么防"改 A 坏 B"？ | 金字塔+全量回归；AI 协作下全量回归是安全网——"没有这个网，AI 的产出速度会变成事故速度" |
| 测试覆盖率多少？ | 不背覆盖率数字，答"关键语义和失败路径全覆盖，权限和队列的失败分支每条都有用例"——覆盖率是手段不是指标 |
| 验收谁做的？ | 评测集=验收标准（准确率/拒答），smoke=功能验收；"我自己扮演 QA 写验收清单，用测试脚本固化" |

## 阶段 6：上线——发布、检查单、回滚

**标准做法**：发布方式（滚动/蓝绿/灰度金丝雀）、发布检查单（配置/迁移/依赖/回滚预案）、**数据库变更纪律**（迁移只向前、向后兼容、先库后码）、发布窗口与审批。

**你的项目对应事实**：
- **数据库变更纪律你真执行了**：Flyway V1-V8 已执行不可修改，任何库表变更新增 V9+——这就是"迁移只向前"的实践，还能讲出为什么（已上线的库不能重放历史）。
- **发布检查单**：ProductionConfigGuard——prod 缺 9 个必填键/用默认密码/JWT 密钥不足 32 位直接拒绝启动。"上线事故在部署那一刻暴露，而不是半夜在请求里暴露"。
- 回滚预案：ES 不一致有重建端点（数据层回滚思路）；Flyway 场景答"迁移向后兼容设计（加列不删列），回滚代码不回滚库"——标准答案，且你有实践底座。
- 上线方式你可以说："本地/内网部署为主，但我理解并能在方案里写灰度：按用户百分比放量+指标观察+快速回滚。我的系统支持这个做法，因为配置和健康检查都内建了。"

**预判问答**：
| 问 | 答 |
| --- | --- |
| 上线流程走一遍？ | 检查单：①迁移向后兼容确认 ②配置防呆通过 ③smoke 全绿 ④健康检查五组件绿 ⑤回滚预案（代码回滚+库不回滚）⑥发布后 30 分钟盯指标 |
| 出过上线事故吗？怎么处理？ | 诚实桥接："独立项目没有'生产事故'级别的经历，但我做过故障演练：故意上传腐坏文件+kill worker，验证退避/死信/恢复全链路，还真抓出一个重试互斥 bug。公司里 P1 处理的标准姿势我清楚：先止损（回滚/降级）→再定位→最后复盘写 action。" |
| 灰度发布怎么做？ | 概念级+方案级：按用户/流量百分比放量，观察错误率与延迟指标，异常即回滚；我的系统健康检查与指标内建，具备灰度观察条件。诚实标注"未在真实生产流量上操作过" |
| 数据库迁移怎么管理？ | Flyway 版本化+不可变纪律+向后兼容（加列/加表不删改）；V9+ 命名进约定 |

## 阶段 7：运维——监控、告警、on-call

**标准做法**：指标（RED：Rate/Error/Duration；USE：利用率/饱和度/错误）、告警分级（P1 电话/P2 IM）、on-call 轮值、故障复盘（blameless postmortem，产出 action 项）。

**你的项目对应事实**：
- 指标：LLM 用量/成本/成功率/延迟落库可视；队列深度指标；五组件健康检查。
- 告警思路能讲：队列深度超阈值、死信堆积、成功率下跌——"该告警的是症状（死信堆积）不是原因"。
- 恢复自动化：StaleProcessingDocumentRecoveryRunner（卡死任务自动重入队）——把 on-call 里最常见的"重启大法"做成了系统行为。
- 复盘真实发生过：两层重试互斥坑就是一场完整复盘——现象→演练→定位→修复→结论沉淀成文档。

**预判问答**：
| 问 | 答 |
| --- | --- |
| 监控告警怎么设计的？ | RED 思路：检索延迟/错误率/队列深度/死信数；告警绑症状不绑原因；附例子：死信>0 告警是因为它代表"自动恢复失败" |
| 出过线上故障吗？ | 同阶段 6 的诚实桥接；重点讲演练与复盘方法学 |
| 深夜报警电话你怎么处理？ | 标准姿势：先看告警对应哪个症状→止损优先（降级/回滚）→再查因→事后复盘。诚实补一句"我没真正值过生产 on-call，但我把'值夜班会发生的事'前置设计进了系统（恢复 Runner/死信/防呆）" |

## 三分钟连贯叙事逐字稿（背熟：被问"讲一个你从 0 到 1 负责的项目"就交这个）

> "我完整讲一遍这个项目从想法到可运行系统的过程。
>
> **立项与需求**：起点是企业内部的真实痛点——资料散落、找数字靠翻文档，而且财务数据有严格保密要求。我把需求拆成三个 MVP：一期文档问答，二期在线表格协同，三期财务导入与运维完善。每个 MVP 都定了可验收的指标，比如一期就是评测集准确率和拒答质量。
>
> **方案设计**：我做的最大的三个选型是 PG 任务队列而不是 MQ、模块化单体而不是微服务、SSE 做问答流而不是 WebSocket。每个都有书面记录的对比和否决理由——核心依据是量级（日均几百任务）和一致性（任务和业务数据同库同事务）。作为独立开发者，我把评审内化成'书面选型对比 + 让 AI 扮演质疑者攻击设计'，很多设计真的被这一步改掉了。
>
> **开发与测试**：契约先行，接口定义好后前后端并行；AI 协作开发，但人工审查是硬门槛——AI 产出必须先说明调用链、事务边界和失败路径，我对着安全红线逐条审，真的抓出过两个越权漏洞，都是先写失败测试再修。测试是金字塔：1646 个后端测试全绿，外加 126 项端到端 smoke 全链路，再加 40+170 两级评测集管效果回归。
>
> **上线与运维**：上线我做的第一件事是配置防呆——生产环境缺配置、用默认密码、密钥强度不够，直接拒绝启动；数据库用 Flyway 版本化，迁移只向前、向后兼容。运维侧五组件健康检查、LLM 成本观测、队列深度指标都是内建的。我还主动做过故障演练：故意投喂腐坏文件、模拟 worker 挂死，结果真抓出一个两层重试互斥的 bug——业务层的 Spring Retry 把异常吞了，队列的退避和死信根本收不到。修复后失败路径完全可预测：三次退避进死信，同键重传自动复活。
>
> **复盘与迭代**：现在这个系统的文档、架构决策、教程和代码是同步维护的。回头看，这个项目给我的最大收获不是功能，而是**失败思维**——每个环节我都问'它坏了会怎样'，然后把答案做进系统里。"
