# 08 · 后台任务队列 —— 用户不该等的事，都交给它

> 代码入口：`backend/src/main/java/com/argus/rag/job/service/BackgroundJobService.java`（队列核心）
> `BackgroundJobWorker.java`（执行器）、`mappers/job/BackgroundJobMapper.xml`（SQL 精髓）

## 用户的故事

小王上传了一份 200MB 文档。界面立刻显示"上传成功，正在解析"，
他继续做别的事。5 分钟后文档状态变成"可检索"。
**他从上传到可用的全程没有"盯着进度条等待"这个动作**。

如果一个操作可能超过 3 秒，它就不该发生在 HTTP 请求里——
这就是后台任务队列存在的理由。文档解析、Excel 导出、财务导入，全是它的客户。

## 人话版：餐厅后厨的接单板

把后台队列想象成餐厅后厨的**接单板**（词典里的比喻，这里展开讲）：

- 前台（HTTP 接口）收了单，往板上一挂就回身招呼下一位客人——
  **绝不站在灶台前等这盘菜炒完**。用户看到的"正在解析"就是那张小票。
- **一张表 = 接单板**。每个订单写清楚：什么菜（job_type）、单号
  （idempotency_key，防止同一单写两遍）、状态（QUEUED 排队中 / RUNNING 炒制中 /
  SUCCEEDED 出餐 / DEAD_LETTER 做废了等经理处理）。
- **SKIP LOCKED = 两个厨师同时抢单**（词典里有）：厨师 A 伸手拿单 3 号时，
  系统把 3 号"扣在手下"（行锁），厨师 B 扫一眼直接跳过它拿 4 号——
  两人绝不炒同一盘菜。
- **租约 = 认领的菜牌**（词典里有）：厨师拿单时把"此单我做，有效期 5 分钟"
  的牌子插在灶台上。万一厨师中途晕倒（服务器崩溃），5 分钟后牌子失效，
  经理把菜重新挂回板子上，别的厨师接手重做——**一个人倒下，厨房不停摆**。
- **退避重试 = 煳了别急着重炒**（词典里有）：第一次煳了 1 分钟后重做，
  又煳等 5 分钟，再煳等 15 分钟——连续三次说明灶台（依赖服务）可能坏了，
  狂炒只是浪费食材。三次全败 → 进"做废专柜"（死信）等人工来。

为什么用数据库表而不是专业的消息队列（RabbitMQ）？
每天几百单的量，请一位专职传菜员（额外中间件）纯属浪费——
一块板子（一张表）零维护成本，坏了也一眼能看清。**中间件不是荣誉勋章，
够用且简单就是最优**。带着比喻看代码。

## 设计方案：一张表就是一个队列

没有引入 RabbitMQ/Redis，**用 PostgreSQL 一张表实现了一个生产级队列**：

```sql
CREATE TABLE background_job (
    id BIGSERIAL PRIMARY KEY,
    job_type VARCHAR(64) NOT NULL,        -- INGEST_DOCUMENT / EXCEL_EXPORT ...
    idempotency_key VARCHAR(191) NOT NULL, -- 幂等键，防重复入队
    status VARCHAR(32) DEFAULT 'QUEUED',   -- QUEUED/RUNNING/SUCCEEDED/DEAD_LETTER
    attempt_count INT DEFAULT 0,
    max_attempts INT DEFAULT 3,
    lease_owner VARCHAR(128),              -- 当前执行者（租约）
    lease_until TIMESTAMP,                 -- 租约到期时间
    next_run_at TIMESTAMP NOT NULL,        -- 下次可执行时间（退避）
    last_error_code VARCHAR(64), last_error_message VARCHAR(512)
);
```

**为什么不用 RabbitMQ？** 500 人规模的任务量（每天几百个）远够不着 MQ 的适用区间；
数据库队列零新增运维组件、事务一致性好（业务数据和任务在同一个库，同事务落库）、
排查问题就是查一张表。**中间件不是荣誉勋章，够用且简单就是最优**。
什么时候该换？写在 `docs/operations/capacity-runbook.md` 的切换条件里。

**谁在往队列里放任务？（2026-10 接线后的事实）**：上传链路的
`UploadedDocumentFinalizer.finalizeUploaded`——文档元数据落库后、**同一个事务内**
调用 `BackgroundJobService.enqueue(INGEST_DOCUMENT)`。同事务入队是数据库队列
独有的红利：任务行和文档行要么一起提交（Worker 接手），要么一起回滚，
不存在"文档在但任务丢了"的中间态。失败文档的"重试"按钮
（`DocumentDeleteService.retryFailedDocumentIngestion`）也走入队，
幂等键带时间戳代数，不会和历史任务撞键。
幂等键设计：`INGEST:{documentId}:{retryGeneration}`——同代数重复触发直接复用，
死信任务同键再入队会被 `enqueue` 的"死信复活"分支重置回 QUEUED。

## 精髓一：幂等入队

```java
/**
 * 幂等入队：同 idempotency_key 返回既有任务，不重复创建。
 */
public BackgroundJob enqueue(NewBackgroundJobCommand command) {
    BackgroundJob existing = jobMapper.selectByIdempotencyKey(command.idempotencyKey());
    if (existing != null) {
        log.info("任务幂等命中，复用既有任务: jobId={}, key={}", existing.getId(), command.idempotencyKey());
        return existing;
    }
    // ... 创建 QUEUED 任务
}
```

幂等键怎么选？以文档解析为例：`"ingest-{documentId}"`——同一个文档永远只有一个
解析任务，重试、重复触发、人为误操作都指向同一条任务。**幂等键是业务语义，
不是技术随机数**。

## 精髓二：SKIP LOCKED —— 两台服务器不抢活

多个 Worker 同时"取任务"，怎么保证一个任务只被一个 Worker 拿到？看 SQL：

```xml
<!-- FOR UPDATE SKIP LOCKED：多 Worker 并发领取时，被锁定的行直接跳过，不阻塞不重复 -->
<select id="selectDueJobs">
    SELECT * FROM background_job
    WHERE (status = 'QUEUED' AND next_run_at &lt;= #{now})
       OR (status = 'RUNNING' AND lease_until IS NOT NULL AND lease_until &lt;= #{now})
    ORDER BY id
    LIMIT #{limit}
    FOR UPDATE SKIP LOCKED
</select>
```

三个关键词拆开讲：
1. `FOR UPDATE`：选中的行加行锁；
2. `SKIP LOCKED`：已被别的 Worker 锁住的行**直接跳过**（不等待）——
   这是 PostgreSQL 的绝招，MySQL 8 也有。没有它，Worker 之间会互相排队阻塞；
3. 领取后原子 UPDATE（条件更新 + attempt_count+1），0 行 = 被抢走了，跳过。

**面试 30 秒版**：数据库队列的核心是"选行加锁 + 原子认领"两步，
`FOR UPDATE SKIP LOCKED` 让多 Worker 无锁竞争地各拿各的。
对比 Redis 队列：简单可靠但要自己处理"取出后崩溃"的问题——我们的租约就是答案。

## 精髓三：租约（lease）—— 崩溃自愈

Worker 领任务时写下"我认领了，我到 `lease_until` 时间点为止"。
如果 Worker 中途崩了？**任务还在 RUNNING 状态但没人干活**——
其他 Worker 看到"租约过期"，可以接管重跑：

```xml
<update id="claim">
    UPDATE background_job
    SET status = #{toStatus}, started_at = COALESCE(started_at, now()),
        attempt_count = attempt_count + 1
    WHERE id = #{id}
      AND (status = #{fromStatus}
           OR (status = 'RUNNING' AND lease_until IS NOT NULL AND lease_until &lt;= now()))
</update>
```

注意 WHERE 里的第二支：**RUNNING 且租约过期 = 可被接管**。
任务不会因为一台机器死亡而卡死——这就是"自愈"。

**追问：租约设多长？** 5 分钟。太短：慢任务还没跑完就被别人接管 → 重复执行；
太长：真崩溃后要等很久才自愈。**取"正常任务耗时的 P99 再放宽"**，
并且任务执行本身要幂等（解析前先清理旧数据再重建），就算偶尔重复执行也无害。
**租约解决"接管"，幂等解决"接管后重跑不出错"——两者必须成对出现**。

## 精髓四：退避重试与死信

```java
/** 失败重试退避（分钟）：第 1/2/3 次失败后的等待时间。 */
private static final int[] RETRY_BACKOFF_MINUTES = {1, 5, 15};

if (newAttemptCount > maxAttempts) {
    job.setStatus(BackgroundJob.STATUS_DEAD_LETTER);   // 死信：等待人工处理
} else {
    job.setNextRunAt(LocalDateTime.now().plusMinutes(RETRY_BACKOFF_MINUTES[backoffIndex]));
}
```

两个问题各一句话：
1. **为什么不等长重试（每次都 1 分钟）？** 依赖（ES/LLM）故障通常持续一段时间，
   指数退避避免"无效重试打爆对方"，给依赖恢复的时间窗。
2. **为什么要有死信？** 有的任务永远成功不了（文件本身损坏）。无限重试是浪费；
   直接丢弃是事故。死信 = **承认失败并交给人工**，配合监控告警（09 篇），
   `argus.job.dead_letter > 0` 就报警。

**错误信息也讲究**：`last_error_code/last_error_message` 落库且截断（64/512 字符），
人工处理时第一眼就能看到"为什么死"。**死信不是垃圾桶，是待办事项**。

## Q&A：真实世界与面试追问

### Q1：用户上传后马上提问，说"查不到新文档"——怎么让用户不骂街？

技术上一时半会儿好不了（解析就是分钟级），**产品上立刻能好**：
文档状态可见（处理中/可检索/失败 + 失败原因）、失败可重试（前端"重试"按钮 →
重置任务为 QUEUED）、处理完成可通知。**把等待变成可感知、可预期、可干预的过程，
等待就不是问题**。这是全教程反复出现的主题：诚实告知 > 掩盖延迟。

### Q2：任务重复执行了怎么办？（兜底思维）

三层防御：入队幂等（同键不重复建）、认领原子（同任务不被双领）、
**执行幂等**（万一前两层都漏了——比如租约接管后的重跑——任务本身先清理再重建，
重复执行不产生重复数据）。验收门槛里"任务重复执行造成的重复数据 = 0"说的就是第三层。
**防御纵深：每一层都可能被击穿，叠加起来才可靠**。

### Q3：怎么知道队列积压了？

指标化（09 篇详述）：`argus.job.queued`（排队数）、`argus.job.oldest_wait_seconds`
（最久等待——**这个数字比积压总数更能代表用户痛苦**）、`argus.job.dead_letter`（死信）。
告警线：最久等待 > 15 分钟。扩容手段：直接加 Worker 实例（SKIP LOCKED 天然支持多开）。

### Q4：任务优先级怎么实现？（加分思考）

表里预留了 `priority` 列。最简实现：`selectDueJobs` 按 `priority DESC, id` 排序。
但先问业务：**真的需要吗？** 500 人规模 FIFO 通常够用；真需要时优先做"解析任务
让路导出任务"这种粗粒度隔离（不同类型不同线程池），再考虑细粒度优先级。
**先粗后细，先测后优化**。

### Q5：Worker 和 API 部署在一起还是分开？

部署手册（`docs/operations/deployment.md`）的答案：分开。Worker 任务重（解析吃 CPU 内存），
和 API 混部会互相干扰；分开后可以独立扩容（API 2 台 Worker 1 台）、
独立升级（Worker 幂等，重启安全）。**资源画像不同的负载，分开部署**。

## 深挖 Q&A 第二梯队：面试官追问两轮之后的题

> 这一梯队来自 `BackgroundJobWorker` / `BackgroundJobService` /
> `DocumentIngestionAsyncService` 的教学注释（2026-10 补），
> 四个"精髓"章节讲的是机制本身，这里讲**机制背后的取舍和术语**——
> 面试官听到你说了"租约"之后，接下来就会问这些。

### Q6：为什么用数据库表做队列，不用 RabbitMQ/Kafka？（必考，几乎是第一追问）

**30 秒版**：三个理由——① 项目已强依赖 PostgreSQL，任务量级（百级/天）
远够用，引入 MQ 是纯增的运维成本；② 数据库事务让"领取任务"和"业务数据"
保持强一致（MQ 要靠 Outbox 模式迂回实现，本项目 excel 包的协同 Outbox
才是真正用 Outbox 思路的地方）；③ 表结构语义和 MQ 消息几乎一一对应
（status/next_run_at/payload ↔ 消息状态/延迟投递/消息体），**等任务量真上来
再换 MQ，迁移路径是平滑的**。

**展开**：面试官这题真正考的是**技术选型是否匹配量级**，不是"哪个更高级"。
可以补一句加分的："如果日任务到百万级或需要扇出广播，我会换 MQ；
但那时候 SKIP LOCKED 这套语义可以直接翻译成 MQ 的消费者组 + 手动 ack +
死信交换机，业务代码的分发逻辑一行不用改。"——体现"我知道边界在哪"。

### Q7：你说"租约 + 幂等"，面试官说"这在分布式术语里叫什么"？

**30 秒版**：消息投递语义。队列只保证 **at-least-once**（任务至少执行一次——
租约过期接管、Worker 重试都可能让同一任务跑多遍），不保证 exactly-once
（恰好一次——分布式系统里几乎做不到，代价极高）。**所以幂等不是可选项，
是 at-least-once 语义下业务正确性的必要条件**。本项目三处幂等互相独立：
入队幂等（idempotency_key 唯一索引）、认领原子（条件更新）、执行幂等
（ETL 先清理后重建）。

**展开**：这题答出术语层级立刻显专业："at-least-once 投递 + 幂等消费 = 效果上的
exactly-once"——这是 Kafka 官方文档反复强调的等价关系。反过来如果面试官问
"能不能让队列直接保证 exactly-once"，答："Flink 这类流处理引擎在特定拓扑里
可以，但通用任务队列做不到，工程上从不朝这个方向努力。"

### Q8：为什么轮询用 fixedDelay 而不是 fixedRate？这种细节面试官真会问吗？

**30 秒版**：会，而且恰恰爱问——它暴露"背概念"和"真调过"的区别。
fixedRate 每 15 秒触发一次不管上一轮完没完，一轮任务执行慢了下一轮就叠上来，
多批任务同时跑；fixedDelay 是"上一轮跑完后隔 15 秒再跑"，天然串行。
**轮询调度必须用 fixedDelay**，一句话讲清就够。

### Q9：ETL 里 markJobSucceededQuietly 这些 try-catch，是"防御性编程"还是"吞异常"？

**30 秒版**：是有边界的容忍，划线标准是**"它是不是用户可见的事实"**。
任务记录表（ingestion_jobs）是观察窗口，更新失败顶多监控盲区，只 warn 不抛；
文档状态（document.status）是用户看到的事实，更新失败必须抛。
同样的原则在 QaService：LLM 记账失败可容忍（回答已到手，不该作废），
问答落库失败必须抛（业务数据完整性）。

**展开**：面试官追问"那你怎么发现观察窗口坏了？"答："warn 日志有告警规则，
ingestion_jobs 的状态和 document.status 定期对账（可加定时校验任务）。
**容忍 ≠ 不管，是降低失败的爆炸半径后再监控它**。"这个回答把"吞异常"的质疑
翻转成了分层设计。

### Q10：重试为什么是 2s/4s/8s（ETL）和 5/15 分钟（队列）两套？乱不乱？

**30 秒版**：不乱——**重试间隔要匹配故障的预期时长**。ETL 的失败多是
秒级抖动（数据库连接闪断、ES 短暂超时），指数退避 2/4/8 秒几次内大概率恢复；
队列任务的失败常是分钟级故障（ES 磁盘满、外部服务宕机），退避单位用分钟，
5/15 分钟的间隔还带"人工还没介入前别疯狂空转"的意味。**没有万能重试参数，
只有匹配故障画像的参数**。

**展开**：可补一个原则性细节：两处都配了上限（maxAttempts=3 + 死信）——
重试策略永远和"放弃策略"成对出现，只写重试不写放弃的任务是定时炸弹。

### Q11：一分钟讲完你们的异步链路（面试收尾常用）

逐字稿，可以背：

> "上传接口只做三件事：存文件、建文档记录、入队，秒回。后台 Worker 用
> SKIP LOCKED 从任务表原子认领，执行 ETL——先清理旧产物再解析分块再向量化，
> 保证可重跑的幂等。执行层故障按 5/15 分钟退避重试，耗尽进死信等人工（业务性失败由 ETL 层快速终结为文档 FAILED）；
> Worker 崩溃由 5 分钟租约兜底，其他实例自动接管。文档状态机
> PENDING→PROCESSING→READY/FAILED 驱动前端展示，用户随时知道文档在哪一步。
> 监控看三条线：READY 率、死信数量、最久等待时间。"

每个短语都对应代码：入队=`UploadedDocumentFinalizer.finalizeUploaded`（调 `BackgroundJobService.enqueue`，同事务），
认领=`claimDueJobs`，
幂等=`DocumentIngestionAsyncService.cleanupProcessingArtifacts`，
退避死信=`failOrRetry`，租约=`lease_until` 字段，状态机=`DocumentStatus`。
面试官挑任何一个词深入，你都接得住——这就是"把项目讲成自己写的"的标志。

## 动手实验

1. 上传一份损坏的 xlsx，观察任务进入重试 → 最终 DEAD_LETTER，
   查看 `background_job` 表的 `last_error_message` 和 `attempt_count`。
2. 手动把一条 QUEUED 任务的 `next_run_at` 改到过去，
   观察它在 15 秒内被 Worker 领走（如果日志开着，能看到认领记录）。
3. 读 `BackgroundJobMapper.xml` 全文（只有 40 行），逐条 SQL 说出它在解决什么问题。
