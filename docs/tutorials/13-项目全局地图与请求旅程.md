# 13 · 项目全局地图与请求旅程 —— 对着目录树讲 5 分钟

> 面试官说"带我看看你的项目结构"时，这一篇就是你的底稿。
> 目标：合上文档，你能对着 IDE 的目录树从上讲到下，把一个请求从浏览器讲到数据库。

## 一、整体架构：三层楼

把系统想象成一栋三层楼：

- **三楼（前端 Vue3）**：用户看到的一切页面。它自己不存任何重要数据，
  所有事情都靠打电话（HTTP 请求）问二楼。
- **二楼（后端 Spring Boot）**：干活的楼层，18 个业务房间（包）各管一摊。
  楼里有一条铁律：**任何房间接活前先过安检（登录校验 + 权限校验）**。
- **一楼（基础设施）**：PostgreSQL（数据库）、Elasticsearch（搜索引擎）、
  MinIO（文件仓库）。二楼的所有记忆都存这里，二楼自己几乎不记东西——
  重启了也不丢，因为"进度必须落库"（01 篇讲过的核心原则）。

**为什么要分三层而不是混在一起？** 每层可以独立升级、独立扩容、独立排错：
页面改版不用动业务逻辑；业务量大时多开几个二楼（多实例）；换数据库也不用重写页面。
这个"为什么"本身就是面试高频题。

## 二、后端 18 个包的地图（按"讲给人听"的顺序分组）

所有包都在 `backend/src/main/java/com/argus/rag/` 下。别按字母序背，按功能组记：

**入口与规则（谁都能进来的门厅）**
| 包 | 管什么 | 对应教程 |
| --- | --- | --- |
| `auth` | 登录、JWT 签发/刷新/吊销、密码哈希 | 02 |
| `user` | 用户资料、偏好 | 02 |
| `common` | 全楼公用的工具间：统一异常、日志、限流（`ratelimit`）、线程池、健康检查（`health`） | 09 |
| `config` | Spring 的装配说明书（各种 Bean 怎么造） | — |

**知识库主线（这栋楼存在的原因）**
| 包 | 管什么 | 对应教程 |
| --- | --- | --- |
| `group` | 知识库（群组）：建库、成员、邀请、加入申请 | 03 |
| `document` | 文档：分片上传、秒传、文件存取（`storage` 子包对接 MinIO） | 01 |
| `ingestion` | 入库管线：解析 → 分块 → 向量化 → 双索引落库 | 04 |
| `embedding` | 把文字变成向量（本地 bge-small-zh，512 维） | 04 |
| `job` | 后台任务队列：一张表 + SKIP LOCKED + 租约 + 退避 | 08 |
| `qa` | 问答：检索（`rag` 子包）、引用、拒答判定、历史记录 | 04 |
| `assistant` / `llm` / `prompt` / `engine` / `evaluation` | 对话助手会话、大模型调用封装、提示词模板、执行引擎、效果评估 | 04 |

**Excel 与财务线（第二支柱）**
| 包 | 管什么 | 对应教程 |
| --- | --- | --- |
| `excel` | Excel 解析（流式 SAX）、协同编辑（`collab` + Outbox）、版本/导出/回收站、权限（含财务隔离） | 03/05/06 |
| `excel/finance` + `finance` | 财务导入、期间开关、报表 | 07 |
| `metrics` | 监控指标（队列深度、积压等，喂给 09 篇的告警） | 09 |

**面试一句话总结**：*"后端按业务域分包，每个包内部分 controller（接请求）/
service（干业务）/mapper（碰数据库）/model（数据形状）四层——
横切关注点（安全、限流、监控）抽到 common，不跟业务代码搅在一起。"*
这句能接住 90% 的"讲讲你的项目结构"。

## 三、前端地图（30 秒版）

`frontend/src/` 下：

- `views/` = 页面（`documents` 文档、`qa` 问答、`excel` 协同表格、`groups` 知识库、
  `admin` 管理、`settings` 设置）；
- `api/` = 所有 HTTP 请求的封装（页面不直接写请求地址，统一从这里调）；
- `stores/` = Pinia 全局状态（最典型的是登录态：Access Token 存内存）；
- `router/` = 路由（网址 → 页面的映射表，带登录守卫）；
- `components/` = 可复用的小部件（按钮、弹窗、上传条）。

前端的一句话总结：**页面（views）只管长相，请求（api）只管传话，
状态（stores）只管共享，谁也不越界**。

## 四、核心数据表：系统的"户口本"

数据库几十张表，记住这 10 张就能讲清全项目（建表脚本在
`backend/src/main/resources/db/migration/`，Flyway 自动执行）：

| 表 | 存什么 |
| --- | --- |
| `users` / `user_refresh_tokens` | 用户和刷新令牌（02 篇的"票根"） |
| `groups` / `group_memberships` | 知识库和成员关系（03 篇的"酒店房间和住客"） |
| `documents` / `document_upload_sessions` / `document_upload_chunks` | 文档 + 上传会话 + 已收分片（01 篇的"搬家登记簿"） |
| `document_chunks` / `vector_store` | 文本块 + 向量（04 篇的"卡片和索引"） |
| `ingestion_jobs` / `background_job` | 解析任务和通用后台任务（08 篇的"接单板"） |

其余围绕它们展开：协同（`excel_collab_outbox` 便签盒）、财务
（`finance_import_batch` 导入批次 + 期间表）、问答审计（`qa_records` + 引用表）。

## 五、重头戏：一次问答请求的完整旅程

面试官最爱"讲一个请求的完整流程"。用最核心的问答举例——用户在页面问
"差旅住宿标准是多少？"：

```
① 浏览器：POST /api/qa/ask（带着 Access Token）
      ↓ Vite 开发服务器反向代理 → 后端 10001
② 过滤器链：验 JWT 签名和有效期（02 篇的"扫手环"）→ 拿到"你是谁"
③ QaController（qa/controller）：参数校验，把活转给 Service 层
④ QueryPlanningService：审题——问题清楚吗？要不要改写/拆解？（04 篇）
⑤ HybridChunkRetrievalService（qa/rag）：双路召回
      ├─ PostgreSQL pgvector：按"意思"找（向量距离）
      └─ Elasticsearch：按"字面"找（关键词）
      → 合并去重 → DocumentRoleGate 权限过滤（没权限的卡片直接扔掉）
      → 重排序
⑥ EvidenceAssessor：看着检索结果判断——证据够不够回答？
      不够 → 直接返回"知识库中没有找到依据"（RETRIEVAL_NOT_GROUNDED），不调用大模型
      够   → 把"问题 + 选中的资料块"拼成提示词（prompt 包的模板）发给大模型
⑦ 大模型"看着资料说话" → CitationAssembler 把答案和引用编号组装好
⑧ 落库：qa_records 存这轮问答 + qa_record_citations 存引用（可审计、可回溯）
⑨ 响应沿原路返回浏览器，页面渲染答案 + 可点击的引用
```

**这段旅程串起了教程 02（认证）→ 03（权限）→ 04（RAG）→ 08（审计落库）**。
面试时你能一口气讲完并随时停在任意一步展开，"懂这个项目"就不需要自证了。

类似地，还有两条值得背下来的旅程：

- **上传旅程**（01 篇）：前端算指纹 → init 三级判定 → 分片上传 → complete 合并 →
  异步入队（08 篇）→ Worker 解析分块向量化 → 状态变"可检索"；
- **协同旅程**（05 篇）：单元格编辑 → 乐观锁校验版本 → 单格落库 →
  Outbox 便签 → 发布器广播 → 对方屏幕秒级更新。

## 六、怎么用这张地图（练习方法）

1. 打开 IDE，按第二节的分组顺序把 18 个包点开各看 1 分钟，只看包里
   `controller` 和 `service` 的类名，混个脸熟；
2. 对着第五节，在 IDE 里真的从 `QaController.ask` 一路点进去走到
   大模型调用为止——**亲手走一遍胜过看十遍**；
3. 合上文档，白纸上画出三层楼 + 问答旅程，画不全的地方就是你的盲区；
4. 面试前一晚重画一遍。能画出来，结构题就稳了。
