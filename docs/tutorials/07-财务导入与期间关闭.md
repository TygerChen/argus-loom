# 07 · 财务导入与期间关闭 —— 真实业务规则如何写进代码

> 代码入口：`excel/service/FinanceImportService.java`（导入+幂等+乐观锁）、
> `excel/service/FinancePeriodService.java`（期间开关）、`excel/service/FinanceAnalysisService.java`（分析）

## 用户的故事

月底，财务小周导入 9 月费用流水。她传了一个含错误的文件——系统没有直接入账，
而是列出 10 条问题："第 5 行金额格式错误、第 12 行日期超出导入期间……"。
她改好重传，这次校验通过，确认后正式入账。两天后她发现一笔 9 月的报销录错了想改——
**系统拒绝了：9 月已经关账**。她找财务组长重开期间，组长填了原因"补录 9 月第 47 笔凭证"，
系统留下审计记录后才放行。

财务软件和普通软件最大的区别：**用户的每一个"失误"都可能是资金事故**，
所以流程里到处是"刹车"。

## 人话版：为什么财务系统到处是"刹车"

普通系统追求"丝滑"，财务系统还要追求"每一脚都有刹车"。这一篇的几个刹车：

1. **先预览后入账 = 试衣间**。买衣服先试穿（校验报告），
   合身才买单（正式入账）。没有试衣间的财务系统，用户只能"提交后祈祷"。
2. **文件指纹幂等 = 超市小票核对**（01 篇讲过指纹）。同一张小票不能报销两次——
   同一份文件不能入账两次。和知识库上传不同：知识库重复了**默默复用**（用户爽），
   财务重复了**明确拦下**（防重复记账）。同一个技术，不同的刹车力度。
3. **关账 = 盖章的档案盒**。9 月过完，账本放进档案盒、盖上章（关账），
   谁都不能再往里塞纸条。想塞？组长必须填写"为什么拆封"（重开原因），
   而且拆封动作本身会被记录在案（审计）——**不是禁止改，而是改必须留痕、必须有理由**。
4. **fail-closed = 门禁断电时的选择**。期间状态拿不准（系统故障、数据异常）时，
   系统按"已关账"处理——宁可让你干等，也不让你往可能封死的账本里写数据。
   这叫 fail-closed（出错即封闭）。反过来 fail-open（出错放行）在财务场景等于裸奔。

记不住细节时记住一句话：**财务系统的每个"麻烦"，都是某次真实资金事故换来的**。

## 设计一：先校验预览，确认后才入账

上传 → 解析 → **只生成校验报告（预览），不写台账** → 用户看过问题清单 →
确认 → 真正入账。把"检查"和"入账"拆成两步，用户从"提交后祈祷"变成"提交前知情"。

**为什么不让系统自动修错？** 金额格式错误可以自动修，但"日期超出期间"背后可能是
业务决策（这笔记 10 月还是改期间？）。**机器修明显的错，人做判断的题**。

## 设计二：文件指纹幂等

```java
/**
 * 文件幂等校验：同哈希文件已存在批次时抛 FINANCE_FILE_DUPLICATED。
 */
void assertFileNotImported(String fileHash) {
    Long count = batchMapper.selectCount(new QueryWrapper<FinanceImportBatch>()
            .eq("file_hash", fileHash));
    if (count != null && count > 0) {
        throw new BusinessException(ErrorCodes.FINANCE_FILE_DUPLICATED,
                "该文件已导入过，请勿重复上传；如需重导请先删除旧批次或改用新文件");
    }
}
```

注意和知识库上传（01 篇）的区别：**知识库重复 → 静默复用（用户友好），
财务重复 → 明确拒绝（安全第一）**。同一个技术（SHA-256），
不同的产品决策——财务场景"相同文件"可能意味着"忘了换数据"，静默复用会掩盖错误。
拒绝信息里还告诉用户出路："删除旧批次或改用新文件"。

## 设计三：并发编辑的乐观锁（行级指纹）

两个财务同时改同一笔流水，怎么防止后写的覆盖先写的？每行记录算一个"内容指纹"：

```java
static String recordFingerprint(FinanceLedgerRecord record) {
    return String.join("|",
            text(record.getDayLabel()), text(record.getSummary()),
            text(record.getCounterparty()), /* …所有业务字段… */ amount(record.getIncome()));
}
```

编辑请求必须带 `expectedFingerprint`（"我看到的版本"）。数据库行级锁
（`selectByIdForUpdate`）保证读-比-写原子：指纹不匹配 → 抛 `CONCURRENT_MODIFIED`
"记录已被其他用户修改，请刷新后重试"。

**为什么不用版本号列而用内容指纹？** 内容指纹不依赖额外字段、语义直白
（"内容变了就是别人改过"）。版本号列在多字段部分更新时更容易出错。
两种都是乐观锁，选型看团队习惯和数据特征。

## 设计四：期间关闭（关账）

```java
/**
 * 核心规则：期间关闭后，业务日期落在该月的导入与编辑一律拒绝（fail-closed）；
 * 重新打开必须填写原因；关闭与重开都记录操作人与原因，形成审计线索。
 */
public void assertPeriodOpen(LocalDate businessDate) {
    FinancePeriod period = selectByMonth(
            businessDate.format(DateTimeFormatter.ofPattern("yyyy-MM")));
    if (period != null && FinancePeriod.STATUS_CLOSED.equals(period.getStatus())) {
        throw new BusinessException(ErrorCodes.FINANCE_PERIOD_CLOSED,
                "期间 " + month + " 已关闭，禁止修改财务数据");
    }
}
```

三个设计点：
1. **fail-closed**：查询失败/期间不存在 → 放行（OPEN 语义）；状态明确是 CLOSED → 拒绝。
   错误方向要选对：财务宁可"该改的没改成"，不可"该锁的没锁住"。
2. **重开必填原因**：不是技术需要，是**审计需要**——"谁在什么时候为什么重新打开了
   已关账的期间"是财务合规的核心问题。重开原因、操作人、时间全部落库。
3. **拦截位置在服务层**：不管请求从哪个入口来（网页/接口/未来的批量工具），
   只要经过服务层，关账就拦得住。**规则放在离数据最近的地方**（03 篇权限同款思想）。

## 设计五：分析必须可下钻，AI 只看汇总

```java
/**
 * AI 财务问答上下文：只包含聚合数字、期间、定位信息与问题原文；
 * 原始明细行不出服务层，AI 只在授权汇总上工作。
 */
public Map<String, Object> aiQuestionContext(LocalDate from, LocalDate to, String question) {
    context.put("summary", periodSummary(from, to));       // 聚合数字
    context.put("topCounterparties", dimensionSummary(...)); // Top N
    context.put("anomalyCount", detectAnomalies().size());  // 异常数
}
```

两条产品红线：**每个数字都能点开看到原始行**（可复核——财务数字必须能对账）；
**AI 拿不到明细**（它可能编造一行不存在的流水，而财务的编造是事故）。
异常提醒（大额支出、重复付款）也只是"提醒 + 命中原因 + 原始记录链接"，
永远不写"这是违规"——**系统提示风险，人做结论**。

## Q&A：真实世界与面试追问

### Q1：导入到一半失败了，会不会出现"半批数据"？

整个导入在一个数据库事务里（`@Transactional`）：任何一步失败全部回滚，
台账里要么有这个批次要么完全没有。**事务是"原子性"的教科书应用**——
一批数据要么全进去，要么全不进，不存在"导了一半"的中间态。

**追问：几万行一个事务，事务太大回滚不也慢吗？** 慢（几秒），但正确性优先；
真到百万行级别，拆子事务 + 批次状态机（每 5000 行一个检查点，失败从检查点续传）。
500 人规模用不到，但面试能说出演进路线。

### Q2：财务数据错了，怎么改？直接 UPDATE 吗？

可以改（有编辑权的人，通过界面），但每次修改都过指纹乐观锁 + 操作日志
（改前值、改后值、谁、何时）。**财务永远不做"无声修改"**。
更好的实践是"红字冲销"（录一笔负数抵消原记录），保留完整业务轨迹——
我们目前支持直接修改+留痕，冲销是迭代方向。

### Q3：关账后发现漏了一笔怎么办？（真实高频问题）

正规流程就是设计好的路径：组长重开期间（填原因）→ 补录 → 重新关账。
重开动作本身带审计，事后可查"9 月账为什么在 10 月 3 日被打开过 20 分钟"。
**系统不给后门，但给带记录的正门**——既满足业务，又满足合规。

### Q4：为什么报表数字和我自己用 Excel 算的对不上？

排查路径（面试考"排查思维"）：① 筛选条件是否一致（区域/币种/期间）；
② 是否只统计"当前版本"批次（历史版本默认不参与）；③ 收入支出口径
（income/expense 字段 vs 借贷方向）。分析接口的响应里显式返回
`periodFrom/periodTo/batchIds`——**口径跟着数据走，用户看得见口径**。

### Q5：异常提醒会不会天天误报，最后没人看？

阈值可配（默认单笔 1 万、7 天 3 笔同供应商），并且**每条提醒都展示规则和命中明细**，
让财务自己判断"这是正常的大额房租还是异常"。误报的治理：按部门/科目调阈值、
白名单（房租这种固定大额）。**告警的生命周期管理比告警本身更重要**——
这和 09 篇运维告警是同一个道理。

## 动手实验

1. 用同一个文件连续导入两次，观察第二次的 `FINANCE_FILE_DUPLICATED` 错误提示。
2. 关闭当前月 → 尝试修改该月流水 → 观察拒绝 → 重开（填原因）→ 再改成功，
   然后去数据库看 `finance_period` 表里的审计字段。
3. 开两个浏览器同时编辑同一笔流水，观察后提交的那个收到 `CONCURRENT_MODIFIED`。
