# 03 · 权限系统 —— "你能干什么"的判定机器

> 代码入口：`backend/src/main/java/com/argus/rag/excel/service/ExcelPermissionService.java`
> 辅助：`com/argus/rag/group/service/GroupMembershipService.java`（知识库成员）

## 用户的故事

财务组长老张建了一份预算工作簿，把"查看"权限给了全部门，"编辑"只给了两个人。
普通员工小王试图改一个格子——系统拒绝；他试图用接口直接猜文档 ID 下载——也被拒绝；
而公司系统管理员（技术上权限最大）打开财务工作簿，同样被拒——
**财务数据只有财务角色能看，管理员也不行**。小王说：这系统"分得清边界"。

权限系统的目标就是这三句话：该进的进，不该进的进不来，**连"系统自己"也不许越界**。

## 人话版：权限就是"酒店房卡"

把系统想象成一家酒店（词典里的比喻，这里展开讲）：

- ** owner（创建者）= 总统套房的住客**：这间房是你的，想干嘛干嘛，还能决定给谁配钥匙。
- **editor（编辑者）= 拿了带开房门钥匙的访客**：能进屋、能搬动家具（改数据），
  但不能把房子转给别人。
- **viewer（查看者）= 只能隔门玻璃看的访客**：能看屋里摆设（读数据），
  但摸不到任何东西。
- **系统管理员 = 酒店工程部**：能修电梯、换门锁（维护系统），
  **但钥匙串打不开任何客房**——工程部能进客人房间，这家酒店就没人敢住了。

而"IDOR 攻击"（词典里有）就是：一个只订了 1018 房的客人，**挨个门把手试钥匙**——
1019、1020……哪扇门开了，就是酒店的失职。所以我们有两道铁律：
**每次按编号取房间，必须先刷一次权限**；每次刷不开，记录"谁在什么时候试了哪扇门"
（审计日志）。下面看代码里这台"判定机器"怎么运转。

## 设计方案：角色层级 + 显式授权

Excel 文档的权限判定，源码里的注释就是设计文档：

```java
/** 权限优先级：财务文件隔离 > 系统管理员 > 文档创建者（owner）> ACL 授权（EDITOR/VIEWER）。 */
```

判定是一个短路链条，代码一目了然：

```java
/** 计算当前用户对文档的权限等级（owner / editor / viewer / null）。 */
if (user.systemRole() == SystemRole.ADMIN) return "owner";
if (user.userId().toString().equals(String.valueOf(document.getCreatorId()))) return "owner";
// ... 否则查 ACL 授权表
return permission.getRole() == null ? "viewer" : permission.getRole().toLowerCase();
```

然后所有"能不能"都变成对等级的比较：

```java
// canEdit = owner 或 editor
return "owner".equals(level) || "editor".equals(level) || isAdmin();
```

**为什么用一个字符串等级而不是一堆布尔字段？** 一堆布尔（isOwner/isEditor/canDownload/
canShare…）组合爆炸且互相矛盾；单一等级天然有序（owner > editor > viewer），
新增能力只是改等级的判断规则，不用加字段。

**为什么财务隔离放在优先级第一位？** 这是最小权限原则的体现：
管理员的存在意义是"维护系统"，不是"查看业务数据"。如果管理员可以看财务，
那么任何一个管理员账号被盗 = 全公司财务数据泄露。**权限模型里"例外"越少越安全**。

## Q&A：真实世界与面试追问

### Q1：前端已经把按钮藏起来了，后端还要校验吗？

**必须**。藏按钮是给正常用户的引导；后端校验才是防线。攻击者不需要你的前端——
`curl -X DELETE https://xxx/api/excel/documents/1` 一行命令直达后端。
**前端权限控制的是"可见性"，后端权限控制的是"可能性"**。凡是只有前端校验的接口，
等于没校验。

本项目做法：控制器层先 `requireFinance()` / `requireView()` 拦一道，服务层关键操作再拦一道
（双保险，防止新控制器忘了校验）。

### Q2：什么是 IDOR？为什么它常年霸榜 OWASP？

IDOR（不安全的直接对象引用）大白话：**把 URL 里的 ID 换成别人的，就能看别人的数据**。
比如 `/api/excel/documents/100` 是你自己的，改成 `/api/excel/documents/101`——
如果后端只查了文档存在而不查"你是否可见"，数据就泄露了。

它霸榜的原因：自动化扫描测不出来（每个 ID 都要合法登录才有意义），
而且**每个接口都要单独防**——漏一个就是事故。

**我们的解法**：所有按 ID 访问的资源，先取文档，再过 `canView/canEdit`，
无权一律返回 403/404。验收手册（`docs/acceptance/security-regression-checklist.md`）
把"普通用户猜测财务资源 ID"列为必测项——**反向测试和正向测试一样重要**。

**面试 30 秒版**：IDOR 的根治方法是"永远不裸查"——按 ID 查询后必须接权限判定，
并把越权访问记入审计日志（我们连"猜 ID"的行为都留痕）。

### Q3：权限判断写在服务层还是控制器层？

我们两层都写，职责不同：控制器层负责"统一入口拦截"（保持薄），
服务层负责"业务兜底"（防止别的调用方绕过控制器）。
只写控制器层的问题是：一旦有人新写了一个控制器（或内部定时任务直接调服务），
权限就被绕过了。**越靠近数据的地方校验，越安全**。

### Q4：为什么"查看"和"编辑"要分开？合并成一个"有权限"不行吗？

不行，因为**查看和编辑的风险完全不对称**：看错数据的代价是泄露，改错数据的代价是
数据损坏 + 无法追责。财务场景下编辑权必须精确到人——所以才设计了
owner/editor/viewer 三级，而且每次编辑都落操作日志（谁、何时、改了什么、改之前是什么）。
**权限粒度 = 追责粒度**。

### Q5：两个人同时有编辑权，怎么防止互相覆盖？（权限的邻居问题）

权限只解决"谁可以改"，并发解决"改的时候谁赢"。这是 05 篇的主题
（乐观锁 revision + LWW），但权限侧也有一半责任：**没有编辑权的人连制造冲突的资格都没有**。
面试聊到协同编辑，先讲权限闸门再讲冲突合并，逻辑才完整。

### Q6：权限缓存了会怎样？改了权限多久生效？

实时查询（每次按 ID 查文档+ACL）在 500 人规模完全够用，不做缓存——
因为**权限一旦缓存，"回收权限"就有了延迟**，而延迟期间的数据泄露无法追回。
性能不够时的正确姿势是：缓存 + 权限变更主动失效，而不是无限期缓存。
这是"性能 vs 安全即时性"的又一组权衡。
