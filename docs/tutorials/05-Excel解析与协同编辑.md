# 05 · Excel 解析与协同编辑 —— 大文件不爆内存，两个人不打架

> 代码入口：`backend/src/main/java/com/argus/rag/excel/service/StreamingParserService.java`（流式解析）
> 编辑持久化：`backend/src/main/java/com/argus/rag/excel/service/ExcelSheetService.java`
> 冲突核心：`backend/src/main/java/com/argus/rag/excel/collab/CollabService.java`

## 用户的故事

财务老张上传了一份 80 万行的银行流水（40MB），系统 10 秒后就能在线查看。
同时，他和同事小刘都在编辑这份表——小刘改了 B3 单元格，老张的屏幕上 1 秒内
跳出了同样的修改；老张几乎同时改了同一个 B3，系统弹窗：
"该单元格已被他人更新——刷新查看，或覆盖服务器内容"。

这一篇的两个主角：**怎么让 80 万行进得了内存（流式解析），
怎么让两个人不打架（冲突合并）**。

## 人话版：吃巨无霸和共用白板

两个主角各有比喻（词典里有，这里展开讲）：

**上半场 · 流式解析 = 一口一口吃巨无霸**。40MB 的 Excel 就是一个巨型汉堡。
全量加载 = 试图整个塞进嘴里——噎住（内存爆掉）是必然的。
流式 SAX = 一层一层吃：咬一口（读一行），咽下去（处理完就扔），
嘴里（内存里）**永远只有一口的量**。吃多厚的汉堡都不会噎住。
代价是不能"回头咬第 5000 层"——所以小文件还是整个拿起来啃更方便，
大文件才必须一口一口吃。

**下半场 · 协同编辑 = 一块共用白板**。你和小刘在写同一块白板：
- 每写一笔，白板右上角的"第 N 版"数字就 +1（**版本号**）；
- 你动笔前瞄一眼版本："我是照着第 10 版改的"（**baseRevision**）。
  交上去时发现已经是第 11 版了——有人抢先了，服务先把你的笔还给你：
  "先看看人家写了啥，再决定怎么改"（**冲突弹窗**）；
- 万一你俩**同一秒**写同一个格子？裁判按"后动手的算数"裁决
  （**LWW，最后写入胜出**）——规则简单，但必须有，否则两人各说各话。

还有个隐藏问题：小刘写了字，怎么让老张的屏幕立刻看到？
靠"广播"。但广播有丢的可能——所以用一个**捎话便签盒**（**Outbox**，词典里有）：
每次改完先写一张便签"待广播：B3 变成 500"放进盒子，发布员每半秒扫一次盒子
挨个广播，广播失败便签还留着、下轮再试。**先记账，再喊话，喊不响就再喊**。
带着比喻看代码。

## 上半场：两种解析模式

项目里并存两个解析器，各自服务不同场景：

```java
// ExcelParserService：常规模式 —— WorkbookFactory 全量加载
Workbook workbook = WorkbookFactory.create(is);

// StreamingParserService：流式模式 —— XSSFReader + SAX
/**
 * 大文件流式解析服务 — XSSFReader + SAX，内存恒定，支持合并单元格和格式化。
 */
```

| 模式 | 内存 | 速度 | 能做什么 |
| --- | --- | --- | --- |
| 全量加载（WorkbookFactory） | 与文件大小成正比，40MB 文件可能吃掉 1-2GB 堆内存 | 快 | 随机读写、样式、公式重算 |
| **流式 SAX（我们的选择）** | 恒定（逐行读，读完就处理） | 快 | 顺序读取；样式支持有限 |

SAX 的原理：xlsx 本质是 XML 打包，SAX 是"边读 XML 边回调"的解析器——
读到 `<row>` 就处理这一行，处理完就扔。**内存里永远只有一行**，80 万行也扛得住。

**为什么不全部用流式？** 流式不能"回头"（不能随机访问第 5000 行）、
复杂样式/合并单元格处理受限。所以小文件用全量（体验好），大文件用流式（活命要紧）——
**按输入规模选实现，是后端工程师的基本功**。

## 下半场：协同编辑的冲突设计

### 设计三件套

1. **文档版本号（revision）**：每次成功编辑，文档版本 +1；
2. **乐观锁**：编辑请求带 `baseRevision`（"我是基于第 10 版改的"）。
   服务器当前已是第 11 版 → 拒绝，返回 `REVISION_CONFLICT` + 服务器最新版本；
3. **LWW（Last-Write-Wins）兜底**：同一单元格毫秒级碰撞时，时间戳新的赢。

**为什么选乐观锁不选悲观锁？** 悲观锁（"编辑前先锁住这个格子，别人不能动"）
体验差：老张锁着 B3 去吃饭，小刘干等两小时。乐观锁默认"不会冲突"，
冲突了再让用户决策——**协同编辑的冲突率天然低（两个人同时改同一格本来就罕见），
为低概率事件加高成本约束不划算**。

**为什么还要 LWW？** 版本锁是文档级的，锁粒度粗；两个请求都基于第 10 版
但改的是不同单元格，其实不冲突（都能接受）。只有**同一单元格**的毫秒级碰撞
才需要最后仲裁——LWW 以"最后发起者胜出"这个简单规则收尾。

**冲突了不是扔异常，而是给用户选择权**：

```
REVISION_CONFLICT + serverRevision
  → 前端弹窗：① 刷新后重试（看别人的修改再改） ② 覆盖服务器内容（我的修改优先）
```

记住产品原则：**系统不替用户做决定，但必须把后果讲清楚**。

### 广播可靠性：Outbox 模式

小刘的修改怎么出现在老张屏幕上？WebSocket 广播。但直接广播有个致命问题：
**广播成功 → 保存数据库失败**，老张看到了一个"不存在的修改"。
我们用 Outbox（发件箱）模式解决：

```
保存编辑 → 写一条 PENDING 事件进 excel_collab_outbox（同一流程）
        → 发布器每 500ms 扫 PENDING → 广播 → 标记 SENT
        → 广播失败？保持 PENDING，下轮重发
```

代码注释就是最短解释（`ExcelCollabOutboxService`）：

```java
/**
 * 只负责在业务成功路径上落一行 PENDING 事件，绝不直接广播；
 * 广播由 ExcelCollabEventPublisher 在其后的发布周期完成，
 * 保证"先持久化、后广播"，广播失败也能靠清扫重发补偿。
 */
```

**面试 30 秒版**：本地消息表/Outbox 模式——业务数据和"待广播事件"一起落库，
广播变成可重试的异步动作。核心思想：**把"通知别人"降级为"记下要通知"，
用重试保证最终一致**。

### 临时事件不过审计

光标位置（"小刘的鼠标在哪"）也走 WebSocket，但**不落库、不进审计、不推进版本**——
它是瞬时状态，存下来除了撑爆磁盘没有任何价值。**持久化和广播要用两套标准审视**，
不是所有消息都值得存。

## Q&A：真实世界与面试追问

### Q1：100 个人同时编辑怎么办？你们的方案还扛得住吗？

分层看：编辑本身（单格写入）每次毫秒级，数据库扛得住几千 TPS；
真正的瓶颈是**广播扇出**（100 人编辑，每人要看 99 人的修改 → 消息量平方级）。
解法按顺序：合并广播（50ms 窗口内的编辑合成一条）、按房间隔离主题
（只发给同文档的人）、超大规模再上专业协同引擎（CRDT/OT，如 ShareDB）。
**500 人公司的 Excel 协同，同时在线编辑同文档的人通常 ≤ 10——先用简单方案，
别为想象中的规模过度设计**。

### Q2：服务器重启，编辑中的数据会丢吗？

编辑是"先持久化后广播"：只要用户看到"已保存"，数据已在数据库，重启不丢；
还没保存的（毫秒级窗口）丢失，前端下次编辑会重新提交。
**协同编辑的丢数据窗口 = 单次编辑的毫秒级，不是"整个会话"**——
这就是为什么必须逐条保存而不是攒一批。

### Q3：Excel 里的合并单元格、公式怎么处理？

流式解析支持合并单元格（SAX Handler 专门处理），公式**存原文**
（`=SUM(B2:B10)`），不做重算——企业场景公式错了宁可让用户在 Excel 里改，
系统不假装自己算得对。**诚实比聪明重要：系统能力边界要写进产品行为**。

### Q4：为什么编辑要走 WebSocket 而不是轮询？

轮询（每 2 秒问一次"有更新吗"）：延迟最高 2 秒 + 99% 的请求是空转。
WebSocket 是服务器主动推：延迟毫秒级、零空转。代价是连接管理复杂
（断线重连、心跳、多实例广播）。**实时性要求和用户量都到那个份上了，WebSocket 才值得**；
内部审批流那种分钟级实时性的场景，轮询反而更简单可靠。

### Q5：两个人编辑会不会把数据库写挂？

单元格编辑单行 UPDATE，且有文档版本乐观锁挡并发；真正要防的是**前端批量粘贴**
（一次请求改 10000 个格子）——批量接口有单批上限，超出拒绝并提示分批。
**并发设计的最后一课：防护要同时考虑"意外"和"故意的合理使用"**。

## 动手实验

1. 开两个浏览器窗口登录不同账号，编辑同一文档不同格子——观察秒级同步；
2. 两个窗口**同时**改同一格子，观察 REVISION_CONFLICT 弹窗和两个选项的实际效果；
3. 用 DevTools 网络面板找 WebSocket 帧，对比一次"格子编辑"和一次"光标移动"的消息内容，
   确认后者没有触发数据库写入（看后端日志）。
