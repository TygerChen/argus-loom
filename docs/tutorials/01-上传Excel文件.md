## 先讲一个故事

财务小王要上传一份 200MB 的年度账目 Excel。他点了上传，进度条走到 80%，
公司网络抖了一下——**这时候他心里想的是"完了，又要从头传一遍"**。

两分钟后他重试，发现进度条**从 80% 继续走**；传完系统还提示
"检测到相同文件，已复用之前上传的版本"。小王觉得这系统"挺懂我"。

这一篇就讲：为了让小王这 30 秒的顺心体验，背后要做对多少件事。
每件事我都会先说"人话版"，再看项目里的真实代码。

## 人话版：整个上传是怎么工作的

用"搬家"来打比方。你的 200MB 文件就是一个大衣柜——

1. **搬家前先打电话问（init）**：你告诉搬家公司"我有个大衣柜，编号是 ABC123"
   （编号 = 文件指纹/哈希，词典里有）。公司查记录发现三种可能：
   - **"这衣柜我们仓库已经有同款了"** → 直接登记，衣柜根本不用搬（这叫**秒传**）；
   - **"你上次搬到一半没搬完"** → 告诉你"已经搬进屋 15 箱，你从第 16 箱继续"（这叫**断点续传**）；
   - **"没见过，新活"** → 正常开搬。
2. **装箱搬运（chunks）**：把衣柜拆成 20 个箱子，一趟搬一箱。搬砸了一箱，
   只重搬那一箱，不是整个衣柜重来。
3. **到货确认（complete）**：全部箱子到位，公司在清单上打勾，
   然后安排工人慢慢拆装组装（解析文件）——组装期间你该干嘛干嘛，不用盯着。

下面看项目里对应的真实代码。

## 真实代码：后端给这次搬家定的规矩

`DocumentUploadService.java` 一开头就把"游戏规则"写成了常量：

```java
/** 分片上传最大文件大小：256MB */
private static final long MAX_FILE_SIZE = 256L * 1024 * 1024;
/** 单个分片的最大大小：10MB */
private static final long MAX_CHUNK_SIZE = 10L * 1024 * 1024;
/** 上传会话过期时长：24 小时 */
private static final long SESSION_EXPIRE_HOURS = 24L;
/** 直接上传最大文件大小：10MB */
private static final long MAX_DIRECT_FILE_SIZE = 10L * 1024 * 1024;
```

**这四个数字怎么读（人话版）**：

- **256MB** = 搬家公司最大只接 256MB 的衣柜。再大的柜子？拆开分两次报（提示用户拆分）。
- **单片 10MB** = 一个箱子最大 10 斤。注意！这是**后端划的红线**——你送来的箱子
  超过 10MB 我拒收。至于前端把文件切成 5MB 还是 8MB 一箱，是前端自己的选择。
- **前端实际切 5MB 一箱**。看前端代码：

```typescript
// frontend/src/views/documents/composables/useChunkedUpload.ts
const DEFAULT_CHUNK_SIZE = 5 * 1024 * 1024; // 5MB，比后端 10MB 上限留了一倍余量
```

  为什么不贴着 10MB 的上限切？因为后端限制可能调整，前端留余量就不会
  "后端一收紧、前端全线拒收"。**后端设上限保安全，前端留余量保兼容**——
  这是面试时能讲出层次感的细节。

  另外 5MB 这个数本身也是权衡：箱子太大，断网重传浪费多；太小，
  200MB 要拆 2000 趟，网络来回开销（每个请求都有"握手、报头"等固定成本）
  反而把速度拖慢。5MB 在"重传成本"和"请求数"之间刚好。

- **24 小时** = 半截搬家的记录只保存一天。不清理的话，仓库迟早被
  "搬了一半不要的柜子"堆满。
- **10MB 直传** = 小衣柜不用拆箱，一趟拎走。拆箱本身也有开销（要发 3 个请求），
  小文件直接传反而更快。这是"简单路径优先"的设计习惯。

## 真实代码：三段式流程

前端把搬家过程封装成一个组合式函数（Vue 的代码组织方式，可以理解为
"把上传这件事的所有状态和动作装进一个盒子"）：

```typescript
// useChunkedUpload.ts —— 第一步 init：先打电话问
const init = await documentApi.initChunkedUpload({
  fileName: file.name,
  fileSize: file.size,
  fileHash: fileHash,          // 文件指纹，64 个字符的"身份证号"
  chunkSize: DEFAULT_CHUNK_SIZE,
  chunkCount: Math.max(1, Math.ceil(file.size / DEFAULT_CHUNK_SIZE)),
})
```

注意 `fileHash` 从哪来——前端在发送**任何数据之前**，先用浏览器自带的
密码学工具把文件内容算出指纹：

```typescript
// useChunkedUpload.ts —— 边读边算，200MB 也不用担心内存
const digest = await crypto.subtle.digest('SHA-256', ...) // 流式计算
```

**为什么算指纹这么重要？** 因为指纹就是后面一切聪明的根源：
秒传靠它判断"传过没有"，续传靠它找回"上次的搬家记录"，幂等靠它判断
"是不是同一个文件"。没有指纹，这些全都做不了。

后端 init 接口按优先级做三级判定（这就是开头的"三种可能"）：

```java
/**
 * 初始化分片上传会话。
 * <p>按优先级依次尝试：
 * <ol>
 *   <li>秒传：存在相同哈希的 READY 文档则直接复用</li>
 *   <li>断点续传：存在相同哈希的未过期会话则恢复</li>
 *   <li>新建会话：创建全新的上传会话</li>
 * </ol>
 */
```

- **第一级 秒传**：指纹命中一个已就绪（READY）的文档 → 直接返回旧文档 ID。
  200MB 的文件 0.5 秒"传完"。网盘的秒传就是这个原理。
- **第二级 续传**：文档没有，但存在同指纹、没过期的上传会话 →
  返回"已收到的箱子清单"，前端只补缺的箱子。
- **第三级 新建**：老老实实从第 0 箱开始。

之后前端循环搬箱（每箱一个请求），全部搬完后调 complete：

```typescript
// useChunkedUpload.ts —— 切一箱、传一箱
const start = index * chunkSize
const chunk = file.slice(start, Math.min(start + chunkSize, file.size))
```

`file.slice()` 是浏览器的"切箱刀"——它**不会**把 200MB 整个读进内存，
只是拿着刀在文件上比划出"第 N 段"，浏览器每次只碰眼前这一段。
所以小王的电脑不会卡死。

## 真实代码：永远不要相信前端

在业务逻辑跑之前，`UploadInputGuard`（一个纯静态工具类，可以理解为
"门口的安检员"）先把所有输入过一遍：

```java
private static final int MAX_FILE_NAME_LENGTH = 255;
private static final int MAX_CONTENT_TYPE_LENGTH = 128;
private static final int MAX_FILE_HASH_LENGTH = 128;
private static final int MAX_FILE_EXT_LENGTH = 16;
```

安检员做四件事：
1. **文件名清洗**：把文件名里的路径符号（比如 `../`）去掉。有人上传一个
   名叫 `../../etc/passwd` 的文件，想骗后端把文件写到不该写的地方
   （这叫**路径穿越攻击**，词典里有）——清洗之后这种名字变成无害字符串。
2. **扩展名白名单**：只收 `.xlsx/.xls` 等列出来的类型，其余全拒
   （为什么用白名单不用黑名单？词典里有）。
3. **Content-Type 长度校验**：防止超长字符串捣乱。
4. **哈希格式校验**：指纹必须是合法的 64 位十六进制字符串，防止塞垃圾。

**为什么不直接信前端校验？** 因为前端的一切都能被绕过——用户按 F12 打开
开发者工具就能改，用命令行工具（curl、Postman）根本不走你的网页。
安全第一定律：**客户端校验是为了体验（早点提示用户），服务端校验才是为了安全。**

## Q&A：真实世界会出的事，以及面试官会追问的话

### Q1：网络波动，用户上传失败了怎么办？

**人话版**：搬到第 15 箱下雨了怎么办？——已经进屋的 15 箱不动，
改天从第 16 箱继续。

**项目里的两层解法**：
1. **一箱失败**：只重传这 5MB，成本几乎为零，用户根本无感（前端自动重试）。
2. **整个搬家中断**：后端一直记着"这个指纹的搬家，收到过哪些箱子"。
   用户回来重新点上传，init 时后端按指纹找到旧会话，返回缺箱清单，
   前端只补缺——这就是断点续传。会话保留 24 小时，第二天接着传都行。

**面试 30 秒版**：大文件分片上传；单片失败单片重试；服务端用
文件哈希 + 会话记录进度，init 时返回已收分片实现断点续传；
过期会话定时清理防止磁盘堆积。

### Q2：用户手抖点了两下上传，怎么保证不重复入库？——幂等性（面试必考）

先用人话讲清楚"幂等"（词典里有）：**同一个操作做一次和做一百次，结果一样**。
电梯按钮按 10 次只到 3 楼一次——电梯按钮天然幂等。网络会重试、用户会手抖，
所以重要接口必须设计成幂等的。

**我们选什么当"这是不是同一次操作"的判断依据？文件内容的 SHA-256 指纹**，不是文件名。
为什么？
- 文件会重命名："报表.xlsx" 和 "报表-最终版.xlsx" 可能是同一个文件；
- 同名文件内容可能完全不同：上个月和这个月的表都叫"报表.xlsx"；
- **内容相同就是同一个文件**——这才是业务的真实语义。

于是：手抖传两次 → 两次指纹一样 → 第二次 init 直接命中秒传，
返回同一个文档 ID。**做两次的结果 = 做一次的结果**，天然幂等。

**追问：应用层查了数据库，为什么数据库还要建唯一索引？**
因为两个请求可能**同时**到达（小王和同事恰好同时传同一份文件）：
A 查"没有记录"，B 也查"没有记录"，然后两人都开始新建——应用层检查
在并发下会"同时通过"。兜底是数据库的部分唯一索引
`(group_id, file_hash) WHERE status='READY'`（见 `V1__init_core_schema.sql`）：
两个插入只有一个能成功，另一个收到"重复键"错误后转为复用已有文档。
记住这句：**应用层判断管效率，数据库约束管正确性**——幂等设计的标准套路。

**追问：财务数据导入的幂等也是这样吗？**
同一个思想（都靠文件指纹），但**产品决策不同**：上传文档时重复 → 静默秒传
（用户爽）；财务导入时重复 → 在 `FinanceImportService.assertFileNotImported()`
里检查指纹，发现导过就直接抛 `FINANCE_FILE_DUPLICATED` 拦下来并提示用户。
为什么拦？因为财务场景里"重复"可能意味着**重复记账**——
你以为用户是网络重试，他可能是想重新导入修正过的数据，这需要人来确认。
**同一个技术，不同的业务判断**——面试里说出这句话，体现的是"懂业务"。

### Q3：超大文件超时怎么办？

先把"超时"拆成三种，每种各有解法：
1. **单个 HTTP 请求超时**：网关通常 30-60 秒就掐断一个请求。200MB 一次传完
   必死，但切成 5MB 一片后，每片几秒就完，离超时线很远。
   **把一个大请求变成很多小请求，超时问题自然消失。**
2. **后台处理超时**：传完之后的解析（切块、转向量）不在用户等待的请求里做，
   而是丢给后台队列异步执行（08 篇细讲）。complete 接口立刻返回"已收到，
   处理中"，用户不用盯着转圈的页面等 5 分钟。
3. **浏览器内存"超限"**：`file.slice()` 只拿眼前一段，200MB 不会整个进内存。

**追问：传到一半服务器重启了怎么办？**
两个关键点：每片收到后立刻**落盘**（写进存储），会话进度记录在**数据库**——
两者都不在内存里，重启不丢。用户重新 init，按指纹找回会话继续传。
反面教材：如果把进度记在服务内存里，一重启全忘光，用户只能从头传。
**进度必须落库**，这是本设计的核心原则。

### Q4：上传接口被恶意刷怎么办？

分片上传的本质是"很多个小写请求"，攻击者可以伪造海量分片把磁盘写满。
防线从外到内：
1. **先登录才能动**：init 校验登录态和群组管理员身份，匿名请求进不来；
2. **尺寸红线**：每片 10MB、单文件 256MB 上限，超出直接拒绝；
3. **限流**：接口上有 `@RateLimit` 注解（原理见 09 篇），请求太频繁返回
   标准限流错误码。

**追问：攻击者用合法账号恶意传呢？** 那就不只是技术问题，是治理问题：
配额（每用户存储上限）、审计（操作日志留痕，谁传的查得到）、
告警（上传量突增自动报警）。面试时主动说"技术防线之外还有治理手段"
是明显的加分项。

### Q5：用户上传了假 Excel（改了扩展名的危险文件）怎么办？

扩展名检查只能防"手滑"，防不了"故意"。更深的防线：
1. **格式校验**：真正的 xlsx 其实是个 ZIP 压缩包。解析库（Apache POI）
   打开假文件会直接抛异常——解析任务标记失败，并给用户讲清楚原因；
2. **爆炸隔离**：解析在后台异步进行，坏文件炸的只是它自己的任务，
   主服务和其他用户毫发无损；
3. **文件名消毒 + 随机改名**：安检员去掉路径符号和控制字符之后，
   落盘时干脆用 UUID 重新命名——原文件名只存在数据库里给用户看，
   **永远不参与文件系统路径**。就算文件名有毒，也毒不到磁盘。

### Q6：上传失败时，怎么提示用户才算好？（产品思维加分题）

原则：**每一次失败都要给用户一条出路，而不是一句"失败"。**

| 失败场景 | 差的提示 | 好的提示 |
| --- | --- | --- |
| 文件太大 | "上传失败" | "文件超过 256MB 上限，请拆分后上传" |
| 格式不支持 | "上传失败" | "仅支持 .xlsx/.xls，检测到 .csv，请先转换" |
| 重复文件 | "上传失败：文件已存在" | "检测到相同文件，已为你复用（秒传）" |
| 网络中断 | "上传失败" | "网络中断，已保留进度，点击继续上传" |
| 解析失败 | "上传失败" | "文件已收到，但内容解析失败（原因：…），可重新上传或联系管理员" |

注意最后一行：文件本身传成功了、解析失败了，这是**两个阶段**，
提示必须分开——"你的东西没丢，是内容有问题，你可以……"。
这就是"用户体验优先，拒绝不是终点"。

## 动手实验（做完这一篇才算学会）

1. **复现秒传**：上传任意文件两次，观察第二次浏览器网络面板里 init 的响应，
   是不是直接带回了已有文档 ID、后续分片请求一个都没发。
2. **复现续传**：上传大文件到一半，在 DevTools 网络面板里把网络切到 Offline
   再切回来，观察重新 init 时返回的已收分片清单。
3. **观察指纹进度条**：传一个大文件，注意上传按钮上会先出现"计算指纹"进度，
   然后才是上传进度——对应 `hashingProgress`，说明指纹是分步算的，不是卡住。
4. **读代码找答案**：打开 `DocumentUploadService`，找到会话状态从 UPLOADING
   推进到 COMPLETING 的那行代码，然后回答：complete 合并到一半服务崩了，
   状态停在哪？用户重试时会发生什么？（提示：想想哪些信息在数据库里、哪些丢了。）
