# 09 · 运维与监控 —— 系统上线只是开始

> 代码入口：`backend/src/main/java/com/argus/rag/common/health/QueueHealthIndicator.java`（健康检查）
> `common/ratelimit/RateLimitAspect.java`（限流）、`common/config/AppThreadPoolConfig.java`（线程池）
> 运维文档：`docs/operations/` 四件套

## 用户的故事

上线第三周晚上 10 点，Outbox 积压告警响了。值班的老张打开监控大盘：
协同事件 PENDING 数量 2000+，两台 API 的一台 CPU 100%。
他重启那台 API，5 分钟后积压清零，全程没人打电话投诉——
**因为监控发现问题的速度，比用户发现问题快**。这就是运维的意义。

## 人话版：餐厅的消防系统

开发是把餐厅开起来，运维是保证它**每天安全营业**。这一篇的几件装备：

1. **线程池 = 后厨灶眼**。灶眼数量有限、每口灶前排队的位置也有限（有界队列）。
   最怕的是"无限排队"：单子增长比炒菜快，队伍排到马路上（内存爆掉，全店关门）。
   我们的做法：排队区满了，就让**收银员亲自下厨**（CallerRuns 策略）——
   收银一慢，接单自然就慢了，队伍自动不再变长。这就是**背压**（词典里有）：
   让压力往回传，而不是硬撑到爆炸。
2. **限流 = 取号机**。再大的餐厅也接待不了同时 1 万人进店。限流就是门口取号机：
   每分钟只放行固定数量，超出的客人拿到一张礼貌的"稍后再来"
   （标准限流错误码），而不是全店挤爆谁都没得吃。
3. **健康检查 = 每天开门前的自查清单**。燃气正常吗（数据库连得上吗）？
   出菜口堵吗（队列积压了吗）？清单不过关，接待员（负载均衡）就别把客人
   往这家店领。
4. **监控告警 = 烟雾报警器**。着火（Outbox 积压 2000+）时报警器先响，
   而不是等客人闻到烟味在差评里告诉你。**报警永远要早于用户投诉**。

记住运维的第一性原理：**系统不是"上线了就完了"，而是"活着的"——
活着的东西需要体温计、烟雾报警器和应急预案**。

## 一、线程池：为什么必须有界

```java
/**
 * 此前 @Async、@Scheduled、CompletableFuture.runAsync 与 parallelStream 都落在
 * Spring 默认执行器或 JVM 公共 ForkJoinPool 上：队列无界、无拒绝策略、
 * 与业务争抢公共线程。这里定义显式线程池与调度器，做到：
 *   - 线程名可辨识（argus-*），日志/线程转储可直接归因；
 *   - 队列有界 + 拒绝策略（CallerRuns：不丢任务，把背压交回调用线程）；
 *   - 按用途隔离（通用异步 / 导出 / 检索并行 / 定时），互不饿死。
 */
```

这段注释值得背下来。OOM 事故的标准剧本：无界队列线程池 + 任务生产速度 > 消费速度
→ 队列无限堆积 → 内存耗尽 → 整个进程死亡。**有界队列 + 拒绝策略**是疫苗：

```java
private static ThreadPoolTaskExecutor buildExecutor(int coreSize, int maxSize, int queueCapacity,
                                                    String threadNamePrefix) {
    executor.setQueueCapacity(queueCapacity);                      // 有界！
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    // CallerRuns：队列满了让提交者自己跑——天然限流，任务一个不丢
}
```

`CallerRunsPolicy` 的妙处：满了不让提交线程闲着（它自己去执行任务），
新任务自然慢下来——**背压（backpressure）**，比"抛异常"或"静默丢弃"都优雅。

**追问：为什么不一个"大池子"搞定所有？** 隔离！导出任务重（吃 IO 和内存），
检索任务轻（毫秒级）。混在一起，一次 10 个导出能把检索饿死——全站问答跟着卡。
**按负载画像分池，是线程池设计的核心思想**（和 08 篇"Worker 分开部署"同源）。

## 二、健康检查：/actuator/health 里有什么

Spring Actuator 自带数据库/ES 的探活，我们补了一个业务探针：

```java
/**
 * 队列健康检查：死信任务或协同 Outbox 积压超过阈值即降级。
 * 详情只暴露计数，绝不带连接串/密钥/异常堆栈。
 */
public Health health() {
    Long dead = jobMapper.selectCount(...STATUS_DEAD_LETTER...);
    Long pendingOutbox = outboxMapper.selectCount(...PENDING...);
    boolean down = deadCount > 0 || outboxCount > outboxBacklogThreshold;
    return builder.withDetail("deadLetterJobs", deadCount)
                  .withDetail("pendingOutboxEvents", outboxCount).build();
}
```

三个设计点：**业务探针**（数据库连着不代表系统正常——死信堆积时数据库健在）；
**敏感信息零泄露**（健康接口匿名可访问，异常消息可能带 SQL 片段，
所以只报 "queue probe failed"）；**阈值来自 runbook**（Outbox 积压 1000 = 协同广播出问题了）。

## 三、限流：单机内存版及其边界

```java
/**
 * 限流 AOP 切面。基于 ConcurrentHashMap 实现内存级滑动窗口计数器，
 * 以用户 ID 为维度进行限流。生产环境高并发场景建议替换为 Redis 滑动窗口实现。
 */
```

用法（注解在方法上）：`@RateLimit(limit = 10, window = 1, unit = TimeUnit.MINUTES)`。
超限抛 `RateLimitExceededException`，前端拿到标准错误码提示"操作太频繁，请稍后再试"。

**追问：两台 API 时限流会怎样？** 每台各算各的，用户实际能传 2 倍量。
500 人规模可接受；真要精确就上 Redis（集中计数）——注释里写明了这个演进方向。
**知道当前方案的不完美和升级路径，比假装完美重要**。

**追问：被限流的用户体验？** 错误信息带"什么时候能重试"，前端倒计时展示。
限流本身是保护，但**被限流的提示要像帮助而不是惩罚**。

## 四、指标与告警：发现问题的速度决定口碑

项目暴露的关键指标（Prometheus 格式，`/actuator/prometheus`）：

| 指标 | 回答的问题 |
| --- | --- |
| `argus.job.queued / running / dead_letter` | 任务队列健康吗 |
| `argus.job.oldest_wait_seconds` | 用户等得最久的是谁（> 900 秒告警） |
| `llm.dialogue`（Timer 带 outcome 标签） | AI 对话 P95 延迟和错误率（> 5% 告警） |
| `hikaricp_connections_active` | 数据库连接池是否饱和（> 80% 告警） |

告警设计的通用原则（写在 `docs/operations/capacity-runbook.md`）：
每条告警必须带**处置方法**（"重启 Worker""查 last_error"）——
没有处置方法的告警是狼来了。**告警不是越多越好，是"每条都值得人来看"**。

## 五、备份与故障演练

`docs/operations/backup-restore.md` 的核心数字：PostgreSQL 每日全量 + WAL 归档，
RPO ≤ 15 分钟（最多丢 15 分钟数据）、RTO ≤ 2 小时（恢复时间）。
**恢复演练每季度一次**——没演练过的备份等于没有备份（演练时才发现备份文件损坏、
恢复步骤缺依赖，这种事故后知后觉就晚了）。

## Q&A：面试综合题

### Q：生产环境 500 报错激增，你的排查路径？

标准顺序（背下来，面试必考）：
1. **先看影响面**：监控大盘——全部接口还是个别？全部用户还是个别？
2. **看变更**：10 分钟内发过版吗？改过配置吗？（80% 的事故紧跟变更）；
3. **看依赖**：健康检查——数据库/ES/LLM 哪个 DOWN 或变慢；
4. **看日志**：按 traceId 拉一条失败请求的全链路日志（结构化日志的价值就在这）；
5. **止血优先于根治**：能重启/回滚/降级就先做，恢复后再复盘根因。
**顺序体现的是"先止损再破案"的运维价值观**。
