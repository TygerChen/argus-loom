# 06 · 版本 · 导出 · 回收站 —— 数据安全的"后悔药"三件套

> 代码入口：`excel/service/ExcelVersionService.java`（版本）、
> `excel/service/ExcelExportService.java`（导出）、`excel/service/RecycleBinService.java`（回收站）

## 用户的故事

小刘不小心把预算表 B 列全删了。她的第一反应不是喊运维，而是打开"版本历史"，
选了十分钟前的版本一键恢复。上个月她要导出一份 50 万行的报表，点了导出后去开别的会——
回来发现任务列表里躺着"导出成功，点击下载"。上周组长误删了整份工作簿，
在回收站里躺了 3 天，一键还原。

这三件事背后是同一个设计哲学：**用户一定会犯错，系统的职责是让每个错误都可逆**。

## 人话版：后悔药三件套

- **版本 = 游戏存档**。每次保存都拍一张"快照"存进档馆。存档只增不改——
  你回到第 10 版，不是"抹掉后来的历史"，而是"以第 10 版为基础存一张新档"。
  所以任何一次恢复本身也是可恢复的，永远不会"退回去就回不来了"。
- **导出 = 餐厅等位取号**。50 万行的报表要煮几分钟（生成 Excel 很慢），
  让你站在灶台前干等既难熬也容易"断单"（HTTP 超时）。所以给你一个号：
  "任务已受理，好了叫你"。你先去干别的，回头凭号取餐（下载文件）。
- **回收站 = 垃圾桶旁边放三天的"反悔期"**。扔掉的东西不直接进焚化炉，
  在回收站躺几天——这三天里扔的人随时可以捡回来。
  过了反悔期才真正清掉。

三件套的共同点：**都是把"不可逆操作"变成"可逆操作"**。
用户犯错不是异常，是常态；好系统的标准不是"用户不犯错"，
而是"犯了错都能救回来"。

## 版本：每次保存都是一个快照

设计要点：版本记录**数据 + 元信息**（谁、何时、为什么），恢复 = 用旧快照覆盖当前，
而恢复这个动作本身也产生一个新版本——**历史永远向前追加，永不改写**。

```java
// ExcelDocumentVersion：一份文档多个版本，(document_id, id) 建索引加速版本列表查询
```

**为什么不存差异（diff）而存快照？** diff 省空间但恢复时要逐版本重放，实现复杂、
任何一步重放错误就全错。500 人规模存储便宜、正确性第一，快照直白可靠。
数据量大了再演进到"定期全量 + 中间 diff"。

**追问：版本会不会无限膨胀？** 会，所以有保留策略：最近 N 个版本 + 关键里程碑
（手动保存/导入产生的版本）优先保留，自动保存的旧版本定期清理。
清理策略也是产品决策：问用户"你们最想回到多久之前"，答案往往是"昨天"。

## 导出：为什么点"导出"后不是立刻下载？

小文件导出可以同步返回，但 50 万行有两个致命问题：**HTTP 超时**（Excel 生成要几分钟）
和**内存爆炸**（不能把 50 万行同时攒在内存里拼 Excel）。

我们的设计是**异步任务 + 产物文件**：

```java
// ExcelExportService：任务投递到专用 excelExportExecutor（有界队列 + CallerRuns），
// 并按 taskId 持有 Future，使 cancelTask 能真正中断正在写盘的线程
private final ExecutorService exportExecutor;
```

流程：点导出 → 立即返回 taskId → 后台生成文件（流式写，边生成边写盘）→
任务状态变"成功" → 用户点下载。**用户界面上"导出"永远秒回**，
等待发生在任务列表里，进度可见、可取消。

**追问：为什么导出要专门的线程池？** 如果和普通请求共用，一次 10 个导出任务
就能把公共线程池占满，全站所有接口跟着卡死。**用资源隔离防"一家着火全楼断电"**
（线程池设计的详细原理见 09 篇）。

**追问：取消导出是怎么实现的？** 每个 taskId 对应一个 `Future`，
取消时 `cancel(true)` 中断正在写盘的线程。**"能取消"是异步任务的产品必需品**，
不是锦上添花——用户点错导出范围时，取消按钮是他唯一的朋友。

**追问：导出的文件会不会把磁盘撑爆？** 会，所以产物有过期时间（24 小时），
定时清扫任务把过期产物标记 EXPIRED 且拒绝下载。**凡是生成物，必有生命周期**。

**追问：下载的时候还要再校验权限吗？** 要。任务创建时有权限 ≠ 下载时有——
这 24 小时里权限可能被收回。下载接口重新过 `requireView`。
**权限校验跟着"数据访问"走，不跟着"按钮"走**（这是 IDOR 防御的延续）。

## 回收站：删除是个动词，不是个事实

```java
/** 回收站保留 30 天 */
public static final int RETENTION_DAYS = 30;
```

删除 = 打标记（`deleted_at`），不删数据；30 天内可还原；过期由定时任务物理清理。
每个"删除"动作在产品上都要二次确认 + 影响范围提示（"该工作簿含 5 个工作表将一并删除"）。

**为什么不真删？** 因为"误删"在企业场景不是 if 而是 when。真删的代价不是存储
（存储便宜），是**无法挽回的业务中断**（财务月末删错账，等恢复备份要 4 小时）。
**软删除是给业务买保险，保费是存储成本**。

**追问：软删除的数据会被检索搜到吗？** 不会——所有查询默认带 `deleted_at IS NULL`，
RAG 入库管线同样过滤。**软删除最大的坑就是"漏过滤"**：任何新查询忘了加条件，
删除的数据就"诈尸"。所以用 MyBatis-Plus 统一拦截或代码评审强制检查。

**追问：管理员能绕过回收站彻底删除吗？** 可以（合规场景：离职员工数据必须删除），
但这属于"治理动作"而非"用户功能"——要审批、要留痕。**技术给产品选项，
流程决定谁能用**。

## Q&A 汇总：三件套的共同面试题

### Q：这三个功能本质上是同一个东西吗？

是——**都是"时间维度的数据安全"**：版本 = 回到过去，回收站 = 推迟现在，
导出 = 把现在带走。面试聊到任何一个，都能引到另外两个，展示系统性思维。

### Q：这些功能会不会让系统变慢？

每一样都有代价（写放大、磁盘占用、清扫任务），但都是**后台成本换前台安全**。
用户感知不到 5% 的写放大，但感知得到"删错东西找不回来"。
性能优化永远排在正确性后面——除非 profiler 说不然。

## 动手实验

1. 改一个格子 → 看版本列表 +1 → 恢复上一版本 → 再看版本列表（恢复本身也生成新版本）。
2. 导出一份小表，立刻在任务列表点"取消"，观察状态变化和文件是否残留。
3. 删除一份文档，去数据库看 `deleted_at` 字段，再用检索接口确认它搜不到了。
