# 04 · RAG 检索与引用 —— 让 AI "开口有据，拒答有理"

> 代码入口：`backend/src/main/java/com/argus/rag/qa/rag/HybridChunkRetrievalService.java`（检索）
> 问答编排：`backend/src/main/java/com/argus/rag/qa/service/QaChatService.java`（拒答判定）
> 入库管线：`backend/src/main/java/com/argus/rag/ingestion/`（分块 → 向量化 → 双索引）

## 用户的故事

小王问系统："差旅住宿标准是多少？"系统回答："一线城市每晚 500 元（引用：
《差旅费管理办法 2026 版》第 3.2 条）"。他又问："隔壁公司年会在哪开？"
系统回答："知识库中没有找到能回答这个问题的依据，无法作答。"
**第二次"不回答"恰恰是系统最值钱的地方**——通用大模型会编一个像模像样的答案，
而企业系统编造一个报销数字是会出事故的。

RAG（检索增强生成）的本质：**回答之前先去知识库"查资料"，把查到的资料连同问题
一起交给模型，让模型"看着资料说话"**。这一篇讲怎么查得准、怎么引用得可信、
什么时候宁可拒答。

## 人话版：RAG 就是"开卷考试"

把 AI 回答问题想象成一场考试（词典里的比喻，这里展开讲）：

- **普通大模型 = 凭记忆闭卷考试**：全靠自己脑子里背过的东西答题。
  记不清怎么办？硬编。企业场景里，编出来的报销数字是会出事故的。
- **RAG = 开卷考试**：答题前先翻书。题目是"差旅住宿标准多少？"，
  你先翻到《差旅费管理办法》第 3.2 条，**照着书上内容写答案，
  还要注明"答案出自第几页"**（引用）。书里没有？老实写"书上没有"（拒答），
  而不是瞎编。

那么"翻书"怎么翻得快？一本几千页的书从头翻到尾太慢，所以：
1. **提前把书拆成卡片**（分块 chunk）：每张卡片两三段话，内容相近的下张卡片
   略有重复（overlap），防止关键句子正好被切成两半；
2. **给每张卡片做索引**（向量化 embedding）：把卡片内容变成一串数字，
   "意思相近的卡片数字也相近"——这样"出差住宿报销上限"和"差旅住宿标准"
   意思一样但字面不同，也能通过数字距离找到彼此；
3. **同时准备两种索引**（双路召回）：数字索引管"意思相近"，
   传统关键词索引管"字面精确"（查"QA-2026-042"这种编号还得靠字面）；
4. **考试时先审题再翻书**（查询改写）：题目问得含糊就先改写清楚，
   题目复杂就拆成几个小问题分别翻书。

最后还有一条公司规定：**你只能翻你有权限看的那部分书**。
财务的账本锁在柜子里，就算检索技术再好，普通员工也翻不到。
带着这些比喻，下面看真实管线和代码。

## 设计方案：一条文档的旅程

```
上传文档 → 解析 → 分块(chunk) → 向量化(embedding) → 双索引落库
                                                      ├─ PostgreSQL pgvector（语义）
                                                      └─ Elasticsearch（关键词）
提问 → 查询改写 → 双路召回 → 合并去重 → 权限过滤 → 重排 → 拼 Prompt → 生成/拒答
```

### 为什么要分块（chunk）？

配置里的数字就是答案：

```yaml
chunking:
  target-tokens: 240    # 目标块大小
  max-tokens: 320       # 硬上限
  overlap-tokens: 32    # 相邻块重叠
```

分块的原因：**向量检索的粒度是块，不是文档**。整篇文档压成一个向量，
细节全被平均掉——检索"住宿标准"会命中一堆讲差旅的文档却定位不到那一条。
块太小则句子被切断、语义不完整。240 目标 + 32 重叠是"语义完整"和"检索精度"的折中：
重叠保证"标准是 500 元"这种跨块边界的句子，至少在一个块里是完整的。

### 为什么双路召回（向量 + 关键词）？

| 检索方式 | 强项 | 弱项 |
| --- | --- | --- |
| 向量（语义） | "出差住宿报销上限"能命中"差旅住宿标准" | 精确编号、人名、代码容易漂移 |
| 关键词（BM25） | "QA-2026-042" 这种精确词一查一个准 | 同义改写就抓瞎 |

企业知识库里一半问题是"精确查找"（制度编号、项目代号），一半是"意思查找"。
两路都查，合并去重（`mergeVectorHits` / `mergeKeywordHits`），召回率大幅提升。
可选的第三路是联网搜索（默认关闭，安全白名单管控）。

### 检索结果必须过权限闸门

```java
private final DocumentRoleGate roleGate;   // 检索管线里的权限过滤组件
```

**这一行是全篇最重要的一行**：检索出来的块，逐个检查当前用户是否有权看其所属文档，
无权的直接丢掉。否则会出现"小王搜索'薪资'，AI 引用了他无权看的薪酬表"——
检索系统成了越权后门。**AI 不改变权限规则，只是权限规则的又一个消费者**。

## Q&A：真实世界与面试追问

### Q1：AI 还是编造了答案（幻觉），怎么办？

三道防线，从软到硬：
1. **Prompt 约束**："仅根据提供的资料回答"——软约束，模型偶尔不听；
2. **证据不足拒答**（硬约束，代码级强制）：检索证据得分低于阈值或为空时，
   **根本不调用模型**，直接返回结构化拒答：
   ```java
   /** 拒答原因编码：证据不足 */
   private static final String INSUFFICIENT_CODE = ErrorCodes.RETRIEVAL_NOT_GROUNDED;
   // 137 行附近：2. 若无证据，直接返回拒答响应
   ```
   这就是 `RETRIEVAL_NOT_GROUNDED` 错误码的来历——前端可以按码展示
   "没有找到依据"而不是模型编的话。
3. **引用可核验**：每句关键结论都带引用卡片（文档名 + 位置），用户点击能跳到原文核对。
   **引用让用户可以抓到 AI 的错**——可追责的 AI 才能进企业。

**面试 30 秒版**：幻觉无法根除只能管理——检索增强缩小说话范围、
证据不足硬拒答、引用让错误可核验。拒答率不是坏指标，编造率才是。

### Q2：检索很慢，用户等不了怎么办？

先测再优化——慢可能在任何环节。本项目几手准备：
1. **检索并行化**：向量路和关键词路用独立线程池并发执行（`retrievalExecutor`），
   总耗时≈最慢一路而不是两路之和；
2. **只检必要的量**：top-k 默认 5，单文档切块数有上限（`max-chunks-per-document`），
   防止一份大文档霸占整个上下文；
3. **门槛设定**：已命中检索 P95 < 2 秒是验收门槛（不含 LLM 生成——
   生成慢是模型侧问题，靠流式输出让用户"看着字出来"感知更快）。

**追问：为什么不用缓存？** 问答缓存命中率低（问题千奇百怪），但**检索结果**
对高频问题可以缓存。数据更新时要主动失效（新文档入库，旧缓存就错了）。
缓存是优化项不是架构项。

### Q3：用户上传了新文档，马上提问能查到吗？

不一定，而且**不应该是"能"**：上传后要解析→分块→向量化→写两个索引，
这是分钟级异步任务（见 01/08 篇）。正确的产品设计是**把状态告诉用户**：
文档详情页显示"处理中/可检索/失败"，处理中的文档明确标注"暂不可被问答检索到"。
比"沉默地查不到"好一百倍——用户不怕等，怕的是不知道在等什么。

**追问：两个索引（pgvector + ES）写一个成功一个失败怎么办？**
入库任务失败会标记任务状态可重试（08 篇的队列）；重试前先清理已写入的部分再重建
（幂等重建）。这正是任务要"幂等"的原因：失败重试是常态，不是异常。

### Q4：怎么评测检索质量好不好？

项目自带评测链路：`scripts/rag_eval/`（评测集 40 条：36 条正例 + 4 条拒答用例），
`python scripts/rag_eval/run_eval.py --profile local` 一键跑分，
门槛"有依据回答率 ≥ 85%"写在验收手册。**没有评测集的 RAG 调优是玄学**——
改一个参数感觉"变好了"没有意义，跑分才知道。

**追问：拒答太多用户体验差怎么办？** 看拒答原因分布：证据得分略低于阈值 →
调阈值；知识库真没有 → 引导用户上传（拒答文案带"去上传"入口）；
分块把关键句切碎了 → 调分块参数。**每一类拒答都有对应的改进动作**，
这就是"用户满意优先"在 RAG 里的落地。

### Q5：查询改写是干嘛的？（加分项）

用户的问题经常不是检索友好格式："那个报销的事"——改写服务
（`QuestionQueryRewriteService`）把它扩展成"报销 标准 流程 限额"这类检索词。
还有多问题分解（一次问三件事拆成三个子查询分别检索）。
这是检索质量提升最大、也最容易被忽略的一环：**检索的上限由查询质量决定**。

## 动手实验

1. 问知识库一个它绝对不知道的问题（"你们 CEO 的银行卡密码"），确认返回拒答
   而不是编造。观察响应里的错误码。
2. 用管理员检索一篇财务文档关键词，再用普通账号搜同样的词——

3. 读 `application.yml` 里 `max-chunks-per-document` 注释，

## 进阶 Q&A：RAG 深挖追问（面试高频第二梯队）

以下问题比前面更"卷"，来自真实 RAG 岗位/后端 AI 方向面试的追问链。
每题仍然先给 30 秒版，再结合本项目实现展开。

### Q7：现在大模型上下文很长了（128K/1M），把整个知识库塞进去不就行了，为什么还要 RAG？

**30 秒版**：成本、精度、权限三座山——128K 上下文每问一次的钱和延迟都不可接受；
长上下文中段的召回精度会下降（"lost in the middle"）；最致命的是**权限**：
把全库塞进 Prompt 等于给每个提问者看所有文档。

**展开**：RAG 的本质是"先筛选再生成"——只把相关的几块（top-k=5）送进上下文，
成本降低几个数量级；检索环节可以插入权限过滤（本项目 `DocumentRoleGate` 在检索管线里
逐块过滤，这是"全塞上下文"永远做不到的）；检索失败还能拒答，
而长上下文里的模型会倾向于"既然看见了就编一个"。
**长上下文和 RAG 不是替代关系：RAG 负责缩小范围和权限控制，长上下文让单次检索
能装更多证据**。

### Q8：向量库怎么选型？Milvus/FAISS/pgvector 有什么区别？你们为什么用 pgvector？

**30 秒版**：数据量千万级以内、团队已有 PostgreSQL → pgvector（运维零新增，
事务和权限数据同库同事务）；亿级向量、高 QPS → Milvus/Qdrant 这类专用库；
纯本地实验 → FAISS（是库不是服务）。

**展开**：本项目用 pgvector（HNSW 索引 + 余弦距离，512 维 bge-small-zh），
决策理由是**运维成本和事务一致性**：500 人规模文档数万块，
pgvector 的 HNSW 毫秒级返回绰绰有余；而且向量数据和文档权限数据在同一个数据库，
不存在"向量库查到了、权限库说没删干净"的一致性问题。
面试的关键不是背参数对比，而是**给出规模匹配的决策过程**——
"我们评估过 QPS/数据量/运维成本，在这个规模下 pgvector 是最优解，
数据涨到 X 时迁移到专用库"。

### Q9：分块策略有哪些？固定长度、递归、语义分块怎么选？

**30 秒版**：三主流——固定窗口（简单但切句子）、递归字符/按结构
（按段落标题层级切，制度文档首选）、语义分块（按 embedding 相似度找断点，贵但准）。
我们用"目标 240 token + 32 重叠 + 按文档结构优先切"，并通过评测集验证。

**展开**：企业制度文档有天然结构（章节/条款），**按结构切**比按字数切质量高得多；
`overlap-tokens: 32` 解决跨块边界的句子被切断问题；
`max-tokens: 320` 是硬上限，保证单块永远不会撑爆 embedding 模型窗口
（bge-small-zh 窗口 512 token）。
**分块没有银弹，唯一可靠的验证方式是评测集**——改任何参数都跑一遍
`run_eval.py`，用数字说话（本项目 40 条评测集，改前改后对比）。
面试官想听到的是"我承认分块是玄学重灾区，所以我用评测集把它变成工程"。

### Q10：Embedding 模型怎么选？为什么用本地小模型而不用 OpenAI 的 embedding？

**30 秒版**：三个理由——数据不出内网（财务制度是敏感数据）、成本
（每次入库+每次提问都要 embedding，按量付费积少成多）、延迟稳定
（本地推理不受第三方限流影响）。

**展开**：本项目用 `bge-small-zh`（512 维）本地进程内推理。中文效果好、模型小
（CPU 都能跑）、维度低意味着向量索引也小。代价是精度弱于大模型——
**靠检索管线弥补**：双路召回（向量 + 关键词）+ 查询改写，小模型也有好召回。
选型逻辑：**embedding 精度不够时，先用检索架构补，再考虑换大模型**。

### Q11：什么是 Rerank？它和向量检索的区别？为什么需要两阶段？

**30 秒版**：向量检索是"粗筛"（快，但要索引，精度有限），rerank 是"精排"
（把 query 和每个候选块拼在一起用交叉编码器精细打分，准但慢）。
先粗筛 20 块再精排取 5 块，兼顾质量和延迟。

**展开**：本项目定义了 `RerankingService` 接口（内置 NoOp 实现——**没有 rerank 模型时
管线也能跑**，这是良好的工程习惯：可选增强做成接口注入，而不是硬依赖）。
两阶段的原因是复杂度不对称：向量检索靠 ANN 索引，百万块也是毫秒级；
交叉编码器每对 query-doc 都要跑一次前向计算，只能作用于小候选集。
**面试加分点**：rerank 提升最大的场景是"多条件问题"
（"北京地区 2026 年差旅住宿标准"——粗排会混入北京 2025 的、差旅餐饮的），
精排能把这些排下去。

### Q12：多轮对话怎么处理？用户问"那食宿呢？"，检索词是空的怎么办？

**30 秒版**：查询改写（指代消解）——把"那食宿呢"结合上一轮改写成
"差旅住宿补贴标准"，用改写后的词去检索；改写用小模型或规则都行。

**展开**：本项目 `QueryPlanningService` 承担这个职责，而且**规划失败自动回退
DIRECT 策略**（直接用原问题检索）——绝不让"改写服务挂了"变成"整个问答挂了"。
它有四种策略：DIRECT（直接查）、REWRITE（改写）、DECOMPOSE（复合问题拆成多个子查询
分别检索再合并）、GLOBAL（全局综述类）。**查询规划是 RAG 里性价比最高的模块**：
不换模型不换库，只改"怎么问"，检索质量就能上一个台阶。

### Q13：怎么评估 RAG 系统的好坏？有什么指标？

**30 秒版**：检索侧看召回率/命中率（该找到的块找到没），生成侧看有据回答率、
引用正确率、拒答正确率；所有指标必须基于**人工标注的评测集**，不能凭感觉。

**展开**：本项目的评测集（40 条：36 正例 + 4 拒答）每条都标注了
`expected_files`（应该命中的文档）、`expected_keywords`、`should_answer`（是否应该回答）。
运行 `run_eval.py` 输出各指标。进阶指标（面试可提）：
忠实度（faithfulness，回答是否忠于检索内容，可用 LLM 当裁判）、
上下文精度（命中的块里有多少是真正相关的）。
**RAG 调优的循环 = 改参数 → 跑评测 → 对比数字，没有别的路径**。

### Q14：RAG 和微调（fine-tuning）怎么选？

**30 秒版**：知识更新频繁、要引用溯源、有权限隔离 → RAG；
要改变模型的"行为风格"（输出格式、领域话术）→ 微调。
企业知识库 99% 选 RAG，两者可以组合。

**展开**：微调的致命伤在本项目场景全中：知识更新要重新训练
（制度每周都在改）；无法溯源（答案说不出出处）；无法做文档级权限。
RAG 的知识就是数据库里的块，更新即生效、引用天然携带、权限逐块过滤。
微调适合的例子：让模型学会公司特有的报表术语表达。
**面试时能说清"微调改行为，RAG 供知识"这个分界**就达标了。

### Q15：检索出来的块不连贯（答案跨了两个块），怎么处理？

**30 秒版**：三招——块重叠（提前预防）、邻居窗口扩展（命中块的上下文块一起带出）、
父块检索（小块用于检索，大块用于生成）。

**展开**：本项目用邻居窗口：`DEFAULT_NEIGHBOR_WINDOW = 1`——
命中第 N 块时把第 N-1、N+1 块也取回来拼上下文，跨块的答案就完整了。
父块检索（small-to-big）是更进一步的方案：用 100 token 的小块做精准检索，
命中后取它的父级 500 token 大块送生成。
**核心思想：检索要"准"（小块），生成要"全"（大块），两个粒度可以不同**。

### Q16：用户反馈"引用是对的但答案不对"，可能是什么问题？

**30 秒版**：检索没问题，生成环节丢分——按序排查：上下文是否超长被截断
（关键块被截掉）、Prompt 指令是否清晰（"仅根据资料回答"）、
模型本身能力、回答格式解析是否出错（本项目有专门的"回答格式错误"拒答码）。

**展开**：这是排查题的变体，考的是**把 RAG 系统拆成独立环节分别验证**的意识：
检索对（引用在）+ 答案错 = 生成侧问题，不要去动检索参数。
本项目甚至区分了"证据不足拒答"和"回答格式错误拒答"两种错误码——
**错误分类的粒度决定排查的速度**。

### Q17：知识库有 10 万份文档，你们这套架构还扛得住吗？怎么演进？

**30 秒版**：分层看瓶颈——embedding 入库（离线任务，加机器即可）、
向量检索（pgvector 到亿级块依然可用，加索引内存）、rerank 和 LLM（QPS 瓶颈，靠缓存和降级）。
架构不用推倒重来，逐层扩。

**展开**：这题考"演进思维"而不是"现在够不够"。具体演进路径：
① 入库吞吐：解析/embedding 本来就在后台队列（08 篇），加 Worker 即可；
② 检索延迟：pgvector HNSW 参数调优 → 分区（按知识库/时间）→ 专用向量库；
③ 高频问题缓存（相同问题检索结果短 TTL 缓存）；
④ LLM 层：流式输出 + 多模型路由 + 降级拒答。
**强调"监控指标驱动演进"**：哪个指标先恶化就先扩哪层，拒绝无脑堆机器。

## 深挖 Q&A 第三梯队：面试官追问两轮之后的"杀手题"

> 这一梯队整理自 2026 年各大厂真实面经（知乎大模型面试题库、腾讯云 28 题 RAG 面经、
> 卡哥 llm-master 面试题汇总等），特点是：**不再问"是什么"，而是问"为什么不用别的"
> 和"代价你算过吗"**。回答它们的核心武器只有一个——诚实地讲清你项目的真实做法，
> 再给出你理解的演进方向。**项目没做的就说没做，但要说出"如果要做该怎么做"**，
> 这比背十个名词更能拿分。

### Q18：RRF 为什么比直接加权求和更稳？你们的 k 值是多少？为什么？

**30 秒版**：BM25 分数和向量相似度**量纲不同**（BM25 是无上界的词频分，向量是 0~1 的余弦值），
直接加权要先归一化，归一化方案本身又引入新参数，不同问题的最佳权重还不一样。
RRF 只看**排名**不看原始分数，天然同量纲，几乎零调参。k 是平滑因子：
k 越大排名差距越平缓，k=0 就是最朴素的 1/rank。

**展开（贴真实代码）**：`RrfFusion.java` 就是整个融合算法的全部——总共十行：

```java
// backend/src/main/java/com/argus/rag/qa/support/RrfFusion.java
public static double rankScore(int rank, int k) {
    return 1D / (Math.max(k, 0) + Math.max(rank, 1));
}
```

候选合并时两路各累加一次（`RetrievalCandidate.java`）：

```java
void mergeVectorHit(PgVectorRetrievalAdapter.VectorHit hit, int rank) {
    this.vectorMatched = true;
    this.vectorScore = Math.max(this.vectorScore, hit.score());
    this.rankingScore += RrfFusion.rankScore(rank);   // 向量路贡献 1/rank
}

void mergeKeywordHit(ElasticsearchChunkIndexService.KeywordHit hit, int rank) {
    this.keywordMatched = true;
    this.keywordScore = Math.max(this.keywordScore, hit.normalizedScore());
    this.rankingScore += RrfFusion.rankScore(rank);   // 关键词路再贡献 1/rank
}
```

**诚实标注（面试官追问时这么答）**：

- 业界默认 k=60（ES、LangChain 都这么用），作用是防止第 1 名和第 2 名分差过大。
  **本项目 k=0，即精确 1/rank**——这是历史实现保持的默认值，代价是头部排名权重很"尖"，
  好处是简单、可解释、没有魔法数字。
- k 的选法：在有标注的验证集上对 NDCG@10 / Recall@5 做网格搜索。本项目还没做这一步，
  如果面试官问"你怎么知道 k=0 够用"，标准答案是：**双通道都命中的候选（BOTH）分数自然翻倍浮到顶部，
  融合排序对 k 不如对召回质量敏感；但要成为生产级结论必须补 k 值对比实验**。
- 一个具体例子帮助理解：向量第 1 名（1/1=1.0）+ 关键词第 3 名（1/3≈0.33）= 1.33，
  会赢过"向量单路第 1 名"（1.0）——**两个检索器都认可的结果胜过单路冠军**，这正是 RRF 的精髓。

### Q19：你们 rerank 是真的上了模型，还是只有个接口？（面试官看过太多"简历 rerank"）

**30 秒版**：诚实答——**工程链路完整，模型默认没启用**。`RerankingService` 是接口 +
`NoOp` 空实现，线上当前走的是"RRF 融合排序"直出；接口设计保证了接入真模型时
**一行配置都不用改调用方代码**。能讲清"为什么这么设计"比谎称"上了模型"得分高得多。

**展开（贴真实代码）**：

```java
// backend/src/main/java/com/argus/rag/engine/reranking/RerankingService.java
public interface RerankingService {
    List<RerankResult> rerank(String query, List<String> candidates);

    class NoOp implements RerankingService {
        @Override
        public List<RerankResult> rerank(String query, List<String> candidates) {
            if (candidates == null || candidates.isEmpty()) return List.of();
            return java.util.stream.IntStream.range(0, candidates.size())
                    // 每个候选给一个「随下标略降」的分数：不改变相对顺序，
                    // 但让下游拿到"有分可排序"的结果，链路不因缺模型而中断。
                    .mapToObj(i -> new RerankResult(i, 1.0 - i * 0.001))
                    .sorted(Comparator.comparingDouble(RerankResult::score).reversed())
                    .toList();
        }
    }
}
```

调用侧（`HybridChunkRetrievalService.applyReranking`）已经把"Recall K 取大、Context K 取小"
的两阶段结构搭好了：先取 `recallK=50` 个候选送进 rerank，出错自动回退 RRF 原序。

**如果面试官追问"真要上模型你怎么上"**（这套答下来就是加分项）：

1. 选型：bge-reranker-v2-m3（中文友好、CPU 可跑）或 Cohere Rerank API（效果最好但有外发数据风险，
   企业内网场景基本排除）；
2. 新增 `BgeRerankingService implements RerankingService`，用 `@ConditionalOnProperty` 按配置切换；
3. 延迟对策：Cross-Encoder 对 50 个候选逐对打分，延迟从几十毫秒涨到几百毫秒——
   批量推理、候选数从 50 降到 20、模型 INT8 量化三招压回来；
4. 效果验证：接上 08 篇讲的评测集，对比 rerank 前后的 Recall@5 和答案准确率，
   **没涨就不要上**——这正是"评估驱动"的表达范式。

### Q20：权限过滤发生在检索的哪一步？这种做法有什么安全风险？

**30 秒版**：本项目是**文档级白名单 + 检索后过滤**：先用 `DocumentRoleGate` 查出当前角色
可读的文档 ID 集合，检索完成后把不属于白名单的候选剔除。风险是：被剔除的候选已经
**消耗了检索名额**（白名单外的块占掉了 topK 位置），且过滤逻辑一旦遗漏就是越权。
演进方向是把权限作为过滤条件下推到向量查询和 ES 查询里，让无权文档**根本不参与召回**。

**展开（贴真实代码）**：

```java
// backend/src/main/java/com/argus/rag/qa/rag/HybridChunkRetrievalService.java（检索主流程）
// 检索层角色门槛（单一授权点，fail-closed）：
Set<Long> allowedDocIds = effectiveAllowedDocumentIds(validGroupId);
if (allowedDocIds != null && allowedDocIds.isEmpty()) {
    // 当前角色无一可读文档 → 直接返回"无可检索信息"。
    // 返回与"知识库内无此信息"完全一致，绝不返回"无权访问"，杜绝存在性泄露。
    return RetrievedEvidenceBundle.empty();
}
// ... 双路检索、RRF 融合之后：
// 检索层角色门槛：仅保留当前角色可读文档的切片，杜绝受限切片进入重排/上下文/大模型。
if (allowedDocIds != null) {
    candidates.values().removeIf(c -> !allowedDocIds.contains(c.documentId()));
}
```

`DocumentRoleGate` 的设计有三个值得背下来的点：**fail-closed**（未认证按最低权限 USER 处理）、
**角色优先级单点定义**（USER < FINANCE < ADMIN，只在一处实现）、
**反存在性泄露**（无权 ≠ 报错拒绝，而是让文档"消失"，用户无法试探出受限文档的存在）。

**为什么说"检索后过滤"有风险、生产级怎么做**（面试官深挖时的标准答案）：

1. 本项目已在向量路做了 `groupId` 过滤下推（`PgVectorRetrievalAdapter` 用
   `FilterExpressionBuilder.eq("groupId", groupId)` 把群组隔离压进向量查询），
   但**角色级过滤还在召回之后**——受限块可能占掉 topK 名额，导致用户"该看到的没看到"；
2. 生产级做法一：把 `requiredRole` 写进每个 chunk 的元数据，向量查询的 FilterExpression
   同时带上 groupId + 角色，权限过滤下推到检索层——AWS 的多租户 RAG 方案
   （Bedrock + Verified Permissions）就是这个"检索前过滤"模式；
3. 生产级做法二：PostgreSQL 行级安全（RLS），让数据库自己保证无权行不可见——
   用 pgvector 的团队可以白嫖同一个数据库的 RLS，应用层连过滤代码都不用写；
4. 无论哪种做法，都要写一条**自动化越权测试**：让 USER 角色问一个只有 FINANCE 可见的
   问题，断言拿不到任何受限内容——放进 CI 每次都跑。本项目的权限闸门已有单测覆盖，
   这是面试时可以直接讲的点。

### Q21：HyDE 是什么？什么情况下值得用？

**30 秒版**：假设文档嵌入——用户的问题往往很短、很口语，和长篇正式文档"长得不像"，
向量相似度吃亏。HyDE 让大模型**先编一个假设性答案**，拿这个"伪文档"的向量去检索，
因为它和真实文档同一种"文体"，相似度反而更高。代价：每次检索前多一次 LLM 调用，
延迟 +1 秒左右、成本上升，还可能被假设答案的错误方向带偏。

**展开**：适合用的信号：问题极短（"报废流程"）、召回分数整体偏低、文档库正式文体为主。
不适合：问题本身已经写得很详细、低延迟场景（客服实时问答）。
**本项目没做 HyDE**，但做了同方向的 cheaper 替代——查询改写（Q5）：用规则 + LLM 把
口语问题改写成检索友好的形式，分 DIRECT/REWRITE/DECOMPOSE/GLOBAL 四种策略。
面试可以这么说："我用查询改写解决了 HyDE 想解决的一半问题，成本只有它的几分之一；
如果评测显示短问题召回仍不达标，下一步才是 HyDE。"——**体现的是按成本递进选方案**。

### Q22：除了邻居窗口，跨块上下文还有什么更高级的做法？

**30 秒版**：父子分块（small-to-big）：子块（~100 token）专职检索，命中后返回父块
（~500 token）送生成；层次分块：文档 → 章节 → 段落三层索引，先定位章节再在章节内检索；
late chunking：先对整篇文档算 token 级 embedding，再切块池化，让每个块天生带着全文语境。

**展开**：本项目已实现的是**邻居窗口扩展**（`DEFAULT_NEIGHBOR_WINDOW = 1`，
命中第 N 块带回 N-1、N+1）加**聚类分组**（`RetrievalClusterBuilder` 把连续命中的切片
聚成一簇），实测已解决大部分跨块断裂。
面试深挖时这样答演进路线："邻居窗口解决的是'相邻块'的连贯性，但父子分块解决的是
'检索粒度和生成粒度解耦'——子块精准命中、父块完整表达。改动量也不大：
入库时给每个 chunk 存 parentChunkId，检索命中后按 ID 换父块文本即可，
向量索引规模不变。"——**说出具体改动方案**，面试官就知道你真懂而不是背名词。

### Q23：GraphRAG 听说过吗？你的项目要不要上？

**30 秒版**：听过但不上——GraphRAG 用 LLM 从文档里抽实体和关系建知识图谱，
擅长多跳问题（"A 供应商的母公司的合规负责人是谁"）和全局聚合问题（"总结所有合同的共同风险"）。
但成本吓人：公开基准测试里，同样的语料 GraphRAG 索引构建比标准 RAG 慢 40~57 倍，
单次查询延迟 14 秒 vs 1.7 秒，朴素实现的 token 消耗能差几千倍。**我们的问题日志里
跨文档多跳问题占比很低，先把向量 RAG 做扎实是投入产出比最高的选择。**

**展开**：这是"成本账"题，面试官想听的是**决策框架**而不是名词解释：

1. 审计查询日志：如果需要跨文档连接实体的问题不足 10%，不值得上；
2. 先把基础检索做好：分块差、召回差的问题，GraphRAG 只会放大不会解决；
3. 真要上，从窄领域起步（比如本项目的**财务报销规则**——实体关系密集、定义清晰），
   配一个包含多跳问题的评测集，证明它显著超过向量基线再扩大；
4. 中间方案：LightRAG 这类轻量图结构，token 消耗比完整 GraphRAG 低约 99%，
   或者干脆"结构化数据走 SQL，非结构化走 RAG"的混合架构——财务场景里
   金额、期间这类聚合查询本来就该让模型生成 SQL 去查，不是检索。

### Q24：语义缓存了解吗？如果让你给这个项目加，你怎么防"缓存越权"？

**30 秒版**：语义缓存 = 不要求问题一字不差，新问题和缓存问题**向量相似度超过阈值**
（比如 0.95）就直接返回缓存的答案，省掉检索和 LLM 的钱和延迟。
最大的坑是**权限混淆**：财务总监问过的答案被缓存，普通员工问了相似问题直接命中——泄密。

**展开**：正确设计要把"相似"和"可共享"分开判断：

1. 缓存键必须包含**权限作用域**：`hash(groupId + requiredRole + normalizedQuestion)`
   ——不同角色不共享缓存，宁可少省一点钱也不能越权；
2. 只缓存"检索确定性高"的部分：先缓存检索结果（同一群组内相似问题召回的块基本一致），
   生成层不缓存——LLM 答案措辞每次不同，直接缓存答案的用户体验和一致性都差；
3. 阈值分级：精确缓存（0.98+，直接返回）和相似推荐（0.90+，"您是不是想问…"）分开；
4. 失效：文档更新/删除时按文档 ID 反查受影响的缓存条目删除，不能只靠 TTL。

**本项目现状**：没有语义缓存，这是 10 倍流量演进（Q17）里的第一梯队优化项。
面试就这么说："500 人规模还轮不到语义缓存，真到 QPS 压力时我会先做它，
但缓存键设计必须带权限作用域。"——一句话同时展示演进意识和安全意识。

### Q25：线上出现 Bad Case，从用户投诉到修复上线，你的完整流程是什么？

**30 秒版**：五步闭环——**归因（检索 or 生成）→ 复现（固化成评测用例）→ 修复
（改对应环节）→ 回归（跑全量评测集确认没改坏别的）→ 监控（同类问题报警）**。
核心思想：Bad Case 是资产不是麻烦，每个都变成评测集的一条用例，系统越跑越强。

**展开**：拿本项目真实链路走一遍这个流程：

1. **归因**：`qa_records` / `qa_record_citations` 表落了每条问答的引用和证据，
   先看"引用对不对"。引用错 → 检索问题：查 `HybridChunkRetrievalService` 的日志
   （双路各自命中数、RRF 分数、权限剔除数都打了 info 日志）；引用对答案错 → 生成问题
   （Q16 的排查路径）；证据不足但硬答了 → 检查 `EvidenceAssessor` 的阈值。
2. **复现**：把这条问题和期望答案写进 `scripts/rag_eval/` 的评测集——
   本项目已经带评测脚本和报告，这就是"评测集从哪来"的真实答案：**从 Bad Case 里长出来**。
3. **修复**：按归因结果动对应环节——分块参数、召回 topK、证据阈值、Prompt，
   **一次只改一个变量**，否则你不知道是哪个改动生效的。
4. **回归**：全量跑评测集，确认修复的这道题变对了、原本对的题没变错——
   没有评测集的 RAG 调参是玄学，这句话面试可以直接说。
5. **监控**：拒答码分布（`RETRIEVAL_NOT_GROUNDED` 占比突增 = 知识库覆盖出问题或
   检索质量回退）、用户点踩率，都该进监控面板。

### Q26：算过你单次问答的成本和延迟账吗？要压成本从哪里下手？

**30 秒版**：算过。延迟大头在 LLM 生成（秒级），检索侧可控在几百毫秒内；
成本大头在 LLM token。压成本四板斧：**拒答前置**（证据不足不调模型，白嫖级省钱）、
**上下文瘦身**（不是块越多越好，top-k=5 够了）、**本地 embedding**
（查询向量化在进程内完成，零 API 费）、**语义缓存**（高频问题兜底）。

**展开（用项目真实数字算账）**：

1. **检索放大系数**：查询规划可能产出多条子查询（DECOMPOSE 策略），每条都要跑
   向量 + ES 两路，`channelTopK=50` 意味着单次问答最多召回百级候选——
   这是用检索量换召回率的主动选择，评估 QPS 容量时要乘上这个系数；
2. **LLM 是大头**：进模型的内容 = 5 个证据块 ×（块文本 + 邻居窗口扩展）+ 系统提示词。
   块文本平均几百 token，一次问答输给模型 3~5K token 是正常量级。
   Prompt 压缩（去掉证据里的重复表头、无关段落）比换便宜模型有效得多；
3. **拒答是最便宜的回答**：`RETRIEVAL_NOT_GROUNDED` 拦住的每一次调用都是纯省——
   这也是为什么"证据不足不调模型"不只为防幻觉，也是成本设计；
4. **延迟体验**：SSE 流式输出（用户 1 秒内看到第一个字）对感知延迟的贡献
   远大于把检索从 200ms 压到 100ms——**优化感知延迟优先于优化绝对延迟**。

### Q27：追问弹药库：来不及展开的题，30 秒内这样接住

| 追问 | 一句话接法 |
|------|-----------|
| 多文档说法冲突怎么办 | 按"来源权威性 + 时间新"排序让新文档靠前，Prompt 要求标注分歧；财务场景里新旧制度冲突本质是知识库治理问题 |

## 第三梯队的"诚实原则"（比题目本身更重要）

整理完这 10 道深挖题，请记住一条总原则，它比任何单题答案都值钱：

1. **项目做了的，讲细节**：RRF 的 k=0、邻居窗口=1、top-k=5、拒答码——数字要背熟，
   说错数字比不说更减分；
2. **项目没做的，讲方案**：rerank 模型、HyDE、语义缓存、GraphRAG——
   先说"当前没启用/没做"，紧接着说"如果要上，我会……"，
   展示的是选型判断力，这是高级工程师和调包侠的分水岭；
3. **被问倒的，讲思路**：真的不会的题，诚实说"这块我没实操过，
   我的理解是……，您看这个方向对吗"——面试官对新手的目标是判断潜力，不是考百科全书。
