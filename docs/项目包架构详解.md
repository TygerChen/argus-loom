# Argus Loom 包架构详解

> 目标读者：正在学习本项目的你。这份文档回答三个问题：
> **项目分几块？每块管什么？一块代码想找另一块帮忙该怎么走？**
> 建议配合 `docs/tutorials/13-项目全局地图与请求旅程.md` 一起看：
> 那篇讲"一次请求怎么流动"，这篇讲"代码放在哪、为什么放那"。

---

## 一、全景：项目由三大块组成

```
┌─────────────────────────────────────────────────────────┐
│  前端 frontend/        Vue 3 + TypeScript + Pinia        │
│  用户看到的界面：登录、传文档、问答、多人编辑 Excel        │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP / SSE / WebSocket
┌────────────────────────▼────────────────────────────────┐
│  后端 backend/        Spring Boot 3 + Java 21            │
│  业务逻辑全部在这里，按"业务模块"拆包（见下文）            │
└──┬──────────┬──────────┬──────────┬──────────┬──────────┘
   │          │          │          │          │
┌──▼───┐  ┌──▼───┐  ┌───▼──┐  ┌───▼──┐  ┌───▼──────┐
│Postgre│  │pgvector│ │  ES  │  │MinIO │  │  Redis   │
│ SQL  │  │ 向量   │  │关键词│  │ 文件  │  │ 缓存/协同 │
└──────┘  └───────┘  └──────┘  └──────┘  └──────────┘
```

- **PostgreSQL**：所有业务表（用户、文档、问答记录、Excel 元数据……），
  表结构由 Flyway 迁移脚本管理（`backend/src/main/resources/db/migration/V1~V8`）；
- **pgvector**：PostgreSQL 的向量插件，存文档切片的 embedding，做语义检索；
- **Elasticsearch**：关键词检索（BM25），和 pgvector 组成"双路召回"；
- **MinIO**：对象存储，存上传的原始文件（文档、Excel）；
- **Redis**：缓存 + Excel 多人协同的在线状态/事件通道。

## 二、后端包架构总览

所有后端代码都在 `com.argus.rag` 下，按**业务功能**分包（不是按技术分层分包）。
每个业务包内部再按 `controller → service → mapper/model` 分层——
这就是"**顶层按业务切、内部按层分**"的结构，找代码先想业务再想层。

```
com.argus.rag
├── auth/          认证：登录、JWT、刷新令牌、Spring Security 配置
├── user/          用户：账户管理、管理员管用户
├── group/         群组：知识库的隔离边界（谁能看到哪个知识库）
├── document/      文档：上传入口、元数据、权限标记、分享
├── ingestion/     入库流水线（ETL）：解析 → 清洗 → 分块 → 向量化
├── embedding/     向量化：本地 bge-small-zh 模型（512 维，进程内）
├── engine/        检索引擎的"司机层"：对接 pgvector / ES / 联网搜索 / 重排 / MinIO
├── qa/            RAG 问答核心：查询规划 → 混合检索 → 证据评估 → 生成 → 引用
├── assistant/     AI 助手 Agent：带工具、带记忆的对话（和 qa 是两条独立链路）
├── llm/           大模型调用抽象：ModelClient 接口，屏蔽底层是哪家模型
├── prompt/        提示词模板管理
├── excel/         Excel 中心：解析、多人实时协同、版本、回收站、导出、审计
├── finance/       财务：Excel 导入、分析、工资条、财报 PDF
├── job/           后台任务：通用任务队列 + Worker（入库、导出都跑在这）
├── metrics/       指标：成本统计、管理员监控面板
├── evaluation/    RAG 评测（占位，评测脚本在 scripts/rag_eval/）
├── common/        全家桶公共件：统一响应、异常、安全上下文、限流、日志
└── config/        全局配置：AI 服务、模型参数、MyBatis-Plus
```

**记忆口诀**：`auth/user/group` 管"人"，`document/ingestion/engine` 管"资料"，
`qa/assistant` 管"回答"，`excel/finance` 管"表格"，`job/metrics/common` 是"后勤"。

## 三、逐包详解

### 3.1 auth/ —— 你是谁（认证）

```
auth/
├── controller/AuthController.java      登录 / 注册 / 刷新令牌 / 登出
├── service/                            认证业务
└── security/                           ★ 安装的"安检门"
    ├── SecurityConfig.java             Spring Security 总配置：哪些 URL 要登录
    ├── JwtAuthenticationFilter.java    每个请求先过这里：从 token 解出用户
    ├── JwtAccessTokenService.java      签发 / 校验 JWT
    ├── RefreshTokenService.java        短期 token 过期后用长期 refreshToken 换新
    └── AuthCookieSupport.java          token 放 HttpOnly Cookie，防 XSS 偷 token
```

- **为什么 filter 要单独一个包**：JWT 过滤器是"横切"所有请求的，不属于任何业务，
  放 security 子包里独立管理。
- **教程**：03 篇（认证与权限）。

### 3.2 user/ + group/ —— 人和组织的边界

- `user/`：账户本身（改密码、管理员封禁用户），三层标准结构 controller/service/mapper。
- `group/`：**知识库隔离的边界**。每个群组 = 一个独立知识库；
  文档、问答、Excel 全都挂在 groupId 下。
  加群要审批（`GroupJoinRequestController`、`InvitationDecisionController`），
  群主管理成员（`GroupManagementController`）。

> **面试高频**："你们多租户隔离怎么做的？"——答：群组即租户边界，
> 所有查询强制带 groupId，向量检索在查询层就下推 groupId 过滤（见 engine 包）。

### 3.3 document/ —— 文档的名册（不管内容，管"户口"）

```
document/
├── controller/DocumentController.java   上传入口、列表、删除、版本
├── service/                             元数据管理、权限标记
├── storage/                             上传的临时落盘
└── security/DocumentRoleGate.java       ★ 检索层唯一的"谁可读哪份文档"判定点
```

关键理解：**document 包只管元数据**（文件叫什么、属于哪个群、什么状态、要求什么角色才能读），
文件的二进制内容在 MinIO（engine.storage），解析后的切片在 ingestion 包。
`DocumentRoleGate` 是全项目权限设计的灵魂：fail-closed（未认证按最低权限）、
反存在性泄露（无权的文档不是"报错拒绝"而是"消失"）。
**教程**：01 篇（上传）、03 篇（权限）。

### 3.4 ingestion/ —— 一份文档变成检索卡片的工厂（ETL）

```
ingestion/
├── service/
│   ├── DocumentIngestionAsyncService.java   异步入口：上传后立刻返回，后台慢慢处理
│   ├── DocumentIngestionProcessor.java      处理器接口
│   └── pipeline/
│       ├── parser/       第 1 站：解析。PDF/DOCX/MD/TXT 各一个解析器 + 工厂
│       ├── transformer/  第 2 站：清洗 + 分块。结构感知切块（240/320/32 参数）
│       └── reader/       从 MinIO 把文件读回来
├── vector/VectorIngestionService.java       第 3 站：调 embedding 写入 pgvector
└── mapper/                                  document_chunks / ingestion_jobs 两张表
```

三站流水线：**解析 → 清洗分块 → 向量化入库**，全程异步（job 包驱动），
状态机 `PENDING → PROCESSING → READY / FAILED / DEAD_LETTER`。
**教程**：08 篇（异步入库与失败兜底）。

### 3.5 embedding/ + llm/ + prompt/ —— AI 能力的三小件

- `embedding/LocalEmbeddingConfig`：本地加载 bge-small-zh 模型（512 维），
  **进程内运行不走 HTTP**——查询向量化零 API 费、零网络延迟；
- `llm/ModelClient`（接口）+ `SpringAiModelClient`（实现）：
  调大模型的唯一出口，换模型供应商只动这一个包；
- `prompt/PromptTemplateManager`：提示词模板统一管理，不散落在代码里。

### 3.6 engine/ —— 检索引擎的司机层（每个外部系统一个司机）

```
engine/
├── pgvector/PgVectorRetrievalAdapter.java   向量检索司机：FilterExpression 下推 groupId
├── elasticsearch/ElasticsearchChunkIndexService.java  关键词检索司机（BM25）
├── youcom/ + freeweb/                        联网搜索司机（第三路，默认关闭）
├── reranking/RerankingService.java           重排接口 + NoOp 兜底实现（04 篇 Q19）
├── storage/MinioStorageService.java          文件存取司机（ObjectStorageService 接口）
├── ModelGateway.java + StructuredDataRetrievalService.java  结构化数据检索
```

**为什么叫"司机层"**：业务代码（qa 包）不想关心 pgvector 的查询 API 长什么样、
ES 的分词怎么配——engine 包把每个外部系统包成一个"会开车的司机"，
业务只说"去哪"。这是**适配器模式**的教科书应用，也是换数据库不换业务的保险丝。

### 3.7 qa/ —— RAG 问答的心脏（面试重点包，没有之一）

```
qa/
├── controller/QaController.java             提问入口（SSE 流式返回）
├── service/
│   ├── QaService.java                       ★ 总指挥（编排整条链路）
│   ├── QueryPlanningService.java            审题：DIRECT/REWRITE/DECOMPOSE/GLOBAL 四策略
│   ├── QaRetrievalService.java              调检索
│   └── QaRecordPersistenceService.java      问答落库（qa_records / qa_record_citations）
├── rag/                                     检索流水线（每个类一个零件）
│   ├── HybridChunkRetrievalService.java     ★ 核心引擎：双路并行 → RRF 融合 → 权限过滤
│   ├── RetrievalCandidate.java              候选切片（累加 RRF 分数的地方）
│   ├── RetrievalClusterBuilder.java         相邻切片聚成一簇
│   ├── EvidenceAssessor.java                证据充分度评估（不足就拒答，不调模型）
│   └── EvidenceDocumentAssembler.java       把数据库行组装成给大模型的证据文档
├── support/
│   ├── CitationAssembler.java               引用标注组装
│   └── QaAnswerParser.java                  解析大模型的结构化回答
├── route/KnowledgeGroupRouter.java          问题路由到哪个群组知识库
└── mapper/                                  qa_records 等表
```

**一次提问的穿包顺序**（背下来，面试画图用）：

```
QaController → QaService → QueryPlanningService（审题改写）
  → QaRetrievalService → HybridChunkRetrievalService
      ├─ PgVectorRetrievalAdapter（向量路）
      ├─ ElasticsearchChunkIndexService（关键词路）
      ├─ RrfFusion 融合 → DocumentRoleGate 权限过滤
      └─ EvidenceAssessor（证据不足？→ 拒答码 RETRIEVAL_NOT_GROUNDED，结束）
  → llm.ModelClient（生成答案）→ CitationAssembler（引用标注）→ 落库 → SSE 返回
```

**教程**：04 篇（RAG 与引用，含 27 道 Q&A）。

### 3.8 assistant/ —— AI 助手 Agent（qa 的兄弟包，架构不同）

```
assistant/
├── agent/
│   ├── AssistantAgentFacade.java            对外门面
│   ├── AssistantReactAgentFactory.java      ReAct Agent 工厂（Spring AI）
│   └── tool/                                ★ Agent 的工具箱（@Tool 注解）
│       ├── AssistantKnowledgeBaseTool.java   查知识库（内部复用 qa 的检索链路！）
│       ├── StructuredDataQueryTool.java      查结构化数据（SQL）
│       ├── WebSearchTool.java / CurrentTimeTool.java
│       └── ToolSafetyMarkers.java            工具风险分级
├── memory/
│   ├── AssistantShortTermMemoryHook.java     短期记忆：当前对话上下文
│   └── longterm/ + AssistantSessionSummaryService.java  长期记忆：历史会话摘要
└── service/                                  会话 / 消息管理
```

和 qa 包的区别一句话讲清：**qa 是"一条固定流水线"，assistant 是"让模型自己决定调什么工具"**。
assistant 的知识库工具内部调用的还是 qa 的检索——两套门面共用一个引擎。
`groupId/userId` 通过 Spring AI 的 ToolContext 注入工具，防止越权。

### 3.9 excel/ —— 第二主角：Excel 协作与分析

```
excel/
├── controller/     9 个 Controller：文件、版本、导出、回收站、ACL、分享……
├── service/
│   ├── ExcelUploadService / StreamingParserService   流式解析（大文件不吃内存）
│   ├── ExcelSheetService        ★ 表格数据核心：LSM 风格 基线+增量+压实
│   ├── ExcelDocumentLockService  编辑锁
│   ├── ExcelVersionService / SnapshotService / RecycleBinService
│   ├── ExcelExportService       导出（异步 job）
│   └── ExcelPermissionService / DocumentAccessService   细粒度权限
├── collab/       ★ 多人实时协同
│   ├── CollabController.java     WebSocket 入口（STOMP 协议）
│   ├── CollabService.java        编辑事件广播
│   ├── OnlineUserTracker.java    在线人数（Redis）
│   └── StompSessionAuth.java     WebSocket 握手也要认证
├── pipeline/     单元格编辑流水线（celldata/filter 子包）
└── finance/      表格转结构化数据：TableSchemaService / TableIngestionService
```

**教程**：02 篇（Excel 解析）、05 篇（协同编辑）。

### 3.10 finance/ —— 财务场景（建立在 excel 之上）

- `FinanceImportController/Service`：把上传的财务 Excel 导入成结构化数据
  （幂等性设计，V7 迁移专门加了 import 幂等）；
- `FinanceAnalysisService`：阈值分析（单笔超 5 万元、报销次数异常，阈值可配）；
- `PayrollService` + `finance/service/` 下工资条、财报 PDF。

依赖方向：**finance 依赖 excel，excel 不依赖 finance**——业务分层不倒挂。

### 3.11 job/ —— 后台任务的统一车道

`BackgroundJobService`（入队）→ `BackgroundJobWorker`（消费）→
`BackgroundJobMapper`（background_job 表，任务状态落库）。
文档入库、Excel 导出都走这条队列。设计动机：HTTP 请求必须秒回，
慢活全部丢进队列慢慢干，失败了还有 DEAD_LETTER 死信兜底（08 篇）。

### 3.12 metrics/ + evaluation/ —— 度量

- `metrics/`：成本统计（cost 子包：每次调模型花了多少 token）、管理员监控面板；
- `evaluation/`：目前是占位，真正的评测在 `scripts/rag_eval/`（Python 脚本 + 评测集）。

### 3.13 common/ + config/ —— 全家桶公共件

```
common/
├── api/          统一响应体 ApiResponse<T>：所有 Controller 出口格式一致
├── exception/    BusinessException + ErrorCodes + GlobalExceptionHandler（全局异常翻译官）
├── security/     UserContext（当前用户上下文，ThreadLocal）+ InputSanitizer
├── ratelimit/    接口限流
├── logging/      日志 AOP 切面
├── metrics/      业务指标埋点
└── util/         工具类
config/
├── AgnesAIService.java      大模型接入
├── ModelConfig.java         模型参数
└── MybatisPlusConfig.java   ORM 配置
```

**规则**：common 包不依赖任何业务包（否则会变成垃圾抽屉）；
业务包可以随便用 common。

## 四、模块依赖图（谁能找谁帮忙）

```
                    ┌──────── controller 层（HTTP 入口）────────┐
                    │  auth  document  excel  qa  assistant ... │
                    └────────────────┬─────────────────────────┘
                                     ▼
   excel ──► finance          service 层（业务逻辑）
     │        │               qa.service ──► qa.rag ──► engine ──► 外部系统
     │        └──────►excel.service        │            │        (pgvector/ES/MinIO)
     └──► job ◄── ingestion.service ◄──────┘            │
              │                                          │
              └────────► document ◄── assistant.agent.tool（查知识库）

   所有包都可依赖：common / config / llm / prompt / embedding
   common 不依赖任何业务包；engine 不依赖业务包（只做司机）
```

三条**铁律**（读代码时用来验证自己有没有迷路）：

1. **controller 不直接碰 mapper**：必须经过 service（事务和权限都在 service 层）；
2. **业务包不直接写外部系统的 API**：必须走 engine 的适配器；
3. **权限判定单点化**："哪份文档可读"只问 `DocumentRoleGate`，别处不得复制角色判断逻辑。

## 五、前端包架构（frontend/src）

```
src/
├── api/            后端接口的统一出口（一个业务一个文件：qa.ts / excel.ts ...）
│   └── http.ts     ★ axios 封装：带 token、401 自动刷新、错误统一弹
├── stores/         Pinia 全局状态：auth（登录态）/ admin-user
├── router/         路由 + 守卫（没登录跳登录页）
├── views/          页面（按业务分子目录）
│   ├── qa/         问答页（QaView + 转写板 + 引用栏 CitationRail）
│   ├── assistant/  助手页
│   ├── documents/  文档列表 + 上传（composables/useChunkedUpload 分块上传）
│   ├── excel/      Excel 中心（SheetEditor 多人编辑、FinanceDashboard 财务看板）
│   ├── groups/     群组管理
│   └── admin/      管理后台
├── components/     跨页面复用的组件
├── utils/          collabClient（WebSocket 客户端）/ safeMarkdown（防 XSS 渲染）/ format
└── types/          TypeScript 类型定义
```

**读前端代码的正确顺序**：`http.ts`（所有请求怎么发出去的）
→ `stores/auth.ts`（登录态怎么存）→ `router`（页面怎么守卫）
→ 再挑一个业务页面（推荐 `views/qa/QaView.vue`）顺着读。

## 六、按这份路线读代码（两周计划）

| 阶段 | 读什么 | 验收标准 |
|------|--------|----------|
| 第 1~2 天 | common/api + common/exception + auth | 能说清一个请求从进来到返回的完整生命周期 |
| 第 3~4 天 | document + ingestion.pipeline | 能画出"一份文档变成卡片"的三站流水线 |
| 第 5~6 天 | engine（pgvector + es）+ qa.rag | 能默写第四章 qa 的穿包顺序图 |
| 第 7~8 天 | qa.service + support + llm | 能解释拒答码何时触发、引用怎么组装 |
| 第 9~10 天 | excel（sheet + collab） | 能讲清 LSM 基线+增量+压实 和协同事件流 |
| 第 11~12 天 | assistant + job + metrics | 能对比 qa 和 assistant 两条链路的架构差异 |
| 第 13~14 天 | 前端 http/stores/qa 视图 | 前后端对上号：每个按钮知道打哪个接口 |

每天读完写一条"这个包为什么这么设计"的笔记——设计动机比代码本身更值钱。
