# 企业制度压力测试语料（批量灌库）

在正式评估之外，还提供一套**大规模企业制度语料**用于检索压测与干扰实验：

```bash
python build_corpus.py            # 生成 108 篇语料 + 170 条测试题（关键词自检）
python bulk_upload.py             # 上传到"压力测试专用组"并等 READY（幂等，可重跑）
python bulk_upload.py --verify 12 # 抽样 12 题验证可检索性
python bulk_upload.py --verify-only --verify 20   # 跳过上传只验证
```

语料构成（2026-09-27 已灌入群组 14，108/108 READY）：

- **44 篇基础制度**：考勤/休假/绩效培训/招聘离职/差旅报销/采购预算/信息安全/行政后勤/员工福利/研发管理/客户销售/法务合规 12 大类
- **10 篇分公司变体**：差旅（华南 480/西南 420/华北 460/华中 400/东北 380）、制造基地考勤（华东/华北/西南）、团建（华东/华南）——
  同一主题不同数字，专门测"同城不同标准"的检索歧义
- **54 篇历史存档版**：每篇自动生成上一版存档件（编号日期回退一年 + "以最新版为准"声明）——
  测新旧版并存的排序行为
- 内容基于公开的企业制度范本条款改编（考勤罚则、差旅标准、信息安全条款、采购比价等），
  每条测试题的关键词经生成器自检与正文严格对应
- ES 实测：灌入后 `argus_rag_document_chunks` 共 191 个切片（含评估组 3 篇）

抽样验证结果（12 题）：8 题可回答全部首命中、要点覆盖 100%，4 条超纲负例全部正确拒答。

### 压力语料完整跑分（170 题，2026-09-28）

| 指标 | 结果 |
|---|---|
| 检索命中率 HitRate@5 | **97.6%**（163 正例，仅 4 题未首命中） |
| MRR | **95.1%** |
| 答案要点平均覆盖率 | 94.6% |
| 正例问答准确率 | 94.0% |
| 拒答准确率（4 条负例） | **100%** |
| 综合准确率 | **94.1%** |

失分题归因（不是系统缺陷，恰是语料的测试价值）：
- 「餐补一天多少钱」等 3 题是**刻意设计的歧义题**——同一问题在总部+5 个分公司版本里有 5~7 个不同正确答案，
  问题未指明分公司时系统无法替用户选择，检索返回其中之一；这类问题的正确解法是问题里带上组织范围
  （对应面试考点：查询规划/多版本歧义）。
- 「补充医疗保险保额」等数题为**同义词/空格匹配误伤**：正文「2 万元（20000 元）」模型回答带空格，
  关键词「2万」匹配不上——改进方向是判分时做数字归一化或语义相似度。

跑分命令：`python run_eval.py --testset stress_testset.json --group-id 14`
（支持断点续跑：每题落盘 `eval_checkpoint_stress_testset.json`，中断后重跑只补剩余；`--fresh` 全量重测）

## 正式评估（40 用例）

一套端到端的 RAG 评估工具：**测试文档自带、标准答案可控**，跑完得到可直接写进简历的真实数字
（HitRate@5、MRR、答案要点覆盖率、拒答准确率、综合准确率）。

## 原理

评估可信的前提是"标准答案已知"。本工具分三步：

1. `prepare_testset.py` 生成 **3 篇内容完全已知的测试文档**（差旅报销制度 / 考勤请假制度 / 平台操作手册）
   和 **40 条测试用例**（36 条应回答 + 4 条知识库里不存在、应拒答的负例）。
   因为事实只存在于这 3 篇文档里，命中与否可以精确判定。
2. `run_eval.py --prepare` 把文档上传到自动创建的"RAG评估专用组"，等待切片向量化完成（READY）。
3. `run_eval.py` 逐题调用 `POST /api/qa/ask`，按以下口径计分：
   - **HitRate@5（检索命中率）**：引用列表前 5 条中是否出现期望文件
   - **MRR（平均倒数排名）**：第一条相关引用的排名倒数取均值，衡量"排序质量"
   - **答案要点覆盖率**：`answer` 中命中 `expected_keywords` 的比例（避免人工逐条看答案）
   - **拒答准确率**：负例应 `answered=false`，衡量"不编造"的能力
   - **综合准确率**：正例(回答且覆盖≥60%) 与负例(正确拒答) 合并统计

## 使用

```bash
# 0. 依赖（仅需一次）
pip install requests

# 1. 生成测试文档与测试集（eval_docs/ 与 testset.json）
python prepare_testset.py

# 2. 首次运行：注册评估用户 → 建群 → 上传 → 等 READY → 评估
#    （管理员账号被禁止访问业务区，脚本用普通用户 evaluser / Eval#User2026）
python run_eval.py --register --prepare

# 3. 以后重复评估（复用已建群组）
python run_eval.py

# 其他参数
python run_eval.py --base http://localhost:10001 --user admin --password admin123
python run_eval.py --group-id 3            # 指定已有群组
python run_eval.py --dry-run               # 不连后端，演示报告结构
```

输出：

- `eval_result.json` — 逐题明细 + 指标汇总（可二次分析）
- `report.md` — 人类可读报告，含逐题判定表

## 实测结果（2026-09-27，本机 40 用例）

| 指标 | 结果 |
|---|---|
| 检索命中率 HitRate@5 | **100%**（40/40 全部首命中，MRR = 1.0） |
| 拒答准确率（4 条超纲负例） | **100%**（全部正确拒答，零编造） |
| 答案要点平均覆盖率 | 97.2% |
| 自动口径综合准确率 | **95.0%**（2 条被关键词覆盖规则扣分） |
| 人工复核后事实正确率 | **100%**（扣分的 2 条为同义词误伤：「三甲」vs「三级甲等医院」，答案本身正确） |
| 端到端时延（同步接口，含 LLM 全文生成） | 平均 **3.2s**（2.1~4.8s） |

两条扣分 case 是关键词判分的同义词盲区，不是系统错误——这本身就是"自动化指标需配合人工抽检"的活案例，
也是引入 LLM-as-judge 或语义相似度判分的理由。

## 注意

- **LLM Key 前提**：评估的答案环节依赖可用的 Chat LLM。网关（11435）需要有效的
  `AGNES_API_KEY`：注意环境变量会覆盖脚本内置 key——2026-09-27 曾因环境变量里是一把失效的旧 key
  导致 401，显式以 `AGNES_API_KEY=<有效key> python ../chat-only-gateway.py` 启动即恢复。
- **Key 失效时的表现**：每个问题会先走查询规划的 LLM 调用，Spring AI 内部重试带指数退避（实测重试 8+ 次），
  单题可达数分钟——如果你的评估每题耗时异常长，先检查 key 是否有效，别硬等。
- 已验证可用的环节（本机 2026-09-27 实测）：注册普通用户、建群、上传 md、ETL 至 READY、
  检索层 SQL/ES 查询均正常，即评估链路除 LLM 生成外全部打通；管理员（admin）账号被禁止访问业务区，
  必须用普通用户（脚本默认已处理）。
- 问答接口限流 **20 次/60 秒**，脚本每题间隔 3.5 秒，40 题约 3 分钟，请勿把间隔调到 3 秒以下。
- LLM 回答有随机性，建议跑 2~3 次取中位数再写进简历。
- 想换成自己的文档：改 `prepare_testset.py` 里的 `DOCS` 与 `CASES`，保持
  `expected_files` 与文件名对应、`expected_keywords` 能在文档中找到依据。
- 修改文档内容后用 `python prepare_testset.py --force` 重新生成，并重新 `--prepare` 上传。
